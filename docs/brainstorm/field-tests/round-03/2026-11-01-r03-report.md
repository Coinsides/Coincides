## 五、新发现 · 🅰 正确性（建议判级）

### A-16 刷新后标题与段落的显示顺序和存储顺序不一致
- **现象一（笔记 de003655）**：服务器块序是 3 井号标题、4 F7标题后第一次、5 空、6 F7第二标题、7 [空 + F7双回车后 + F7标题后第二次]、8 空。刷新后按纵坐标显示成：井号标题 → F7第二标题 → 空 → F7标题后第一次 → 空 → 空 → F7双回车后 → F7标题后第二次。两次刷新稳定复现。
- **现象二（全新笔记 b6515942）**：服务器块序是 7「节五」heading（10:41:32 用「# 」从段落块里拆出）、8 空标题（10:40:06 创建）、9 空标题（10:39:52 创建）。刷新后「节五」显示在两个空标题之后，纵坐标 807，而两个空标题在 720 和 763。
- **对照**：在标题末尾回车往中间插入一行（「中间插入行」），刷新前后顺序都一致。所以简单插入不会触发。
- **判断**：我输入时的意图和服务器块序一致，错的是显示。用户看到的顺序，和导出、Agent 读到的顺序不同。
- **线索**：两次都涉及「用『# 』或回车把一个单元拆成新块」。块接口里只有 order_index，没有坐标，屏幕位置由页帧落位决定。疑似拆块时新块的落位追加到了末尾（或沿用了旧位置），没有按 order_index 插入。两篇笔记都可直接作为夹具，需施工方读代码确认。
- **建议判级**：🅰。

### A-17 独立空块里打「# 文字」丢字，之后整篇笔记卡在只读（3cc2a0e4）
- **场景**（笔记 b6515942）：
  1. 在标题「节二」末尾回车，不打字直接失焦，重复两次，造出两个独立空块。
  2. 双击其中一个空块，快速打「# 节三」。
  3. 另一个空块同样打「# 节四」。
- **现象一（丢字，2/2）**：两块都变成了空标题，服务器上 heading_1 的文字为空，「节三」「节四」永久丢失。辅助功能树里却出现了「Collapse chapter: 节三」「Collapse chapter: 节四」：客户端的章节结构记着标题名，文本那一半是空的。这像 F7 回执里描述的「只写了 flow 半边，文本半边被旧草稿对齐回去」。
- **对照**：在段落里回车得到的新行（同一块内）打「# 节五」，完整保留。
- **现象二（卡死只读）**：
  - 随后又在「节二」末尾回车造了一个新空块，双击它，打「# 」，停 1.2 秒，再打「节六」。页面和服务器都没有任何变化。
  - 检查发现整篇笔记 10 个输入框全部 `readOnly`，持续 4 秒以上没有恢复。底栏「Source locked」常亮，Layout 和装订禁用，块工具条变灰，没有任何提示。
  - 用户此时打的字不显示、不保存，看起来就是被吞了。
- **刷新后**：只读解除。「节六」出现在页面上，服务器在刷新那一刻（10:43:12）才写入。顶部出现恢复条「A block edit is waiting for recovery · 节六 · Apply / Dismiss」。服务器已经有「节六」，再点 Apply 会怎样不清楚，我没有点。
- **推断**：标题结构提交的忙态（F7 回执里的 `headingStructure.busy`）在这种空块场景下没有释放，而 `contentReadOnly` 是包括这个忙态在内的并集，于是整篇只读。F7 加的按键排队只在「焦点送达新段落」时重放，「# 」转换不产生新段落，排队的字没有出口。最小触发步骤还没收窄，b6515942 可作夹具。
- **建议判级**：🅰（静默丢字，加上编辑器整体卡死）。

### A-14 设置页整页加载显示错误提供方
- **初始化**：`client/src/pages/Settings/Settings.tsx:58–62` 用 useState 初始化器从 `user?.settings || {}` 取值，取不到就落回硬编码的 anthropic 和 claude-sonnet-4-20250514（`:21`、`:60–61`）。
- **为什么只在站内跳转时生效**（你点名的时序）：
  - F4-1 的 default_chat_provider 拉取在 `:104–116`，它只在 `settings.active_provider` 为空时发出（`:105`）。
  - 整页加载时，ProtectedRoute 只看令牌（`App.tsx:39`），AppLayout 立刻渲染子页面。设置页在 `/auth/me` 返回之前就挂载了，`user` 还是 null，初始化器把默认值锁死，同时发出 providers 请求。
  - 随后 `/auth/me` 到达，`active_provider` 从空变成 deepseek，触发 effect 清理（`:115` cancelled=true），把在途的 providers 响应作废。effect 重跑时在 `:105` 直接 return。
  - 初始化器不会再运行，表单就停在 anthropic。站内跳转时用户数据早已到位，初始化器一开始就拿到 deepseek。新账号没有 active_provider，effect 的依赖前后都为空、请求不被作废，所以也正常。
- **一旦点保存**：`handleSaveProvider`（`:118–133`）会 `PUT /api/settings`，写入 `active_provider: "anthropic"`。服务端 `resolveActiveProvider`（`providers/index.ts:16`）总是尊重已保存的选择，不回落到有钥匙的提供方。于是该账号此后每次聊天都报「Anthropic 没有钥匙」，Note Proposal 的 AI 模式也一并关掉（`organizedNoteProposals.ts:89`）。
- **同一根因的潜在问题（未实测）**：冷启动后失焦 Agent Name，可能把自定义名字改回 Mr. Zero（`:59`、`:85`）；向量模型可能被重置成该提供方的第一个选项（`:148–149`、`:164`）。
- **建议**：F8 一并修这两处。
- **影响评估：潜在误写，实测未发生**。Main_Designer 已在运维侧核查全部账号：1 个未设置提供方，2 个是 deepseek，没有账号被误写成 anthropic。我本人没有查看任何真实账号。

### A-15 Agent 断言「项目里没有笔记」
- **工具清单**：聊天 Agent 拿到的是 `toolDefinitions`（`orchestrator.ts:231`），共 43 个工具，其中没有一个能按项目或标题列出、搜索用户笔记。`read_note` 必须先有 note_id（`registry.ts:826–828`）。
- **现成工具没开放**：`list_notes`、`get_note`、`list_note_blocks` 已在 `TOOL_REGISTRY` 里，但只以 public 身份开放给 MCP（`registry.ts:925`、`:935`；`mcp/manifest.ts:37`），没有进入聊天工具清单（`definitions.ts:11` 只展开三组 agent 工具）。另外 `listNotes`（`services/notes.ts:118–135`）不区分 Source 投影笔记和用户自写笔记，也没有标题过滤。
- **为什么选择断言而不是声明边界**（提示词层）：
  - `system-prompt.ts:35–38` 把 documents 和 Source 称为「两座内容库」，并说 search_documents「一次检索两者」，暗示这是全部内容。
  - 唯一的找不到规则是「都找不到时如实说明」，只要求如实，不要求说清搜索范围。
  - 「宣称纪律」（`:48–54`）只管写动作和报错，不管「某物不存在」这类断言。
  - search_documents 的工具描述（`definitions.ts:228`）没说用户笔记不在范围内，也没说条数上限（文档 10 条、Source 5 份）；返回里的 `total`（`executor.ts:721`）读起来像库存总数。
  - read_content_groups 的空结果是真实的全量结果，模型把这个真的「空」和 search_documents 的假「空」拼成了「什么都没有」。
- **对 F8 设计的补充**：可以复用现有的 public `list_notes`，但要先解决投影笔记与自写笔记的区分；search_documents 的描述和 `total` 字段应同步改写。

### R2 遗留：「Source 路只认 1/6」是检索词没命中，不是枚举缺损
- **切词方式**：`server/src/services/agentSourceSearch.ts:41` 只按空白和少数全角标点（，。；：！？（）、）切词，没有中文分词。之后每个词做一次 LIKE，词与词之间是 OR。上限是 8 个词、5 份 Source、每份 3 段摘录（`:25–27`）。
- **第一问为什么只回 1 份**：「网络与服务器基础 笔记」被切成两个词。「网络与服务器基础」整串在哪份 Source 里都找不到，「笔记」只碰巧命中了「家里的**笔记**本」。所以只回 1 份，这 1 份也是误中。
- **第二问为什么回 3 份**：「我的笔记：公网、内网和端口」切出了「公网」，于是命中 3 份。
