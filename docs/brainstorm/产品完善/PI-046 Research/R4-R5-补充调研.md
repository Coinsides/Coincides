# R4、R5 补充调研：Canvas-first NoteBlock 手动编辑体验

## 文档定位

这份文档是 PI-046 中 `R4-manual-notebook-minimum-usable-experience.md` 和 `R5-page-editor-freeform-block-box-requirements.md` 的补充调研。

R4 已经回答了一个基础问题：

```text
Coincides 如果完全不依赖 AI，至少要怎样才算人能舒服地写笔记？
```

R5 已经回答了另一个基础问题：

```text
Coincides 是否需要一种介于普通文档编辑器和无限画布之间的 page editor？
```

本补充调研继续往下细化：

```text
在 Coincides 这种 canvas-first、NoteBlock-as-truth、BlockBox-as-layout 的系统里，
用户怎样像普通文档一样自然输入，
又能像操作画布对象一样自由排版 NoteBlock？
```

这既是一份调研，也是一份产品思考。它的目的不是立刻锁死最终实现，而是为后续 `BlockSuite Edgeless-as-page + Coincides semantic sidecar` spike 提供明确的体验验收标准。

## 这次调研要补充 R4 的哪些部分

R4 已经确认：当前 NoteDetail 是工程 seed，不是最终编辑器；最小可用人工笔记体验必须从“表单添加 block”升级为“页面即编辑入口”。

本补充调研要补充的是：

1. 用户点击或双击页面空白处时，系统到底应该怎样创建输入光标。
2. 用户是否应该感知到自己正在被一个 block 限制。
3. `Enter`、`Shift+Enter`、空白处双击之间如何区分。
4. Slash command 如何承担 block type / formula / image / code 等插入入口。
5. 手动输入 LaTeX 公式时，用户应该怎样进入公式 block 或 inline formula。
6. 新建 text block 时，系统如何决定它的位置、宽度和归属。
7. 左边已有图片或 block 时，用户在右侧空白处点击或双击应发生什么。

R4 原本强调“自然输入”，本补充调研进一步强调：

```text
用户体验上应该像普通笔记软件；
系统底层才是 NoteBlock。
```

## 这次调研要补充 R5 的哪些部分

R5 已经确认：Coincides 需要 Page-first freeform block-box editor；NoteBlock 是内容 truth，BlockBox 是 layout / presentation。

本补充调研要补充的是：

1. 新建 block 默认是否撑满页面宽度。
2. 用户缩窄 block 后，文字如何自动 reflow。
3. block 高度是否应随内容自动增长。
4. block 边界什么时候显示，什么时候隐藏。
5. 为什么 Coincides 不只需要上下边界，也需要左右边界。
6. 用户怎样创建左文右图、左图右文、左右并排段落。
7. 两个 text block 水平或垂直对齐时，文字本身如何对齐。
8. 是否需要 snap mode / alignment guide / baseline guide。
9. layout edit mode 和普通写作模式如何分工。
10. 这些规则对 BlockSuite / 自研 fallback 的 spike 验收有什么影响。

R5 原本强调“block-box 可以 resize 和并排”，本补充调研进一步强调：

```text
block-box 的自由排版不能破坏普通文档写作心智。
```

## 本次调研要回答的问题

### 输入与创建

1. 用户点击空白页面时，是直接创建 block，还是只显示 insertion hint？
2. 用户双击空白页面时，是否创建新的独立 text NoteBlock？
3. 如果用户在已有文字内部按 Enter，是当前 block 内换行，还是创建新 block？
4. 如果用户在已有 block 下方空白处双击，是否创建一个新的独立 NoteBlock？
5. 如果用户在已有 block 右侧空白处双击，是否创建一个与它并排的新 NoteBlock？
6. 如果左侧是图片，用户在图片右侧空白处输入，是否创建一个新的 text block？

### Block 体验

1. 用户什么时候能看到 block 边框？
2. 用户什么时候只看到自然文本，而不看到明显 block 框？
3. block 的上下边界、左右边界应怎样表现？
4. block 的 resize handle、drag handle 应什么时候出现？
5. 用户是否需要显式进入 layout edit mode？

### 排版与对齐

1. 新 text block 默认宽度应该是多少？
2. block 缩窄后，文字是否自动提前换行？
3. block 缩窄后，高度是否自动增长？
4. 用户如何让两个 block 水平对齐？
5. 用户如何让两个 block 垂直对齐？
6. 相同字体大小的两个 text block 对齐时，文字 baseline / text top 是否也应对齐？
7. 是否需要轻量吸附和 alignment guides？
8. snap mode 是否默认开启，还是由用户手动开启？

### Slash 与公式

1. `/` 应该打开哪些 block type？
2. LaTeX 公式应该支持 inline 和 block display 吗？
3. 用户输入 `/formula` 后，是否进入专门的 LaTeX 编辑空间？
4. 公式错误时，是显示 warning，还是阻止保存？

### 数据与实现

1. 这些交互是否要求新增 `BlockBox` 或 page placement 层？
2. 当前 `canvas_nodes` 是否足以表达这些 layout？
3. 当前 `note_block_placements` 是否足以表达这些 layout？
4. BlockSuite Edgeless 能否承载这些行为？
5. 如果 BlockSuite 做不到，Coincides-owned fallback 至少要支持哪些能力？

## 初步默认决策

本补充调研建议先采用以下默认决策，后续 spike 再验证是否可行。

### 决策 1：用户不应感觉自己被 block 限制

底层可以是 NoteBlock，但用户表层体验应该是：

```text
点击页面
  -> 出现光标
  -> 直接输入
```

用户不应该先理解“我要创建一个数据库对象”。NoteBlock 是系统结构，不是用户心理负担。

### 决策 2：Enter 与空白处双击分工

建议默认规则：

```text
Enter = 当前 block 内继续，或按编辑器规则创建下一段同类 block
Shift+Enter = 当前 block 内软换行
空白处双击 = 创建新的独立 NoteBlock
```

如果用户在现有文字下面的空白处双击，而不是在当前文本内部按 Enter，系统应理解为：

```text
用户想在新的空间位置开始一个新 block。
```

### 决策 3：新 text block 默认撑满 formal page 可用宽度

新建 text block 时，如果页面没有横向阻挡物，默认应像 Notion / AFFiNE 一样撑满正式页面正文宽度。

但这个默认宽度不是强制宽度。用户可以手动 resize：

```text
full width
  -> half width
  -> one-third width
  -> custom width
```

### 决策 4：resize 改 layout，不改内容 truth

当用户缩窄 text block：

```text
NoteBlock 内容不变
BlockBox / CanvasNode width 改变
文字在 box 内重新换行
height 默认 auto grow
```

文字不能被吞掉。第一版应优先 `auto_height`，避免固定高度导致内容不可见。

### 决策 5：左文右图 / 左图右文是核心需求

如果左边已有图片，用户在图片右侧空白处双击，应创建新的 text block。

如果左边已有 text block，用户在右侧空白处双击，也应创建新的 text block。

这不是高级功能，而是 Coincides 区别于传统单列 block editor 的核心体验。

### 决策 6：block 边界默认弱化，选中或 layout edit mode 才强调

普通写作状态下：

- 不应一直显示强边框。
- 用户应感觉自己在写文档。
- block type、source、relation 等信息可以弱化成 hover badge。

选中或 layout edit mode 下：

- 显示上下边界和左右边界。
- 显示 resize handle。
- 显示 drag handle。
- 显示 source / relation / export intent badges。

### 决策 7：需要左右边界

Notion / AFFiNE 的传统文档流主要强调上下 block 分界。

Coincides 必须额外强调左右边界，因为：

- block 可以并排。
- block 可以缩窄。
- block 可以与图片同一行。
- block 可以在页面空间中自由布局。

左右边界不一定常驻显示，但在 layout edit mode 中必须清楚。

### 决策 8：需要轻量吸附和对齐辅助

自由排版不等于让用户手工对齐到崩溃。

第一版至少应考虑：

- page margin guide；
- nearby block edge snap；
- horizontal alignment guide；
- vertical alignment guide；
- same-width / same-height hint；
- text top / baseline guide；
- snap mode 可开关。

系统不替用户决定排版，但要帮助用户排整齐。

## 交互场景推演

### 场景 1：空白页面开始写

用户打开一篇空白笔记。

期望流程：

```text
双击页面正文区域
  -> 页面左侧正文边界出现光标
  -> 输入文字
  -> 系统创建 text NoteBlock
  -> 默认 full width
```

用户感知：

```text
我在写一篇文档。
```

系统内部：

```text
创建 NoteBlock
创建 BlockBox / placement
设置 page_id / x / y / width / auto_height / export intent
```

### 场景 2：在下方空白处另起一块

用户已经写完一个段落，但没有在段落内部按 Enter，而是在段落下方空白处双击。

期望流程：

```text
双击下方空白处
  -> 创建新的 text NoteBlock
  -> y 位置接近用户点击位置
  -> 默认与页面正文左边界对齐
```

这与当前 block 内换行不同。它代表用户想创建新的空间对象。

### 场景 3：缩窄左侧段落，再在右侧写

用户把左侧 paragraph block 缩窄到页面左半边。

然后在右侧空白区域双击。

期望流程：

```text
系统识别右侧可用空白矩形
  -> 创建新 text NoteBlock
  -> y 与左侧 block 对齐
  -> x 从右侧空白区域开始
  -> width 延伸到页面右边界或下一个阻挡物前
```

用户感知：

```text
我创建了左右并排的两段内容。
```

### 场景 4：左图右文

用户插入一张图片，并将图片放在左侧。

用户在图片右侧双击。

期望流程：

```text
系统识别左侧图片为阻挡物
  -> 在图片右边缘之后创建 text block
  -> text block 默认与图片顶部或用户点击 y 对齐
```

这允许自然图文混排。

### 场景 5：输入 LaTeX 公式

用户输入 `/formula`。

期望流程：

```text
slash menu 选择 Formula
  -> 创建 formula NoteBlock 或转换当前 block
  -> 进入 LaTeX 编辑空间
  -> 支持 preview
```

如果公式有错误：

```text
保留原始输入
显示 warning
不吞掉内容
```

## 数据结构含义

这套体验要求继续坚持：

```text
NoteBlock = 内容 truth
BlockBox / CanvasNode / placement = layout truth
```

至少需要表达：

```text
note_block_id
document_or_canvas_id
page_id
x
y
width
height_mode: auto | fixed
height
z_index
export_intent
ai_visibility
layout_mode
snap_metadata
```

当前 `canvas_nodes` 已经有 `x/y/width/height/z_index`，适合做 spike seed。
当前 `note_block_placements` 已经有 placement 语义，适合保留 note 内顺序和显示模式。

但最终是否需要独立的 `BlockBox` / `PageLayoutPlacement` 表，需要等 BlockSuite spike 后判断。

## 对 BlockSuite Spike 的验收影响

后续 `BlockSuite Edgeless-as-page + Coincides semantic sidecar` spike 不应该只验证“能不能显示 block”。

它必须验证：

1. 能否在 formal page frame 内自然创建 text block。
2. 能否让 text block 默认 full width。
3. 能否 resize text block，并让文字 reflow。
4. 能否 auto-height，避免文字被裁掉。
5. 能否在右侧空白处创建并排 block。
6. 能否做左图右文。
7. 能否显示/隐藏 block 边界。
8. 能否提供基本 alignment guide 或至少保留实现空间。
9. 能否区分 page 内正式内容和 page 外 scratch。
10. 能否把 editor runtime id 映射回 Coincides NoteBlock / placement id。

如果 BlockSuite 只能承载自由画布对象，但无法提供接近普通文档的自然输入体验，那么它只能作为 canvas surface，不足以成为完整 editor foundation。

## 尚未决定的问题

1. 单击空白处是否立即创建 block，还是只显示 insertion hint？
2. 空白处双击是否一定创建 block，还是需要结合当前工具模式？
3. Enter 是在当前 block 内换行，还是创建新的 sibling block？
4. block 的默认高度是否完全 auto，还是有 min-height？
5. 图片右侧创建 text block 时，默认 y 是对齐图片顶部，还是用户点击 y？
6. snap mode 是否默认开启？
7. layout edit mode 是显式模式，还是根据选中对象自动进入？
8. 普通文本 block 和 scratch sticky note 是否都是 NoteBlock？
9. 页面外 scratch 是否默认 AI-readable？
10. 如果用户把 scratch block 标记为正式导出，是否自动进入 page layout？

这些问题不需要现在全部锁死，但 spike plan 必须挑出其中最关键的部分进行验证。

## 本补充调研结论

R4/R5 的补充结论是：

```text
Coincides 的手动编辑体验必须同时满足两件事：

1. 写作时像普通文档，不让用户感觉被 block 限制。
2. 排版时像自由画布，让 NoteBlock 可以 resize、并排、对齐、图文混排。
```

这要求我们把 NoteBlock 和 BlockBox 的关系想清楚：

```text
NoteBlock 负责内容。
BlockBox 负责空间。
Canvas/Page 负责视图。
Export intent 负责传播边界。
ObjectRelation 负责语义关系。
```

后续 editor foundation 的真正验收不是“能不能创建 block”，而是：

```text
用户能否像写文档一样输入，
又能像排版工具一样整理 block，
同时系统还能保留 source、relation、template、domain 和 future AI-readable truth。
```
