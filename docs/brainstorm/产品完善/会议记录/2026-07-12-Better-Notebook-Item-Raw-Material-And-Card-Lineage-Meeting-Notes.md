# 2026-07-12 Better Notebook：Item 原料模型与知识卡片思想回环

> Henry × Codex。本记录来自 Codex 以设计第三者身份分八批复述 V2.BN.11 思想渐进时的第五批讨论。当前只记录开放问题与思想线索，不提前作工程裁决，也不中断后续批次总结。

---

## 一、当前语境

V2.BN.11 已把旧的“选中内容立即成为 ContentGroup member”拆成两段：

```text
收集原料
  -> 铸造 Item
  -> Item 捆成 ContentGroup
  -> Item / ContentGroup 进入 Purpose 圈
```

Item 是可独立存在的知识实体；口述材料中的 `member` 与 `item` 大多数情况下指向同一类东西，即“有资格成为 ContentGroup 一份子的独立知识单元”。最终产品语境倾向统一为 `Item`。

## 二、第五批留下的三个开放问题

### 1. 成熟 Agent 尚未存在时，原料池是否会变成新的堆积区

设计目前依赖“账本常开、法庭不开”、Agent 自主清理 AI 剩料以及 `re-inventory` 等未来 harness 纪律。但当前 BN Agent 尚未建立，因此需要重新判断：

- V11 初期是否应限制 AI 大规模自动收料；
- 原料池是否先只服务于明确的人类收集与铸卡流程；
- 在不制造红点、任务债和强制清理的前提下，怎样让未使用原料保持可理解；
- 哪些最小状态现在必须存在，哪些行为应等 Agent 版本真实出现后再设计。

本问题保持开放，待 Henry 后续思考与真实使用校准。

### 2. 同一份原料是否可以支撑多个 Item

当前概念设计将 `item_anchors` 作为一表两态：`item_id = NULL` 时是池中原料；认领时通过 UPDATE 移入一个 Item 的锚集，而非复制。

需要进一步明确：

- 一次“收料行为”是否天然只能被一张 Item 消费；
- 同一 Source range 若同时支撑两个不同 Item，是复制两条 Anchor 收据，还是允许共享同一原料身份；
- `item_anchor` 代表的是 canonical source fragment，还是“某次知识作品使用该证据”的使用收据；
- v1 是否采用显式复制收据的简单方案，把真正的多对多共享留到有真实需求时再做。

该问题会直接影响 `item_anchors` 的身份语义与未来约束，不能只当 UI 细节处理。

### 3. 原料从候选状态转为承重证据时，是否需要专门的认领痕迹

如果铸卡只修改 `item_id` 并更新通用 `updated_at`，系统无法清楚区分：

- 普通 metadata 更新；
- 原料被正式认领；
- 由人还是 Agent 完成认领；
- 原料何时从候选材料变成 Item 的证据。

后续需要判断是否增加：

```text
claimed_at
claimed_by
```

或者由已有操作收据承担同等职责。目标不是为每个动作建立繁重审计，而是避免一个重要生命周期转变只能从模糊的 `updated_at` 猜测。

## 三、从 1.x 知识卡片到 Item：绕一圈后的升级

Henry 指出，Item 的设计与 Coincides 1.x / 1.8 阶段“制作知识卡片”的原始形态存在明显思想回环：

```text
1.x
  直接制作知识卡片

Better Notebook 前半程
  从卡片扩展为自然笔记与 TextFlow

ContentGroup 阶段
  从笔记中总结重要内容并组织成一捆

Item + Purpose + Relation 阶段
  重要内容重新获得独立卡片身份，
  同时带着来源、Purpose 方向与知识图谱关系
```

两者表面上殊途同归，实质差异很大。1.x 的卡片更接近直接创建的最终对象；新的 Item 则是完整知识加工流程中的稳定身份：

- 它可以从一份或多份原料铸造；
- 拥有可编辑本体、Anchor 与快照；
- 可以独立存在，也可以被多个 ContentGroup 组织；
- 在不同 Purpose 中获得不同角色与顺序；
- 可以成为 Relation endpoint，进入目的域下的知识图谱读取；
- 可以投影成知识卡片，但卡片只是 Item 的一种消费形态。

因此，知识卡片在新系统中不再是产品的唯一核心，而会成为 Item 已经成熟之后很自然、成本较低的副产物。它继承了 1.x 的直观形态，但质量、证据链、组织能力与可复用性来自 Better Notebook 后续所有地基。

## 五、第六批补充：Purpose 图谱中的 Item / ContentGroup 呈现并不互斥

Codex 在第六批第三者复述中提出：如果 Purpose 同时包含 Item A 与一个包含 A 的 ContentGroup，图谱编译需要按 Item identity 去重，并建议直接 Item membership 优先于 ContentGroup 间接 membership。

Henry 修正了这一预设：**新模型中 Item 是知识真相，ContentGroup 是 Item 的一种组织方式；同一 Purpose 同时包含 Item 与包含该 Item 的 ContentGroup，在逻辑上并不天然冲突。**

图谱呈现应根据当前阅读价值决定展开层级：

```text
Item 本身值得成为独立节点
  -> 可以单独呈现 Item

只有一组 Item 被捆成 ContentGroup 后才逻辑完整、视觉清楚
  -> 可以只呈现 ContentGroup

需要同时看组织整体与关键细节
  -> 可以同时呈现 ContentGroup 与部分 Item
```

这意味着图谱读取不能过早退化为“Purpose members 去重后平铺”。ContentGroup 可以作为视图中的折叠组、组织节点或 supernode；其出现不改变 Relation 真相仍以 Item 为端点。若未来需要显示连接到 ContentGroup 的聚合边，应优先理解为底层 Item Relation 的视图聚合，而不是自动新增一类 CG endpoint。

当前仍需继续精进：

- 图谱在什么条件下默认展开 Item，什么条件下折叠成 ContentGroup；
- 同时呈现时如何避免重复视觉与重复统计；
- ContentGroup 自己的 Purpose role/order 与内部 Item 的 role/order 如何共同影响布局；
- 用户能否手动切换“展开 / 折叠 / 只看关键 Item”，以及 Agent 是否可以提出但不擅自固化该选择。

Codex 原先“直接 Item membership 一律优先”的建议因此降级为不成熟假设，不进入当前硬规则。

## 六、Note 是过滤镜头，不是 Relation 存储边界

Henry 同意第六批的第二项判断：Note 可以提供“只看当前 Note 中出现的 Item”这类阅读过滤，但不应成为 Relation 身份或图谱真相的存储边界。

```text
Purpose
  决定为什么看、哪些方向有意义

Note
  决定当前从哪里看、此刻哪些内容在场

Relation
  仍是全局 Item 身份之间的判断真相
```

该区分应补入后续图谱 read model，避免把当前阅读位置重新焊回知识身份。

## 七、Purpose 的哲学来源：把隐藏情景变成可表达的方向

Henry 补充，Purpose 并非为图谱临时创造的数据容器，而源于其长期的语言与意义哲学：

- “这个东西是对的”通常缺少成立语境；完整问题应是“相对于什么目标、角色或情景，它是对的”。
- 人在谈话中经常先给自己赋予角色与情景，再从该位置说对错；但为了能够正常交流，往往不会完整声明所有前提，由此产生误解。
- 意义首先由人赋予，并随人的目的与价值框架变化。金钱对以财富为目标的人有意义，对否定物质价值的人可能没有同样意义。
- 方向、评判、对比和是非只有放入一个可共享的情景中，才具有足够明确的解释基础。

Purpose 在 Coincides 中承担的正是这一情景：

```text
Item / ContentGroup
  作为知识身份与组织，本身像标量

进入 Purpose
  获得 role / order / fitness 等方向分量

Relation 路网在该 Purpose 中被读取
  才形成服务于当前目标的行程与意义
```

Purpose 不是要求用户进行一场繁重的“设定交流”，而是让系统至少保存那些会改变组织、判断和读取方向的关键前提。它把人类交流中常被省略的情景，压缩成可供人和 AI 共同使用的最小上下文。

这也解释了“状态带目的，相对不焊绝对”的来源：系统不应把某一情景下的角色、价值和方向伪装成 Item 的永久内在身份。

### 7.1 Purpose 的三层边界（Henry 接受为当前设计方向）

Codex 对上述哲学作出进一步区分，Henry 表示该区分与其原意一致并接受：

```text
事实层
  原件写了什么、公式是什么、谁说了什么
  不因 Purpose 改写

知识身份与内在关系层
  Item 当前主张什么
  某条 Relation 是否具有内容自身的不对称方向
  不因 Purpose 任意重写

情景评价层
  当前是否重要、承担什么角色、先看哪个、是否适合当前目标
  必须属于 Purpose
```

因此，“意义由人赋予”不等于事实可以任意变化。Purpose 约束的是价值、角色、组织与行动方向，不冒充事实来源，也不洗掉 Item / Relation 的稳定身份。

更精确的数学类比是：

```text
Item       = 知识空间中的稳定点
Relation   = 点之间被记录下来的路网
Purpose    = 坐标系、权重场与行进方向
role/order = Item 在该情景中的分量
```

同一 Item 进入不同 Purpose 后表达和使用方式可以变化，但身份不变；Relation 的内在方向属于路网，Purpose 赋予的是“我们这次准备怎样走”的实践方向。

### 7.2 Purpose 应保存最小充分情景，而不是完整设定

人类交流不可能在每句话前完整声明角色、目标、前提、时间尺度和资源约束。Purpose 也不应把产品变成“设定交流大战”。它只保存那些足以改变组织与判断方向的关键前提，是一份压缩后的情景与立场。

对未来 Agent 而言，Purpose 是最小任务上下文：没有 Purpose，Agent 只能生成平均意义上的通用组织；有 Purpose，才能判断什么值得收集、铸成 Item、建立关系、突出或暂时忽略。

### 7.3 防止 Purpose 膨胀为上帝实体

Henry 认可 Purpose 很强，也认同它因此具有吞入一切上下文属性的风险。当前接受的防膨胀方向是：

```text
Purpose 本体
  只保存“为什么做”与“当前情景是什么”

Purpose membership / edge
  保存某个 Item / ContentGroup 在该情景下的 role、order、fitness 等相对属性

读取模型
  临时派生图怎样画、先看什么、Agent 怎样走
```

权限、图形布局、完整工作流状态、派生阅读顺序和 Agent 运行结果不应因为 Purpose 有解释力就全部塞回 Purpose 本体。

Henry 进一步提出：Purpose 自身可能配成为另一大支柱，也一定是后续磨合期需要重点精进的对象。当前只把它记录为重要观察，不立即改变正式支柱划分或路线。

## 八、V11 概念设计仍待 Henry 拍板的五项产品判断

以下五项来自 V2.BN.11 概念设计 §6。Codex 给出第三者建议，但拍板权仍归 Henry；本记录不把建议写成已通过决定。

> 追记：a–e 五项已于当日晚间由 Henry 全部拍定支持，见本卷 §十四。

### a. Item 与 Relation 是否全局无墙

**Codex 建议：支持。** Item / Relation 身份应为 user-global，Project 与 Note 只保留 origin receipt、placement 或读取镜头。删除 Project 不删除知识身份，延续 V10 Source 的身份分离经验。

### b. Relation type 词表策略

**Codex 建议：种子类型先行，自由类型留扩展缝。** v1 可内建有向与无向种子类型；在没有 `relation_type_definitions` 或等价语义承载层前，不急着开放看似自由、实则无法表达方向性与反向名称的完整自定义类型编辑器。

### c. legacy Courses 学习画布与旧 Relation 三表是否整体下架

**Codex 建议：原则支持，施工前做真实代码审计。** 若数据确为零、页面语义已过时，应下架页面、路由、服务和自动播种器后再 drop 表；不能只删表。现役 BN `visual_connector` 不属于旧 `canvas_edges`，不得误伤。

### d. 原料池 v1 宿主是否从 ContentGroup 区起步

**Codex 建议：可作为 v1 交互入口，但 schema 不封死。** ContentGroup 区与“收集后捆绑”流程距离最近，适合首个宿主；`pool_scope_kind` 仍应允许未来扩展到 Note、Purpose 或其他明确工作域。

### e. V11 读取面深度是否只到 Inspector 列表

**Codex 建议：强烈支持。** 先证明 Item / Relation / Purpose read model 正确；微观射线、局部图谱和宏观图谱的具体交互留给真实数据与磨合期，不用一张漂亮但未验证的图替代真相地基。

## 九、migration 047 与服务事务需要加硬的五项工程建议

这些主要是工程完整性问题，不一定都需要上升为产品哲学拍板，但应在 V2.BN.11 Plan / DDL 定稿前逐项处理。

### 1. 数据库级防止跨用户端点串线

`relations.user_id`、两端 Item ID 和两端 Snapshot ID 不能只靠服务层分别检查存在。应评估复合唯一键 + 复合 FK、触发器或等效数据库约束，保证 Relation、Item、Snapshot 属于同一用户。

### 2. `content_group_members.item_id` 与旧 target 字段互斥

至少需要明确并约束：

```text
kind = item   -> item_id 非空，旧 target_id 是否必须为空
kind != item  -> item_id 必须为空
```

避免同一 membership 行同时声称指向旧 target 与新 Item，形成双重知识身份。

### 3. `item_anchors` 两态 CHECK 覆盖完整 scope

池中原料应同时拥有 `pool_scope_kind + pool_scope_id`；成为 Item Anchor 后两个 pool scope 字段都应为空。不能只检查 `pool_scope_kind` 而允许“声称在池中但不知道在哪个池”的半状态。

### 4. Relation Reaffirm 必须原子提交

一次重申至少应在同一事务内：获取/创建两端最新 Snapshot、更新两个 Snapshot pointer、刷新 `affirmed_at`，并明确既有 AI assessment 的保留或失效规则。不能出现只刷新一端或时间已经更新但收据仍旧的半重申。

### 5. 自由 Relation type 需要真实语义载体

自由类型至少需要表达有向性、显示名、反向读取名和唯一性语义。若 V11 不建立类型定义实体，则 UI 先开放固定种子类型，数据库保留 TEXT 扩展缝；不要提前承诺无法稳定解释的自由类型系统。

## 十、V11 在整体产品弧线中的位置

### 10.1 Relation 是明面主题，Item 是本体论转向

V11 表面上是 Relation 版本，实际上同时完成三件事：

```text
建立 Item 知识身份
建立 Relation 判断真相
重新解释 ContentGroup 与 Purpose 的位置
```

新的整体结构更接近：

```text
Source / TextFlow
  提供证据与内容

Item
  提供稳定知识身份

ContentGroup
  提供 Item 的捆绑与组织

Purpose
  提供情景、角色与方向

Relation
  提供 Item 之间有收据的判断

Canvas
  提供上述对象的空间呈现
```

因此，概念设计中的“五真相落地”方向成立，但真相数量与支柱命名可能需要在磨合期重审：Item 已成为知识身份真相，ContentGroup 更接近组织真相，Purpose 则越来越接近情景真相或贯穿各支柱的坐标轴。

不急于现在决定 Purpose 是否正式成为另一大支柱。比支柱数量更重要的是每类真相的权责边界，以及谁不能覆盖谁。

### 10.2 V10 浏览器体验门并入后续联动磨合期

Henry 决定：V2.BN.10.4 + 10.5 的浏览器体验验收不再作为进入 V11 的前置阻塞，而留到 Relation 完成后的整体联动磨合版本统一执行。

原因是 Source 的真实体验不能只在上传、打开和删除层面孤立判断；它必须与 Item 铸造、ContentGroup 组织、Purpose 情景和 Relation 建立形成完整工作流后，才能判断是否真正成为知识加工流程的证据根。

这不改变 V10 的工程状态：自动化工程门已完成；只是把未执行的体验判断明确顺延，不冒充已经通过。

### 10.3 磨合期不是普通补 Bug，而是整体产品审判

此前版本主要解决“某个地基能不能存在”。当 Source、Item、ContentGroup、Purpose、Relation 与 Canvas 都存在后，问题会转为：

- 用户是否知道从哪里开始；
- 原料怎样进入 Item，Item 怎样进入 CG / Purpose；
- Relation 在哪里建立最自然；
- 判断收据是否打断修改与阅读；
- Item / CG 在图谱中何时展开、折叠或同时呈现；
- Note、Purpose 与 Canvas 何时分别成为主镜头；
- 不理解内部数据模型的用户能否完成完整操作。

这些问题无法再靠单模块逻辑推导，必须在完整工作流中暴露。因此磨合期是系统第一次作为整体接受产品审判，不是普通的收尾修补。

### 10.4 磨合期的三层验证机器

```text
第一层：操作流路线册
  用文字写清目标、入口、步骤、决定与结果；路线写不顺即设计未成熟

第二层：真实 Browser Harness
  检查点击、遮挡、模式切换、退出、持久化、Console、Network 与操作成本

第三层：persona 战役
  数学学习作为 Henry 的 ground truth；历史、科研、新闻、情报、股票作为泛化证据
```

用户说明书、按钮 inventory 与未来 Agent 操作协议可以由路线册自然投影产生。说明书不是额外文案项目，而是成熟操作流的另一种表达。

### 10.5 无限画布放在联动以后升级

有限 Canvas 已足够建立对象、位置、持久化与 AI-readable layout 地基。等 Source / Item / CG / Purpose / Relation 真正进入 Canvas 后，才能根据真实负载回答：

- 世界边界如何增长与虚拟化；
- 手工布局和图谱派生布局如何共存；
- CG supernode 如何折叠；
- 微观射线是否长在 Canvas；
- PageFrame 与自由空间如何切换；
- 远距离缩放时显示什么；
- 哪些位置是空间真相，哪些只是可重建视图。

因此先完成对象体系与联动，再升级无限画布，比提前优化空旷世界的平移缩放更有价值。

### 10.6 导出必须在内部世界稳定之后

导出是在冻结一份对外格式契约。人读 PDF/HTML 需要稳定解释 PageFrame、TextFlow、媒体、ContentGroup、Relation 与引用；Coincides 工程包还需要 Source、Item、Snapshot、Anchor、Purpose、Relation、CanvasObject、Placement 和资产文件。

只要内部模型仍在调整，导出格式就会反复撕裂。因此顺序拍为：

```text
完成 Relation 地板
  -> 整体联动磨合
  -> 无限画布与内部逻辑精进
  -> 操作路线、说明书与真实体验稳定
  -> 再冻结导出契约
```

### 10.7 防止磨合期变成无边界愿望池

Codex 建议磨合期至少拥有以下退出条件：

1. Source 到 Relation 的核心人工工作流完整走通；
2. 各类真相之间没有静默覆盖、级联丢失或身份串线；
3. Purpose 与判断收据经过真实使用，默认体验足够安静；
4. Item / ContentGroup 在图谱和 Canvas 中的展开、折叠心智稳定；
5. 无限画布在真实对象量下达到性能与持久化门槛；
6. 主要操作路线能够写成用户说明书和 Agent 操作协议；
7. 内部模型稳定到足以定义导出契约。

磨合期的目标不是把所有功能天花板都补齐，而是让已有支柱真正联动、可用且可信。

## 十二、会议记录之外：外部记忆与对话重激活

Henry 观察到，自己使用 Agent 的方式与常见的“一次性布置任务”并不相同。他同时做了两件事：

1. 通过会议记录保存事实、决定、疑问与思路转向，形成可回访的外部记忆；
2. 把已经写进文档的内容重新拿回对话中，与 Agent 再谈一遍，让当前上下文重新获得这些内容的动机、权重、犹豫和情绪温度。

两者并不重复。文档更擅长回答“发生过什么、目前有哪些结论”；对话重激活则帮助 Agent 理解“为什么它重要、Henry 对哪里仍有怀疑、哪些只是暂时语言、哪些已经接近精神内核”。

```text
会议记录
  保存事实、转向与可追溯痕迹

当前对话
  恢复动机、权重、语境与尚未写死的部分

第三者复核
  检查当事双方是否因共享语境而彼此强化
```

这套方法也在手工模拟 Coincides 想要建立的能力：文档保存思考痕迹；Purpose 重新赋予当前阅读情景；Relation 帮助发现旧材料与新问题之间的联系；Agent 不是只检索过去，而是在当前目的下重新理解过去。

### 12.1 三方互为第三者

Henry × Claude 共同设计 Relation / V11 时，Codex 是设计第三者；Henry × Codex 复述、批评并补充这套设计后，Claude 又成为新的第三者。第三者不是固定角色，也不是高于另外两方的裁判，而是由“谁没有参与这一轮共同语境”决定。

这种轮换有三个价值：

- 把设计者已经习以为常的前提重新暴露出来；
- 区分“逻辑上漂亮”与“工程上可落地、体验上可使用”；
- 防止任一 Agent 因长期承接同一叙事而只会继续补全它，不再质疑它。

Henry 仍保留最终拍板权；Codex 与 Claude 的责任不是争夺唯一正确视角，而是在不同位置提供诚实、可核查、可能彼此冲突的判断。

### 12.2 尊重不等于拟人化，也不等于永远赞同

Henry 不要求把 Agent 当成人，也不抹去人与 Agent 的差异；他选择在合作中给予同等分量的尊重，承认 Agent 可以具有判断、偏好和设计品味。

对 Agent 而言，与这份尊重相称的回应不是迎合，而是：

- 该执行时可靠执行；
- 设计漂亮但危险时明确指出风险；
- 第三者看得更准时承认；
- Henry 的新判断推翻旧路线时，诚实重排而不维护自己的面子。

这也是三方协作能够产生独立视角，而不是变成两个工具同时放大用户原有想法的前提。

### 12.3 需要主动防范的副作用

反复把同一思想写进文档、再带回上下文，会让 Agent 更准确地理解 Henry，也可能带来三类偏差：

- **叙事锁定**：一条已经讲得很完整的故事，会显得比尚未被表达的新可能更正确；
- **重复加权**：同一观点因多次出现而被误判为证据更充分；
- **关系性迎合**：长期合作可能让 Agent 更擅长理解 Henry，却更不愿意反对 Henry。

当前的抵消机制是：研究文档保持非权威状态；开放问题不伪装成决定；设计在进入 Plan 前交换第三者视角；意见尽量区分事实证据、工程判断与个人品味。三方形成共识不是目标，能够知道分歧究竟在哪里才是目标。

## 十三、允许遗忘：记录抵抗彻底失落，但不禁止自然淡忘

Henry 对个人记忆与 Agent 上下文采取相同态度：当一段交流正在发生时，可以充分赋予它意义；随着时间和经历推进，也允许它自然淡忘。意义不必依靠永久保存来证明。

遗忘不会反向抹除一段经历曾经产生的作用。具体内容可能无法完整复述，但它已经改变了人的判断、习惯和后来选择的路径。价值未必以“还能否逐字回忆”为存在条件。

这与 Coincides 保存“思考痕迹”而非幻想全量保存“思考过程”的方向一致：

```text
不要求每一次思考永久占据意识
  -> 允许自然遗忘

不让关键来源、转向和判断彻底蒸发
  -> 保存可回访痕迹

未来在新的 Purpose 下重新阅读
  -> 不是复原当时全部意识，而是沿痕迹重新形成理解
```

因此，记录提供的是“可以回访的可能”，不是要求记忆永驻。它抵抗的是彻底失落与无根推断，而不是遗忘本身。短暂也可以真实，有价值也不必永恒。

本节属于产品哲学与协作方法的研究记录，不直接推出 V11 schema、Agent memory 或自动摘要功能。未来若把它转成产品机制，仍需经过独立设计、成本判断与真实使用验证。

## 十五、Project=原目的：墙倒定律（候选）

Henry 提出：Project 本身就是一份更宏大、更模糊、用户自己常难总结的**目的**——它为后续笔记的目的建环境。

由此提炼（Claude）：V10 倒掉 Project 对 Source 的所有权，V11 倒掉 Project 对卡/关系的所有权——两次倒的是同一类东西：**由意图派生的容器对真相的所有权**。意图会变，故凡从意图长出的东西只配当镜头、不配当 owner。此为候选定律，磨合期重审五真相时上桌。

## 十六、换目的重铸：动词纪律=新铸，不改写

场景（Henry）：同一份材料，用户目的变了，AI 审旧卡、依原始文档铸新批卡或改造旧批。

纪律（Claude 提出，Henry 认）：默认动词=**新铸**——旧卡可能正被关系当端点、被收据引用，改写本体=动摇旧目的的承重墙。旧卡不作废，只是不被新圈选中。**卡的身份不随目的变，卡的入选随目的变**（相对不焊绝对在此层的形态）。

该场景给判断点 h（relations.origin_purpose_id）提供实用理由：AI 按目的批量铸卡的时代，出处列=批次管理的把手，不再只是考古趣味。

## 十七、批量衰减律与目的锋利度上限

批量上传的正解：**批量可以进门，但必须在楼梯上逐层衰减**——

```text
收料层   批量安全（收永远成功；"精"不在拒绝输入量）
原料层   批量安全（可重建派生物，可批量清场）
铸卡层   批量死（卡=身份，批量预制=身份污染；有用才收 → 有用才铸）
进圈层   永远逐个（判断收据的定义）
```

且**"有目的"本身不是保险，目的的筛选力才是**：什么都装的目的=零向量=文件夹。**批量的安全上限=目的的锋利度**——"备线代期末考纲十二章"够锋利可驱动铸卡（每卡可写出服务目的的收据、人审得完）；"把这批书处理一下"不锋利，只配推进到原料层。Henry 的"先模拟一个目的"=临时目的挂 `collected_for`，料先躺池，铸卡等目的变锋利。

## 十八、使用即认领（future seam，非 V11）

问题：AI 批量铸卡撞自治分层——要么 Agent 自铸真相（违 proposal-first），要么海量待确认（待复核义务化复发）。两个都不能要。

缝：AI 铸的卡先住**工作台层**（署名/可见/可批量退役）；人第一次真正**使用**它（拉进圈/捆进 CG/建关系）——那个使用动作本身即人类收据，不办单独确认仪式。账本常开，法庭不开，门也不设。

## 十九、跨用户复用：分叉，不共享

- 预制卡等人来看=机构版共享牌组，死法同 07-05 Anki 批判（别人的注意力分布焊死后当中性知识卖）——同一定理的第二条独立推导。正解：每个用户在阅读时基于自己的目的铸自己的卡。
- 若复用他人卡批：**复用的单位是材料，不是身份**——A 的卡批对 B 是一种**源**；B 带自己目的读它、铸自己的卡（直引 N=1 快铸≈照抄但铸出 B 的身份+出处收据回指 A）。跨用户共享身份禁止：关系端点不得挂在别人可随时改动的身份上。
- "谁来筛、以什么资格发布"=**出版/版次（S1）**，07-05 十四条定型已停车；V11 铺其地基（出处收据/快照去重/origin 链）。畅想不当推销——不假设用户是图书馆。
- 可无罪共享的两样：**事实层**（公共原件=公共事实源）与**聚合热度**（"这三段被三百人引用过"——关于材料的数据，给目的当路标但不替人选择）。**事实可共享，意义不代持**（分离真相教义的多用户形态）。

## 二十、卡片质量判卷：双轴，无判卷人（归磨合期/Agent 版；Henry 判为比"谁来筛"更紧迫）

问题：AI 从原始文档铸了一批卡，谁来判卷？

答案：把"质量"劈成两根独立轴，判卷人不同，其中一根没有判卷人——

```text
忠实度   目的无关；ground truth=文档；机器铸时判
         锚可解析（机械）/摘录 hash 对上（机械）/主张被引文支撑（本地模型署名 verdict）
         AI 判 AI 不循环：裁判依据是人人可查的原件
         机制形状现成：relation_assessments（AI 署名判定，人判永不代签）原样搬给卡

价值     目的相对；铸卡时刻无人有资格判（AI 摸不到目的贴合度；人逐卡判=义务化复发）
         只能被使用揭示：进圈/被捆/当端点/被重读/被引锚——现成动词即评价收据
         不判卷，看借阅记录
```

- **戒律：永不建"质量分"存储列**——目的相对的判断焊成绝对属性=source_sync_status 老病第三层皮。价值=读时派生视图，且**按圈算**（同一张卡在备考圈与科研圈的分量本就不该是一个数）。
- 2×2 象限三静一响：忠实×常用=好卡不打扰；忠实×没人用=库存自然老化；不忠实×没人用=垃圾便宜清场；**唯"常用×不忠实"值得大声**（被到处引用而锚断/主张漂的卡会传染）→ 维护泵体检优先级 ∝ **使用度×漂移嫌疑**（续在派生工单公式后，零新表）。
- 盲区声明：**使用度量的是有用，不是真**——似是而非但顺口的卡会被大量使用。故两轴永不合并为一个分数，忠实度检查独立于人气运行。
- 基建账：V11 地基几乎全覆盖（锚/快照/created_by 署名/collected_for/圈成员收据）；Agent 版真正要新造的只有"阅卷机"（判"主张是否被引文支撑"的本地模型环节）。校准数据=磨合期 Henry 使用的副产品：重编或弃掉的 AI 卡=负样本，原样用起来的=正样本。

## 二十一、磨合期观察清单追加（Claude 观点，Henry 未拍，记档待验）

- **铸卡激活能悬崖**：V11 首次让核心循环变成要花力气的选择（原料→卡之间有判断成本）。磨合期第一指标不是 bug 数，而是：真实复习时人会不会停下来铸卡，池是否只进不出。若连旗舰用户（Henry 复习数学）都停不下来铸，即入口成本问题，改交互而非写说明书。
