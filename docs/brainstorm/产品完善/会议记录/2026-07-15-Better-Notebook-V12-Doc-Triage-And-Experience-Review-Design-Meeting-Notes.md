# 2026-07-15 Better Notebook：文档分诊、更新手册与体验审查设计

> Henry × Claude。V2.BN.11 已于 07-14 收口(engineering-complete、已 push)之后的第一次 V12 组织会。本卷细化 07-14 卷的两翼:内部调研与体验审查。

## 二、内部调研的第一步 = 文档分诊（Henry）

背景:Henry 自认不具备完整工程团队的开发思维,inventory、种子状态说明书、必要文档都没落好——这是当前要补全的。且**inventory 其实存在但过于久远**:经查即 `docs/contracts/Notebook-Object-Inventory-Contract.md`（2026-06-23 建,V2.BN.8 对象语汇;07-13 打过教义横幅补丁,但正文仍是 V8 时代——横幅补丁救不了正文脱节）。

**分诊协议（Henry 定,调研开跑前先做）**——比起重建,更难的是更正,所以先评估手边所有文档:

1. 哪些需要更正;
2. 更正量特别大的里面,哪些是**必须更正**的（历史/权威价值不可丢）;
3. 哪些是**重建比更正更简单、更准确**的——直接推倒重写。

## 三、文档更新手册：叙述者问题与可执行手册（Henry 提案 + Claude 方案,Henry 认可方向）

**Henry 的问题**:每次改动后该更新哪些文档(inventory、PRODUCT、contract……),目前靠 Henry 记忆或 Claude 盘查——两个都是不可靠叙述者。单次盘查 98% 成功率,100 次连乘 ≈ 13%,"成功率看不到头"。需要一份系统的辅助文档,辅助 Claude 和 Codex 在改动后更新对应记录文档。业界有何解法?

**Claude 的回答（Henry:"倒是可以",进概念稿）**:

- **元问题警告**:散文体"更新手册"自己就是第 N+1 份会过期的文档;它必须**可执行**,不能是散文。核心原则:**文档只要承重(被机器消费)就不会烂**。
- **业界谱系**:docs-as-code + PR 门禁规则(Danger.js/path filter)/文档-代码耦合漂移检测(Swimm 的 snippet 绑定、Google g3doc freshness 催办)/living documentation 生成派(能派生的不手写)/CODEOWNERS 与目录清单(Backstage)/RTM(监管级,不取)。
- **本仓三层方案**(与五真相教义同构:别信叙述者,信机械收据):
  1. **生成层**:表、路由、canvas object kinds、操作、npm scripts 等 inventory 事实面从代码生成(顺手补掉 inventory 欠账,生成物无过期问题);手写只留意图与为什么。
  2. **manifest 层**:机器可读的 doc-map(代码路径 glob → 关联文档清单)+ `check:doc-impact` 脚本进现有 verify 链——diff 碰了左边没碰右边即打印"该核对的文档清单"。这就是"更新手册",但每次提交都被执行,所以自己不烂。house style 现成(仓里已有多个 `check:*` 契约脚本)。
  3. **判断层**:理念级更新(如 PRODUCT.md 段落重写)机器只能指路不能代判;靠 manifest 指出"去看哪几份"+ 状态头纪律兜底。诚实声明:98% 提不到 100%,但第二层消灭"想不起来"这个最大漏源,残余失败模式("看了但改错")由复核接住。
- **两条红线**:manifest 保持小(映射维护成本必须低于漏更成本,宁粗勿细);警告不阻塞 commit(阻塞式门禁教会所有人绕过它)。

## 四、体验审查的目的与两阶段（Henry）

**体验审查服务于什么?——它是上机实测之前的准备工作。** 很多东西打眼一看就知道不合理,不需要深度体验;但若不先清掉,它们会成为深度体验和短流程测试的负担与干扰。

**打眼审查（glance 层）的实例（Henry 举例,声明"肯定不止这些"）**:

1. **TextFlow 写作入口与 text unit 图标**:双击空白区域→新建 paragraph block→回车换行、每行一个 text unit;每个 text unit 前有三个"没什么用的小图标"——模仿 Notion 的设计,在本产品不需要,体感很差:占据文字应占的空间,对文字对齐和格式不利。直观观察即可判定。
2. **按钮交互不合理**若干——肉眼一看即知,无需深度体验。
3. **有功能无入口**:功能做出来了但页面上没有明确按钮——已知例:调节文字缩进的标尺。

**Claude 补（记档待并入概念稿）**:打眼层产出同样入问题总账(🅱/🅲 分级);其中高噪声项可切成**先行 12.x 小批次**先清掉,再跑深度体验——否则深度体验测到的是已知噪声而非真实摩擦。打眼审查之于深度体验,相当于 lint 之于测试。

## 五、体验流程设计与记录纪律（Henry）

- 上机前要**先设计体验流程**,并记录流程中的**任何感受**——哪里好、哪里不好。
- **记录分工**:Henry 跑长流程,只记不好的(好的他一般不说);**Claude 体验时好坏都要记**。
- Claude 补记"好"的理由:重设计轮需要知道哪些东西已经对了,否则容易误伤(Chesterton's fence)——正面记录是未来改版的保护清单。

## 六、桌面应用原则:交互评审的标尺（Henry）

- **既定路线重申**:最终绝对会打包成桌面应用的感觉——网页应用套壳本地化(Tauri 式),暂不用 Rust 重写(Claude/Codex 此前的共同判断,Henry 认可)。
- **推论(评审标尺)**:交互设计的合理性按"本地应用感"评判,不按网页应用惯例。部分概念设计本来就朝跨页面/跨窗口方向(例:ContentGroup 添加、GroupFolder——连开两个窗口,从一个窗口把内容拖到另一个窗口操作;本地应用常见,网页里显得蹩脚),**设计了但没做**。
- 体验审查遇到"网页里蹩脚"的交互,要先判别:是真设计缺陷,还是"等桌面化后自然成立"的类别——别按网页惯例误判后者。
- **追加标准(Henry,本卷后半)**:评审时多问一句——**这个设计面该不该做成独立页面?** 独立页面 = 未来窗口化更方便。(Claude 概括:**路由即窗口**——桌面化多窗口本质是开路由,现在多开一条独立路由,将来窗口化就是免费的。)

## 七、首个模拟场景（Henry 拍定框架）

完全模拟一个**无 Agent 时代**的用户,带着目的进来整理笔记:

```text
Project（任意学科,Henry 选真实在学的）
  └─ 放入 7~8 份原始文档（类型 Claude 提案 → Henry 按类型找实际材料）
  └─ 新建 Note
  └─ 以用户视角设定一个 Purpose
       └─ 在该 Purpose 下进行笔记建设
       └─ ContentGroup 的总结/捆绑
       └─ 独立 Item 的整理沉淀
```

- 流程中设立**很多小目标**,每个小目标 = 以人类视角交互达成的阶段性交互目标(如:打开笔记、在笔记里查看信息、……)。
- **强度分层照旧**:短流程 Claude(内置浏览器、鼠标点、不走 API),复杂长流程 Henry(按 Claude 写的操作指南走)。

## 十、版本单位:旅程段（Claude 提案,Henry"也行"认可方向）

- **转轴命名**:V8–V11 是供给侧版本(单位=系统领域,每版建一层真相);V11 收口后该时代结构性结束(五真相建完,无第六领域)。此后工作单位=**用户旅程**,旅程天然横切所有真相——"哪儿都沾"是常态,非磨合期临时现象。
- **12.x 的切法**:按**旅程段**,不按子系统、不按整旅程。首弧候选段(从 §七模拟场景推导):材料进门(上传→解析→能读)/从读到卡(圈选→锚→铸卡)/从卡到结构(捆绑 CG→挂 Purpose)/回访与检索(全局 Item 搜索是已知硬缺口)。**路线册 = 切版本的刀**:预期先写,实测按旅程打分(RED-first 的体验时代等价物),问题来自总账,验收=重跑旅程看分数。
- **为何不散**:V8–V11 的契约测试与 check 脚本让横切工作的炸伤半径有界——地板闭合正是为了让横切版本可审。配套纪律:每个 12.x plan 加**触及面申报**(声明碰/不许碰哪几层地板);新 done = 地板契约全绿 + 旅程分数;deferred 的体验门升格为每个 12.x 的常规验收仪器。
- **排期形状**:版本外供料 → 12.1 噪声清场(打眼层点修,可按子系统组织)→ 12.2 起旅程段版本。
- 对照记录:按子系统打磨的切法输在结构上——磨合期最值钱的发现在**缝上**(跨窗口拖拽、材料到卡皆是),子系统版本无资格拥有缝。

## 十一、品味授权（Henry）与配套纪律（Claude,未拍）

- **Henry**:磨合期的用户体验(Claude)与代码(Codex)在极大意义上依赖两个 agent 的品味,**不希望过多限制品味**。
- **Claude 指出的特定风险**:AI 的默认品味=行业中位数("Notion 是这么做的"式推理)——text unit 三图标正是不加约束的 AI 品味的产物。纪律:**"业界都这么做"是警示信号,不是理由**;品味应从产品自身语法(真相分离/收据诚实/原文不可侵犯)推导,不从行业均值借用。
- **Henry 的修正(本卷后半,拍定)**:行业中位数**对交互恰恰是 OK 的**——交互设计是 Henry 自认最弱的领域,行业惯例"挑不出毛病",要先做成"感觉好"的常规交互;**代码则按产品自己的目的来**,不追行业时髦。
- **合成教义(Claude 翻译,Henry 语境认可)**——三句话:
  ```text
  交互的皮   行业中位数是地板(按钮/反馈/点击区/快捷键/撤销——兼容用户肌肉记忆,不标新立异)
  交互的骨   借惯例前做一次问题匹配:我们有没有它要解决的那个问题?
  代码       只服务产品自己的目的,不追行业时髦
  ```
  三图标的真正死因在第二条不在第一条:Notion 的拖拽手柄解决的是 block 操纵优先编辑器的问题,TextFlow-first 的本产品**没有那个问题却抄了那个解法**——"借了别人的解法,没借来它的问题"才是要拦的错误类型;中位数的"感觉好"照单全收。
- **三条配套(不限制品味,使品味可审计)**:
  1. **品味管面,不管真相**——红线(Agent 能编辑的人类必须 100% 能编辑)与真相层语义不入品味辖区;
  2. **品味留收据**——有分量的品味判断记入交互报告/设计注记并附理由,Henry 事后否决而非事前审批(延续非对称审计模式);
  3. **两个品味之间留缝**——交互品味与实现品味冲突时入问题总账,Henry 仲裁,不私下互相妥协。
