## 1. 这份文档是什么

R14 不是普通的 roadmap impact 摘要。

它是 v2.5 阶段的总指导文档，用来把 R1-R13 的调研结果收束成后续可执行的小版本 plan 依据。

它应该回答：

```text
v2.5 到底要建什么？
为什么要按这个顺序建？
每个小版本应该做多深？
哪些东西必须先做？
哪些东西要推迟？
哪些能力必须 proposal-first？
哪些数据要为 v3.x graph-native 重建保留证据？
哪些外部工具可以参考，但不能接管 Coincides truth？
```

后续写 v2.5.0、v2.5.1、v2.5.2 等 plan 时，不应该只看 roadmap，而应该把本文件作为 v2.5 阶段的直接总纲。

## 3. 总体结论

v2.5 的真正主题不是“做一个模板编辑器”。

v2.5 的真正主题是：

```text
建立 Coincides 的 Template / Composition / Domain / Package runtime foundation，
让 NoteBlock、Canvas、Source、Relation、Proposal 和未来 AI 操作拥有可扩展、可迁移、可打包、可审阅的结构基础。
```

一句话压缩：

```text
v2.5 是模板与包系统的基础设施阶段，不是 UI polish 阶段。
```

它要把 Coincides 从：

```text
有一些固定 NoteBlock 类型的 canvas-first 笔记系统
```

推进到：

```text
可按领域扩展、可由 AI 理解、可由用户编辑、可被打包迁移、
并为 v3.x graph-native 重建保留证据的信息工作台基础设施。
```

## 4. v2.5 总原则

### 4.1 Runtime first, editor second

先做 runtime，再做编辑器。

v2.5.0 必须先建立：

```text
TemplateDefinition runtime
field_schema
render_hints
source_behavior
relation_behavior
proposal_behavior
summary_for_agent
legacy compatibility report
```

如果没有 runtime，用户模板编辑器只会变成一个脆弱的表单。

如果没有兼容性报告，旧 NoteBlock 会在后续迁移中变成暗雷。

如果没有 behavior 和 `summary_for_agent`，AI 仍然只能靠 prompt vibes 选择模板。

### 4.2 Coincides owns truth

外部 editor、canvas engine、package format、导出格式都不能拥有 Coincides truth。

核心真相仍然属于：

```text
NoteBlock
SourceAnchor / SourceScope / note_block_sources
EvidenceSet
ObjectRelation
TemplateDefinition
CompositionTemplate
DomainBlockSet
Proposal
OperationBatch
PackageManifest
```

外部工具只能负责交互、渲染、缓存、导出、adapter 行为。

### 4.3 Template is contract, not code

模板不是隐藏代码，也不是插件。

模板应该定义：

```text
content shape
validation
display intention
source expectations
relation eligibility
proposal safety
AI guidance
compatibility metadata
```

模板不应该直接执行任意逻辑，也不应该绕过 proposal-first。

### 4.4 Behavior fields are policy, not truth

`source_behavior` 不保存 source truth。

`relation_behavior` 不创建 semantic relation。

`proposal_behavior` 不代表 mutation 授权。

它们只是告诉系统：

```text
这个模板允许什么？
期待什么？
什么操作必须 review？
什么情况下应该 warning？
```

### 4.5 Proposal-first remains a hard boundary

以下事情必须 proposal-first：

- AI 生成或改写语义结构；
- 批量迁移旧 NoteBlocks；
- 改变 source grounding；
- 创建 confirmed ObjectRelation；
- composition apply 中创建多块结构；
- template behavior 的危险改动；
- package import 中影响现有对象的变更；
- domain refinement / classification migration。

直接编辑只适合安全、局部、描述性或 UI-only 改动。

### 4.6 Domain grows as graph, not tree

领域不是死目录。

不要把 `academic.math.probability.biology.organic_biology.xxx` 这种路径越钻越深。

更好的模型是：

```text
stable domain identity
current domain key
aliases
parent domains
related domains
facets
migration history
```

用户和 AI 都会犯错。Coincides 必须允许知识结构被修正。

### 4.7 Package is data, not plugin

v2.5 的 package 不是可执行插件系统。

`.coincides` package 应该先是：

```text
可验证
可预览
可恢复
可导入导出
可携带 source / template / canvas / relation / proposal evidence
```

可执行插件、市场生态、社区分发，都不属于第一阶段。

### 4.8 Editor adapter, not migration

R12 明确：外部 rich editor 只能作为 adapter。

v2.5.0-v2.5.5 不应依赖外部 rich editor。

只有当当前编辑体验成为真实瓶颈时，才做 v2.5.6 或更晚的 spike。

候选顺序：

```text
Tiptap / ProseMirror
Lexical
BlockNote
Milkdown
BlockSuite as reference
```

但任何候选都必须证明：

```text
NoteBlock identity survives
template metadata survives
source markers survive
ObjectRelation not silently mutated
proposal-first preserved
adapter removable
```

### 4.9 Every version must record graph-native evidence

从 v2.5.0 开始，每个小版本 plan / review 都应有：

```text
Graph-Native Migration Evidence
```

它至少回答：

- 新对象是 future graph node、graph edge、property、projection、package object，还是 SQL side table？
- 它连接哪些对象？
- 哪些 provenance 必须保留？
- 哪些可以从 canonical truth 重建？
- 如果 `.coincides` package import 后缺失它，会坏在哪里？

## 5. v2.5 推荐版本拆分

R14 建议保留 roadmap 中的 v2.5.0-v2.5.6 拆分，但每个版本边界要比 roadmap 更明确。

不建议把 v2.5.0 做成巨型版本。

也不建议把 editor、package、domain、composition 全部提前塞进 v2.5.0。

推荐顺序：

```text
v2.5.0 Template Definition Runtime
v2.5.1 User-facing Template Editor Seed
v2.5.2 Composition / Section Template Seed
v2.5.3 Domain Block Set + Package Manifest
v2.5.4 Template Proposal + Migration Proposal
v2.5.5 Package Studio Lite / Export-Import Foundation
v2.5.6 Rich NoteBlock Editor Adapter Spike, only if needed
```

这个顺序的理由：

```text
runtime identity
  -> safe user editing
  -> reusable multi-block composition
  -> domain/package organization
  -> proposal-first migration governance
  -> portable project package
  -> optional rich editor adapter
```

## 6. v2.5.0 Guidance - Template Definition Runtime

### 6.1 Goal

v2.5.0 是 runtime safety version。

它要把 v2.1.1 的静态模板 registry 升级为持久化 runtime。

### 6.2 Must include

```text
template_definitions table
seed import from v2.1.1 static registry
runtime template resolver
legacy NoteBlock compatibility resolver
compatibility report
field_schema
default_content
render_hints
source_behavior
relation_behavior
proposal_behavior
summary_for_agent
strict validation for new blocks
soft reading for legacy blocks
static registry fallback
graph-native migration evidence section
```

### 6.3 Recommended fields

`template_definitions` should likely include:

```text
id
user_id
template_key
version
origin
scope_type
scope_id
label
description
system_type
learning_role
field_schema
default_content
render_hints
source_behavior
relation_behavior
proposal_behavior
summary_for_agent
legacy_block_type
status
is_system
metadata
created_at
updated_at
```

Exact fields belong in engineering spec, but R14 strongly recommends this shape.

### 6.4 Compatibility metadata

New blocks should prefer metadata like:

```json
{
  "template_id": "definition.basic",
  "template_key": "definition.basic",
  "template_definition_id": "uuid-if-known",
  "template_version": "1.0.0",
  "template_resolution_status": "runtime_resolved",
  "taxonomy_version": "v2.5.0"
}
```

Old metadata must be preserved.

### 6.5 Compatibility states

The compatibility report should classify blocks as:

```text
runtime_resolved
legacy_inferred
template_missing
template_deprecated
metadata_conflict
unknown_legacy_type
manual_review_required
```

### 6.6 Out of scope

v2.5.0 should not:

- build full user-facing template editor;
- delete old v2.1.1 template-aware NoteBlocks;
- silently migrate old blocks;
- add external rich editor dependency;
- add package marketplace;
- add executable plugin behavior;
- run real AI provider eval by default;
- do broad visual polish.

### 6.7 Graph-native evidence to record

v2.5.0 must record:

- whether `TemplateDefinition` has stable identity;
- which templates real NoteBlocks use;
- which legacy blocks need inference;
- which fields are populated;
- which fields remain JSON/property rather than nodes;
- which template behavior affects source/relation/proposal;
- which template changes require proposals.

## 7. v2.5.1 Guidance - User-facing Template Editor Seed

### 7.1 Goal

Create a guided template editor, not a raw JSON editor and not a full template IDE.

### 7.2 Must include

```text
template library
template detail
copy-from-system-template
field editor lite
render intent editor lite
source/relation/proposal policy presets
summary_for_agent editor lite
reading/editing/debug/proposal preview
draft / active / deprecated / archived lifecycle
compatibility warning
```

### 7.3 Key boundary

Users edit template variants, not low-level system types.

`system_type` remains closed unless a later plan explicitly opens it.

### 7.4 Out of scope

v2.5.1 should not:

- expose arbitrary low-level system type creation;
- allow dangerous edits without warnings;
- silently migrate existing NoteBlocks;
- build full Package Studio;
- build independent external template-making app;
- add marketplace.

### 7.5 Graph-native evidence to record

v2.5.1 must record:

- which template fields users actually edit;
- which edits are direct-safe;
- which edits create proposals;
- which templates are copied, forked, deprecated, or archived;
- whether user-created templates behave like graph-adjacent capability nodes.

## 8. v2.5.2 Guidance - Composition / Section Template Seed

### 8.1 Goal

Create reusable multi-block structures.

`CompositionTemplate` is not a larger NoteBlock. It is a section recipe.

### 8.2 Must include

```text
composition template identity
slot schema
allowed TemplateDefinitions per slot
required / optional / repeatable slots
layout_behavior
source_behavior
relation_blueprint
proposal_behavior
summary_for_agent
preview
proposal-first apply
```

### 8.3 Use cases

Initial examples can include:

```text
formula sheet
theorem-proof-example cluster
source quote + interpretation
evidence comparison section
briefing section
side-note cluster
```

### 8.4 Relation boundary

`relation_blueprint` is design intent.

It can propose relation, but it is not confirmed ObjectRelation.

Confirmed semantic relation remains:

```text
ObjectRelation via review/apply
```

### 8.5 Out of scope

v2.5.2 should not:

- create confirmed ObjectRelations silently;
- implement full AI auto-composition without proposal;
- build full visual template designer;
- solve all canvas layout/presentation polish;
- build package import/export.

### 8.6 Graph-native evidence to record

v2.5.2 must record:

- whether CompositionTemplate needs a table;
- whether CompositionInstance is necessary;
- which slots are filled, skipped, or repeated;
- which relation blueprints become suggested relations;
- which suggested relations become confirmed ObjectRelations;
- how composition maps to CanvasNode / CanvasFrame.

## 9. v2.5.3 Guidance - Domain Block Set + Package Manifest

### 9.1 Goal

Define how templates become domain-specific packages and capability sets.

DomainBlockSet should be a composable domain graph, not a rigid taxonomy tree.

### 9.2 Must include

```text
DomainBlockSet identity
stable_id
domain_key
display_name
aliases
parent_domain_ids
related_domain_ids
facets
status
migration_history
PackageManifest seed
package identity
package compatibility metadata
package as data, not plugin
```

### 9.3 Domain model rule

Do not force infinite paths like:

```text
academic.math.probability.biology.organic_biology.xxx
```

Prefer:

```text
domain = probability
subdomain = biological_probability
application_domain = biology
usage = learning / research / report
level = intro / advanced / expert
source_policy = recommended / required
relation_policy = evidence_heavy / learning_logic
```

### 9.4 AI-facing future hooks

v2.5.3 should preserve enough structure for future:

```text
Template Coverage Check
Domain Fit Check
```

These checks may remain future work, but the model should not block them.

### 9.5 Out of scope

v2.5.3 should not:

- implement full domain marketplace;
- implement executable plugins;
- implement full DomainRefinementProposal UI;
- force all templates into one tree;
- perform domain-wide migration.

### 9.6 Graph-native evidence to record

v2.5.3 must record:

- whether DomainBlockSet behaves as graph, DAG, or tag-like set;
- how domain paths differ from identity;
- how aliases work;
- which templates belong to multiple domains;
- which templates are borrowed or forked;
- package membership implications.

## 10. v2.5.4 Guidance - Template Proposal + Migration Proposal

### 10.1 Goal

Make template changes and old-data migration reviewable, previewable, and recoverable.

### 10.2 Must include

```text
TemplateProposal
TemplateMigrationProposal
direct-safe vs proposal-required edit classification
diff
affected object count
sample before/after
source impact
relation impact
render impact
operation batch
recovery metadata
basic migration modes
```

### 10.3 Migration modes

R14 recommends three modes:

```text
alias / mapping
soft migration
hard cascade migration
```

Alias / mapping:

- safest default;
- preserves old values;
- adds resolver mapping.

Soft migration:

- updates current classification;
- preserves created_with and history.

Hard cascade migration:

- for mechanical low-risk changes only;
- requires proposal, dry run, transaction, rollback/recovery evidence.

### 10.4 Domain refinement

v2.5.4 may define or reserve:

```text
DomainRefinementProposal
```

But it does not need to implement full domain restructuring UI unless implementation proves cheap and safe.

### 10.5 Out of scope

v2.5.4 should not:

- silently rewrite old NoteBlocks;
- turn all domain refinement into hard migrations;
- bulk change source/relation truth without proposals;
- solve full package import/export.

### 10.6 Graph-native evidence to record

v2.5.4 must record:

- which proposals affect which objects;
- which migration mode was chosen;
- affected object links;
- before/after mapping;
- recovery evidence;
- whether proposal history should become graph node, SQL history, or hybrid.

## 11. v2.5.5 Guidance - Package Studio Lite / Export-Import Foundation

### 11.1 Goal

Create the first schema-first `.coincides` package boundary.

This is not yet marketplace and not full engineering package completeness.

### 11.2 Must include

```text
Package Studio Lite
.coincides package manifest
Light / Trusted / Full package levels
import preview
export preview
source inclusion mode
template inclusion
composition inclusion
domain block set inclusion
canvas/source/relation reference strategy
validation warnings
broken relation recovery
operation batch
headless package engine boundary
```

### 11.3 Source inclusion choices

Package should distinguish:

```text
omit source
reference source
snapshot source
bundle original source
```

The right choice depends on trust, file size, privacy, portability, and future source jump-back behavior.

### 11.4 Headless engine rule

Package Studio Lite can be embedded in Coincides UI.

But package validation/import/export logic should be headless.

Future independent package/template-making tools should be able to call the same engine.

### 11.5 Out of scope

v2.5.5 should not:

- build community marketplace;
- run executable plugins;
- guarantee perfect cross-machine source recovery for every media type;
- finish full graph-native import/export;
- require rich editor adapter.

### 11.6 Graph-native evidence to record

v2.5.5 must record:

- what package contains as truth;
- what package contains as snapshot;
- what package references only;
- what degrades on import;
- how broken CanvasEdges and stale ObjectRelations are reported;
- how PackageManifest maps to future graph import/export.

## 12. v2.5.6 Guidance - Rich NoteBlock Editor Adapter Spike If Needed

### 12.1 Goal

Only run this if current editor becomes a real bottleneck.

Do not add it just because the UI is rough.

### 12.2 Candidate priority

```text
1. Tiptap / ProseMirror
2. Lexical
3. BlockNote
4. Milkdown
5. BlockSuite as reference
```

### 12.3 Hard gates

Any adapter must prove:

```text
NoteBlock identity round-trip
Template metadata round-trip
Source marker display without source truth loss
ObjectRelation not reduced to ordinary link
Proposal-first boundary preserved
Adapter removable
Readable fallback from Coincides tables
```

### 12.4 Out of scope

v2.5.6 should not:

- migrate Coincides to editor-native document model;
- store source truth inside editor JSON;
- store relation truth inside editor marks;
- require external cloud service;
- block v2.5.0-v2.5.5.

### 12.5 Graph-native evidence to record

v2.5.6 must record:

- which editor states are rebuildable;
- which editor nodes map to NoteBlocks;
- which marks map to source/relation markers;
- what degrades if adapter is removed;
- whether adapter state remains cache/projection/operation metadata.

## 17. Roadmap Revision Recommendation

The current roadmap v2.5 direction is basically correct.

R14 recommends not changing the version count yet.

But roadmap should treat v2.5 as:

```text
Template / Package Runtime Infrastructure Track
```

not:

```text
Template Editor Track
```

Recommended roadmap wording:

```text
v2.5 establishes the runtime, governance, package, and migration foundations that let templates become a durable extension layer for NoteBlocks, compositions, domains, AI behavior, and future graph-native migration.
```

The most important roadmap clarifications:

1. v2.5.0 is runtime safety, not editor.
2. v2.5.1 is guided editor, not low-level system type editor.
3. v2.5.2 composition is proposal-first multi-object structure.
4. v2.5.3 domain is graph-like, not rigid taxonomy.
5. v2.5.4 migration is governed by proposal/diff/recovery.
6. v2.5.5 package is data/package boundary, not plugin marketplace.
7. v2.5.6 rich editor is optional and adapter-only.
8. Every v2.5 version records graph-native evidence.

## 18. R14 Final Guidance

If v2.5 succeeds, Coincides will have the first stable version of its extension substrate:

```text
TemplateDefinition
  -> what a block can be

CompositionTemplate
  -> how blocks form reusable structures

DomainBlockSet
  -> how templates become domain capabilities

Proposal / MigrationProposal
  -> how template changes become safe

PackageManifest
  -> how work becomes portable

EditorAdapter rule
  -> how interaction can improve without losing truth

Graph-native evidence
  -> how v3.x can rebuild without guessing
```

The v2.5 engineering mantra should be:

```text
Build the extension engine before the extension UI.
Preserve truth before improving interaction.
Record migration evidence before graph-native rewrite.
```

This is the safest path from the current v2.x SQLite MVP toward a future graph-native, source-grounded, AI-operable information workspace.
