# v2.5 Research Outline - Template / Package / View Infrastructure

**Created**: 2026-05-23
**Status**: Active research outline

---

## 1. Purpose

v2.5 is the template / package / view infrastructure phase after the v2.4 Canvas foundation.

This research track exists because v2.5 cannot be treated as a light template UI pass. It must decide how Coincides turns the v2.1.1 static template registry and v2.4 Canvas operations into durable, editable, packageable, AI-readable product infrastructure.

Core question:

```text
How should Coincides define, validate, render, migrate, package, and let AI reason over templates without losing NoteBlock identity, source grounding, relation safety, or future graph-native migration evidence?
```

---

## 2. Research Rules

- Each v2.5 small version must have a detailed plan before implementation.
- Each v2.5 small version must answer what it teaches about future v3.x graph-native migration.
- Do not delete old v2.1.1 / v2.4 template-aware NoteBlocks before v2.5.0 compatibility testing.
- Old NoteBlocks should be used as migration and compatibility samples.
- Template work must not reopen arbitrary low-level system block type creation.
- Template changes that affect existing semantic content should be proposal-first.
- External editor tools may be researched, but Coincides must own template definitions, source behavior, relation behavior, package metadata, and proposal history.
- Research outputs should be written in this folder before the matching version plan is locked.
- Future research outputs should be written in Chinese by default unless Henry explicitly asks for English.

### R1: TemplateDefinition Runtime Model

Goal: define what a persistent template is before building an editor.

Questions:

- What fields are required for `TemplateDefinition`?
- How do we distinguish seed templates, user templates, course-local templates, and package templates?
- Should `template_id` remain human-readable, or should runtime templates use stable UUID plus `template_key`?
- How should versioning work?
- What status states are needed: active, draft, deprecated, archived, system_seed?
- What lives in structured columns versus metadata JSON?

Expected output:

- `r1-template-definition-runtime.md`

---

### R2: Legacy NoteBlock Compatibility And Migration Surface

Goal: use existing v2.1.1/v2.4 template-aware NoteBlocks as compatibility samples instead of deleting them.

Questions:

- How do old `block_type` and metadata map to runtime `TemplateDefinition`?
- What happens when a block references a template that no longer exists?
- Do we need a compatibility report route?
- When should legacy blocks be left alone, inferred, upgraded, archived, or migrated by proposal?
- How can old data prove that v2.5 did not break real user material?

Expected output:

- `r2-legacy-noteblock-compatibility.md`

- code
- list

- relation_target

Questions:

- What is the minimal schema for each field?
- Which validation rules are required?
- How do default values work?
- Which fields are allowed in v2.5.0 versus deferred to later template editor work?
- How do we preserve unknown field metadata for future versions?

Expected output:

- `r3-template-field-schema.md`

## 6. Initial v2.5.0 Recommendation

v2.5.0 should not build the user-facing template editor first.

Recommended v2.5.0 boundary:

```text
TemplateDefinition Runtime
  -> persistent template definitions
  -> seeded registry import
  -> field schema
  -> render hints
  -> source/relation/proposal behavior flags
  -> summary_for_agent
  -> legacy NoteBlock compatibility report
  -> graph-native migration notes
```

v2.5.0 should not:

- delete existing v2.1.1 template-aware NoteBlocks;
- silently migrate old NoteBlocks;
- add a full template editor;
- add external rich editor dependencies;
- create executable plugin or marketplace behavior;
- call real AI unless a later plan explicitly adds provider evaluation.
