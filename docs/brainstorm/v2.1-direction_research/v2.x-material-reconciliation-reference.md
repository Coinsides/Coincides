# v2.x Material Reconciliation 调研

**创建日期**: 2026-05-21
**状态**: 调研草稿
**范围**: 多来源材料合并、去重、冲突、证据集、canonical object、恢复机制

这份文件是 post-v2.1.1 产品/架构调研的一部分。它回答：

> Coincides v2.2 的 Material Reconciliation 应该怎么做，才能把多批、重复、乱序、冲突的材料整理成可信的学习对象，同时为未来个人知识处理中台打地基？

结论先行：

```text
Material Reconciliation 不只是去重。
它是从“来源碎片”到“可信知识对象”的审阅式合并流程。

v2.2 应该做 conservative proposal-first reconciliation。
不要静默删除来源，不要过早做全自动 canonical truth。
```

---

## 1. 为什么这件事重要

当 Coincides 只是学习系统时，Material Reconciliation 解决的是：

- 同一门课多次上传材料；
- slides、教材、作业、笔记内容重复；
- upload order 不等于 learning order；
- 同一 theorem / formula / definition 出现在多个来源；
- 用户需要知道哪些内容被用过、排除、合并、待 review。

但从更长远看，它也是未来个人知识处理中台的地基：

- 多网页、多 PDF、多报告、多 agent 输出之间的重复和冲突；
- 证据来源可信度；
- 同一事件/概念的多个版本；
- 情报线索之间的合并与拆分；
- 把 source evidence 组织成 briefing / report / board。

所以 v2.2 做得越稳，v2.3 Source Board 和 v2.4 Learning Canvas 就越自然。

---

## 2. 调研问题

Material Reconciliation 需要回答：

- 什么算重复？
- 什么算相似但不重复？
- 什么应该合并成 canonical block？
- 什么只应该作为多个 evidence 保留？
- 用户如何审阅合并建议？
- 合并错了如何恢复？
- excluded scope 和 ignored duplicate 有什么区别？
- AI 可以自动做多少，哪些必须 proposal-first？

## 3. 参考对象

### Zotero duplicate detection / merge

重点参考：

- Zotero 有 Duplicate Items 入口。
- 系统认为可能重复的 items 会被聚合显示。
- 用户可以选择 merge。
- merge 会保留 collections 和 tags 等上下文信息。
- 用户仍然可以手动选择同类型 items 并 merge。

启发：

```text
重复检测不等于自动删除。
merge 应该保留来源上下文、标签、集合关系。
```

### Rayyan duplicate detection

重点参考：

- Duplicate detection 是两阶段流程。
- 系统先检测可能重复。
- 用户可以 side-by-side review 每一组 duplicate pair。
- 自动 resolver 是额外能力，不应该成为默认信任假设。

启发：

```text
候选重复应该进入 review queue。
用户要能看到为什么它们被认为相同。
```

### Covidence duplicate / study merge

重点参考：

- Covidence 区分 duplicate references 和 merged studies。
- duplicate 是重复引用。
- merge study 是多个不同 reference 指向同一 study。
- 系统检测和人工标记都存在。
- 可以 merge，也可以 un-merge。

启发：

```text
重复材料 和 多来源支持同一知识对象 不是一回事。
Coincides 必须区分 duplicate source、overlapping source、same concept evidence。
```

### Systematic Review Deduplication

重点参考：

- 系统综述工具通常保守处理 duplicate。
- 高精度去重会漏掉一些重复，但减少误删。
- 大规模自动去重需要 exclusion log / decision audit。
- 研究者最终负责检查去重结果。

启发：

```text
v2.2 应该优先避免误删 evidence。
宁可留下待 review，也不要静默丢材料。
```

### Git / version merge 思路

不是直接参考代码实现，而是参考原则：

- merge 要有 base、ours、theirs 或 equivalent evidence context；
- conflict 需要显式标出；
- merge 后要可追踪；
- 错误 merge 需要 revert / split / unmerge。

启发：

```text
Material Reconciliation 需要 operation batch 和 recovery metadata。
```

## 4. 他们大概怎么做

### 4.1 Zotero：重复项分组，用户确认 merge

Zotero 的思路很适合 v2.2 的最小模型：

```text
Possible duplicate group
  -> show candidate items
  -> user reviews fields/context
  -> merge into one item
  -> preserve collections/tags/attachments
```

Coincides 类比：

```text
Possible duplicate material fragments
  -> show source excerpts/page ranges
  -> user reviews confidence/warnings
  -> accept as same evidence group or keep separate
```

### 4.2 Rayyan：检测和解决分开

Rayyan 的价值是流程：

```text
detect duplicates
  -> duplicate candidates
  -> manual resolution
  -> optional auto resolver
```

Coincides 也应该如此：

```text
detect overlapping fragments
  -> reconciliation proposal
  -> user review/apply
  -> canonical block / evidence set
```

### 4.3 Covidence：duplicate reference 与 merged study 分开

这个区别非常关键。

在 Coincides 中：

```text
duplicate source:
  两个 chunk 基本是同一段来源文本。

same knowledge evidence:
  slide、教材、笔记都讲同一个 theorem，但内容和表达不同。

conflict:
  两个来源对同一概念给出不同定义、公式、条件或结论。
```

这三类不能混用一个 `duplicate` 标签。

### 4.4 系统综述工具：保守、可审计、可回滚

系统综述工具的场景和 Coincides 相似：材料多、来源复杂、误删代价高。

Coincides 应该学它们的审计原则：

- 每一次 exclude / merge / split 要有记录；
- proposal 要保存 decision reason；
- 被排除的材料不能直接消失；
- 用户可以恢复；
- AI 只能提出建议。

## 5. Coincides 应该学什么

### 5.1 Reconciliation 不是 deduplication

推荐区分四类结果：

```text
DUPLICATE:
  基本同一来源或同一片段。

OVERLAP:
  内容重叠，但不是完全重复。

SAME_CONCEPT_EVIDENCE:
  支持同一个 canonical learning object 的多个证据。

CONFLICT:
  可能互相矛盾，需要用户或后续 AI review。
```

### 5.2 CanonicalNoteBlock 不应该抹掉 source evidence

v2.2 可以创建或提出 canonical block，但 source evidence 必须独立保留：

```text
CanonicalNoteBlock
  -> EvidenceSet
    -> SourceAnchor / SourceFragment / MaterialSegment
```

不要把多个来源合成一段文字后就丢掉来源。

### 5.3 Reconciliation Proposal 是主界面，不是后台任务

v2.2 的核心产品界面应该是 proposal review：

```text
MaterialReconciliationProposal
  candidate groups
  source excerpts
  proposed canonical blocks
  confidence
  warnings
  suggested actions
```

用户可以：

- accept merge；
- keep separate；
- mark conflict；
- exclude from current scope；
- defer；
- split group；
- request revised proposal。

### 5.4 Exclude 不是 delete

学习材料里经常会出现：

- 本次考试不考；
- 这页是封面；
- 这章暂时不学；
- 这是重复版本；
- 这是老师旧版 slides；
- OCR 太差，先不用。

这些都不是 delete。

推荐状态：

```text
included
excluded_current_scope
duplicate_hidden
needs_review
failed_parse
conflict_review
deferred
```

### 5.5 Recovery 是 v2.2 的必要能力

只要有 merge，就要有 unmerge。

v2.2 不需要完美版本系统，但需要：

- operation batch；
- merge decision log；
- source membership before/after；
- canonical block before/after；
- undo/unmerge path。

## 6. 对 Roadmap 的影响

### v2.2 Material Reconciliation

建议：**明显修改并细化。**

Roadmap 现在的 v2.2 方向正确，但需要更明确：

新增或强化：

- Reconciliation is proposal-first。
- Duplicate / overlap / same-concept evidence / conflict 必须分开。
- CanonicalNoteBlock 不替代 source evidence。
- EvidenceSet 或 MergedSourceEvidence 是一等对象。
- ExcludedMaterialScope 必须可恢复。
- NoteBlockMergeProposal 要支持 accept / reject / split / unmerge。
- UI 需要 side-by-side review。

不建议加入：

- 全自动去重；
- source authority ranking；
- 跨课程 reconciliation；
- 完整 source viewer；
- 完整 canvas。

### v2.3 Source Snapshot Viewer + Source Board

建议：**保持上一份调研的修改。**

v2.3 应该继承 v2.2 的 reconciliation 结果：

- 显示 canonical block 的 evidence set；
- 显示 duplicate / excluded / conflict 状态；
- source anchor 可以跳转到 evidence；
- Source Board 可以显示哪些材料已被合并或排除。

### v2.4 Learning Canvas

建议：**不直接提前。**

v2.4 Canvas 可以把 reconciliation 结果空间化：

- evidence group；
- conflict cluster；
- concept map；
- source support graph；
- learning path。

但 v2.2 不应该为了 canvas 做复杂可视化。

### 长期个人知识处理中台

建议：**新增长期方向记录。**

Material Reconciliation 未来可以扩展到：

- 网页/报告/论文/聊天记录去重；
- 多 agent 输出合并；
- 情报线索冲突处理；
- 简报/报告证据管理；
- 个人知识数据库维护。

这说明 v2.2 的 reconciliation 不能写死成“课程材料专用去重器”。它应该是 course-local 起步，但概念上可迁移。

## 7. 推荐 v2.2 最小产品形态

### 7.1 Reconciliation Candidate List

显示：

- candidate group；
- group type: duplicate / overlap / same concept / conflict；
- confidence；
- affected sources；
- warnings；
- suggested action。

### 7.2 Side-by-side Evidence Review

显示：

- source document；
- page/chunk/segment；
- excerpt；
- parser confidence；
- existing NoteBlocks；
- proposed canonical block。

### 7.3 Apply Actions

最小动作：

```text
Accept merge
Keep separate
Mark conflict
Exclude from current scope
Defer
```

后续动作：

```text
Split group
Unmerge
Restore excluded scope
```

### 7.4 Reconciliation Output

输出：

```text
CanonicalNoteBlock candidate
EvidenceSet / MergedSourceEvidence
ExcludedMaterialScope
ConflictReviewItem
OperationBatch
```

## 9. 风险

### 风险 1：误删 evidence

如果去重太激进，会破坏 source trust。

应对：默认 proposal-first，exclude 不 delete。

### 风险 2：canonical block 过早变成“真理”

AI 合并出的 canonical note 可能过度解释。

应对：canonical block 旁边必须保留 evidence set 和 warnings。

### 风险 3：用户 review 负担太重

材料多时，逐条审查会累。

应对：先做 confidence 分层；低风险 duplicate 可批量建议，高风险 conflict 必须单独 review。

### 风险 4：reconciliation UI 过早画布化

会抢 v2.3/v2.4 工作。

应对：v2.2 用 candidate list + side-by-side review，不做自由 canvas。

---

## 10. 当前结论

Material Reconciliation 是 v2.2 的核心，不应该被缩成“去重功能”。

它应该是：

```text
多来源材料
  -> candidate groups
  -> reviewed reconciliation proposal
  -> canonical learning objects
  -> preserved evidence sets
  -> recoverable decisions
```

对 roadmap 的最终建议：

- **v2.2 明显细化**：增加 duplicate / overlap / same-concept evidence / conflict 四类区分。
- **v2.2 保持 proposal-first**：AI 只建议，不静默合并。
- **v2.2 加 recovery**：merge / exclude 都要可追踪、可恢复。
- **v2.3 继承 evidence set**：Source Board 展示 reconciliation 结果。
- **长期记录**：这套能力未来可以扩展成个人知识库/情报库的多来源合并层。
