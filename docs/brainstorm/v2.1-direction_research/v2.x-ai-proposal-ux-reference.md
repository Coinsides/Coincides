# v2.x AI Proposal UX 调研

**创建日期**: 2026-05-21
**状态**: 调研草稿
**范围**: AI proposal、review/apply、source grounding、diff、warnings、回滚、授权边界

这份文件是 post-v2.1.1 产品/架构调研的最后一项。它回答：

> Coincides 的 AI 不应该只是“生成内容”。它应该怎样提出结构变化，让用户能审阅、理解、接受、拒绝、回滚，并始终追溯到 source evidence？

结论先行：

```text
Coincides 的 AI UX 核心不是 Chat。
核心是 Proposal -> Review -> Apply -> Evidence -> Recovery。

AI 负责提出结构化建议。
用户负责授权和产品判断。
系统负责保留来源、diff、warnings、operation batch 和恢复路径。
```

---

## 1. 为什么这件事重要

前面所有调研都会回到 AI Proposal UX：

- Material Reconciliation 需要 AI 提出 merge/split/exclude 建议。
- Source Board 需要 AI 提出 source selection / source anchor / generated block 建议。
- Learning Blocks 需要 AI 识别 learning role、relations、projection。
- Template Engine 需要 AI 选择 block template / composition template。
- Canvas 需要 AI 提出 node/edge/layout，而不是静默改知识图。

如果 AI Proposal UX 不清楚，后续所有功能都会变得危险：

- source 不可信；
- 用户不知道 AI 改了什么；
- merge 错了无法恢复；
- 模板被误用；
- canvas 关系图看起来漂亮但事实错误。

## 2. 参考对象

### Cursor / AI coding agent

重点参考：

- AI 生成代码变更后，用户可以查看 diff。
- Review changes 是核心体验。
- 用户可以接受或拒绝变更。
- diff 是理解 AI 改了什么的关键。

启发：

```text
Coincides 的 proposal 也需要 diff/review。
只不过 diff 不只是代码行，而是 source、block、relation、template、canvas node 的结构 diff。
```

### GitHub Copilot coding agent / PR review

重点参考：

- agent 可以完成任务并创建 PR。
- PR 是 review boundary。
- 代码安全、secret scan、review gate 是自动化工作流的一部分。

启发：

```text
Coincides 的 AI apply 应该像 PR 一样可审阅。
大规模结构变化不能直接写入正式知识库。
```

### ChatGPT Canvas

重点参考：

- Canvas 是协作编辑空间。
- 用户可以选中局部内容，让 AI 提供 inline feedback 或 revision。
- 它适合 writing/coding 这种需要迭代编辑的内容。

启发：

```text
Coincides 未来也需要 local proposal：
只改一个 section、一个 block、一个 source range、一个 canvas cluster。
```

### NotebookLM

重点参考：

- 以 source-grounded research assistant 为定位。
- 回答带有 citation，用户可以查看来源片段。
- 支持 PDFs、websites、YouTube、audio、Docs、Slides 等 sources。

启发：

```text
Coincides 的 AI proposal 必须把 source evidence 做成一等信息。
没有 source，就不能假装有证据。
```

### Elicit / systematic review workflow

重点参考：

- 搜索、筛选、提取、报告生成是分步骤 workflow。
- AI extraction 提供 supporting quotes 和 explanation，方便用户检查。
- 系统综述强调 screening、extraction、audit trail。

启发：

```text
AI proposal 应该是 workflow stage，不是一次性魔法结果。
每一步都要能保存决策和审计痕迹。
```

## 3. 他们大概怎么做

### 3.1 Cursor：AI 变更必须进入 diff

Cursor 的强点是让用户看到：

```text
AI proposed change
  -> diff
  -> review
  -> accept/reject
```

这对 Coincides 很关键。我们的 diff 不是代码 diff，而是：

```text
Source diff:
  included / excluded / used / unused

Block diff:
  created / updated / deleted / reordered

Relation diff:
  added / removed / confidence changed

Template diff:
  template selected / fallback used / warnings

Canvas diff:
  nodes / edges / frames / layout
```

### 3.2 GitHub PR：review boundary 是社会契约

GitHub PR 的价值是把自动化放在一个可审阅边界内：

```text
branch changes
  -> PR
  -> checks
  -> review
  -> merge
```

Coincides 可以类比：

```text
draft proposal
  -> proposal review
  -> checks/warnings
  -> Henry/user authorization
  -> apply operation batch
```

这也对应我们现在的 workflow：Codex 工程内循环结束后更新 plan/review/experience review，Henry 做 release/hold 决策。

### 3.3 ChatGPT Canvas：局部编辑很重要

大型 AI apply 很危险。局部 proposal 更可控：

```text
rewrite this block
summarize this source range
turn this section into formula sheet
add examples to this theorem
create a side note from this paragraph
```

所以 AI Proposal UX 应该支持 scope：

```text
scope_type:
  source_range
  material_segment
  note
  block
  composition
  canvas_cluster
```

### 3.4 NotebookLM：source citation 是信任底线

NotebookLM 的定位证明 source-grounded 是强需求。

但 Coincides 要比“答案里有 citation”更进一步：

```text
proposal block
  -> source anchors
  -> excerpt
  -> confidence
  -> warnings
  -> jump back to source
```

并且保存到数据库，不只是显示在聊天回答里。

### 3.5 Elicit：AI workflow 应该分阶段

Elicit 的 systematic review 流程说明：

```text
search
screen
extract
synthesize
report
```

每一步都有不同 review 需求。

Coincides 也应该避免“一键生成完整知识库”：

```text
source ingest
material map proposal
reconciliation proposal
note proposal
review projection proposal
canvas proposal
report proposal
```

## 4. Coincides 应该学什么

### 4.1 Proposal 必须有类型

不同 proposal 的 review UI 不一样。

建议长期类型：

```text
material_map
organized_note
material_reconciliation
source_selection
block_update
block_relation
template_selection
composition
canvas_layout
report_briefing
template_migration
```

v2.1 已经有 material_map 和 organized_note。v2.2/v2.3/v2.4 应该逐步扩展。

### 4.2 Proposal 必须有 scope

AI 应该明确自己要改哪里：

```text
course
source_material
source_range
material_segment
note
note_block
composition_section
canvas_region
projection
```

没有明确 scope 的 proposal 不应该 apply。

### 4.3 Proposal 必须有 evidence

建议最小结构：

```text
evidence:
  source_anchor_ids
  excerpts
  source_material_ids
  confidence
  warnings
```

如果没有 evidence，proposal 应该明确写：

```text
No source evidence available.
This is an ungrounded suggestion.
```

不要让 AI 用像“显然”“根据材料”这种模糊语言掩盖缺证据。

### 4.4 Proposal 必须有 diff

用户需要知道 apply 会发生什么。

建议：

```text
before
after
created
updated
deleted
linked
unlinked
reordered
excluded
merged
split
```

对不同对象使用不同 diff：

- block diff；
- source scope diff；
- evidence set diff；
- template diff；
- relation diff；
- canvas diff。

### 4.5 Proposal 必须可部分接受

尤其是复杂 proposal：

```text
accept all
accept selected
reject selected
defer selected
request revision
split proposal
```

这对 Material Reconciliation、Template Selection、Canvas Layout 很重要。

### 4.6 Apply 必须生成 OperationBatch

每次 apply 都应该记录：

```text
operation_batch
  proposal_id
  source_type
  created objects
  updated objects
  previous state snapshot
  warnings
  applied_by
  applied_at
```

否则无法 rollback、review 或 explain。

### 4.7 AI 文案必须诚实、保守、可验证

推荐语言：

```text
I found these source ranges.
I propose these candidate blocks.
This relationship is inferred and needs review.
This template is a fallback because no better match was found.
This section has no direct source evidence.
```

禁止语言：

```text
I fully understand this course.
This is the correct answer.
You should study this because you are weak at it.
I merged these sources silently.
```

## 5. 对 Roadmap 的影响

### v2.2 Material Reconciliation

建议：**明显强化。**

v2.2 必须定义 `MaterialReconciliationProposal` 的 review/apply UX：

- candidate groups；
- duplicate / overlap / same-concept / conflict；
- side-by-side evidence；
- accept / reject / split / defer；
- operation batch；
- unmerge / restore path。

### v2.3 Source Viewer / Source Board

建议：**强化。**

v2.3 应该支持：

- source selection proposal；
- source range -> candidate blocks；
- evidence preview；
- jump to source；
- used/unused/excluded state diff；
- proposal warnings on weak anchors。

### v2.4 Learning Canvas

建议：**强化。**

Canvas AI 必须 proposal-first：

- propose nodes；
- propose edges；
- propose layout；
- propose grouping/frame；
- propose relation labels；
- user review before apply。

尤其是 relation edges，不能静默生成权威知识图。

### v2.4.x / v2.5 Template Engine

建议：**强化。**

Template AI 必须走：

```text
TemplateProposal
CompositionTemplateProposal
TemplateMigrationProposal
```

并支持：

- template summary；
- best_for / not_good_for；
- visual risk；
- affected blocks；
- migration preview。

### 长期个人知识处理中台

建议：**记录长期原则。**

AI 生态成果展示板也应该遵守同样规则：

```text
agent output
  -> evidence
  -> proposal
  -> review
  -> apply
  -> board/report/projection
```

## 8. 风险

### 风险 1：AI 看起来太确定

用户会过度信任。

应对：source evidence、confidence、warnings、保守语言。

### 风险 2：review UI 太重

每个小 proposal 都要求完整 review 会拖慢体验。

应对：按风险分级：

```text
low risk:
  simple block rewrite / label suggestion

medium risk:
  template selection / note section generation

high risk:
  merge / conflict / source exclusion / canvas relationship graph
```

高风险必须完整 review；低风险可以轻量确认。

### 风险 3：AI 改动难以恢复

应对：operation batch、before snapshot、unmerge/restore path。

### 风险 4：source citations 错位

应对：source anchor、excerpt、confidence、多重定位信息。

### 风险 5：模板选择错误但视觉上很漂亮

应对：template summary、visual risk、fallback warning、用户可切换模板。

---

## 9. 当前结论

AI Proposal UX 是 Coincides 的核心工作流，不是附加功能。

推荐总原则：

```text
AI proposes.
User reviews.
System applies.
Evidence remains.
Recovery exists.
```

对 roadmap 的最终建议：

- v2.2: 强化 MaterialReconciliationProposal。
- v2.3: 强化 source selection / source evidence proposal。
- v2.4: Canvas node/edge/layout 必须 proposal-first。
- v2.5: Template / Composition / Migration proposal 必须独立成型。
- 长期: AI 生态成果展示层也必须遵守 proposal-first。
