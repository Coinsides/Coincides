# v2.x Learning-Specific Blocks 调研

**创建日期**: 2026-05-21
**状态**: 调研草稿
**范围**: definition、theorem、proof、formula、example、exercise、answer、review card、learning projection

这份文件是 post-v2.1.1 产品/架构调研的一部分。它回答：

> Coincides 的学习块不应该只是普通 block editor 里的几个 block type。它们应该如何服务学习、复习、source evidence、proposal 和未来报告/展示输出？

结论先行：

```text
Learning-specific block 的核心不是“多几个类型”。
核心是同一个学习对象可以生成不同 projection。

NoteBlock 是学习内容本体。
Review card、formula sheet、proof list、exercise set、briefing/report 都是 projection。
```

更准确地说，`learning-specific blocks` 不是底层 system block type，而是一套 domain block set：它由 system type 之上的 semantic role、template variant、relation、projection rule 共同组成。

---

## 1. 为什么这件事重要

v2.1.1 已经把 NoteBlock 拆成：

```text
system_type
learning_role
template_id
```

这解决了一个重要问题：`paragraph` 和 `definition` 不再是同一类概念。

但下一步要明确：

- definition 和 theorem 到底应该有什么字段？
- proof 是一个 block，还是 theorem 的子结构？
- formula 应该如何连接变量解释、例子、推导？
- exercise 和 answer 是一个组合，还是两个独立 block？
- review card 是 block 本身，还是 projection？
- 未来 report / briefing 是否也从同一批 block 生成？

---

## 2. 参考对象

### Anki

重点参考：

- Note 和 Card 分离。
- Note Type 定义字段。
- Card Template 决定从 Note 字段生成哪些 card。
- 一个 Note 可以生成多个 Card。
- 改 Note 字段会影响所有由它生成的 Card。

启发：

```text
NoteBlock 不应该等于 ReviewCard。
ReviewCard 应该是 NoteBlock 的 projection。
```

### RemNote

重点参考：

- Concept / Descriptor framework。
- 用户组织 concept 与 descriptor，系统可以自动生成 flashcards。
- Powerups / templates / properties 可以给 Rem 加学习行为。
- 结构化和非结构化笔记可以混合。

启发：

```text
learning role 可以驱动复习、查询、模板、AI proposal。
```

### Mathpix Markdown

重点参考：

- 支持 theorem、proof、equation、table、chemistry diagram 等 STEM 内容。
- theorem/proof 是文档表达层的成熟结构。
- 数学内容需要同时保留文本、LaTeX、编号、引用关系。

启发：

```text
formula / theorem / proof 不只是样式，它们有结构关系。
```

### Jupyter Notebook

重点参考：

- Notebook 是 ordered list of cells。
- cell 可以是 code、markdown、output、rich media。
- 一份 notebook 同时包含解释、公式、代码、结果。
- `.ipynb` 是 JSON schema，不是 Markdown 文件。

启发：

```text
复杂学习材料应该允许不同 system_type 的 block 组合。
导出前是对象图，导出后才变成文件。
```

### Lean / Formal Proof 系统

重点参考：

- definition、theorem、proof、hypothesis、goal、dependency 有清晰关系。
- 证明系统要求结构可验证。
- 普通学习笔记不需要形式化到 Lean，但可以借鉴 proof dependency 的概念。

启发：

```text
proof block 可以包含 steps / assumptions / conclusion / dependency。
```

## 3. 他们大概怎么做

### 3.1 Anki：内容本体和复习卡分离

Anki 最值得学的一点是：

```text
Note
  fields
  note type
  card templates
    -> generated cards
```

这和 Coincides 的未来非常接近：

```text
NoteBlock
  content_json
  learning_role
  template_id
  source evidence
    -> ReviewProjection
    -> FormulaSheet
    -> ExerciseSet
```

不要把 `ReviewCard` 做成新的内容本体。它应该引用 NoteBlock，或者从 NoteBlock snapshot 生成。

### 3.2 RemNote：学习语义驱动自动复习

RemNote 的 concept/descriptor 很接近我们想要的学习语义：

```text
Concept
  Descriptor
  Properties
  Generated Flashcards
```

Coincides 不需要复制它的 UI，但应该学习：

- learning role 会影响系统行为；
- descriptor / property 可以变成复习问题；
- 不同学习结构可以在同一文档里混合；
- AI 可以帮助生成结构，但用户应该能审阅。

### 3.3 Mathpix：STEM 文档结构不是普通段落

Mathpix Markdown 对 theorem/proof/math 的支持说明：

```text
数学/工程笔记需要语义结构。
```

例如：

```text
Theorem
  statement
  assumptions
  proof_refs

Proof
  steps
  conclusion

Formula
  latex
  variables
  conditions
  derived_from
```

如果只用 paragraph + latex，会丢掉大量学习价值。

### 3.4 Jupyter：多 cell 类型混合成一个学习叙事

Jupyter 的价值是证明“不同系统能力可以混合在一个文档里”：

```text
Markdown explanation
Formula
Code
Output
Figure
Commentary
```

这对应 Coincides：

```text
text block
latex block
code block
media block
source quote
exercise
answer
```

但 Coincides 比 Jupyter 多 source evidence 和 proposal history。

## 4. Coincides 应该学什么

### 4.0 先把四层分类彻底分清楚

后续不要再把所有东西都叫 `block type`。更稳的分层是：

```text
System Block Type
  -> block 的底层编辑/渲染能力
  -> text / latex / code / media / table / task / source_quote

Semantic Role
  -> block 在某个知识/任务系统里的语义身份
  -> concept / definition / theorem / formula / clue / evidence / claim

Template Variant
  -> 某个 system type + semantic role 下面的具体模板
  -> paragraph.poetry / formula.math / evidence.webpage / clue.game

Domain Block Set
  -> 一套 roles + templates + relations + projections
  -> Learning Block Set / Literature Block Set / Investigation Block Set
```

所以：

```text
text 是 system block type。
concept 是 semantic role。
paragraph 是 text 下的基础模板/角色。
paragraph.poetry 是 text 下的 literature-specific template variant。
definition.basic 是 text 下的 learning-specific template variant。
formula.math 是 latex 下的 learning-specific template variant。
```

`Learning-specific blocks` 更准确的名字应该是：

```text
Learning Domain Block Set
```

它不是和 `text / latex / code` 平级的东西，而是挂在这些 system block type 之上的一套领域语义层。

同理，未来可以有：

```text
Literature Domain Block Set
  roles:
    poem_line
    stanza
    motif
    metaphor
    character_note

  templates:
    paragraph.poetry
    text.stanza
    concept.literary_motif

  relations:
    motif_appears_in
    metaphor_explains
    character_develops

Investigation Domain Block Set
  roles:
    clue
    evidence
    witness
    event
    contradiction
    claim

  templates:
    clue.basic
    evidence.webpage
    event.timeline
    testimony.quote

  relations:
    supports
    contradicts
    happened_before
    source_of
```

这会直接影响后续 Template Engine / Package Studio：用户未来最好不是随便新增底层 system type，而是在固定 system type 下新增 template variant，并通过 domain block set 组织 roles、relations 和 projections。

### 4.1 学习块应该服务多个 projection

一个 `definition.basic` 不是只在 Note editor 显示。

它未来可以进入：

```text
Organized Note
Review Card
Concept Focus Note
Formula Sheet
Theorem-Proof List
Exercise Set
Briefing / Report
Learning Canvas
```

所以 NoteBlock 的设计不能被当前 Note editor 限死。

### 4.2 ReviewCard 应该是 projection，不是主数据

v1 Card/Deck 已经证明 review 很重要，但 v2 应该反过来：

```text
NoteBlock -> ReviewProjection -> ReviewCard
```

而不是：

```text
Card -> NoteBlock
```

这样一条 definition 修改后，相关 review、formula sheet、report 都能知道它变了。

### 4.3 学习 role 需要最小字段建议

v2.1.1 只做 seed，后续可以逐步扩展字段。

建议最小字段方向：

```text
definition:
  term
  statement/body
  examples?
  non_examples?
  source_refs

theorem:
  name
  statement
  assumptions
  conclusion
  proof_refs

proof:
  theorem_ref?
  strategy
  steps
  dependencies

formula:
  latex
  variables
  conditions
  interpretation
  derived_from?

example:
  prompt/context
  solution_or_walkthrough
  takeaway

exercise:
  prompt
  hints?
  answer_ref?
  difficulty?

answer:
  solution
  explanation
  checks?
```

这些不应该一次性全做 UI，但可以进入 template engine 的未来规划。

### 4.4 Exercise 和 Answer 应该能成对，也能分离

很多学习系统会把 question/answer 强绑定。但实际材料里：

- 题目可能没有答案；
- 答案可能在另一个 PDF；
- 一个 answer 可能解释多个 exercise；
- AI 可能先生成候选 answer，需要用户确认。

推荐：

```text
ExerciseBlock
AnswerBlock
BlockRelation(kind = answers / explains / checks)
```

不要把 answer 永远塞进 exercise 的同一个 JSON 字段。

### 4.5 Proof 更适合支持层级结构

proof 可能是：

- 一段自然语言；
- 多步推导；
- 引用前面的 theorem/definition；
- 包含 formula；
- 包含 diagram。

所以 proof 可以先作为单 block，但未来要允许：

```text
ProofBlock
  -> proof step blocks
  -> formula blocks
  -> source quotes
```

这呼应第一项调研中的 block hierarchy / composition。

## 5. 对 Roadmap 的影响

### v2.2 Material Reconciliation

建议：**小幅修改。**

v2.2 需要在 reconciliation proposal 中识别学习角色：

- definition candidate；
- theorem candidate；
- formula candidate；
- example candidate；
- exercise/answer pair candidate；
- conflict or overlap candidate。

但 v2.2 不需要完整 Learning Block Template Editor。

### v2.3 Source Viewer / Source Board

建议：**小幅修改。**

Source Viewer 应该显示 source range 可能生成的 learning roles：

```text
This source range contains:
  definition candidate
  formula candidate
  exercise candidate
```

Source Board 可以把 source range 和 generated/proposed learning blocks 关联起来。

### v2.4 Learning Canvas

建议：**增强。**

Learning Canvas 应该支持学习关系：

- theorem -> proof；
- formula -> variables；
- exercise -> answer；
- concept -> examples；
- source quote -> block；
- definition -> non-example。

这些关系边可以先轻量，AI 自动生成仍然 proposal-first。

### v2.4.x / v2.5 Template Engine

建议：**明确新增。**

需要未来版本支持：

- template field editor；
- role-specific field suggestions；
- projection rules；
- review card generation rules；
- source behavior rules；
- template preview。

## 6. 推荐的学习块设计方向

### 6.1 四层模型

```text
System Type:
  text / latex / code / source_quote / task / media / table

Learning Role:
  definition / theorem / proof / formula / example / exercise / answer / concept / warning / source

Template Variant:
  definition.basic / formula.math / paragraph.poetry / evidence.webpage

Domain Block Set:
  Learning Block Set / Literature Block Set / Investigation Block Set

Projection Role:
  note section / review card / formula sheet item / proof list item / report evidence / canvas node
```

v2.1.1 已经做了 system type、learning role、template variant 的 seed。后续要补 domain block set 和 projection rule。

### 6.2 BlockRelation

推荐新增长期概念：

```text
BlockRelation
  from_block_id
  to_block_id
  relation_kind
  confidence
  source_type
  proposal_id?
```

relation_kind 可以包括：

```text
proves
uses_definition
uses_formula
example_of
counterexample_of
answers
explains
depends_on
source_supports
```

这不一定进入 v2.2，但 v2.4 Learning Canvas 会需要。

### 6.3 ReviewProjection

复习不应该直接等于 NoteBlock。

```text
ReviewProjection
  source_block_id
  card_template
  front_snapshot
  back_snapshot
  scheduling_state
```

这样可以保留 Anki 的 note/card 分离思想，也能兼容 FSRS。

## 7. 风险

### 风险 1：学习 role 过早复杂化

如果 v2.2 一次性支持太多字段，工程会膨胀。

应对：v2.2 只识别 role candidate，不做完整模板编辑。

### 风险 2：把 ReviewCard 当成主数据

会重走 v1 Card/Deck 的路。

应对：ReviewCard 是 projection，NoteBlock 是 source-grounded learning object。

### 风险 3：所有学科都硬编码模板

数学、工程、化学、生物、法律、医学都可能需要不同模板。

应对：先固定系统类型，后续做用户可编辑 template variant。

### 风险 4：proof / exercise / answer 关系变乱

如果没有 BlockRelation，后续 canvas 和 review 会难做。

应对：先在 brainstorm/roadmap 记录 BlockRelation，等 v2.4 或 template engine 阶段实现。

---

## 8. 当前结论

Learning-specific blocks 是 Coincides 区别于普通 block editor 的核心之一。

最终模型应该是：

```text
Source evidence
  -> NoteBlock with system_type + semantic_role + template_variant
  -> Domain Block Set
  -> BlockRelation
  -> Projection
```

对 roadmap 的建议：

- v2.2: reconciliation 要识别 learning role candidate。
- v2.3: source viewer 要显示 source range 与 learning block 的关系。
- v2.4: Learning Canvas 要支持学习关系边。
- v2.4.x / v2.5: 明确加入 Learning Template Engine / Review Projection Rules。
- Template Engine / Package Studio: 应该把 Domain Block Set 作为核心概念，而不是开放任意低层 system block type。
