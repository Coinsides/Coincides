# v2.x Template Engine / Package Studio 调研

**创建日期**: 2026-05-21
**状态**: 调研草稿
**范围**: 模板引擎、Composition Template、Domain Block Set、模板包、Package Studio、用户友好编辑、导入导出

这份文件是 post-v2.1.1 产品/架构调研的一部分。它回答：

> Coincides 未来的模板引擎应该怎么设计，才能既允许用户自由扩展，又不把系统变成危险、失控、难测试的插件平台？

结论先行：

```text
不要开放任意底层 system block type。
优先开放 template variant 和 domain block set。

Package Studio 的第一阶段不应该是代码插件市场。
它应该是 schema-first 的模板/关系/projection 组合包。
```

补充判断：

```text
模板不只分“单个 block 模板”和“整篇 note 模板”。
中间还需要 Section Template / Composition Template。

Composition Template = 一组 blocks 如何组合、排列、降级、导出、供 agent 选择。
```

---

## 1. 为什么这件事重要

v2.1.1 已经完成模板引擎的 seed：

```text
system_type
learning_role
template_id
```

但这只是地基。后续真正有价值的是：

- 用户能按自己的学科创建模板；
- AI 可以提出模板草案；
- 模板能控制字段、默认内容、显示方式；
- 模板能描述一组 blocks 的组合方式；
- 模板能定义和 source evidence 的关系；
- 模板能生成 review card / formula sheet / report section；
- 成套模板能形成 Domain Block Set；
- Domain Block Set 未来可以被打包、导入、分享。

## 2. 参考对象

### Notion Templates / Synced Blocks

重点参考：

- Notion 有模板库、database templates、页面模板。
- 模板可以组合 docs、projects、wikis、database views 等核心产品类型。
- Synced blocks 允许同一块内容在多个地方同步显示。

启发：

```text
模板的价值在于降低工作流启动成本。
但 synced/shared template 行为必须非常清晰，否则用户会误改所有实例。
```

### Tana Supertags / Templates

重点参考：

- Supertag 可以给普通 node 加上类型和字段。
- Default content 可以在添加 supertag 时生成结构。
- Optional fields 避免模板过重。
- Tana templates 是 pre-built supertags、workflows、systems。

启发：

```text
Domain Block Set 可以像 Tana template 一样，是一套 role + field + workflow。
```

### Anytype Types / Templates

重点参考：

- Everything is object。
- Type 是宽分类。
- Template 是某个 Type 下的创建方式。
- 每个 Type 可以有多个 templates，也可以设置 default template。

启发：

```text
Coincides 应该保持 system type 宽而稳定，template variant 负责细分。
```

### Obsidian Templates / Plugin Ecosystem

重点参考：

- Templates 插件插入预定义内容。
- Obsidian 插件生态强大，但也意味着用户需要自己组装大量工作流。
- 文件/Markdown 模型使导入导出容易，但复杂结构需要插件补足。

启发：

```text
Coincides 的模板系统应该比纯文本模板更结构化，但第一阶段不要开放任意执行代码。
```

### BlockSuite BlockSpec

重点参考：

- BlockSpec 包含 schema、service、view、widgets。
- 这是成熟 editor framework 的底层扩展方式。

启发：

```text
Coincides 暂时不要让用户写 BlockSpec。
但未来 internal template definition 可以朝 schema / behavior / view 分层演进。
```

## 3. 他们大概怎么做

### 3.1 Notion：模板降低工作流启动成本

Notion 的模板强在：

- 一键复制；
- 面向具体场景；
- 可以包含页面结构、database view、说明文字；
- 社区模板容易传播。

弱点是：

- 模板实例和同步内容的边界容易让用户困惑；
- 模板更新是否影响旧实例不总是直觉清晰；
- 模板高度依赖 Notion 自己的页面/database 模型。

Coincides 要学的是场景化模板，不是照搬 Notion 的 synced block 行为。

### 3.2 Tana：supertag 是领域语义层

Tana 的 supertag 很接近我们说的 Semantic Role / Domain Block Set。

例如：

```text
#Book
  fields: author, status, rating
  default content: summary, notes, quotes

#Meeting
  fields: date, attendees, action items
```

Coincides 未来可以有：

```text
Learning Block Set
  roles
  templates
  relations
  projections

Investigation Block Set
  roles
  templates
  relations
  projections
```

### 3.3 Anytype：Type 宽，Template 细

Anytype 支持一个 Type 下多个 templates，这和我们当前方向完全一致：

```text
system_type = broad type
template_id = refined variant
```

Coincides 要进一步加上：

```text
semantic_role
source_behavior
projection_rule
AI proposal rule
```

### 3.4 Obsidian：开放生态很强，但配置成本高

Obsidian 证明了本地文件和插件生态的力量，也证明了另一个问题：

```text
越开放，越需要用户自己装配系统。
```

Coincides 应该优先给普通用户可用的模板包，而不是让用户从插件开始。

### 3.5 BlockSuite：底层扩展应该留给系统内部

BlockSuite 的 BlockSpec 很成熟，但它是工程级扩展：

```text
schema
service
view
widgets
```

这不适合 v2.5 前后直接开放给普通用户。

Coincides 应该内部学习这种分层，但对用户暴露更安全的模板层。

## 4. Coincides 应该学什么

### 4.1 Package Studio 第一阶段应该是无代码/低代码模板包

第一阶段不要做：

- 任意 JavaScript；
- 自定义 renderer code；
- 外部 API 脚本；
- 插件市场；
- 沙盒执行。

第一阶段应该做：

```text
Template fields
Default content
Render hint
Source behavior
Relation rules
Projection rules
AI proposal prompts / constraints
Import/export manifest
```

### 4.1.1 模板需要分层：Block / Composition / Note / Board

未来模板不应该只有一种粒度。

建议分成：

```text
Block Template
  单个 NoteBlock 的字段、默认内容、渲染提示。

Composition Template / Section Template
  一组 blocks 如何组合。
  例如 formula sheet section、side note section、evidence table section。

Note Template
  一整篇 note 的结构。
  由多个 composition templates 和 block templates 组成。

Board / Canvas Template
  一张 Source Board / Learning Canvas 的初始布局、frame、node group。

Domain Block Set
  某个领域的一整套 roles、templates、relations、projections。
```

这里最重要的新概念是：

```text
Composition Template
```

它不是完整 note，也不是单个 block，而是“一段结构化内容如何呈现”。

例子：

```text
Formula Sheet Section
  heading
  formula blocks
  variable explanation table
  example block
  source references

Side Note Section
  callout block
  source quote
  short explanation

Evidence Table Section
  claim
  evidence rows
  source anchors
  confidence/warnings
```

这个概念越早建模越好，因为它会影响：

- agent 如何选择模板；
- organized note proposal 如何组装多个 blocks；
- report / briefing 如何从 NoteBlocks 生成；
- canvas 上一组节点如何作为一个 section；
- PDF/HTML 导出时如何降级显示。

但这不意味着要很早做完整 UI。更稳的路线是：

```text
早期:
  先在数据模型和 agent contract 中保留 composition template 概念。

中期:
  内置若干高质量 composition templates。

后期:
  在 Template Studio / Package Studio 中开放用户编辑。
```

### 4.2 Domain Block Set 是 Package 的核心单位

一个 package 不应该只是单个 template。

更合理的是：

```text
DomainBlockSetPackage
  metadata
  system_type dependencies
  semantic_roles
  template_variants
  composition_templates
  relation_kinds
  projection_rules
  source_behavior_rules
  AI proposal rules
  sample blocks
```

例如：

```text
Learning Math Pack
  roles: definition, theorem, proof, formula, example, exercise, answer
  templates: formula.math, theorem.basic, proof.steps
  relations: proves, uses_formula, answers
  projections: formula sheet, proof list, exercise set
```

### 4.3 模板实例和模板定义必须分开

要避免 Notion synced block 那种困惑。

推荐规则：

```text
TemplateDefinition:
  模板本体。

TemplateInstance / NoteBlock:
  根据模板创建出来的内容。

更新 TemplateDefinition:
  不自动静默改旧 NoteBlocks。
  可以生成 TemplateMigrationProposal。
```

这和我们的 proposal-first 一致。

### 4.4 模板更新也要 proposal-first

如果用户修改模板字段，比如把 `formula.math` 加上 `variables` 字段：

系统不应该静默改所有旧 blocks。

应该：

```text
TemplateMigrationProposal
  affected blocks
  proposed field defaults
  warnings
  preview
  apply / skip / per-block review
```

### 4.5 AI 可以生成模板草案，但不能直接安装高风险模板

AI 可以帮助：

- 从用户描述生成模板；
- 从已有 blocks 总结模板；
- 建议 domain block set；
- 生成 projection rules；
- 生成 composition template 草案；
- 生成 sample blocks。

但必须 review/apply：

```text
TemplateProposal
  -> Review
  -> Apply
```

### 4.6 Source behavior 是模板的一部分

模板不能只定义字段和显示。

它还要定义：

- 是否允许 source references；
- 是否必须有 source evidence；
- source badge 如何显示；
- source quote 是否能作为 evidence；
- export 时 source 如何降级显示。

这会接上 v2.3 Source Viewer。

### 4.7 每个模板最好有 agent-facing summary

如果希望 agent 能判断“这段内容适合用哪个模板”，模板本身需要有简短说明。

建议字段：

```text
agent_summary:
  这个模板适合什么内容。

best_for:
  适合的 source/content 特征。

not_good_for:
  不适合的内容。

visual_strength:
  为什么这样呈现更清楚。

visual_risk:
  例如表格不适合长中文段落，PDF 导出可能拥挤。

degrade_strategy:
  如果导出 PDF / 移动端 / 无法播放 media，应如何降级。
```

这个想法先记录，不要求 v2.2/v2.3 实现。未来 Template Studio 可以帮助用户或 agent 生成这些 summary。

### 4.8 Runtime App 和 Template Studio 要分开

普通用户在主应用里应该看到的是有限、友好的配置：

```text
选择模板
改字段名
调整字段顺序
开关可选字段
保存为我的模板
```

更专业的能力应该放进独立的 Template Studio / Package Studio：

```text
domain block set 编辑
composition template 编辑
projection rule 编辑
source behavior 编辑
template migration preview
package import/export
```

更底层的 system type、renderer、schema migration、插件执行能力，应该继续留给系统内部，至少在 v2.x 不开放给普通用户。

## 5. 对 Roadmap 的影响

### v2.2 Material Reconciliation

建议：**不直接加入 Template Engine。**

v2.2 只需要保留 template metadata，并让 reconciliation 能识别 semantic role candidate。

不要在 v2.2 做模板编辑器。

### v2.3 Source Viewer / Source Board

建议：**小幅修改。**

Source Board 可以开始显示 template/source behavior：

- 哪些 block 必须有 source；
- 哪些 block 可以从 source quote 生成；
- 哪些 template 适合当前 source range。

但不做模板编辑器。

### v2.4 Learning Canvas

建议：**保留接口。**

Canvas 节点可以根据 template hints 决定默认显示方式。

例如：

```text
formula.math -> compact equation card
exercise.general -> prompt + answer slot
source.quote -> excerpt card
```

但不要让 canvas 自己定义模板。

### v2.4.x Composition Template Seed

建议：**新增候选。**

如果 v2.4 Learning Canvas 之前已经发现 organized note / briefing / formula sheet 组装需求很强，可以在 v2.4.x 单独做一个 Composition Template seed：

- 不做完整用户编辑器；
- 内置若干 section/composition templates；
- agent 可以在 organized proposal 中引用它们；
- proposal preview 能展示用了哪些 composition；
- 导出时能按 composition 做降级。

### v2.4.x / v2.5 Template Engine

建议：**明确新增版本候选。**

候选名称：

```text
v2.5 Learning Template Engine + Domain Block Sets
```

或：

```text
v2.4.x Package Studio Seed
```

建议范围：

- template definition table；
- domain block set manifest；
- composition template manifest；
- user-friendly template editor；
- AI template proposal；
- template migration proposal；
- package import/export；
- no-code projection rules。

## 7. 风险

### 风险 1：开放底层 system type 导致系统不可控

如果用户能随便新增 renderer/code block 行为，会导致安全、兼容、导出、测试都复杂化。

应对：固定 system type，开放 template variant。

### 风险 2：模板更新静默破坏旧内容

应对：模板定义和实例分离；旧 block 不静默迁移。

### 风险 3：Package Studio 过早变成插件市场

应对：第一阶段只做 schema-first templates / relations / projections，不做执行代码。

### 风险 4：领域包太抽象，用户看不懂

应对：普通用户看到的是“数学学习模板包”“侦探线索模板包”“课程阅读模板包”，高级概念隐藏在编辑器里。

### 风险 5：模板 summary 过多导致系统杂乱

如果每个模板都有大量 summary、适用场景、降级策略，会增加维护成本。

应对：先把 summary 字段作为可选元数据；内置核心模板优先写好，用户自定义模板可以先没有完整 summary。

---

## 8. 当前结论

Template Engine / Package Studio 是 Coincides 从学习系统扩展到个人知识处理中台的重要桥。

但正确顺序是：

```text
v2.1.1:
  template metadata seed

v2.2:
  role-aware reconciliation

v2.3:
  source-aware blocks and source behavior

v2.4:
  canvas projection hints

v2.4.x:
  composition template seed if organized sections become urgent

v2.5:
  user-facing template engine + domain block sets
```

最关键的原则：

```text
开放 template variant。
开放 composition template。
开放 domain block set。
不轻易开放底层 system block type。
不开放任意代码插件。
模板变更也走 proposal-first。
```
