# v2.4 Canvas Engine And Relation Layer Notes

**Created**: 2026-05-22
**Status**: Brainstorm notes before v2.4.1 planning
**Scope**: Canvas engine choice, external tool adoption, Coincides canvas data sovereignty, relation layers, and future view extraction.

---

## 1. Why This Note Exists

v2.4.0 introduced the first Learning Canvas foundation, but v2.4.1 is the point where Coincides must decide how the real canvas interaction layer should be built.

This is not a small UI choice. Canvas is likely to become one of the core supports for:

- NoteBlock spatial organization;
- Source Board projection;
- evidence and source inspection;
- AI layout proposals;
- relation visualization;
- future report / briefing / presentation surfaces;
- export and project-package workflows.

Because of that, v2.4.1 should not blindly self-build a canvas engine, blindly adopt a third-party canvas SDK, or blindly fork an existing product. The canvas engine choice should be researched and recorded before implementation.

## 3. Core Difference Between Coincides And Existing Canvas Tools

Coincides is not a generic canvas editor.

The central distinction:

```text
Existing canvas/editor tools:
  Canvas document or editor document is often the content source.

Coincides:
  Canvas is a projection over source-grounded knowledge objects.
```

Coincides owns:

- Course;
- NoteBlock;
- SourceMaterial;
- SourceSnapshot;
- SourceAnchor;
- SourceScope;
- EvidenceSet;
- Proposal;
- LearningCanvas;
- CanvasNode;
- CanvasEdge;
- future ObjectRelation / BlockRelation.

Canvas engine may own:

- rendering;
- panning and zooming;
- selection;
- dragging;
- shape interaction;
- connector editing;
- visual tool modes;
- UI-level undo/redo.

Canvas engine must not own:

- source truth;
- NoteBlock truth;
- evidence truth;
- proposal lifecycle;
- accepted semantic relation truth;
- future Coincides package format.

The guiding rule:

```text
External canvas tools can answer "how to draw and interact."
Coincides must answer "what this object is, where it came from, why it is trustworthy, and whether it was accepted."
```

## 4. Candidate Adoption Strategies

### A. Pure Self-built Canvas Engine

Build all canvas behavior ourselves.

Possible benefits:

- maximum fit with Coincides domain objects;
- full control over serialization, source grounding, and relation layers;
- no third-party store or SDK constraints.

Risks:

- high implementation cost;
- immature interaction quality;
- every small feature may become a low-level canvas problem;
- drag, pan, zoom, selection, multi-select, connectors, frames, snapping, history, and export are all nontrivial;
- weaker initial user experience.

Current stance:

Pure self-build should not be the default unless research shows third-party engines cannot be safely adapted.

### B. Third-party Library Integration

Use a mature engine such as tldraw or Excalidraw directly inside Coincides.

Possible benefits:

- mature drag/pan/zoom/select behavior;
- existing shape, arrow, frame, image, text, and history behavior;
- faster path to a usable canvas;
- better user experience earlier.

Risks:

- engine store may try to become the true document;
- Coincides objects could be forced into foreign shape metadata;
- migration/export/package path may become difficult;
- license/runtime restrictions must be recorded;
- future engine replacement becomes harder if adapter boundaries are weak.

Current stance:

Worth serious research, especially tldraw as an interaction/rendering layer.

### C. Coincides Data Model + Canvas Adapter

Coincides keeps all domain objects and projection records. The external engine renders and manipulates a translated view.

Model:

```text
Coincides objects
  -> adapter
  -> canvas engine shapes
  -> interaction events
  -> adapter
  -> Coincides CanvasNode / CanvasEdge updates
```

Possible benefits:

- mature engine helps with hard interaction work;
- Coincides keeps data sovereignty;
- future `.coincides` package remains independent;
- engine can be replaced later if needed;
- adapter can decide which engine state is persistent and which is session-only.

Risks:

- adapter design becomes important and must be tested;
- some engine-native features may not map cleanly;
- harder than direct integration in the short term.

Current stance:

This is the preferred direction to research first.

### D. Fork / Adapt Existing Open-source Product Code

Fork or directly adapt parts of tldraw, Excalidraw, AFFiNE, or BlockSuite.

Possible benefits:

- can start from mature code;
- can deeply customize behavior;
- can credit upstream openly;
- may reduce duplicated effort if the codebase boundaries are clean.

Risks:

- reading, pruning, and maintaining a large foreign codebase may exceed the cost of adapter integration;
- upstream architecture may not match Coincides;
- dependency/build complexity can increase sharply;
- ongoing upstream sync can become its own product track;
- AFFiNE / BlockSuite are full editor frameworks, not small canvas widgets.

Current stance:

Fork/adaptation should be evaluated but not assumed to be cheaper than self-build or adapter integration. It may be useful for isolated reference patterns, but direct fork is probably not the first implementation path.

## 5. Tools That Need Research

### tldraw

Research focus:

- custom shapes;
- shape bindings;
- arrow/connector attachment;
- store model;
- persistence and serialization;
- session/camera state separation;
- undo/redo;
- tool modes;
- performance;
- license/runtime limits;
- adapter feasibility.

Key question:

Can tldraw be used as renderer/interaction layer while Coincides remains the source of truth?

### Excalidraw

Research focus:

- element model;
- arrow binding;
- frames/groups;
- scene JSON;
- export behavior;
- image/file handling;
- collaboration assumptions;
- adapter feasibility.

Key question:

Is Excalidraw better as a lightweight visual/whiteboard reference, export reference, or actual engine candidate?

### AFFiNE / BlockSuite

Research focus:

- document/canvas relationship;
- block projection into edgeless canvas;
- editor runtime layering;
- block tree vs spatial view;
- how connectors and frames behave;
- whether any component is realistically reusable without importing the full product architecture.

Key question:

What should Coincides learn from AFFiNE / BlockSuite without becoming an AFFiNE fork?

### Figma / Miro / XMind

Research focus:

- user-facing canvas interaction expectations;
- project files;
- export;
- frames/pages;
- multi-layer or view filtering;
- relation visualization;
- diagram and mind-map editing patterns.

Key question:

What product-level canvas behaviors should Coincides eventually support?

## 6. Canvas Editor vs NoteBlock Editor

Coincides likely needs two editors:

```text
NoteBlock Editor
  Edits knowledge/content objects.

Canvas Editor
  Edits projection, layout, visual organization, and relation display.
```

Canvas editor is still real even though Canvas is only a projection layer. It edits:

- node position;
- node size;
- frame placement;
- visibility;
- style;
- visual objects;
- connector display;
- relation layer visibility;
- reading/presentation layout.

It should not directly edit source truth or accepted semantic truth without explicit domain operations.

---

## 7. Canvas Objects, Connectors, And Relations

Canvas should separate visual objects from semantic objects.

Recommended conceptual model:

```text
CanvasNode
  Projection of a domain object, such as NoteBlock, SourceScope, EvidenceSet.

CanvasVisual
  Pure visual object, such as shape, sticker, decoration, background, rough annotation.

CanvasConnector / CanvasEdge
  Visual connector between nodes or ports.

ObjectRelation / BlockRelation
  System-readable semantic relation between domain objects.
```

Important rule:

```text
Not every arrow is a relation.
Not every relation needs to be visible as an arrow.
```

Connector states:

```text
dangling
  no valid endpoint

incomplete
  one valid endpoint

visual_linked
  both endpoints connected, but no semantic relation

relation_backed
  connected to a real ObjectRelation / BlockRelation
```

This allows users to draw freely without polluting the knowledge graph, while also allowing meaningful edges to become machine-readable.

---

## 8. Connection Points And Ports

Meaningful connectors need stable attachment points.

Possible model:

```text
CanvasNode
  has connection ports

CanvasEdge
  from_node_id
  from_port
  to_node_id
  to_port
  relation_id nullable
```

If an arrow has both endpoints connected and a relation type is assigned, it can become relation-backed.

If an arrow is only decorative or incomplete, it remains a visual connector.

AI should read relation objects, not screenshots.

## 9. Relation Layer System

The relation system should not be a single all-or-nothing graph overlay.

Coincides should support multiple relation layers.

Examples:

```text
User-visible main relation layer
  Major block-to-block connections.

AI reading-order layer
  Hidden or semi-hidden relations that help AI understand the intended traversal path.

Formula derivation layer
  Step-by-step mathematical derivation relations.

Source evidence layer
  Links between source ranges, evidence sets, and blocks.

Topic-specific layer
  Example: all relations related to trigonometric functions.

Theorem-specific layer
  Example: all relations related to Green's theorem.

AI suggested relation layer
  Machine-generated suggestions pending review.
```

The important correction:

Relation layers are not only "macro" vs "micro." They can represent purpose, audience, topic, reading path, evidence source, AI workflow, or user-defined views.

---

## 10. Hidden Relation Layers For AI

Some relation layers may be mostly invisible during normal reading, but available to AI and advanced users.

Example:

```text
Page 1 concept
  -> Page 3 formula
```

The user may not draw a visible arrow across pages, but AI may infer that the reading or reasoning path should jump from one object to another.

Rules:

- AI-generated hidden relations should start as proposals or suggested relations.
- User may accept, reject, edit, hide, show, or promote them.
- Accepted hidden relations can guide future AI note review, summarization, layout, quiz generation, or report generation.
- Hidden relation layers should be inspectable and editable by advanced users.

This avoids relying on OCR or screenshot interpretation. AI can read structured relation records from the data layer.

## 11. Topic-specific Relation Layers And View Extraction

Relation layers can support extracted views.

Example use case:

```text
Original note:
  50 pages of mathematics notes.

User asks:
  Show me everything related to trigonometric functions.

System:
  uses or creates a trigonometric-functions relation layer;
  extracts related blocks and relations;
  renders them as a focused graph, map, or reading view.
```

Another example:

```text
Show everything related to Green's theorem.
```

The extracted view may be:

- a graph-like canvas;
- a filtered A4 reading view;
- a source-backed study map;
- a generated review path.

This is a major long-term differentiator:

```text
The same note can produce multiple relation-driven views.
```

## 12. Relation Layers vs Graph Database

This begins to resemble a graph database, but Coincides does not need to adopt a graph database now.

Initial implementation can use relational tables:

```text
object_relations
relation_layers
canvas_edges
canvas_edge_bindings
```

Potential fields:

```text
relation_layers:
  id
  course_id
  canvas_id nullable
  name
  layer_kind
  visibility
  owner_type
  status
  metadata

object_relations:
  id
  course_id
  relation_layer_id nullable
  from_target_type
  from_target_id
  to_target_type
  to_target_id
  relation_type
  status
  visibility
  confidence
  source_type
  metadata

canvas_edges:
  id
  canvas_id
  from_node_id
  from_port
  to_node_id
  to_port
  relation_id nullable
  edge_kind
  visual_style
  metadata
```

Graph database can remain a later research topic if relation queries become too complex.

## 13. Project Package / Shareable Engineering File

Coincides should eventually support a project package similar in spirit to XMind project files.

Future concept:

```text
my-note.coincides
```

Likely implemented as a zip-like package with:

```text
manifest.json
canvases.json
notes.json
blocks.json
relations.json
source-snapshots.json
source-anchors.json
evidence.json
assets/
original-files/
metadata/
```

Potential package levels:

```text
Light Package
  canvas + notes, without full source material.

Trusted Package
  canvas + notes + source snapshots + anchors.

Full Package
  canvas + notes + source snapshots + anchors + original files.
```

This should influence v2.4.1 architecture, but likely belongs to v2.5 Package Manifest / Package Studio work.

Key rule:

```text
Coincides package format must not be a raw tldraw store, raw Excalidraw scene, or AFFiNE document.
```

External engine data may be embedded as cache or engine-specific projection metadata, but not as the authoritative project format.

Research output should include:

```text
docs/brainstorm/v2.4-canvas-engine-reference.md
```

v2.4.1 implementation can still stay narrow:

- pan / zoom;
- move canvas nodes;
- save node positions;
- open/jump node targets;
- preserve Coincides as data source;
- avoid full relation implementation.

But v2.4.1 spec should already reserve:

- relation layers;
- connector states;
- visual-only vs relation-backed edges;

## 17. Working Recommendation

Current recommended direction:

```text
Coincides owns data.
Canvas engine owns rendering and interaction.
Adapter translates between them.
Relation layer makes the canvas machine-readable.
Project package remains Coincides-native.
```

Do not choose pure self-build, direct third-party store ownership, or full product fork until the canvas engine reference research is complete.
