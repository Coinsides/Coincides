# v2.x Block Architecture Reference Review

**Created**: 2026-05-21
**Status**: Research draft
**Scope**: Block architecture, schema, object typing, and template systems

This research file is part of the post-v2.1.1 product/reference review. It focuses on what Coincides should learn from mature block and object systems before locking v2.2, v2.3, and v2.4.

It is not a dependency proposal. It does not recommend importing AFFiNE, BlockSuite, Notion, Tana, Anytype, or Logseq as product dependencies.

---

## 1. Research Question

What should Coincides learn from mature block systems so that NoteBlock, Course Material Library, source-grounded proposals, template editing, and future canvas work do not drift into an unstable custom editor architecture?

The key distinction:

```text
Generic block editor:
  block = editable content unit

Coincides:
  block = source-grounded learning unit
  + editor capability
  + learning role
  + template variant
  + evidence links
  + proposal/apply history
```

Coincides should borrow architecture patterns, not product identity.

---

## 2. Sources Reviewed

- BlockSuite docs:
  - `BlockSpec` splits schema, service, and view.
  - block tree docs describe `doc` as an independent block tree with unique block flavours, parent/child operations, undo/redo, selection, services, and commands.
  - block schema docs describe flavour, props, metadata, role, and parent/child constraints.
- Notion API docs:
  - block objects are typed content units.
  - blocks can have children, trash state, type-specific payloads, and rich text/plain text.
  - pages/databases add property systems, relations, and rollups outside ordinary block text.
- Tana docs:
  - nodes are structured by supertags and fields.
  - supertags behave like object type overlays with templates, default content, optional fields, pinned fields, searches, commands, and AI autofill.
  - fields carry semantic relationships such as `is a`, `has a`, and experimental `part of`.
- Anytype docs:
  - everything is an object.
  - objects have Types, and Types can be broad while Templates refine repeated structures.
  - templates are saved at the Type level; each Type can have multiple templates.
- Logseq docs:
  - blocks are small addressable/linkable units.
  - blocks can have arbitrary sub-blocks.
  - pages are special higher-level block/file containers.

## 3. What They Do Well

### 3.1 BlockSuite / AFFiNE

BlockSuite is the strongest architecture reference for editor internals.

Useful patterns:

- separate schema, service, and view for each block type;
- keep the document as a block tree, not just a flat ordered list;
- give every block type a unique namespaced flavour;
- validate parent/child relationships at the schema layer;
- isolate selection, commands, and services from visual rendering;
- support undo/redo through operation history;
- treat editor runtime as framework-adaptable, not tied to one UI layer.

Coincides should learn from this, but not import it yet. Directly adopting BlockSuite now would change the project from a learning-material OS into an editor-platform integration project too early.

### 3.2 Notion

Notion is useful as a product-surface reference.

Useful patterns:

- simple block types for user-facing editing;
- child blocks for nested structure;
- page/database/property split;
- relation and rollup ideas for structured pages;
- broad content block coverage such as paragraph, heading, code, equation, table, media, toggle, to-do, and quote.

Limit for Coincides:

- Notion blocks are not inherently source-grounded learning units.
- The database/property model is powerful but too generic for our immediate v2.2/v2.3 needs.

### 3.3 Tana

Tana is the strongest reference for user-editable semantic overlays.

Useful patterns:

- supertags can turn ordinary nodes into typed objects;
- fields express structured metadata;
- templates can add default content and fields when a tag is applied;
- optional fields prevent templates from becoming too heavy;
- pinned fields help views and filters;
- semantic relationships are powerful, but expensive recursive relationships need care.

Coincides should learn from Tana for future Learning Block Template Engine design.

### 3.4 Anytype

Anytype is useful for broad object/type/template separation.

Useful patterns:

- keep Types broad;
- use Templates to refine repeated structures under a Type;
- allow multiple templates per Type;
- let object types own properties and templates.

This strongly supports the v2.1.1 decision:

```text
system_type = broad capability
learning_role = semantic role
template_id = reusable variant
```

### 3.5 Logseq

Logseq is useful for the smallest possible model:

- blocks are addressable and linkable;
- sub-blocks are natural;
- pages are a special container over blocks.

Coincides should preserve the idea that NoteBlocks are addressable and reusable, but Coincides needs stronger source evidence and proposal history than a plain outliner.

## 4. Lessons For Coincides

### Lesson 1: NoteBlock needs tree capability, even if v2.0/v2.1 are flat

Current NoteBlock placements are ordered. That is enough for foundation and proposal apply, but later proof steps, nested examples, source quotes, exercise-answer pairs, and canvas grouping will need parent/child or composition support.

Recommendation: do not force tree editing immediately, but reserve the data model and API language for block hierarchy.

Roadmap impact: **Modify v2.2 and v2.4 planning.**

### Lesson 2: Block behavior should eventually split into schema, service, and renderer

v2.1.1 created a template registry. The next step is not a full template editor yet, but future template work should avoid mixing:

```text
data shape
rendering
commands
AI proposal rules
validation
source-reference behavior
```

Recommendation: future `NoteBlockTemplateDefinition` should grow toward separate sections:

```text
schema
rendering
editor behavior
proposal behavior
source behavior
review behavior
```

Roadmap impact: **Add to v2.4.x / v2.5 template engine planning.**

### Lesson 3: Coincides should not make every learning variant a system block type

AFFiNE/Notion style block types are editor primitives. Tana/Anytype style templates are better references for learning semantics.

For Coincides:

```text
latex = system capability
formula = learning role
formula.math / formula.physics / formula.mechanical_engineering = template variants
```

Recommendation: keep `system_type` closed for now and make template variants extensible later.

Roadmap impact: **Keep v2.1.1 direction; add explicit guardrail to v2.4.x/v2.5.**

### Lesson 4: Source evidence must remain separate from block presentation

Generic editors store content. Coincides also stores evidence. A `Definition` block can be presented in many notes and projections, but its source references should not be embedded as brittle display-only text.

Recommendation: keep `NoteBlockSource` / source references as a first-class relation. Do not reduce source references into template fields only.

Roadmap impact: **No change; reinforces v2.2/v2.3.**

### Lesson 5: Proposal history is part of the architecture, not a UI detail

Block editors usually optimize direct editing. Coincides has a stronger rule: AI changes must go Proposal -> Review -> Apply.

Recommendation: future template and reconciliation systems should continue to produce proposals, not silent mutations.

Roadmap impact: **No change; reinforce product guardrail.**

### Lesson 6: A future canvas should render the same learning blocks, not create a second block universe

AFFiNE's document/canvas thinking is valuable because it treats different surfaces as different views over structured content.

Recommendation: v2.4 Learning Canvas should reuse NoteBlocks, material segments, source references, and projections. It should not introduce an unrelated canvas-only node model unless there is an adapter.

Roadmap impact: **Modify v2.4 planning.**

### Lesson 7: Template editing should be user-friendly first, advanced second

Tana and Anytype show that end users can handle types/templates if the language is clear. But they also show the danger: too many object/type/relation concepts make the product feel abstract.

Recommendation: Coincides should expose learning words first:

```text
Definition template
Formula template
Example template
Exercise template
Source Quote template
```

Advanced schema editing can come later.

Roadmap impact: **Add to v2.4.x/v2.5 template editor plan.**

## 5. Roadmap Impact

### v2.2 Material Reconciliation

Recommendation: **Modify.**

Add explicit planning language for:

- candidate parent/child relationships between reconciled NoteBlocks;
- recovery actions at the block/subtree level;
- canonical block vs. source evidence separation;
- merge proposals that can create or update block groups, not only single blocks.

Do not add:

- full block tree editor;
- canvas;
- user template builder.

### v2.3 Source Snapshot Viewer + Scope Selection

Recommendation: **Mostly unchanged, with one addition.**

Add:

- source viewer should support source-range anchors that can attach to block groups, not only individual leaf blocks.

Keep unchanged:

- first viewer prioritizes source trust, page jump, and scope selection;
- no full PDF editing;
- bbox/region selection can wait.

### v2.4 Learning Canvas / Larger Learning Material OS

Recommendation: **Modify and sharpen.**

The canvas should be planned as another rendering/projection surface over the same learning substrate:

```text
Course Material
  -> SourceFragments / MaterialSegments
  -> NoteBlocks / block groups
  -> Projections
  -> Document view / Source board / Canvas view
```

Do not create separate canvas-native learning objects unless they map back to NoteBlocks or MaterialSegments.

### v2.4.x / v2.5 Template Engine

Recommendation: **Add explicit version candidate.**

Add a future version candidate for:

- user-facing template editor;
- template fields;
- optional fields;
- default content;
- template preview;
- proposal rules;
- source-reference behavior;
- import/export of template packs.

This should happen after Source Snapshot Viewer and early canvas/source-board lessons, unless template friction blocks v2.2/v2.3 work.

### v3.x+

Recommendation: **No immediate change.**

Cross-course knowledge graphs and community package systems should remain later. The block architecture should avoid blocking them, but v2.x should stay course-local first.

## 6. Architectural Recommendation

Coincides should move toward this internal model:

```text
NoteBlock
  id
  course_id
  system_type
  learning_role
  template_id
  content_json
  metadata
  source references

NoteBlockComposition / Placement
  parent_block_id?
  child_block_id
  projection_id or note_id
  order_index
  relation_kind

TemplateDefinition
  schema
  fields
  renderer_hint
  editor_behavior
  proposal_behavior
  source_behavior
```

v2.1.1 already started the first layer. The next architectural risk is that NoteBlock remains a flat row forever. We do not need to solve this immediately, but v2.2 should not make reconciliation decisions that assume all future blocks are flat.

---

## 7. Decisions Recommended Now

1. **Do not add BlockSuite/AFFiNE dependency in v2.2.**
   Treat it as architecture reference only.

2. **Keep v2.1.1 taxonomy direction.**
   It matches the better pattern from Anytype/Tana: broad type, refined template.

3. **Add block hierarchy/composition awareness to v2.2 planning.**
   Reconciliation needs groups, evidence sets, and recoverable merges.

4. **Keep v2.3 source viewer focused.**
   Source viewer should connect evidence to blocks and block groups, not become a full editor.

5. **Plan canvas as a projection surface over learning blocks.**
   The canvas should not become a separate product universe.

6. **Create a later explicit Template Engine version candidate.**
   Suggested label: `v2.4.x` or `v2.5 Learning Template Engine`.

## 8. Open Questions

- Should block hierarchy be stored directly on `note_blocks`, or through a separate composition/placement table?
- Should a proof with steps be one block with structured fields, a parent proof block with child proof-step blocks, or both?
- Should template variants eventually be course-local, workspace-local, or package-provided?
- Should template definitions be stored in the database before the UI exists, or only after a real editor is planned?
- How much of source-reference behavior belongs in template definition vs. hard product rules?

---

## 9. Bottom Line

AFFiNE / BlockSuite is more mature than Coincides as an editor framework, but Coincides can be stronger as a learning-material system.

The right move is not to compete with or absorb AFFiNE. The right move is to borrow the architectural separation:

```text
schema
tree
service/commands
view
selection
history
```

Then reinterpret it through Coincides' own core:

```text
source evidence
learning role
proposal-first AI
reviewable projections
course-rooted material organization
```

That gives us a cleaner path into v2.2, v2.3, and v2.4 without turning the app into a generic Notion clone.
