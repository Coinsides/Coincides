# v2.x Continuity Register

**Created**: 2026-05-19
**Updated**: 2026-06-05
**Status**: Active for carryover / v2.0-v2.5.6 closeout reference

This file is the major-version continuity register for Coincides v2.x.

It is not a development log, changelog, roadmap, or replacement for version review files. It records only items that must survive from one v2.x minor version into later planning or implementation.

Use this file when a finding, decision, risk, or deferred item affects a future v2.x version but does not belong only to the current version's plan.

Long-lived items that affect multiple major versions, product principles, architecture direction, or repeated deferred work should also be promoted to `docs/continuity/Coincides-Continuity.md`.

---

## Continuity Rules

Each item must use these fields:

- **ID**
- **From**
- **Type**
- **Status**
- **Priority**
- **Suggested Version**
- **Owner**
- **Context**
- **Decision So Far**
- **Next Action**

Allowed statuses:

- `OPEN`
- `PROMOTED`
- `DEFERRED`
- `CLOSED`
- `SUPERSEDED`

Allowed item types:

- `UX_DEBT`
- `ENGINEERING_FOLLOWUP`
- `PRODUCT_DECISION`
- `KNOWN_RISK`
- `FUTURE_VERSION_CANDIDATE`
- `UNRESOLVED_QUESTION`
- `RELEASE_CARRYOVER`

Continuity items should be short and decision-oriented. Ordinary implementation activity belongs in the active version's review file. Final release summaries belong in the version changelog.

### V2X-018: v2.x closeout must prepare Neo4j / graph-native rebuild planning for v3.x

- **ID**: `V2X-018`
- **From**: `2026-05-22 v2.4 graph database direction discussion / docs/continuity/Coincides-Continuity.md#gc-006`
- **Type**: `ARCHITECTURE_DECISION`
- **Status**: `OPEN`
- **Priority**: High
- **Suggested Version**: v2.x closeout / v3.x planning
- **Owner**: Henry for product and database direction / Codex for research, migration notes, and planning
- **Context**: v2.x is using SQLite to build a graph-ready MVP: concrete objects, relation tables, source/evidence/proposal lifecycle, projection boundaries, AI-readable layers, and package constraints. Henry now prefers Neo4j as the main v3.x graph-native candidate because Coincides may become a larger AI information-processing hub rather than a small local note app. Before v3.x begins, Coincides must understand how the v2.x system would be rebuilt around graph-native storage and query patterns.
- **Decision So Far**: Do not migrate mid-v2.x. Continue v2.x with SQLite as source of truth while collecting graph-native migration evidence. Treat Neo4j as the primary v3.x candidate and keep local-first graph options such as Kuzu as alternatives. A detailed graph-native rebuild research gate is required between v2.x and v3.x.
- **Next Action**: During future v2.x version closeout and v2.x final closeout, record migration evidence: future node candidates, edge candidates, provenance model, projection-vs-truth boundary, relation-layer semantics, package/export implications, and SQL-vs-graph ownership. v2.4.1 adds one concrete migration lesson: `CanvasNode` should remain projection/layout state, while selected object scope is a useful bridge from UI interaction to future graph/AI operations. v2.4.2 adds another lesson: a canvas-created block becomes graph-relevant only when it is semantic content (`NoteBlock`); layout remains `CanvasNode`, visual connectors should become `CanvasEdge`, and confirmed semantic links should become `ObjectRelation`. v2.4.3 adds a third lesson: `canvas_layout` proposals and applied frames are view/preset/projection evidence, not graph truth or knowledge edges. v2.4.4 adds a fourth lesson: `CanvasEdge` can preserve visual intent, including incomplete or visual-only connectors, but only `ObjectRelation` is a graph-edge candidate; `RelationLayer` is likely a graph perspective/policy/display layer rather than raw knowledge content. v2.4.5 adds a fifth lesson: `CommandContext`, `SelectedObjectScope`, `ToolMode`, and `InputBinding` are interaction bridges and control state, while future `AICommandContext` should help agents select graph/projection objects without becoming graph truth itself. v2.5.0 adds a sixth lesson: `TemplateDefinition` has stable identity and is a graph-adjacent capability node candidate; `NoteBlock -> TemplateDefinition` is a future `USES_TEMPLATE` edge candidate; field schemas and behavior policies remain nested properties until reuse/query pressure proves they should become nodes. v2.5.1 adds a seventh lesson: user-copied templates strengthen `TemplateDefinition` as a capability node candidate, while template lifecycle state and editor warnings remain SQL policy/history rather than graph truth. v2.5.2 adds an eighth lesson: `CompositionTemplate` is a reusable section contract and graph node candidate; `CompositionInstance` may become a usage node; `CompositionTemplate -> TemplateDefinition` and `CompositionInstance -> NoteBlock` slot usage are edge candidates; `relation_blueprint` is design intent, not graph truth. v2.5.3 adds a ninth lesson: `PackageManifest` and `DomainBlockSet` are future graph node candidates; domain membership rows are edge evidence such as `DOMAIN_INCLUDES_TEMPLATE` and `DOMAIN_INCLUDES_COMPOSITION`; package contents remain validated package metadata until import/export pressure proves they need deeper normalization. v2.5.4 adds a tenth lesson: `TemplateMigrationProposal` is an operation-history node candidate; `template_migration_mappings` may become compatibility edges such as `TEMPLATE_SUCCEEDED_BY`; per-block migration item rows are provenance evidence, not knowledge truth by default. v2.5.5 adds an eleventh lesson: `.coincides` packages define the first concrete graph export/import boundary; `PackageExport` and `PackageImport` are operation/provenance node candidates; package contents are future `CONTAINS` edge evidence; import record items are recovery/provenance evidence rather than knowledge truth; source snapshot text in Trusted packages is recovery evidence only. Before v3.x planning, produce a dedicated Neo4j rebuild research/design package and consider a Neo4j mirror/spike.
