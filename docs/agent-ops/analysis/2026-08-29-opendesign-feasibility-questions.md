# OpenDesign 集成可行性调查·问题卷 v1

**总纲**:默认假设 = 用户 99% 的设计/改组件/制作组件操作**全部在 Coincides 内部完成**(保留直接去 OD 的权利,但不作主路径)。已裁不重开:token 闭集主权在我 / 导入闸五条 / ⛔ 投影管线不采 OD 渲染件 / DS3.0 不接。**小龙虾** = 我们的管家 Agent(Henry 命名,今日起用)。

---

## 卷 A · 需求时刻——用户什么时候会需要 OD?

- **A1 触发场景清单**:逐场景判「OD 独有价值 vs 我们自绘更快」——①样式三档①产主题预设 ②产房造组件皮(外形件)③笔记内"把这块做好看点" ④导出好看的 PDF/汇报页 ⑤纯灵感浏览(看 151 个品牌包找感觉)。每场景一行判词。
- **A2 用户意识问题(核心)**:用户需要知道 OD 存在吗?**显性入口**(界面上有"深度设计"按钮)vs **隐形后厨**(小龙虾默默驱动,用户只见结果)——选哪个,还是分场景混合?选择的后果各是什么?
- **A3 等待预算**:OD 驱动 agent 生成是**分钟级**。哪些场景配产房定案的异步黑盒交互(提交→干别的→徽标就位),哪些场景用户会站在原地等(那就不能用 OD)?
- **A4 用户分层**:普通学习者 vs 捏脸型用户——两类人看到的 OD 暴露面应该差多少?捏脸型要不要给"直通 OD"的门?

## 卷 B · 存在形态——OD 以什么身份住进我们系统?

- **B1 四形态比选(核心)**:
  (i) **纯后厨**:用户永不见 OD,小龙虾经 CLI/文件系统驱动,产物过闸回家;
  (ii) **检修口深链**:我们 UI 里一个"去深造"按钮,拉起 OD 桌面 app 并带上下文(我们的包已就位);
  (iii) **内嵌预览**:OD 产物 HTML 在我们应用内沙箱预览,OD 本体仍隐身;
  (iv) **全脱钩**:用户手动两边跑(现状,仅作底线)。
  ——各形态的体验/成本/风险三栏表,以及"12.10 起步用哪个、13 演进到哪个"。
- **B2 daemon 生命周期归谁**:随我们 app 启动?小龙虾按需拉起?用户自己开?**daemon 挂了小龙虾怎么降级**(答不上话 vs 排队 vs 直说)?
- **B3 适配器与锁版**:OD 一个月 8 个 release 还敢回滚——适配器层放哪(server 侧 odAdapter?)、锁哪版、谁批升级?
- **B4 包目录归属**:我们的 coincides-theme 包写进它的 `user-design-systems/`——谁写入、何时刷新、**用户在 OD 侧改了这个包怎么办**(单向同步还是双向?)。

## 卷 C · 小龙虾 × OD——两个 agent 怎么配合?

- **C1 角色切分线(核心)**:小龙虾 = 懂我们的库、懂用户语境的**管家**;OD 驱动的 agent = 懂视觉的**皮肤工匠**。切分线画在哪?谁给谁写 prompt?工匠能反问吗?
- **C2 调用链全程**:用户→小龙虾→(接口)→OD→产物→导入闸→小龙虾验收→用户。**每一跳的失败处理**(OD 没装/daemon 死/生成失败/闸拒收)各是什么体验?
- **C3 语境出境问题(⚠️ 隐私边界,必须设计)**:注意力框选中的笔记内容、当前主题、组件概念卡——哪些语境需要翻译给 OD?**OD 驱动的是外部 LLM CLI——用户笔记内容进它的 prompt = 内容出境**。出境范围怎么最小化、要不要用户知情?
- **C4 归因与署名**:产物出错用户骂谁?provenance 怎么记(OD project id + 驱动引擎 + 小龙虾裁剪记录)——「转写器身份=lockfile 指纹」的法在这儿怎么适用?
- **C5 预算归属**:OD 驱动 Claude Code/OpenCode 等 CLI——**烧的是谁的 key、哪个账号**?成本对用户可见吗?

## 卷 D · 回家之路——产物怎么回流、怎么预览?

- **D1 回流物三分类,各配一道门**:①主题 token 包(闸已设计,五条)②组件皮(HTML/CSS → 我们的外形件,**转译规则是什么**——这是最难的一题)③整页设计(灵感参考,⛔ 不进系统只进眼睛?)。
- **D2 应用内预览的最小实现**:iframe 沙箱?静态截图?——"在我们应用里预览 OD 产物"要多大工程,安全边界在哪(它产的是任意 HTML)。
- **D3 用户行使"直接去 OD 设计"的权利后**:改动怎么回认?接口指纹判变体的逻辑适用于 OD 侧改动吗?
- **D4 迭代回路的状态归属**:用户不满意→小龙虾带反馈再驱动→v2——回路状态(第几轮/改了什么)记我们侧还是 OD project 侧?

## 卷 E · 工程可行性——本机就地实验(OD 已装)

- **E1 本机盘点**:装的什么版本/什么形态(桌面 app?)/daemon 起没起/`od` CLI 在 PATH 吗(#4852 在案)。
- **E2 三步冒烟实验**:①手造 coincides-theme 三件套放 `user-design-systems/` → OD 里可见吗;②驱动一次真实生成(用本机哪个引擎?)→ 产物目录结构实拍;③把产物 tokens.css 拷回、人工过一遍闸的五条 → 各步通过判据先写死。
- **E3 无头可行性(纯后厨形态的硬前提)**:不开 Electron,纯 daemon + CLI 能否走完 E2 全程?
- **E4 Windows 摩擦实测**:PATH/WSL 歧义是否命中本机。

## 卷 F · 边界与退路

- **F1 已裁清单只验不重开**:投影管线/DS3.0/组件 fixtures/MIT 模板。
- **F2 反向读取边界**:OD daemon 扫描目录的范围——它会不会看到我们不想给的东西?
- **F3 退出成本**:若 OD 弃坑/回滚到不可用,我们损失什么?(预期答案:token 包还是我们的,损失≈一层适配器——验证这个预期。)
