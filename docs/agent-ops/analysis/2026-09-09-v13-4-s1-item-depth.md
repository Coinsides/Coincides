## 一 · Board–Item 身份桥

### 1. 当前连接点与不变量

- `server/src/db/migrations/057_v13_boards.ts:11` 的 Board 有独立 `id/title/soul_id/project_id`，没有 Item FK。`board_members`、`board_visuals` 挂 Board；`board_edges` 连接成员实例（`:46`），并非 `relations` 的 Item 判断边。
- `server/src/services/boards.ts` 的 `createBoard` 在调用者事务中建立 Board/Purpose，`updateBoard` 维护板名；`deleteBoard` 物理移除板和其自有投影/画物，保留 soul、引用内容及历史搬迁批次。身份桥必须对接这三个生命周期入口，不能只改 resolver。
- `server/src/services/items.ts:169` 的 `normalizeItemBody` 要求非空正文，`:317` 的 `insertItem` 内部生成 UUID；创建即 `ensureSnapshot`，更新正文也确保快照。普通 Item 的编辑/退役入口对所有 Item 生效（`updateItem`、`retireItem`），当前没有 Board identity 专用守卫。
- `server/src/services/relations.ts:139`、`:145` 直接取两端 `items.plain_text`；`:241` 的 freshness 比较当前正文和判断快照。因此“把板名塞正文并同步”会让改名改变关系新鲜度，这是产品语义后果。

### 2. A/B 成本对照（候选，不排序放行）

| 面 | A：`boards.item_id` 一对一 FK | B：Board 与 Item 共主键 |
|---|---|---|
| 最小持久化面 | 新迁移为 Board 增可空 `item_id` 引用和唯一约束，完成回填后再决定如何强制所有新/旧板有身份；或等价独立一对一桥表。 | 新建同 `board.id` 的 Item，把 Board 定为 Item 的结构扩展；需要明确共享主键的数据库约束。 |
| 新建路径 | 在 `createBoard` 同事务创建 identity Item，取返回 ID 写桥；现有 Item 自产 UUID 可保留。 | Item 创建需受控的指定 ID 内部入口；不能把任意 ID 透传权限直接暴露给普通 `POST /items`。 |
| 存量路径 | 保留 Board IDs，为每板新建 Item 并写映射；以唯一约束与可重跑标记防重复回填。 | **可保留已有 Board IDs**，给 Item 插入相同 ID，不必当然重编号全部板成员/FK。仍需盘点 Item ID 冲突、受控建行以及共享主键约束落地。若反向采用 Item 新 ID 重编号 Board，则关系与历史批次射程显著扩大，是另一种更贵迁移。 |
| 读取/导航 | Item→Board 需反查唯一桥，Board→Item 需字段；加入列表/摘要前须标明对象种类和打开目标。 | ID 相同减少映射，但仍需查 Board 是否存在和对象种类，不能由“某个 UUID 相等”隐式决定导航。 |
| 生命周期 | Board 删除后 Item 是保留身份、退役，还是禁止删除，由前置裁定决定；单向 FK 不会自动执行“删板→退役 Item”。 | 同样需要显式生命周期处理；共主键不会自动提供退役或恢复。不要把共享 ID 误解为两表删除必须级联。 |
| 相对成本 | **中**：桥/回填较集中，主要成本在标题、正文、生命周期和消费面。 | **中到大**：同样的语义成本，加受控 ID 创建与共享主键约束审计；保留 Board ID 的方案显著小于重编号方案。 |

两候选都可保持 `relations` 和 CG 的现有 Item FK；“读侧虚拟 Item”没有真实 `items` 行，无法满足这些 FK，不能作为 A/B 的等价完工替身。两候选也都不允许把 Board 视觉线自动转为语义 Relation。

### 3. 三道前置题逐一列选项

| 前置题 | 可交 HQ 的选项 | 最小实现与代价 |
|---|---|---|

| 同上 | **A2** Item 拥有身份正文，Board title 为派生或受控别名。 | 板改名 UI/API 与 Item 编辑写入同一个入口；若保留 `boards.title` 缓存，禁止两边独立写。需规定现有 title 的迁移和读时 fallback。 |

| 同上 | **B2** 普通 Item 写门转发到 Board 领域命令。 | 两种入口必须进同一事务；退役可能关联关板/删板/保留结构，恢复与已存在关系、CG 成员的呈现也要有定义。范围更大。 |
| 同上 | **B3** Item 与 Board 生命周期独立。 | 可形成仍可打开的板对应 retired Item，或者板已删而 identity 仍 active；允许这些组合前须明定查询、导航与降级卡面，不能靠 FK 自作决定。 |
| 存量板如何回填？ | **C1** 升级时逐板原子回填，保留 Board IDs。 | 只从板现有 user/title/project 等事实构建身份，创建最初 Snapshot；校验每板一身份、无重复/半桥、反复升级无新增。回填时点写为迁移时点，不能伪装当年已有 Item 判断历史。 |
| 同上 | **C2** 显式批次回填，过渡期允许无 identity 的旧板。 | 需要可观察的缺失态、重试及最终收口门；不能让普通 GET 隐式铸卡。未回填前不得宣称全板已 item 化。 |

额外需随生命周期决定的边界：identity Item 能否作为普通卡被编入笔记；板是否允许投影自己的 identity；identity Item 的 `origin_board_id` 是否指自己。后者与 Board→Item 桥形成环，创建顺序及删板 FK 行为须核对。**本报告不预设 identity Item 必须以自身板为出生地**。

### 4. 最小改动清单与风险

后续实际选案至少涉及：新迁移与 `server/src/db/schema.sql`；`services/boards.ts` 的 create/update/delete；`services/items.ts` 的受控创建、edit/retire 守卫和 Snapshot；Board/Item DTO、validators、client repository、Inspector/候选导航；升级夹具与三入口生命周期定向验证。不得回改历史 `047` 文件；本单不新增迁移或改其既有表结构。

主要风险是双标题、identity 被普通 retire 留下活板、删板级联伤及知识真相、回填伪造旧历史，以及用类型文字 `item_type` 充当不可篡改的身份判据。对象族身份应来自实际桥/约束，不能靠用户可编辑的 type/topic 自证。

## 二 · 块卡绑定：编入 / 安家

### 1. 上游模型如何落实到当前机器

07-12 [`relation-item-graph-concept-design.md`](relation-item-graph-concept-design.md) §1 明定：**内容层会漂 → 身份层 Item 不漂、跨笔记 → 判断层端点只认 Item**；铸卡取得独立身份，锚是使用收据。09-09 [`v13-4-projection-itemization-plan.md`](../handoffs/plans/v13-4-projection-itemization-plan.md) 已拍裁定四进一步要求：**Item 正文恰有一个住址，住址可迁、身份永续**；无家卡进笔记为编入，有家卡进别笔记为旁引，显式迁居才换家，摘出可逆。

所以“编入”不能复制一份后允许 Item 与 block 各改各的；“迁居”不能重铸 Item 或改变 Relation 端点；`origin_note_id` 也不能当家址，因为它是出生收据。这里需要新家址契约，不需要改判三层模型。

现物证据：

| `client/.../hooks/useNoteCanvasDataAdapter.ts:1322` 的 `saveBlock` 带草稿恢复与回读核对，`:1518` 向 `/note-blocks/:id` 一次发双列。`server/src/routes/noteBlocks.ts:81`、`:115` 直接存块。 | 现有块保存没有 Item 路由/快照参与；不能让 client 先存块再独立 PUT Item，任一路失败即出现两个正文。 |

### 2. 绑定字段落点候选

| 候选 | 最小形状 | 成本/风险 |
|---|---|---|
| 独立家址扩展表 | 示意 `item_content_homes(item_id, home_block_id, home_note_id 或 home_placement_id)`；Item 唯一、宿主 block 唯一；无行表示 standalone。 | 可不改 047 既有表形状，独立审计家址。必须验证 note/placement 与 block 一致、同用户、允许作为正文宿主；FK 删除动作需结合“先摘出再删”及账号整组级联决定，不能草率 CASCADE 丢正文。 |
| Item 加 `home_block_id`，另记 canonical home placement | Item 直接拥有指针，standalone 为 null。 | 读取直观，但属于扩 Item schema 的后续新迁移；单列无法解决多 placement，不能用 origin 补位。 |
| block 加 nullable `item_id` | 唯一约束表达一个 Item 仅一块承载，另有 home placement。 | 块侧容易识别绑定；仍需反查 Item、定义无家态与删除流程。若普通复制盲拷此字段，会制造第二本体或唯一键失败。 |

这些是候选字段示意，**不是本单待执行 DDL**。旁引不是第二个家，应使用不同的投影关系指向 Item，不能给每个引用块都写一条 canonical home。普通无绑定 block 原样独立存在；不自动升级旧 block、annotation 或 content_range。

### 3. 最小正文机制：单写与双写成本

**候选 S：真正单一正文宿主。** 无家时从 Item 双列读取；编入后只以 home block 双列为当前正文。抽服务端 `resolveCurrentItemContent` 一类窄入口（名称为示意），Item 读取/摘要/搜索/快照创建/Relation 两端全从它取当前内容；普通 Item 编辑在有家时转入同一宿主编辑服务，或按裁定拒绝并引导到家。Item 原正文列只留为明确标记的旧缓存/迁移残留，绝不能被消费者当第二真相。

这条路径语义直接，成本为**大**：Item 列表搜索目前在 SQL `items.plain_text LIKE` 上执行，不是改一个 hydrate 就完成；Snapshot 与 relation freshness 直读 Item 的代码也须一起改。必须继续在正文写成功的同一事务内确保当前 Item Snapshot，或显式调整“每次 get 已有 current Snapshot”的现行契约，不能先让 `getCurrentSnapshot` 500 再补救。

**候选 M：单一权威写门，事务内物化双列。** 家在 block，服务端宿主保存一次事务更新 block 正文、Item 的只读物化镜像、Item `updated_at` 和 Snapshot；普通 Item 编辑也只能经同一个宿主写门。保留现有 Item 查询/Relation JOIN 大部分实现，成本**中到大**，但物理两份必须被明确为“本体＋可重建镜像”，不是两个可写住址。是否接受该存储解释须由 HQ 裁定。

其省下的是读侧搬迁，增加的是**所有正文写者必须收口**的证明义务：现行块 PUT、client 草稿恢复、结构编辑、直接服务写入、复制/创建与迁居都不能漏；有一个路径直接更新 block 就会让 Item mirror 和 freshness 静默过期。不能用前端依次请求、异步订阅或后台补扫冒充原子保存。

TextFlow 身份也有转换面：`items.ts:155` 的新 Item unit ID 使用 Item 前缀、metadata 标 `owner_kind: item`；笔记选区则以 block/textflow/unit 地址工作。迁入块时须规定 unit ID 保留还是映射，并处理目标 owner；不能只复制 JSON 后宣称所有锚均自然有效。**已有 item_anchors 的收据不随家搬迁而重写**；这里需要处理的是宿主编辑地址与未来选区，Relation 的 Item 端点保持不动。

**过渡投影插入**（段 plan 已给候裁出口）：正文仍住 Item，笔记仅插入引用投影，可为**中**；它没有完成“编入＝笔记成本体”。需要在产品与验收中明确能力范围，保留将来家址形状，不得称为完整安家。采用与否属于单 10/HQ 裁量。

### 4. 编入、旁引、迁居、摘出的最小状态机

| 动作 | 需要在一个一致性边界内做什么 | 保留什么 |
|---|---|---|
| 编入无家卡 | 先 flush 编辑草稿；确认仍无家且 Item active；创建/选定合格 block 与 canonical placement，转入当前正文并建立家址。并发两个编入只能一个成功，另一条重新按有家处理或报冲突。 | Item id、anchors、Snapshot 历史、relations 端点、origin 收据、所有板成员 ID。 |
| 有家卡旁引 | 在目标笔记建引用投影，只解引用 Item→当前家，不复制为可独立编辑本体。 | 现有家址不变。原板和新笔记都直达同一 Item 身份。 |
| 显式迁居 | 锁定/校验旧家与版本，flush，建立新家、原子切换唯一指针；旧位置转旁引、移除或保留壳需另裁，不能产生双本体窗口。 | Item id 与出生地不变；板投影无需卸下重挂。 |
| 摘出 | 将宿主当前正文转回 standalone 存储，确保 current Snapshot，解除 canonical 绑定。旧 block 是移除、保留旁引还是保留独立副本需 HQ 明定；独立副本若允许，须显式声明已无绑定。 | Item/锚/判断历史不退役不重铸。逆动作只恢复家址/正文承载，不把过期正文覆盖回去。 |

“摘出可逆”至少要记录前后家址和必要正文版本，并定义旧宿主已被改/删时的冲突处理；不能只在内存记一个 block_id。宿主整块 split/merge、类型切换、删除、笔记 duplicate 都要明确：保留一张卡的完整正文、显式摘出后执行，或对绑定块暂拒该动作。**最小首发可限定一 Item 对一整块，不扩到任意 unit/range 家址**；这一限制仍需 HQ 接受，不能偷偷禁掉普通块的既有操作。

板、Gallery 和旁引都应经 Item 身份读取**当前宿主**；这里“跟变”指编辑 Item 本体（包括它的家）后变化，仍不意味着 Item 自动跟随锚原料重铸。原料漂移与本体编辑是不同链，07-12 铸造边界及 09-09 引用裁定二仍在。

| 迁移 | 旧 Item 默认 standalone；旧 block 不绑定、不重铸；旧 CG membership 不改正文。仅显式编入创建新关系。既有双列不能凭文本相等猜测旧 block 就是 Item 的家。 |

**最深风险不在字段，而在写门收口与生命周期**：若严格按安家完成，至少跨内容、Item/Relation、布局、恢复四族，不能静态判为“一个外键的便宜活”。这不是否决安家，也不是准许自动退到投影；由 HQ 选择 S/M/过渡以及首发操作边界，再下单。

## 三 · 板上铸卡的 origin 扩展（单 9 前置）

### 1. 现有射程

`047_v2_item_relation_floor.ts:20` 的 origin 只有 course/note，删除时 SET NULL；`items.ts:288` 的 `resolveOrigins` 验证 note，推导它的 course，再验 course。`createItemSchema`、`castItemSchema` 都是 strict（`validators/index.ts:477`、`:524`），所以只传 `origin_board_id` 当前不会被接纳。`UpdateItemInput` 没有 origin，出生收据本来就不随普通编辑修改。

此外，`castItem` 在 `items.ts:648` 起要求至少一条未认领 Anchor、同一个 CG pool，并在同一事务中移交 anchor；`:673` 明确只允许 `content_group`。**“有 board 出生地”与“允许 board 作为原料池”是两件事**。单加 origin 不会令粉笔自动可认领；不能通过虚构 CG、空 anchor 或修改认领规则假装已完成单 9。

### 2. Schema 选项与最小闭环

| 选项 | 最小机制 | 成本/边界 |
|---|---|---|
| 增 `items.origin_board_id` nullable FK | 后续新迁移/base schema 新增对 Board 的引用、按 user/origin_board 的索引；删除 Board 后保留 Item，出生地降为 null。 | **小到中**；延续 note/course origin 惯例，但这是后续正式 schema 工单，本单不改 047 既有表。须考虑 Board–Item 桥的双向引用。 |
| 独立 Item origin 扩展表 | `item_id` 唯一，关联 board 出生地；同用户校验、Board 删除后保留收据/降级策略由契约规定。 | **中**；可避免往 047 Item 表加列，但每个读取要接表，且必须避免主表 note/course 与扩展表互相矛盾。 |
| 通用 `origin_kind/origin_id` | 将 note/course/board 统一成多态地址。 | **中到大**；失去直接多目标 FK，迁移及既有消费面扩大。当前只多一个 board 出生地，未见必须把旧 origin 系统全部重建的证据。 |

无论选哪一形状，服务端应确认出生板属于当前用户；Board 的 `project_id` 是**弱标签**（`courseLifecyclePolicies.ts:25`），不能当强制容器墙。可选语义须交 HQ：①板出生时把当时 project 记为 `origin_course_id`（之后不随换标签更新）；②只存板出生地、course 留空；③同时允许指定 course，但是否必须等于板标签。当前工单没有代裁这三项。

还需明定 note/board 出生地互斥还是可同时存在。若选互斥，source note/选中材料的出处继续走 anchors，不能塞进第二个“出生地”；若允许并存，UI 必须说明哪个是真正出生场景，不能让列表筛选各讲一个故事。迁居不修改这些收据。
