### 🅰-1 `resolve_selection` 与「什么存在」的权威不同源:软删的块仍被解析为存在

## 6. 我自己的测量错误

**⚠️ 本节是常设自查位。本轮三条,全部由我自己发现并已在实况中纠正:**

1. **误判环境死因(归错人)**:两次 dev server 猝死,我第一次归因「Henry 关面板杀了子进程」并已如此上报 Fable。**二次复现后因果闭合:是我自己用 `preview_start {url}` 开标签页,它会收掉同会话 `preview_start {name}` 起的 server。** 已向 Fable 更正,「关面板=杀环境」那条现场纪律**不应记在 Henry 头上**。教训:**把「现象紧邻某人的动作」当成「某人造成」是最便宜也最容易错的归因**,尤其当我自己也在同一时间窗里动了手。
2. **同源假设错误,白等了一段**:Fable 报「Henry 已登入面板」而我在 5173 读到未登录,我当时倾向认为是转述有误或旧快照。**真相是两者都对 —— `:3001` 与 `:5173` 是不同 origin,`localStorage` 各一份。** 教训:**「登录态」不是全局属性,是 (浏览器 profile × origin) 的属性**;跨端口的应用尤其容易在这里制造「他说登了、我说没登」的假冲突。
3. **过早认定需要「捕获 token + 二次打扰」**:我据此设计了整套反转登录脚本,还为此消耗了 Fable 与 Henry 的多轮往返。**实际存在一条更便宜的路(跨源 import,零重登),是被分类器逼出来的。** 教训:**被拦一次不等于此路不通,先找换路再找绕路;而换路常常比原路更干净** —— 本例里 token 从未离开页面,比原方案「我经手 token」更守边界。

**另记一条不属于「错误」但值得留档的判断**:Fable 在 c-3 已实走完成后下达止损令,要求把 J1–J3 记为「未取证」、把 J3 降为「读码推断的 TD」。**我拒绝执行该记录口径并回报了事实**,Fable 随即改裁(§5 🅰-1 即其结果)。⇒ **纪律是「取证不到别写通过」,不是「取到了也写没取到」;两个方向都算失真。**
