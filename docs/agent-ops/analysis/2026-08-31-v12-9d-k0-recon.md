## 二 · ⛔ 被现物推翻或悬空的三条骨架前提

1. **§一.2「倾向 SQLite 内表 + 暴力余弦,⛔ 不为此引向量库重依赖」** ⇒ ⛔ **前提不成立**。重依赖早就引了且在生产用;**暴力余弦是从现状倒退**,不是省事。
2. **§二「⛔ 云嵌入 API 不做默认(key 零出境红线)」** ⇒ ⚠️ **与现役行为直接冲突**:唯一 provider 是 Voyage 云 API(`embedding/index.ts`,env `VOYAGE_API_KEY`,无 key 则返 `null` 优雅降级)。**BGE-M3 / onnx / 本地推理在 `server/src` 零痕迹。**
3. **§一.2「我们的规模是千级碎片」** ⇒ ⛔ **无实测支撑**。dev 库(`server/coincides.db`)实测:`imprint_fragments`=**0** · `source_imprints`=**0** · `source_files`=**0** · `document_chunks`=**0** · `documents`=**0** · `doc_chunk_vec`=**0** · `agent_memory_vec`=**0**。⇒ 要出规模数字必须**先造数据**。

## 三 · 侦察撞出的三件额外风险(⛔ 非骨架所载)

1. ⭐⭐ **该子系统全仓零测试覆盖。** 按文件名查为零,**按内容再查仍为零**(`grep -rln "embedding\|VectorStore\|doc_chunk_vec\|vec0\|sqlite-vec" server/src/__tests__/` 与全仓 `*.test.*` 双双空集)。⇒ **12.9d 要在一块没有回归网的地上动土**;`test:v2` 的 351 个测试一个都没盖到这里。
2. ⚠️ **静默降级**:`db/init.ts` 的扩展加载失败走 `console.warn` 继续,两处 `CREATE VIRTUAL TABLE` 各自 `catch (_e) {}` **吞掉异常**。⇒ vec0 不可用时应用照常起,**表悄悄不存在**,故障要到检索时才显形。
3. ⚠️ **「同维 ≠ 同空间」**:现役表是 `float[1024]`,BGE-M3 恰好也是 1024 维 ⇒ **维度对得上,向量空间对不上**。若新代复用同一张表,两个模型的向量会在同一 KNN 里比距离,**结果无意义且不报错**。⇒ 这是「形状 ≠ 能力」的一个新实例,**须按转写器身份同族处理**(模型标识入行,换版=新身份)。

## 四 · 因此 d-0 的真问题(⛔ 已上报,候裁)

⛔ 不是「选哪个向量库」,而是:

1. **复用旧代 `vectorStore` 机关,还是为 `imprint_fragments` 另起一套 vec0 表?** —— 与 TD-34(两代并存且都活着)纠缠。调度方倾向**另起表、共用扩展**(表分代,机关共用),⛔ 但设计级归总部。
2. **云嵌入红线 vs 现役 Voyage**:红线只管新代,还是要求新代必须本地 BGE-M3?此条不定,选型冒烟**写不出判据**。
3. **d-0 要不要含造数?** 要实测规模就必须造(走 c-0 的 materialization 链灌一批);否则规模按上限假设申报、实测延到 d-1。

## 五 · 侦察过程的一笔自纠

首次查 `doc_chunk_vec` 得 `no such module: vec0`,**差点报成「vec 表是死的」**。⛔ 那是**量具**:裸 `better-sqlite3` 连接不加载扩展。按 `db/init.ts` 的官方路径 `sqliteVec.load(db)` 重测即通,两表均存在、均 0 行。
