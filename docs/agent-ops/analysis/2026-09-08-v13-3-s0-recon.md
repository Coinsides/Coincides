### 1.5 notes 与多态成员引用完整性

### 3.2 推荐路由包装方案（待实现）

采用“认证后绑定受控通道 + 同步事务回调”的包装器，而非 next()/finish 监听器。逻辑顺序：

1. 在路由注册点固定动作描述，如 POST /api/boards、POST /api/boards/:boardId/members、DELETE /api/boards/:boardId/members/:memberId、POST /api/purposes；channel 用该模板路由名，不能取 body.channel，也无需把每个资源 ID 编成新通道。
2. parse/validate 请求后，由包装器读取已认证 userId，绑定 human actor 与固定 channel；业务 service 只收 db、userId 和领域输入，不接受 actor/channel。
3. 同一连接 db.transaction(() => …) 内做业务动作，取得服务返回的已落定对象 ID / 事件内容，再由包装器调用 recordEvent。事件失败必须抛到外层使业务一并回滚。summary 沿执行者原文传递；固定动作若用机械文案，应在动作契约明确来源，书记官不改写。
4. transaction 返回后才 res.json；不得在响应已发、Promise 完成回调或事件监听器里另开事务补记。事务回调不跨 await，不把 Express next() 当同步业务调用。

旧服务的 db.transaction 已在 services/purposes.ts:321,346–520；路由目前 :32–47 直接调用后回复。better-sqlite3 同连接嵌套事务可形成 savepoint，外层失败仍可回滚，但新板服务宜显式提供同步事务内实现，避免不清楚谁拥有提交权。更不能调用旧 replaceNotePurposes 来“顺便立魂”，其成员名单 / note 副作用见 §1.3。现 helper 已接受显式 db，正好可复用。

开板新立魂：一个事务创建 purpose + board，记 purpose_created 和 board_created；挂靠已有魂：只创建 board / 记 board_created，并核魂尚未占另一板。member 真 INSERT / DELETE 分别 mounted / unmounted；移动几何不能伪装重新 mounted，重复 / 未改变的请求也不凭请求数量造事件。事件 objects 至少能回指 board、member 实例与被投影对象；具体字段契约由单 1 固定。
