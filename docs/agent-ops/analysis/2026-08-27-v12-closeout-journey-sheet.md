## 5. 问题总账

### 🅰-1 块删除「有出口无回路」:trashed 的块在人类侧无持久恢复入口

**发现步**:J1(得 0 分)。

**现物**:
- **能力在**:`server` 有 `PUT /note-blocks/:id {status:'active'}`(`routes/noteBlocks.ts`),`client` 有 `restoreBlock`(`useNoteCanvasDataAdapter.ts:1923`,发的正是该 PUT);
- ⛔ **入口不在**:`restoreBlock` 的**唯一消费者**是 `restoreBlockForHistory`(`useNoteCanvasRuntimeController.ts:279`),而它只服务**撤销栈**(`historyService.ts` / `usePlacementHistory.ts`)。
- ⇒ **只有「删完立刻 Ctrl+Z」这一条路**;**跨会话之后,已 trashed 的块在人类界面里没有任何地方能被看到或恢复**。
- **对照**:**笔记**有持久回收站(`CourseDetail.tsx:122` 的 `active|trashed` 过滤 + `handleRestoreNote`)—— **同一产品里,note 有回收站,block 没有**。

**为什么判 🅰 而非 🅱**:本仓红线是「**Agent 能编辑的,人类必须 100% 都能编辑**」。这里更进一步:**人类自己删的东西,人类自己回不去**;而**能力已经写好了,缺的只是入口**。⇒ 不是体验粗糙,是**门缺失**。

⚠️ **归属与范围(⛔ 不夸大)**:**这是既有缺口,不是 V12 引入的** —— `restoreBlock` 与撤销栈的接线早于本版。本轮走查只是**第一次有人从人类视角去找那扇门**。
**承接建议**(⛔ 不自行立项):给块补一个持久回收视图(可复用 note 回收站的形状),或在 note 层暴露「本 note 的已删块」。**触发器 = 有人再次需要恢复一个跨会话的块。**

### 🅱-1(小)`setToken` 不更新 store 字段,单独调用无效

见 §4.0 的实现细节记实。**不构成产品缺陷**(正常登录流程走的是 `login()`,会同时 set store),但**对任何程序化注入登录态的人是个陷阱**。记此备查。
