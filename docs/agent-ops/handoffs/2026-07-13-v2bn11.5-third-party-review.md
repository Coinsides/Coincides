## 已声明的工程事实

1. Relation endpoint 只允许 Item；没有复用 Canvas visual connector、legacy object relation 或 ContentGroup identity。
2. 九个 seed type 的 directionality 由 server registry 决定，create validator 不接受客户端 directionality。
3. directed 保留顺序；undirected 在 service 层按 Item ID 规范序，并由 migration 047 CHECK 背书。
4. create 只接受同用户 active Item，拒绝 missing / retired / cross-user / self-loop。
5. 同一规范端点对 + type 同时只允许一条 active Relation；revoke 保留历史，之后 recreate 产生新 ID。
   active duplicate 的 409 details 返回既有 `relation_id`。
6. Relation 的双端 judgment receipt 使用各自 Item 当前 Snapshot；服务端复用 Item 层 hash/ensure，客户端拒绝跨 Item 或 ID 不一致的收据。
7. reaffirm 是一个事务，四个 fault point 均证明双 Snapshot 与两个时间字段完整回滚。
   reaffirm 只允许 active Relation 且两端 Item 仍为 active；Item 退役不删除历史 Relation，但阻止重申。
8. `origin_purpose_id` 只作出处收据；Purpose 删除后按 FK 置空，任何 list 都不把 origin 当适用性过滤器。
9. Purpose-scope list 使用 11.4 compiled active Item scope，要求 Relation 双端均在圈内；读模型零反写。
10. `relation_assessments` 只保留历史读取兼容，无模型执行器、无人工伪装 assessment、无 invalidation / stale / sync 列。
11. API 提供 types/create/get/list/revoke/reaffirm，不提供 DELETE Relation。

## 请重点做的对抗复验

### A. Directionality 与单活边

- 反向提交 undirected 是否规范为同一对，并由 active unique 拒绝第二条；
- directed 反向是否仍是另一方向；
- 未知 type、客户端 directionality、自环是否同时在 API/service/DB 合理拒绝；
- revoke 后 recreate 是否新 ID、旧历史是否仍可由 `status=all|revoked` 读取。

### B. Judgment receipt 与 reaffirm 原子性

- 两个 composite FK 是否真能拒绝借用另一 Item 的 Snapshot；
- create/reaffirm 是否只复用 Item 层 canonical Snapshot，不复制 hash 口径；
- 四个 fault point 是否都回滚新建 Snapshot、Relation 指针与 `affirmed_at / updated_at`；
- 相同正文 reaffirm 是否不增加 Snapshot 行。

### C. Purpose 与适用范围

- by-Purpose 是否使用 compiled scope 且要求双端都在圈内；
- Relation 的 origin 是其他 Purpose 或 NULL 时，只要双端在圈内是否仍可读；
- 删除 origin Purpose 后 Relation 是否存活、origin 是否 NULL；
- compiled read 前后 Purpose/Relation 真相表是否零派生写入。

### D. 用户隔离与 API

- endpoint、origin Purpose、get/list/revoke/reaffirm/assessment 是否均按 user 限域；
- client normalizer 是否能拒绝 receipt/endpoint 串线；
- 路由是否确实没有 DELETE 或 assessment 写入面；
- query/body `.strict()` 是否阻止多余字段与 item/purpose 双 scope。

### E. 11.4 LOW 收口

- active Item edge 删除后第二轮 full replace 是否仍保持删除；
- stale payload 是否保持单一历史 edge；
- ContentGroup move/delete 写回失败是否不再形成未处理 Promise rejection，并能被 Rail 告知。
