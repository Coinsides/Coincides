## R1 · [MED,必修] `content_group_members.item_id`:ON DELETE SET NULL → **NO ACTION(去子句)**

**为什么**:SET NULL 与互斥 CHECK 组合——kind='item' 行上 SET NULL 一触发必违 CHECK;账号级联删除时 SQLite **不保证**子表处理顺序,若 items 先于 members 被处理,SET NULL 立即触发→CHECK 炸→整个 `DELETE FROM users` 失败。T5 fixture 恰无 item 成员行,现绿是假安全(你 Review §6.1 自己列了该交互但未测)。NO ACTION 严格占优:直接删卡同样被拒(语句末检查,与 relations 端点 FK 同哲学),账号级联则顺序无关安全(语句末时 member 行已随自身 user_id 级联死亡)。

**改动**:
1. `047_v2_item_relation_floor.ts` rebuild 中 `item_id TEXT REFERENCES items(id) ON DELETE SET NULL` → `item_id TEXT REFERENCES items(id)`;
2. `schema.sql` 同行同改;
3. **T5 fixture 补一行 kind='item' 的 content_group_members 行**(连同其 content_group/course 前置),断言 `DELETE FROM users` 仍成功且全家清零——把 SET-NULL-vs-CHECK 交互从"记录的残留风险"变成"被测试锁死的行为";
4. Review §6.1 措辞随改(SET NULL 语句已不成立);
5. 概念设计 v1.1 勘误**已由 Claude 落**(§2 既有表注释,commit `3cac6e8`),无需你动。
