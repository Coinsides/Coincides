### 问一 · MinerU 真实可用度

- **触发**:只有环境变量 `COINCIDES_PDF_PARSER=mineru` 时 PDF 才走它(`sourceFileIntake.ts:179`),默认 native-pdf。解释器取 `COINCIDES_MINERU_PYTHON`,否则取 `_external_tools/mineru/.venv`。
- **现状**:仓内 box 只有 pyproject 和 uv.lock,**没有 venv,生产路径现在跑不起来**(报 not provisioned)。本次实测用的是 `D:\Coinsides\v12.9-selection` 的遗留 venv(MinerU 3.4.5,1.4G)+ 模型缓存(1.2G)。
- **实测**(与生产 runner 同参:pipeline + ocr + 公式/表格开;4 核 8 逻辑核 Xeon、15.5G、无 GPU、torch 4 线程;单轮,同机有其他负载,作量级看):

| 用例 | 耗时 | 每页 | 峰值内存 |
|---|---|---:|---:|
| 公式密集合成页 1 页,冷 | 73.7s(另一轮 70.0s) | 约 70s | 3.0G |
| 同上,模型已载入 | 56.2s | 56s | 2.85G |
| 公式密集合成 4 页 | 243s | 61s | 3.23G |
| 公开样卷纯文字 5 页 | 34s | 6.8s | 2.05G |

  公式识别约 1.3 秒/个,是主要耗时;合成页每页约 40 个公式片段,属偏重情形。
- **输出**:公式是 LaTeX(行间 `$$…$$` + 行内 `$…$`),表格结构化,图/公式裁图在 `images/`,带 bbox(`mineru-middle-page`)。**没有整页影像**。
- **岛上(4C8G 无 GPU)推算,未实测**:
  - 内存峰值约 3.2G,8G 够,但要和服务共存;
  - 磁盘约 2.6G(venv + 模型),Linux 轮子体积可能不同;
  - 耗时按本机到 2 倍估(vCPU 超售程度不明):文字页约 7–15s,公式密集页约 60–120s+;一本 100 页的讲义约 12 分钟到 2 小时,期间 CPU 基本占满。
- **现行硬限**:`MINERU_TIMEOUT_MS=120s`、`MINERU_MAX_PDF_PAGES=9`(由旧台式机单页 13.18s 算出),公式密集页一到两页就会超时。要用就得改成后台任务,这是施工量。默认 `--lang en`,中文要设 `COINCIDES_MINERU_LANGUAGE`。
- **判定**:岛上「能跑」,但不适合作默认。

### 问二 · docx 展望(一段话,按令未深查)

docx→PDF 的常规路线是 LibreOffice headless,转出的 PDF 页作权威页,之后完全复用第一期的页影像通路,所以第一期做对了,docx 只多一个转换前置步。LibreOffice 的体积、内存和中文字体代价**我没有查实**(一次搜索无可用数字),第二期开工时在岛的同形环境实测;公式与 Word 版式的还原度也要到那时验。

### 问三 · 快照层与页影像通路

- **快照层**:`source_snapshots` / `source_snapshot_pages` 是旧 documents 链的产物,页表只有 `text_content`,由 `document_chunks` 拼出(`sourceSnapshots.ts:129`),**没有任何影像字段**。现行 Source 路(`sourceMaterialization` / `sourceProjectionMaterializer` / `sourceFileIntake`)对它**零引用**。旧 documents 链已按 TD-43 停喂。所以「假快照」不是可扩展的基础,页影像层应当新立,挂在 Source 记录上。
- **栅格化通路(实测,零新依赖)**:现有 `pdf-parse` 2.4.5 自带 pdfjs + `@napi-rs/canvas`,`getScreenshot` 直接可用。
  - 宽 794px:约 230ms/页,145–189KB/页(PNG);
  - 宽 1240px:260–320ms/页,248–314KB/页(PNG),单页最高见到 729KB;
  - Node 进程 RSS 约 150MB。
- **存储量级**(pypdfium2 实测 144dpi):PNG 305–335KB/页,WebP(q80)119–166KB/页,JPEG 213–286KB/页。1000 页约 170–480MB,50G 盘够用,但要计入备份体积。WebP 的数字来自 Pillow 编码,canvas 侧编码未测。
- **另一选项**:不存影像,浏览器端用 pdf.js 按需渲染原 PDF(还能带文本层,原页上可选字)。零存储,代价是 client 新增依赖(现在 client 没有 pdfjs),且打印、Agent 读图还要另走通路。这个取舍留给设计稿。

### 问四 · 阅读视图改造面

**现状(在 v2 副本上用真实服务导入、真实页面查看)**:

1. Source 阅读视图 = 只读的投影笔记,走普通画布。**按块流渲染,不按页**:4 页 PDF 的 p.1、p.2、p.3 块连续堆叠,没有页界,只有「Source p.N」小标(截图 `v2-math5-pages-stacked-no-boundaries.jpg`)。
2. 物化时每个原页确有一个 frame(4 页 4 个、5 页 5 个),但**frame 高度随文字撑大**:同一份 5 页 PDF 里出现 1556、1993(A4 为 1278),宽度固定 904,不取原件尺寸。原页尺寸目前没有被记录。
3. **`image` 画布对象在页面上根本不绘制**:我按图片 Source 的行形状给每页插了整页影像对象,页面没有发出任何资产请求,也没有 `<img>`(截图 `v2-sample5-page-image-object-not-drawn.jpg`)。编辑器里实际绘图的只有媒体块(`MediaBlockProjection`)。**所以不能「落几个图片对象」就完事。**
4. 既有块锚、选区问 Agent、标注都绑在转写块上;页级锚 `page_index` 已有,原页入口可以直接用。MinerU 路才有 bbox,native-pdf 没有。

**建议形状**:Source 投影笔记加一个**独立的「原页」视图**(页为单位、影像为底),与现有文本视图并列切换,不改分页 flow plan,也不把影像塞进块流(合分离真相:显示归页层,引用归转写块)。

- 改动面:
  - 服务端:物化时栅格化 + 新页影像存储 + 取图路由 + 记录原页尺寸,删除 Source 时一并清理;
  - 客户端:新页视图组件 + 切换入口 + 「Source p.N」跳到对应原页。尽量不进 2323 行的 `NoteWritingSurfaceLayer`。
- 交互取舍:影像上不能选字,除非上 pdf.js 文本层;第一期可以让选字、标注、问 Agent 留在文本视图,原页视图只负责看和跳转。**这条会直接影响体验,请过 Henry。**
- 未做原型:媒体块路线、页视图都没有原型,以上改动面是读码判断。
