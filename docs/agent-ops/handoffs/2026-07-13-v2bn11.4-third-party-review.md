## 已声明的工程事实

1. `purpose_members` 不迁移；沿用 generic `member_kind / member_id`，server/client 同版支持 `content_group | item`。
2. 新 direct Item edge 只允许当前用户的 active Item。
3. 全量替换保留 deleted / missing ContentGroup 与 retired / missing Item 的历史边。
4. stale pre-retirement payload 不会把隐藏 Item edge 当新边校验，也不会借保存改写其历史 role / fitness / order。
5. compiled scope 在读时合并 direct 与 `Purpose -> ContentGroup -> Item` 路径；同 Item 去重，但路径不丢。
6. retired Item 不进入 active scope；derived Item 永不持久化到 `purpose_members`。
7. Item Inspector 只提供最小 direct membership UI，不扩张 Purpose 工作台、Relation UI 或 graph layout。

## 请重点做的对抗复验

### A. 全量替换与隐藏边

- Item 退役后，客户端只提交可见成员时，隐藏 direct Item edge 是否保留；
- 客户端在退役前已加载该 Item，退役后再提交 stale payload，是否既不报“新建 retired edge”，也不改写旧收据；
- missing Item 与 deleted / missing ContentGroup 是否遵循同一恢复原则；
- visible active edge 的显式删除是否真的删除，而不是被 hidden recovery 复活。

### B. compiled scope 真相边界

- 同一 Item 同时 direct、经一个或多个 ContentGroup 进入时，是否只返回一个 Item identity，并完整保留所有来源路径；
- ContentGroup membership 变化是否在下一次读取动态生效；
- retired Item 是否从 active scope 排除；
- compiled read / search 前后 `purpose_members` 是否零变化。

### C. 身份与隔离

- 跨用户 Item、Purpose、ContentGroup 是否无法串入查询或写入；
- search 的 `q / limit` 是否严格解析，并且只在目标 Purpose scope 内返回；
- client normalizer、保存与 reload 是否可能把 `item` 洗回 `content_group`。

### D. Client 保存语义

- role / fitness draft 是否只有显式保存才写入；
- generation-safe optimistic rollback 在连续保存、前一次失败后一次成功时是否会错误回滚新状态；
- retired Item 是否确实关闭新增与编辑动作；
- Item Inspector 的 `via current group` 文案是否只陈述当前已知路径，没有冒充完整 compiled scope。
