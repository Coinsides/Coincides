## 核心判断（先读）

**FK 拓扑（migration 041）造成的泄漏**：`DELETE FROM courses`（foreign_keys=ON, init.ts:30）级联时——
- `image_object_extensions.course_id/note_id` 是 **ON DELETE CASCADE**（041:35-36）→ 扩展行随课程消失；
- `canvas_assets.course_id/origin_note_id` 只 **ON DELETE SET NULL**（041:11-12）→ canvas_assets 行**存活**、course_id 被置 NULL；
- `cleanupOnDelete`（唯一做 blob unlink + 删 canvas_assets 的地方，canvasObjects.ts:1950）**只在 `deleteCanvasObject` 事务内跑、FK 级联根本不触发它**。

→ 删一个课程，其下所有图片的 **canvas_assets 行 + 磁盘 blob 变永久孤儿**：扩展行没了 → refcount 再也 COUNT 不到它们 → 永远无路可 GC。

**修法**：在 course 删路径里、**在 cascade 发生之前**，enumerate 该 course 的 image extension 行，逐个走**和 per-object `cleanupOnDelete` 完全一样的两步**（先删 self-extension 行、再 `releaseAssetReference(exclude self)`），复用既有已测原语。

**为什么"先删 extension 再 release"是必需**（同 per-object 路径）：`asset_id ON DELETE RESTRICT`（041:38）—— 若 self-extension 行还指着 asset 就 `DELETE FROM canvas_assets`，RESTRICT 会**抛错**。必须先删 self-ext，再 release。

**为什么逐个循环而非一把梭**：这样天然复用 `releaseAssetReference` 的 exclude-self、user-scoped COUNT，正确处理三种共享：
- **课内共享**（同 course 两图共 asset）：删前一个时后一个 ext 还在 → COUNT≥1 → 留；删到最后一个 → 归零 → 释放。✅
- **跨 course 共享**（未来 AI/duplicate 把同 asset 放到别 course 的 note）：删 course A 时 course B 的 ext 还在（不同 course_id）→ COUNT≥1 → **留**，绝不删仍被 B 引用的 blob。✅（正是上一单坚持 user-scoped 而非 note-scoped 的原因，这里兑现价值）
- **课内独占**：归零 → 释放 + unlink。✅

**相对不焊**：teardown 仍是**读时 COUNT-at-delete**、复用同一原语、无 counter 列。canvas_assets.course_id 被 SET NULL 是良性 provenance 丢失（幸存的跨 course asset 仍被别处 ext 引用、活得好好的）。

## 簇 A · course 硬删的 refcount 资产 teardown（收 CR-8.11.16-01）· 一个 commit

**修**：
1. `server/src/services/canvasAssets.ts`：在 `releaseAssetReference` 旁 export
   ```
   export function releaseCourseCanvasAssets(db, userId, courseId): { released: number } {
     const rows = db.prepare(
       `SELECT object_id, asset_id FROM image_object_extensions WHERE user_id = ? AND course_id = ?`
     ).all(userId, courseId);
     let released = 0;
     for (const row of rows) {
       // 先删 self-ext（否则 asset_id ON DELETE RESTRICT 会挡住 canvas_assets 删除）
       db.prepare(`DELETE FROM image_object_extensions WHERE object_id = ? AND user_id = ?`)
         .run(row.object_id, userId);
       // 再走同一个 refcount 原语（exclude self、user-scoped、归零才删行+best-effort unlink）
       if (releaseAssetReference(db, userId, row.asset_id, row.object_id).released) released += 1;
     }
     return { released };
   }
   ```
   加**不变量注释**：本函数**必须在 `DELETE FROM courses` 之前、同一事务内**调用；顺序"先删 ext 再 release"不可颠倒（RESTRICT）。
2. `server/src/routes/courses.ts`（155-167 DELETE 路由）：保留既有 ownership 预检（158-161），把删除**包进一个事务**、teardown 在 cascade 前：
   ```
   getDb().transaction(() => {
     releaseCourseCanvasAssets(db, req.userId!, req.params.id);   // NEW — cascade 之前
     db.prepare('DELETE FROM courses WHERE id = ?').run(req.params.id);
   })();
   ```
   （import `releaseCourseCanvasAssets`。DELETE 语句维持既有形态、user 归属由预检守。）

**验收（RED-first · blob 必真文件正控）**：
- **课内独占正控**：建 course+note+image 对象（`seedCanvasImageAsset` writeBlob:true 真写盘）→ 断言 canvas_assets 行 + blob `existsSync===true` → 删 course（调 service 或路由处理器）→ 断言 canvas_assets 行**没了** + extension 行没了 + blob `existsSync===false`。**RED**：不加 teardown → asset 行 + blob 残留 → fail。
- **跨 course 共享负控**（直接 seed 两条 ext：同 user、同 asset_id、不同 course_id/object_id，锁不变量，即便今天无 UI 路径造它）：删 course A → 断言 asset 行 + blob **仍在**（course B 持有）→ 删 course B → 断言释放 + unlink。
- **课内共享**（同 course 两图共 asset）：删 course → 断言两 ext 都清、asset 只释放一次、blob unlink（归零在最后一个）。
