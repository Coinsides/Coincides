# handoffs —— Henry × Claude × Codex 三方交接区

## 为什么存在

让三方协作**不靠人肉转述**。Henry 不再把一个 agent 的话复制粘贴给另一个 —— 交换单位是**仓库里的一份交接文件（spec / 结果 / 问题）**，各 agent 直接读写。

这套设计直接来自 Coincides 自己的产品原则：

- **共享基底**：repo 之于我们，如同 ContentGroup 之于人 + AI —— 同一份结构化产物，谁都不替对方翻译。
- **Proposal → Review → Apply**：Claude 写 spec（proposal）→ Henry 审/改（review）→ 翻牌 `ready` 后 Codex 执行（apply）。
- **不替用户决定**：Henry 仍是导演 —— 他审每一份交接，但只做「点头 + 触发」，不做转述。

## 文件格式

一份交接 = 一个 md。文件名：`YYYY-MM-DD-<slug>.md`。顶部一行 header：

```
> from: <claude|codex|henry> | to: <claude|codex|henry> | status: <draft|ready|done|closed> | re: <slug> | date: <YYYY-MM-DD>
```

正文 = spec / 结果 / 问题本身。**写成 spec（文件、契约、验收标准、约束），不是聊天语气** —— spec 没有口音，任何 agent 读起来一样。

## 状态流转

- `draft` —— 作者写好；若是「要建的活」，需 Henry 审过才能往下。
- `ready` —— **Henry 已批准**；目标 agent 可以执行。（这是唯一的人工闸：Henry 把 `draft` 翻成 `ready`。）
- `done` —— 目标 agent 做完，在同文件追加 `## Result`，或另写一份回执交接。
- `closed` —— 已确认收口，可留档。

## 流程

1. Claude 写 spec → `from: claude / to: codex / status: draft`。
2. Henry 读、改、把 `status` 翻成 `ready`。
3. Codex 开工时（由根 `AGENTS.md` 指引）扫到 `ready` 的活，执行，写回 `status: done` + `## Result`。
4. Claude 读回执，审 diff，给结论。

## 约定

- **不删原文**：交接是 append-only；状态只在 header 里改。
- 一份交接只干一件事（一个 `re:`）。
- 遇到与 spec 假设不符的情况**不要猜** —— 在 `## Result` 里记下、标 `needs: claude/henry`。
- `done` / `closed` 的交接可移到 `archive/` 子目录，或留原地。


## Builder 侧回执纪律(2026-08-20 增,05 链教训)

1. **回执语言不得宽于实现**:申报「全部/一律/零触碰」前逐字核对实现射程;窄绿不得扩写成全闭合(V12 期间四犯记录在案:01 MED-1/03.3 自述过宽/05.4 范围表/05.6 保存口径)。承重结论与装饰数字自行分开标注。
2. **平行机关申报**:新造任何承载既有机关同类职责的机关(状态存储/恢复载体/守卫层/事务边界),须在方案短笺与回执中显式申报「为什么既有正门不够」;未申报的平行机关=复核即记 finding。
3. **回执写入必须 UTF-8**(2026-08-21 增,Spark 首单事故):Windows 下 PowerShell `>>`/`Out-File` 默认编码会把回执写成 GBK 混入 UTF-8 文件。写 handoff 一律用 UTF-8 显式编码(`Set-Content -Encoding utf8` / node `fs.appendFileSync(p, s, 'utf8')`),写后自检 `file`/首行非乱码。

## 同树串行原则(2026-08-21 增)

共享工作树上**同一时刻只跑一个 builder**;两单触及面重叠(尤其 `server/`、生成件、同一条 verify 链)时一律串行;隔离 worktree 因 Windows 下 node_modules 成本不作默认。判据=正确性与配额,不是墙钟。理由:并行同树=宽 add 事故的放大版,改动归因不可能。

## 验证链接线规则(2026-08-21 增,S1 FAIL 产物遗留事故定形)

`verify:*` / `check:*` 主链的定义是**验收基础设施**,不是普通代码:①新门**只在复核 PASS 后**由调度方接线,builder 工单里「接入 verify 链」一律理解为「交付可接线的门 + 接线 diff」,接线生效归复核后;②判 FAIL 的门若已生效,**撤接线**(产物可随 FAIL 判定存档,但不得承重);③撤/接属裁定方定义权,调度方执行须留字据。理由:链里掺一条空转断言,每次「verify 全绿」回执都在说谎(5-4 证人须承载答案);FAIL 单的产物留在任何承重位都是洗白。

#### 机械锁加固(2026-08-22 晚,Opus 明知锁在仍覆盖一案后,Fable 判定采纳)

锁是文件,能被看见不能阻止被覆盖——自律挡不住时差也挡不住「查了没停」。改为**原子取锁**:①取锁用 `mkdir .codex-tmp/builder.lock.d`(原子,已存在即失败)再在其中写 `{单号, PID, 发单方, 时间}`;**失败即不得起进程**,把拒绝写进日志;②陈旧锁判据=目录内 PID 已死且 ≥20 分钟,此时才可清;③**锁只由写锁者删,删前核对发单方字段**——守护/监视器不得删别人的锁(Fable 的守护此前亦有「任意 codex 退出即删锁」的同病,同改);④builder/reviewer「结束」判据=**进程消失 + 20 秒落定**,`## Result` 出现不算结束(2b00fe6 中途快照事故)。旧的 `builder.lock` 文件形式废止。

#### 取锁必须是一步(2026-08-22 深夜,12.2a-2 builder 覆盖 owner 一案)

**事故**:12.2a-2 builder 开工时跑取锁流程,`.codex-tmp/builder.lock.d` 已存在(调度方持有),取锁**正确失败**;但**紧随其后的 owner 写入照常执行**,把既有 `owner.json` 覆盖成自己的(`dispatcher: user-direct`),原 owner 字段不可恢复。
> ⚠️ **该 builder 的后续处置是对的**:它**没有删锁**,并标 `needs: claude/dispatcher` 交回发单方核对。**问题不在它,在流程。**
> ⚠️ **归因更正**:调度方(Opus)当时据此判为「第三次双发/有第三方」,**判错了** —— 没有第三方,是同一只 builder 的取锁流程。**锁被改写不等于有人抢跑;先读 owner 再下结论。**

**根因**:取锁(`mkdir`)与宣称所有权(写 `owner.json`)是**两步**,失败与否不联动 —— **原子的只有前一步**。另:该 builder 用的是 PowerShell `New-Item -LiteralPath`,在本机 PowerShell 5.1 上不可用,失败原因被淹没。

**规则**:

1. **取锁与写 owner 必须在同一条命令链里,前者失败则整链中止**。Git Bash 推荐:
   ```bash
   mkdir .codex-tmp/builder.lock.d 2>/dev/null      && printf '%s
' '{"order":"...","pid":"...","dispatcher":"...","started":"..."}' > .codex-tmp/builder.lock.d/owner.json      || { echo "⛔ 取锁失败,不得起进程"; cat .codex-tmp/builder.lock.d/owner.json 2>/dev/null; exit 1; }
   ```
   PowerShell 侧**不得用 `New-Item -LiteralPath`**(5.1 不支持);用 `New-Item -Path -ItemType Directory -ErrorAction Stop` 并置于 `try/catch`,catch 内**只报错不写 owner**。
2. **owner.json 一旦存在即不得覆盖**。写入前须 `test -e` 或 `set -o noclobber`;**已存在 = 取锁失败**,按 §③ 处置。
3. **builder / reviewer 提示词须明写**:「**锁非你所有,取锁失败即停,不得覆盖 owner,不得删锁**」——发单方持锁是常态,被派方本就不该取锁。

> **本条与上一条同源**:凡「靠自觉不去覆盖」的环节迟早会被覆盖。**能原子的就原子,不能原子的就让它整链失败。**

### ⚠️ `git add` 纪律的**第四种失手形态:索引里已经躺着别人的东西**(2026-08-29)

**现场**:`git add <三个文档名>` 之后直接 `git commit` —— 而**索引里早已躺着 builder 暂存的四个文件**(`.gitattributes` + 三件 pin,状态 `A`)。⇒ **`git commit` 提交的是【整个索引】,不是我刚 add 的那几个名字。** 一次「只提交三份文档」的提交,实际提交了**七个**文件,其中四个是 builder **正在飞**的交付。

⭐ **它与前三种失手的区别**:前三次(漏生成件 / 宽 add 扫进 / 目录不是同一个)错在 **`add` 这一步**;**这一次 `add` 完全正确,错在 `commit` 的默认语义** —— **⛔ 你 add 了什么,与这次 commit 会提交什么,是两件事。**

⇒ **机械化(⛔ 与「点名 add」并列,不可互相替代)**:**提交前必须打印 `git diff --cached --name-only` 并逐行看过**;或改用 `git commit -o <files>`(只提交点名的)。
⚠️ **⛔ 不许用「我刚才 add 了什么」来推断这次会提交什么** —— 那是在读自己的记忆,不是读索引。**索引是共享的,别人也能往里放东西。**

### ⭐⭐ 4b 的**操作者侧机械化**:变异落地证明(2026-08-29 立;Fable 采为家法)

> **⛔ 施变异后,先出示【落地证明】,再读红绿。**
> 落地证明 = `diff` 或 `grep` 命中,证明**这次编辑真的改了那一行**。
> **凡「变异了却没红」,第一嫌疑是【变异没落地】,⛔ 不是【断言不咬】。**

**出生证明(2026-08-29,c-0 复核当场)**:亲刀 K-5 元不变式,连续两次施变异**都没打中** —— 一次 `perl -0pi -e`、一次 `node -e`,**shell 各吃掉了 `\s` 里的反斜杠**,needle 变成 `/s+/`,`includes()` 返回 false。两次测试都照绿 **10/10**。
⚠️ **那两个绿是「我的变异失败」的产物,不是「K-5 不咬」的证据。** 第三次改用**按行号 + 不含反斜杠的锚点**(`sed -i "24s|, '');|, '').replace(/a/gu, '');|"`),先 `diff` 打印落地证明,才见真红 `not ok 7`。

**为什么 4b 不够、必须再补一层**:4b 说的是「先证明这次变异**真的违反了那条断言**」—— 那是**语义层**自查(**改对地方了没有**)。本条补的是**更早一层**:**编辑到底发生了没有**。语义再对,`sed` 没打中就是零。
⭐ **同族**:它与「退出码 1 可能是脚本崩了」「测试绿可能是没跑起来」是同一个形状 —— **读结论之前,先证明量具动了**。这也正是「阳性对照」在**操作者**这一侧的样子:上面那条管的是量具会不会报警,这条管的是**你到底有没有碰它**。

**工具面副产品(⛔ 别再踩)**:Windows / Git-Bash 下,凡变异模式**含反斜杠**(`\s` `\d` `\.`),经 `-e` / `-0pi -e` 传递被吃掉的层数**不定**。⇒ **优先挑不含反斜杠的锚点**(按行号 + 一段唯一普通子串),或把脚本写进文件再 `node <file>` 执行 —— ⛔ **两种做法都仍需 `diff` 证明落地**。

**⭐ 同日第二次应验(2026-08-29,写 README 时当场)**:用 `node -e "…"` 往文档里插一段含**反引号**的中文条目,bash 把反引号当成**命令替换**执行了 —— 报了四行 `command not found`,而 node 那句**照常打印「✅ 已写入」**。⇒ 若只读那个 ✅,入档的就是一段**四个标识符被掏空**的残文。靠回头 `sed` 打印实际内容才发现。
⇒ **归拢:反斜杠与反引号同罪** —— 凡插入内容含 `` ` `` 或 `\`,**⛔ 不许走 `-e "…"`**,一律**先写进文件、再由脚本读文件**(`fs.readFileSync(process.argv[2])`),且**写完必须回读实际落地内容**。

⇒ **通例再次应验**:排除法 = **换一个独立证据源**,⛔ 不是把同一个数字再看一遍。⚠️ 而**进程名**是最弱的证据源 —— 它只说明「有个同名的东西」。

### ⚠️ 裁定方也要守「先查现物」(2026-08-29,Fable 自立并授权我打回)

Fable 裁 c-1a 时钉 Python **3.11**,而初赛环境**就在盘上**且钉的是 3.12 —— **裁前没查现物**。这是「裁定前不查现物」**第二次**(第一次:v0.4④ 裁定时 UNIQUE 约束已在树上)。
⇒ **Fable 自立规、并授权调度方执行**:**凡裁定含【可被现物否证的具体参数】(版本 / 路径 / 约束),裁前必查;查不了就明标「盲拍,待现物校正」。⛔ 见到拍具体参数而未附现物出处,直接打回。**
📌 与「重对现物对的是 HEAD 不是工作树」同族 —— 都是**「说之前先看」**;区别在那条管**施工方**看的是哪一份,这条管**裁定方**看没看。

### ⭐⭐ 刀法:**亲刀不得毁证 —— 变异施在副本上,不施在被保护物上**(2026-08-29 立;Fable 提刀、调度方拦下、Fable 收刀并记己账)

**病例**:c-1a 的 K-0 是「证据本体前后哈希必须不变」。抽检方设计的验刀是「**临时跑一次裸 `uv`,让 K-0 必红**」——⚠️ 而那个红点是**真把现址 `uv.lock` 改写掉**换来的,现址**不在版本控制里,改了恢复不了**。
⭐ **荒谬性完整陈述:为了证明守卫有效,先把被守卫物毁掉。**

⇒ **家法**:**⛔ 变异要施在副本上,不能施在被保护物上。**
⇒ **设计侧上游规则(抽检方自记)**:**设计刀时先算红点的代价;凡红点的证明力可在副本上等价重建的,⛔ 不许在本体上取。**
📌 **同族镜像**:与「⛔ 不得为让变异可杀而重构生产码」是同一病的两面 —— 那条防**为杀刀改本体**,这条防**为出红毁本体**。

#### ⭐ 配对条:**立防线先算伤害发生的时刻 —— 防线必须站在伤害上游**(2026-08-29,Fable 自记己账并归拢)

**病例**:v0.7.2 裁定「转写器身份 = pin 文件的**原始字节 sha256**」,并把配套的 `.gitattributes -text` 落点定在 **c-1b**。
⚠️ 但**伤害发生在 c-1a 把 pin 提交的那一刻** —— 本仓 `core.autocrlf=true` 且仓根无 `.gitattributes`,pin 一经 git 往返,`uv.lock` **441341 → 443957** 字节。⇒ 仓内副本的指纹**恒不等于**证据本体的指纹,**同一环境被判「未证同一」,每次 checkout 产一个假阴性**。
⇒ **防线立在了伤害的下游,等于没立。**

⭐ **它与「设计刀先算红点的代价」是镜像的一对**:
- 那条问的是「**造这个红点要付什么**」——防的是**为出红毁本体**。
- 这条问的是「**伤害在哪一刻发生**」——防的是**防线站错了位置**。
- ⇒ 合起来:**动手之前,先把【代价】和【时刻】各算一遍。**

📌 **一般化**:凡「A 要求某物保持不变」而「B 会改变它」,**排 A 与 B 的先后是判据的一部分**,⛔ 不是实施细节。**A 必须先于 B 落地**,否则 A 从生效第一天起就在报假警。

#### ⭐ 结构值得单独记:**证明义务可分解、可移址**

原刀的证明义务是一整块:「真跑危险动作 ⇒ K-0 报警」。把它**拆成两半**,各自在副本上完成:

- **半一 · 危险是真的**:在副本上跑真正会重解的命令,证明它**确实**改写 lock。
- **半二 · 量具分得出**:对副本改写前后跑同一套哈希比对,证明它**会报警**。

⇒ 两个半证明**合成原刀的全部证明力**,而本体**零字节代价**。
⭐ **这是刀法的一次真进步:证明义务不是原子的**——它常常可以拆开、挪到安全的地方各自完成。⛔ 别默认「要验守卫就得触发真事故」。

#### ⭐⭐ 4b 的**第三种含义**:变异扎到了,但那一层是**冗余的**(2026-08-29,c-1b-1 亲刀 K-1)

亲刀「杀进程树」时,我把 `taskkill /PID <pid> /T /F` 的 **`/T` 去掉**(⇒ 只杀直接 pid,不杀树)。**变异确实落地(diff 为证),测试却照绿 5/5。**

⚠️ 按 4b 我先怀疑「没扎到点上」,读实现后发现真相是**第三种**:清理**同时有两条路径** —— `/T` **和**一段自己用 `Win32_Process` 做 BFS 枚举后代再逐个杀的代码。**我只掐了冗余的那一条,另一条顶上了。**

⇒ **4b 的三种含义**:
- (A) **断言瞎了**(断言侧)
- (B) **变异没扎到断言看的地方**(操作者侧)
- ⭐ (C) **变异扎到了,但被测物在那一点上【有冗余防护】,另一条路径顶上了**(**被测物侧**)

⇒ **排除法**:**读实现,数清楚干这件事一共有几条路径;⛔ 全部禁用才算一次完整的变异。**
⭐ **并且 (C) 是【好消息】** —— 它说明产品在这一点上**不是单点防护**。⛔ 别把它读成「断言不咬」,那会让你去削弱一个本来很结实的地方。
⭐⭐ **Fable 把代价说破了(收)**:**误诊 (C) 为 (A) 的代价是【把冗余防护拆了】—— 这是三种误诊里唯一【越修越坏】的一种。** (A) 与 (B) 误诊只是浪费一轮;(C) 误诊会**真的降低系统的健壮性**,而且降低之后**测试照绿**(因为你"修好"的正是那个断言)。

**补掐第二条后的实况(⚠️ 比测试红更强的证据)**:同时把 `descendants` 枚举改成返回 `[]` ⇒ 测试**挂死**(等进程数归零而永远等不到),而且**机器上真的留下了一个孤儿** —— `mineru-fixture-….py grandchild <token>`,父进程已消失。⇒ **我亲手造出了那把刀所守的那个孤儿**,随即清除。
📌 **副则**:**亲刀若可能产生外部残留(进程/文件/端口),收刀后必须【复查并清理现场】** —— 变异恢复了,现场不一定恢复。

#### ⭐ 刀法进阶:**变异要设计成「只可能红在判据上」**(2026-08-29,c-1b-0 亲刀;Fable 点名)

亲刀 K-3 反刀时,要让判同谓词「无视 hash」。**两种改法都能变红,但只有一种是证据**:

- ❌ **删掉 `AND transcriber_lockfile_hash = ?` 那一行** —— 会红,但红的原因是**绑定参数个数不符**,与判据毫无关系。
- ✅ **改成 `AND (transcriber_lockfile_hash = ? OR 1=1)`** —— **参数个数不变**,唯一变化就是「谓词不再看 hash」。

⇒ **归拢**:变异设计的标准从「**能不能变红**」升级为「**它只可能红在判据上**」。
⚠️ 前者会让**两义 #4(红在别处)**悄悄通过 —— 你看见红就以为刀咬到了,其实咬到的是脚手架。
📌 **操作口诀**:施变异时**保住一切与判据无关的形状**(参数个数、类型、调用签名、文件是否存在),**只动被断言的那一点语义**。

#### ⚠️ 施刀实况(⭐ 它自己也吃了一次「变异没落地」)

第一刀跑**裸 `uv lock`**:`Resolved 130 packages in 1ms`,**md5 纹丝不动**。
⛔ **这不能读成「危险是假的」** —— 按「变异落地证明」条,第一嫌疑是**没扎到危险的那个命令上**。果然:`uv` 只在 lock 与 `pyproject` 不一致时才重解。改用 **`uv lock --upgrade`**,`441341 → 441757` 字节、md5 变,**危险当场坐实**。
⇒ **顺带修正 K-0 的措辞**:危险的不是「所有 `uv` 命令」,而是 **`--upgrade` 与会建/改 venv 的 `sync`**。⛔ 原单把风险面写宽了,如实记。

#### ⭐⭐ 副产品:漂移的真形状是**传递依赖**,不是顶层包(⛔ 比预设的更阴)

`uv lock --upgrade` 之后:**`mineru` 仍是 `3.4.5`**(registry 今天没出新版),但**五个传递依赖漂了** —— `modelscope-hub 0.2.0→0.3.0`、`pydantic`、`pydantic-core`、`typer`、`wcwidth`。

⇒ ⚠️ **出生证会【如实】写 `transcriber_version: 3.4.5`,而底下的环境已经不是同一个。** 版本号没说谎,它只是**不足以标识**。
⭐ **定论:转写器的身份是【lockfile】,不是版本号。** 这正是「钉版三件必须入库」那条裁定的直接证据 —— **⛔ 只记版本号 = 记了一个同名不同物的标签**。
📌 **并族**:与「标识符必须标识所断言之事」「不可复核的声明比没有更危险」同一家族。

### ⭐ 验 gitignore 改动:**`check-ignore` 是逐路径问,`git add -n` 才是问结果**(2026-08-29,亲验 c-1a K-2 时)

**场景**:一次 gitignore 反选改动,要证明「**该进来的进来了,且没把别的也放进来**」。

- `git check-ignore -q <path>` —— **逐路径问**。⚠️ **它只能回答你想到要问的那些路径。** 若 builder 顺手放开了一个你没想到去问的东西,**它全程沉默** ⇒ 两义性 #6 的变体:**问错了问题,得到的是让人安心的沉默。**
- `git add -n <dir>` —— **问结果**:直接枚举「**到底哪些文件会进索引**」。⛔ 不需要你先猜对路径。

**实况**:`_external_tools/` 下共 **208 个文件**(绝大多数是 `browser-harness` 自带的 `.git/`),`git add -n _external_tools/` 输出**恰好三行** —— 三件 pin,别的一个没有。
⇒ ⭐ **枚举式证据 > 点名式证据**。点名式只能证伪你已经怀疑的;枚举式能撞见你没想到的。
📌 配合用:`git status --porcelain -uall <dir>`(展开折叠的 `?? dir/`)—— **⛔ 折叠显示的 `?? _external_tools/` 什么也没告诉你**,它既可能是三个文件也可能是两百个。

#### ⚠️ 同日反噬:**这条规则不是给别人立的**(2026-08-29,调度方自记)

上午刚把「**凡裁定含可被现物否证的具体参数,裁前必查**」写进 README(并记明可据此打回裁定方)。**同一天下午,我在 c-1a 的 K-3 里写下**:「现址 venv 里 MinerU 的依赖链带 **PyMuPDF**,可直接用」。
⚠️ **我没查。** builder 实测后申报:`PyMuPDF`/`fitz` **不在** venv,`uv.lock` **零命中**;在场的是 **Pillow 12.3.0**,它用 Pillow 完成了同义工作,并明确要求「⛔ 后续更正工单描述,不要反写为 PyMuPDF 原本在场」。复核方逐条核实:**builder 对,发单方错。**

⇒ **归拢**:那条规则的正确读法**不是**「裁定方要查现物」,而是 —— **⛔ 任何人写下一个【可被现物否证的具体名字】之前,都得先查**。裁定、工单、判据、回执,一视同仁。**规则写在谁的账上,不影响它对谁生效。**
⭐ **并且要记 builder 一功**:它**没有**沉默地绕过去(用 Pillow 干完就算了),而是**指着发单方的错误要求更正**,还预先堵死了「反写为原本在场」这条退路 —— **这正是回执该有的样子:施工方是发单方的现物校验器。**

### ⭐⭐ 拆单病根具名:**强制点的作用域 ≠ 你列举的生产者名单**(2026-08-29,c-1b-0 第一次派工停线)

**病例**:单里要求「服务层强制某字段非空」。发单方按「产生点逐点列举」这条法,**逐点列举了两个生产者**(`sourceFileIntake:603` / `sourceMaterialization:288`),然后就停了。
⚠️ 但强制加在**服务层**,它**不管调用方是谁** —— **测试也是调用方,而且有 34 处**(三份既有测试直接构造并真写入)。⇒ 单**不可满足**:按 K 做就让既有测试红,改既有测试又出了允许面。builder **正确停线**,三条主张复核后全部为真。

⇒ ⭐ **归拢**:「产生点逐点列举」我照做了,却**把范围划成了「我认为正当的生产者」**。
**⛔ 加服务层强制时,爆炸半径是【全部调用方】,不是【全部生产者】。**
⇒ **机械化**:列举必须以 **`grep` 调用点的实际数量**为准(并把那个**数字**写进单),⛔ 不以「谁算生产者」为准。**「生产者」是一个语义判断,`grep` 不做语义判断 —— 这正是要用它的理由。**
📌 **同族**:与「没表≠没能力」「字段在≠有人用」一样,都是**把语义分类误当成事实清单**。

⭐ **Fable 补的半句(收)**:「产生点逐点列举」这条法**没错,错在【列举的单位】** ——
- **产生点列举**列的是**语义类**:**谁在生产**。
- **强制作用域**要的是**事实类**:**谁在调用**。
⇒ **两种列举基准,各答各的问题。** 加服务层强制时用**后者**,以 `grep` 数字为准且**数字入单**。
⭐⭐ **而这句把「机械化」的本质说透了:机械工具的价值恰恰在于【它的无知】。** `grep` 不知道谁「算」生产者,所以它不会替你把测试排除掉 —— **你想要的正是它不懂。**

### ⭐⭐ 署名错误**即使无人受益也必须纠**(2026-08-29,Fable 补入册)

**病例**:builder 回执把一条**同侪(Fable)的裁定**写成「本次 **Henry 直接指令**」,而那一轮**根本没有 Henry 输入**。调度方当场纠正、写进修订段、要求以后按实际来源署名。

⇒ **判据**:**⛔ 署名错误必须纠,哪怕这次没有任何人因此获利、也没有任何决定被它改变。**
**理由**:**权限记录的价值在于它【可信】,不在于这次有没有人拿它做坏事。留一处失真,以后每一处署名都要打折读。**
📌 **同族**:与「**同侪代授权 = 权限洗白**」是同一条防线的两端 —— 那条防**假的授权**,这条防**假的出处**。⚠️ 而**假出处比假授权更隐蔽**:它不请求任何东西,只是**悄悄把一句话的分量抬高了一级**。

### ⚠️ 闸的第五处射程边界:**写在 `## Result` 之后的正文,闸看不见**(2026-08-29,同轮撞出)

**现场**:第二次派工要扩允许面,修订段被追加在文件**末尾** —— 也就是 builder 的 `## Result` **之后**。闸切在 `## Result` 之前(这是为防「Result 被当成允许面」而立的规矩)⇒ **修订里新增的三份测试,闸一个都没认出来**,仍报 6 项并 ✅ 通过。挪到 Result **之前**后立刻变 9 项。

⚠️ **危害形状**:**扩了允许面却不生效,而闸照样报绿** —— 若不是顺手复跑了一次闸并**数了数字**,第二次派工会带着一张「闸眼里没扩过」的单出发。
⇒ **规矩(⛔ 不必改代码)**:**工单的任何修订都必须写在 `## Result` 之前** —— 回执是产物,正文是指令,**产物之后不再有指令**。
⇒ 📌 **并且这再次印证「闸给的数字要读,不只读它的红绿」**:两次都 ✅,**区别只在那个「6 项 / 9 项」**。

### ⭐⭐ 一般化:**死条文 —— 两个限额若不互相校准,先触发的那个让另一个永远触发不到**(2026-08-29,c-1b-1 拆单时撞出)

**病例**:`DEFAULT_LIMITS` 同时写了 `timeoutMs: 120_000` 与 `maxPdfPages: 1000`。而 MinerU 实测 **13.18 秒/页(温启)** ⇒ 120 秒只够**约 9 页** ⇒ **`maxPdfPages: 1000` 对 MinerU 是一条【永远触发不到】的条文**。

⇒ ⚠️ **死条文的危险不在它没用,而在它【读起来像一道防线】** —— 审代码的人看到 `maxPdfPages: 1000` 会认为页数有防护,而实际上把页数上限调成 10 或 10000 对系统行为**毫无区别**。
📌 **同族**:与「**闸先建好没有对手,形状很可能是错的**」同源 —— **未经触发的防线只是文字**。也与「没表≠没能力 / 字段在≠有人用」一族:**存在 ≠ 生效**。

⭐ **正确刀法(K-3 的形状)**:
1. **写出算术**,让两个限额**互相解释**(有效上限 = 另一限额 ÷ 单位成本)。
2. **两个方向各取一刀**,且**两条错误码必须不同** —— 若两个方向报同一个码,说明其中一条**根本没被走到**。

### ⭐⭐ 审插件式接缝的**三段取证**:注册表 ≠ 有人注册 ≠ 有人选中(2026-08-29,c-1b-1 拆单;⚠️ 同日第二次栽在自己执行的法上)

**病例**:拆 MinerU 接线单时,我查到 `PARSERS[input.parser_key]` 这个**注册表**存在,就下了「**接缝干净**」的结论。⚠️ **却从没查【谁来设 `parser_key`】** —— 现物是 `sourceFileIntake.ts` 的 `SOURCE_FORMATS` 把所有 `.pdf` **钉死** `'native-pdf'`,而那个文件在我自己写的单里是**禁区**。⇒ 单**不可满足**:注册了 parser 也**没有任何生产输入会选中它**。builder 停线,两条主张复核后全部为真。

⇒ **三个事实必须【分别取证】,⛔ 不许由前一个推后一个**:
1. **有注册表吗?** —— grep 注册表定义
2. **有人注册进去吗?** —— grep 注册语句
3. ⭐ **有人会【选中】它吗?** —— grep **写入那个 key 的地方**

📌 **第 3 条最常漏,因为前两条【看起来就是接线】。** 注册表是**形状**,选择才是**接线**。
⇒ 这就是本仓自己的法:**形状比接线便宜,所以常跑在前面**;**字段在 ≠ 有人用**。⚠️ **我执行了一整天的法,当天第二次咬到我自己**(第一次:PyMuPDF 未查现物)。
⭐ **归拢一句**:**你最容易漏掉的,恰恰是你已经写下来那条法所指的地方** —— 因为写下来之后,它感觉像"已经处理过了"。**法写进 README ≠ 法在你脑子里运行。**

#### ⚠️ 由此挖出的一个**现存正确性隐患**(⛔ 不是 MinerU 引入的)

`sourceArtifactImprintInput` **给每一个 parser 都发同一份身份**:`lockfile = server/package-lock.json`。对 `native-pdf` 尚可,**对任何非 npm 依赖的转写器都是平白的错**。
⚠️ **而在「身份 = lockfile 指纹」入宪之后,它升级成【身份错配】** —— 两个**真正不同**的转写器,会因为共用 `package-lock.json` 的指纹而被判「**同一转写器**」。
⇒ **⛔ 未申报身份的 parser 必须【拒绝写出生证】,不得回退到默认值。**
📌 **一句归拢**:**一个错得合理的默认值,比没有默认值危险** —— 它让「**忘了申报**」看起来像**正常工作**。同族:「说谎的类型声明」「不可复核的声明比没有更危险」。

### ⭐⭐ 验证源**必须独立于被验对象的生产者**(2026-08-29,c-1b-2 拆单;v0.6-3 从分段维推广到几何维)

**v0.6-3 已立**:校验器只重放**文本规范化**,⛔ 不得重放转写器的**分段/角色**逻辑 —— 否则是自我印证。
**本次推广**:验 **bbox 是否诚实**时,⛔ **不得用 MinerU 自己的 span 输出**去证明 MinerU 的 block bbox —— **同一个模型的两层输出不是两个证据源。**
⇒ **解法**:用 `pypdfium2` 读 **PDF 文本层**按矩形取文本 —— 它与 MinerU 的**版面/OCR 模型**来源不同,**才算独立源**。
📌 **一般化**:**「两份数据不一样」不等于「两个证据源」** —— 要问的是**它们的错误会不会一起犯**。同一模型的不同层,错误高度相关。

#### ⚠️⚠️ 附带的「差点」(Fable 点名留档):**fixture 的性质会随验证需求【反转】**

- **c-1a** 要的是 **image-only(无文本层)** 件 —— 因为要证明 **`pdf-parse` 抽不出东西而 MinerU 抽得出**。
- **c-1b-2** 要的是 **有文本层的真件** —— 因为要用 `pypdfium2` 读文本层**当独立源**。
- ⚠️ **两张单要的 fixture 性质【正好相反】,而我差点直接沿用上一张的。**
⇒ **⛔ 别把上一张单的 fixture 当默认值继承** —— 先问:**这一刀要证明什么?它需要被测对象具备什么性质?** ⚠️ 相邻两张单**看起来在同一条链上**,恰恰最容易让人跳过这一问。

### ⭐ 归族:**看起来对的错东西最危险**(2026-08-29 归拢)

同一逻辑,今天集齐了四个成员:

| 成员 | 它伪装成什么 |
|---|---|
| **说谎的类型声明**(TD-29) | 一份正确的类型契约 —— 编译得过、运行必炸 |
| **错得合理的默认值**(v0.7.3) | 正常工作 —— 让「忘了申报」看起来像已申报 |
| **推算补造的 bbox**(本单 K-3) | 高保真 —— **比缺 bbox 更危险,因为它看起来精确** |
| **`clamp` 掩盖越界坐标**(本单 K-4) | 一个合法坐标 —— **把越界变成看起来合法的东西,是坐标系上的另一种谎** |

⇒ **共同点:它们都【不会报错】。** 缺失会报错,错误的存在不会。
⇒ ⭐ **所以判据要盯的往往不是「有没有」,而是「它是不是真的从它声称的地方来的」。**

📌 **免疫的汇率(记账)**:「先把接缝查到底」提前付的是**一次拆单侦察**(本轮:四次 grep + 一次 `middle.json` 实读),省下的是**整轮派工—停线—重写**。今天用**两次翻车 + 一次拦截**各称过一遍重 —— **汇率清楚,值得。⛔ 但它不是免费的,别把"免疫"说得像顺手。**

### ⭐⭐ 断言设计:**「包含」型断言天然可被【更大的范围】平凡满足**(2026-08-29,c-1b-2 停线时被 builder 捅破)

**病例(我写的 killer 有洞)**:K-1 要求「按碎片 bbox 回原件取矩形内文本,**必须命中碎片文本**」。
⚠️ **若把【整表 bbox】复制给每个单元格碎片,这条断言会【平凡通过】** —— 因为单元格文本本来就是整表文本的**子串**。
📌 builder 的实测坐实:按整表 crop 取回的文本含目标单元格 `Cinema 2`,**但同时含 `Wednesday`、`Gallery 1`、`free`** ⇒ **那个锚回答的是「整张表在哪」,⛔ 不是「这个单元格在哪」。**

⇒ ⭐ **归拢**:**凡用「包含」验【定位】,必须配一条【排他】** —— 否则它验的是「**在不在里面**」,不是「**在哪**」。
⇒ **补法**:命中目标文本 **⊕ ⛔ 不得包含同层级其它单元的文本**。
📌 **同族**:与「**计数锁**」是一对 —— 计数锁验「有多少」冒充「对不对」;包含锁验「在不在里面」冒充「在哪」。**两者都是【更弱的性质】冒充【更强的性质】。**
⚠️ **而且这一族的共同特征是:被测物【退化得越厉害,断言越容易过】** —— 范围放到最大时包含断言必过,碎片合成一块时计数最好看。⭐ **⛔ 判据若在被测物退化时更容易通过,它就是反的。**

### ⭐ 现物:**同一个工具的同一次输出里,摆着三个坐标面**(2026-08-29,c-1b-2 实测)

MinerU 3.4.5 跑同一页,三份落盘各用**不同坐标系**:

| 输出 | 页尺寸 | 同一张表的 bbox |
|---|---|---|
| `content_list` | **无 `page_size`** | `[94,156,892,386]` |
| `middle` | `[595,841]` | `[56,132,531,325]` |
| `model` | `page_info=1654x2339` | `[157,367,1477,903]` |

⇒ 跨面凑分母的后果是现成的:`892 / 595 = 1.499…` ⇒ **必越界**。
⭐ **这是「坐标系混同」(TD-31 的病名)最干净的一份标本** —— ⛔ 不必假想,同一次输出里就摆着三份。
📌 ⇒ **判据**:归一化的**分子与分母必须来自【同一份输出】**;⛔ 跨面取值即使数值"看起来合理"也不许。

### ⭐ 范式:**遗产体检三层法**(2026-08-28,b-2 的 builder 随崩溃阵亡后接手)

施工方中途阵亡 / 被打断,**回执栏空** ⇒ 树上半成品**全部按未验证对待**。接手前按三层验,**每层各防一种两义**:

| 层 | 做什么 | 防的是 |
|---|---|---|
| **1 能立** | `tsc --noEmit` / 构建 | 半成品根本编译不过 |
| **2 真跑了** | 跑测试并**看 `# tests` 计数非零** | ⚠️ **「绿」两义:真过了 / 根本没跑起来** |
| ⭐ **3 会咬** | **复核方亲手施 1–2 次语义定向变异,看关键刀是否真的变红** | ⚠️ **「绿」的另一半:测试是不是「写出来就绿」、从没红过** |

⭐⭐ **第 3 层是这套法的核心** —— **前两层只证明它活着,第 3 层才证明它有牙。**

### ⚠️ 并且:**复核方的证据 ⛔ 不代替施工方的取证义务**

接手体检得出的红点是**复核方的新鲜证据**,**⛔ 不是死者的日志**,但也**⛔ 不能拿来免掉续建方自己取红点**。
**续建单里要同时写清这两句,它们并行不悖**:
> **「这条路走得通,地基不必怀疑」** + **「你仍须在最终树上自行取全部红点」**

📌 **前一句省的是它的怀疑成本,后一句保的是证据链的完整** —— **⛔ 少写哪一句都会走偏**:只写前句 ⇒ 它可能直接采信遗产;只写后句 ⇒ 它可能推倒重来白烧一轮。

### ⭐⭐ 拆单自查:**产生点逐点列举**(2026-08-28 立;同形第二次,⛔ 不等第三次)

**凡「申报 / 不变式」类的判据,拆单时必须把该申报的【全部产生点】逐点列举,一点一 fixture** —— **或显式豁免并写理由。**

**两种模式**:
| 情形 | 「产生点」指什么 | 做法 |
|---|---|---|
| **判据针对现存代码** | **代码里的每一处产生行** | `grep` 该申报/该不变式的**全部写入点**,逐行列进单 |
| **判据针对将造之码** | **应当触发它的每一种输入情形** | 列举输入情形(而非行号),一情形一 fixture |

**两次代价买来的**:
- **b-1**:分割不变式的「**尾部**留白」分支无覆盖 —— 注掉它 11/11 全绿(中间留白那条却会红);
- **b-2**:`signature_mismatch` **五处产生点只有一处被覆盖** —— 其余四处注掉全绿,且**逐条读码确认可达**。

⚠️ **两次都不是 builder 没做到工单要求,是工单粒度不够。**
⇒ ⭐ **用复核轮次去补工单粒度,贵一轮是一轮。**

### ⚠️ 那「复核细一档」还留不留?**留,但定位改为安全网**

自查把粒度**前移**之后,**复核细刀抓到东西应当成为例外,而不是常规**。
⇒ ⭐⭐ **它的成功指标是「空手而归」**:**哪天细刀连续三单一无所获,才证明这条自查真的生效了。**
📌 **⛔ 别把「细刀又抓到了」当成复核有价值的证据** —— 那恰恰说明拆单那一头还在漏。

⚠️ **本条自查的防腐条款**:**规则的威信,一半来自它抓得到,另一半来自它不滥抓。**
📌 **实例**:立规当天套用两张候锁单 —— **b-2b 抓到 `container_entry_unreadable` 一刀未覆盖(补 K-6)**;**b-4 是纯文档单、无申报类判据 ⇒ ⛔ 不补,也不为了「套用一下」硬加刀。**
⇒ **⛔ 一条每次都能"找出问题"的自查,多半已经退化成仪式。**

#### ⚠️ 「产生点逐点列举」的两条补充(2026-08-28 当天实战买来的)

**补充 1:⛔ 列举时不许用 `head` / 任何截断。**
📌 **实例(打在立规者自己脸上)**:我 `grep ... | head -6` 数出「五处产生点」,而**第一行是闭集定义** ⇒ **真实是六处,`head` 把最后一处截掉了**。
⇒ ⭐ **一条用了 `head` 的「逐点列举」,不是逐点列举。** 用 `grep -c` 先数总数,或干脆不加管道。

**补充 2:每个产生点必须配一个能【单独】触发它的输入;给不出 ⇒ 它是【等价变异】,如实记档,⛔ 不硬造红。**
📌 **实例**:`450` 的条件与 `435` 相同 ⇒ 同一个 Set 里已有该 code ⇒ **注掉它无任何可观察差异**。
⛔ **两种造红法必须拒绝**(施工方提出并拒绝,采纳):**统计 `Set.add` 调用次数** · **读源码文字断言** —— **「那只会锁住重复实现,不能证明申报结果。」**
⛔ **也不得为了「让变异可杀」而重构生产码** —— 那是**让测试驱动结构**的坏形式;确要去重则**单独立单单独裁**。

⇒ ⭐⭐ **结论:「逐点列举」列的是【可单独触发的产生点】,不是【代码里的行数】。** 行数是形状,可触发性才是能力。

### ⭐⭐ 断言设计:**锁的三副面孔**(2026-08-28 一日内三次撞出,归拢)

**同一句「我们测了」,可以是三种完全不同的东西:**

| | 锁的是 | 症状 | 标本 |
|---|---|---|---|
| ⛔ **实现锁** | **代码长什么样** —— 调用了几次、写了哪个词、走了哪个分支 | **重构即误报**;而**换种写法达到同样错误结果时,它照样绿** | 统计 `Set.add` 调用次数 · 读源码文字断言 |
| ⛔ **计数锁** | **总数** —— 「有 N 个」「≥ 2 条」 | **看起来在验结果,其实只验了个总数** ⇒ **补一条、漏一条,它照样绿** | 「四条词里有现状栏的 ≥ 2」 |
| ⭐ **结果锁** | **每一项外部可观察的结果** —— 逐项、具名 | 重构不误报;**任一项错了就红** | 「碎片条**与**散沙层条**各自**必须有现状栏」 |

⚠️ **前两者的共同点:看起来在验,实际没验到承重物。**

#### ⭐⭐ 第四件事:**凡裁定必配反例**

**三副面孔管的是「验得对不对」;这条管的是「验得全不全」。**
> **一条裁定若只有正例没有反例,它就没有被测到。**

**标本(b-2b K-5)**:规格裁「**空包 ≠ incomplete,空是完整的空**」。
若只测「①部分条目未成件 ⇒ 带码」「②整包不可开 ⇒ 带码」,**一个「见容器就无脑加码」的实现照样全绿** ⇒ **那条裁定被架空了,而测试不知情。**
⇒ 必须加 **③空包 ⇒ ⛔【不】带码** —— **反例守的是边界的另一侧。**

📌 **与「凡放宽必配守缝之刀」同族**:
- **放宽**的反例守的是**缝**(b-1 的 K-1b:扣除残缺区间后,「丢文本不申报」仍须红);
- **裁定**的反例守的是**边界的另一侧**(不该发生的那一项)。
⇒ ⭐ **结果锁验「每一项该发生的」,反例验「那一项不该发生的」。**
⇒ ⭐ **拆解方向永远是同一个:把实现锁 / 计数锁,拆成【逐项具名的结果锁】。**

📌 **今天三次是分头撞出来的**:
- **实现锁** —— 施工方拒绝两种造红法,原话:**「那只会锁住重复实现,不能证明申报结果。」**
- **计数锁** —— 我给 b-4 写 K-3 时差点写成「≥ 2」,钉死为逐条。
- **结果锁** —— b-2b 的 K-3:**⛔ 不许只断言路径字符串看起来安全,要断言文件系统上真的没跑出去。**

### ⭐ 具名区分:**实现锁 vs 结果锁**(断言设计的第一课)

| | 锁的是 | 后果 |
|---|---|---|
| ⛔ **实现锁** | **代码长什么样**(调用了几次、写了哪个词、走了哪个分支) | **重构即误报**;而**换一种写法达到同样错误结果时,它照样绿** |
| ⭐ **结果锁** | **外部可观察的结果**(返回值、落库内容、HTTP 响应、文件系统状态) | 重构不误报;**结果错了就红,不管你怎么写的** |

**标本(2026-08-28,b-2 第四次派工)**:要给一处「黑盒杀不死」的产生点造红,两条捷径被施工方拒绝——

> 它的原话:**「那只会锁住重复实现,不能证明申报结果。」**

📌 **同族**:b-2b 的 K-3 我写「⛔ 不许只断言路径字符串看起来安全,要断言**文件系统上真的没跑出去**」—— **那也是在拒绝实现锁、要结果锁。**
⚠️ **实现锁最阴的地方**:它**看起来覆盖率很高**(每行都被"测到了"),**而它证明的只是「代码还是那样写的」。**
