#### 05.6-HIGH-1 — mount-local counter 不能充当持久 receipt identity

`useNoteCanvasDataAdapter.ts:434,446` 的 route generation 与 block operation sequence 都是 `useRef(0)`；同一初始 note 的新 mount 不推进 generation。`draftBlockPersistence.ts:84-90` 却只用 `noteId + blockId + creationGeneration + operationSequence` 生成持久 key，没有 mount/session nonce。adapter 也没有 unmount invalidation，使旧 async closure 在卸载后仍把自己的 route、latest operation 与 outstanding map 判断为 current。

Reviewer-only 确定性序列：

```text
old mount A(g0/op1) save old-edit，PUT held，写 key K
→ unmount
→ new mount A(g0/op1) save new-edit，生成同一个 K 并替换 queue bytes
→ old PUT success settle
→ old closure 的本地 current/latest/outstanding 判断仍通过
→ success cleanup forget(K)
→ 实际删除 new-edit receipt
```

临时 test `review probe: preserves a remounted save receipt when an old instance settles`：exit 1，1 failed / 28 skipped。settle 前 V2 bytes 明确含 `new mount edit` 与 `block-edit:note-1:block-1:0:1`；settle 后期望 bytes 精确不变，实际为 `null`。若新 PUT 随后 pre-commit reject，其 catch 只假定预先落盘的 receipt 仍在，不会重建，故新 intent 已无持久恢复载体。

同一身份域错误还有两个后果：

- reload/remount 后 active generation 又为 `0`，hydration 在 `useNoteCanvasDataAdapter.ts:587-615` 会把旧 mount 的 `creationGeneration:0` 当成本 generation，自动灌入 plain/TextFlow/field drafts，而非只保留为显式 Apply/Dismiss 队列；
- 旧 mount 的 held template conversion 也没有 unmount fence；其 callback 可在 `:1720-1728` 通过旧 closure 的 current 判断并枚举删除同 block 的全部当前 edit receipts，甚至不要求 key collision。

这不是 TD-6 所排除的 durable OCC：服务端 revision/CAS 无法修复客户端持久 receipt 身份碰撞。对照同文件 `createDraftClientCreateKey`（`:526-530`），03 create receipt 已明确使用 `crypto.randomUUID()`（含 fallback 随机 identity）；05.6“归家”漏继承了这条既有纪律。

修复需同时覆盖：不可复用的 receipt/mount identity；unmount 后旧 continuation 对 UI 与 storage 的零副作用；hydration 不以可重置裸 generation 判断“当前 visit”；conversion 只消费创建时快照的 exact keys。常驻 killer 必须走完整 `old held → unmount → new save → old settle → new reject/hydrate`，锁新 bytes/key 与可寻回性。

#### 05.6-HIGH-2 — 显式 Apply 在真实 focus/blur 次序中被普通 save 抢先

`NoteRuntimeDocumentLayer.tsx:53-63` 的两个按钮只调用 `event.stopPropagation()`，没有 `preventDefault()`。Text、Code、Formula editor 分别在 `TextBlockProjection.tsx:1182-1185`、`CodeBlockProjection.tsx:51-54`、`FormulaBlockProjection.tsx:177` 的 blur 上保存；因此 button mousedown 的默认聚焦会先让 editor blur，再发生 click。

两段独立 probe 将事件层与 adapter 层拼成完整反例：

1. DOM physical-order probe `review probe: keeps editor focus until the recovery action runs`：exit 1，1 failed / 1 skipped；期望 `['apply']`，实际 `['blur-save', 'apply']`。
2. adapter probe `review probe: applies the selected receipt after focused-editor blur queues a save`：先制造 selected recovery receipt，再模拟 blur save 在首个 `await` 前同步 remember 新 same-scope receipt，随后以 selected old key 调 Apply；exit 1，1 failed / 28 skipped，期望 `true`，实际 `false`。

直接调用 Apply 的代码形状本身没有绕过正门：`useNoteCanvasDataAdapter.ts:1603-1626` 先按 active note 与 exact validated key 查找，再唯一委托 `saveBlock`；后者重新经过 source-readonly、route、当前 generation/hydration、operation 与 reconciliation guards，并创建当前 receipt。问题在于 UI 物理序列使 selected key 在 click 前已被 blur save 取代，且 UI 忽略 `false` 返回值。当前 `fireEvent.click` 正控 mock 掉 writing surface，无法命中这一状态。

该序列可把用户明确选择的旧编辑替换为当前 editor 内容并让 Apply 静默失败，属于可达的数据保全错误。修复应保持 recovery action 前的 editor focus，或给 blur save 与 recovery action建立原子次序裁决；永久 test 应使用真实 focused TextFlow/editor 跑 `mousedown → blur → click`，并锁 selected edit 最终 durable 或仍可寻回。

#### 05.6-MED-1 — kind validator 可双重承认同一 raw receipt

`validateBlockEditRecoveryReceipt`（`draftBlockPersistence.ts:93-143`）正确要求 `kind === 'block_edit_recovery'`；但 03 的 `validateV2Receipt`（`:283-288`）只验证 version 与 draft shape，不拒绝显式 edit kind。`loadDraftRecoveryQueue` 在 `:326-330` 又先跑 draft validator，成功后不再分派 edit kind。

Reviewer-only hybrid test 把一份 raw 同时填入合法 edit 与 canonical draft 字段：

```text
expected: draft replayable=[]，blocked=[]，只出现在 edit queue
actual:   draft replayable=[hybrid-create-key]，blocked=[]，同时也出现在 edit queue
```

临时 test exit 1，1 failed / 35 skipped。adapter 的 mount replay effect（`useNoteCanvasDataAdapter.ts:1233-1252`）会把该 raw 送入 03 finalizer 并按 create key forget，绕过 05.6 的显式 Apply。该路径依赖畸形/污染的 sessionStorage，而非当前 producer happy path，故定 MEDIUM；但它直接否定“kind 与既有 blocked/replay 纪律一致”。修复应按显式 kind 先分派并令 validators 互斥；hybrid/unknown kind 必须零 finalizer、零 network、原 bytes 保留，并落常驻负例。
