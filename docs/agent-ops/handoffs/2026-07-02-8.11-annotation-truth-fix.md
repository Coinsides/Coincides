# Stage-4 修正：pending 真·读时派生（拆掉焊死）+ 补红线回归锁

> **背景**：Stage-4（V2.BN.8.11.15）已落地，Claude 5 维对抗核查确认**簇 1（backfill·CR-8.11.1-02）+ 簇 2（服务端闸·CR-8.11.1-04）真 PASS**、"块软删不删 range 行"也守住。**但簇 3（CR-8.11.1-03）的读时失效机制自身破了 = BLOCKER 红线数据丢失**（亲验）。本单只修这个 blocker + 其连带正确性 + 补上 40/40 绿测漏掉的红线回归锁。
> **一件事**：让 `anchor_status='pending'` 成为**纯读时展示标志**——每读重算、**永不 durable 存、永不焊死**（相对不焊）——使 trash→restore 后高亮**必然复活**；并让所有消费者一致尊重 pending。
> **过程说明**：本 spec 的根因链已由 Claude 逐行亲验（见下 file:line）。**红线回归锁是本单硬闸**——现有 40/40 绿测证明**没有它，红线改坏也测不出**。

---

## 根因链（亲验·先读）

pending advisory 被**焊进 durable 存储**，环如下：
1. **读路径塞入 DTO**：`hydrateAnnotationTruth`（annotationTruths.ts:299）`metadata: deriveRangeMetadata(range, blockStatesById)` → 读回的 range.metadata 带 `anchor_status:'pending'`。
2. **写路径 verbatim 持久化**：`replaceNoteAnnotationTruths`（:453）`metadata: stringifyJson(range.metadata, {})` → 下次任何标注保存把 pending **durable 写进** annotation_ranges.metadata。
3. **健康块不 strip**：`deriveRangeMetadata`（:274）对健康+在界块**原样返回存储 metadata**、不清 anchor_status。
→ 环：trash 块 → 读一次（pending 入 DTO）→ 任何保存（pending durable）→ restore 块 → 派生见健康块但存储里仍 pending、不 strip → **高亮永不复活（红线）**。

**核心洞**：`anchor_status`/`anchor_reason` 是**派生展示态**（"目标块此刻是否 active / offset 是否在界"），**不是 AnnotationRange 的真相**。真相只有 block_id + offset。所以它**绝不该进 durable 存储**，每次读**从 live 块态重算**。

## 修（F1 阻断 → F4 硬闸）

### F1 · pending 真·读时派生：写不存、读重算（收 CR-8.11.15-01 · BLOCKER）

**修（双向权威，两处都要）**：
1. **写边界剥离（根治）**：`replaceNoteAnnotationTruths` 持久化 range 前（:453 一带），**从 range.metadata 里删掉 `anchor_status` 和 `anchor_reason`** 再 `stringifyJson` → durable 存储**永不含**这个 advisory。（durable = 只存真相：block_id/offset/其它用户 metadata。）
2. **读边界重算（纵深 + 兼容已污染数据）**：`deriveRangeMetadata`（:238-275）**先从 base metadata 剥掉任何 `anchor_status`/`anchor_reason`**，**再**按 live 块态**重新**决定是否加 pending。即健康+在界块**必返回不含 anchor_* 的 metadata**（不管存储里有没有旧焊值）。这样即便存量 DB 已被旧版烤入 pending，健康块读出来也**必然不 pending**。
- **只剥这两个派生 key**，不动用户其它 metadata。
- 结果：trash→restore 后，健康块读 deriveRangeMetadata 重算=不 pending → **高亮复活**。

**验收**（见 F4 的红线锁）：trash 块 B（range 进 pending）→ **中间存一次标注**（这一步是暴露 bug 的关键——它会把 pending 焊进 DB）→ restore B → 断言 range **不 pending、offset 原样、可渲染**。修前 fail（pending 焊死不复活）、修后 pass。

### F2 · 所有 range 消费者一致尊重 pending（收 CR-8.11.15-02 · HIGH）

**问题**：高亮层正确抑制 pending，但同 range 的 **badge/marker/preview 仍渲染、且在 stale/归零 offset 上**：`TextBlockProjection.tsx` 的 `annotationRangesForTextUnit`（269-274）、`annotationStartOffsetInTextUnit`（283-293）、`unitAnnotations`（957-963）、`previewFromRanges`（276-281）**都不调 `annotationRangeIsPending`**。

**修**：这些消费路径**统一过 `annotationRangeIsPending`**（pending → 不产 badge/marker/preview，或产"needs-review"占位而非画在错坐标）。**并核查其余读 range 的路径**：导出预览（exportPreviewService）、AI 快照（canvasAiTreeService）、搜索——**任一喂 stale range 给用户或 AI 的都要过 pending 门**（pending range 不进导出/AI/搜索，或标注为未锚定）。

**验收**：pending range → 断言无 badge/marker 渲染、不进导出/AI 快照。修前 fail（badge 在 offset 0 画出）、修后 pass。

### F3 · overlap 失效留 re-anchor 路径（收 CR-8.11.15-03 · MED）

**问题**：`rangeRebaseService.ts:176-183` overlap 分支**永久 null offset**（连"正常编辑只是与 range 重叠"也一刀 null）→ 叠加 F1 前的烤死，被合法编辑穿过的 range **永不能重锚**。

**修**：overlap 失效时**保留 re-anchor 依据**——把 pre-edit 的 `start/end_offset` + `range_text_cache` 存进 `annotation_ranges.metadata` 的 advisory（如 `pre_edit_offsets`），offset 仍 null（不按错坐标画），但保留"这段原文是什么、原在哪"以便未来 re-anchor（文本改回/匹配时可复位）。**注意**：这个 advisory 是**真相性 provenance（用户原始意图），可 durable 存**——与 F1 的 `anchor_status`（派生展示态、不可 durable）区分开。本单不必实现自动 re-anchor 引擎，只**不销毁重锚依据**。

**验收**：overlap 失效的 range → 断言 offset null（不渲染）但 metadata 存了 pre_edit_offsets + range_text_cache 未丢。

### F4 · 红线回归锁 + 测试收紧（收 CR-8.11.15-04 · HIGH · 本单硬闸）

**问题**：红线 round-trip **零测试**；活探把 trash 分支改坏，cutover **40/40 仍全过**。幂等正控只比 parent/child triple、漏 range metadata。

**修**（`server/src/__tests__/v2CanvasPersistenceCutover.test.ts`）：
1. **红线锁（必须）**：seed 真 note_block + text_span range（在界 offset）→ `UPDATE note_blocks status='trashed'` → listAnnotationTruths 断言 range **pending**、**行仍在** → **replaceNoteAnnotationTruths 再存一次全套标注**（复现焊死路径）→ `UPDATE status='active'`（restore）→ listAnnotationTruths 断言 range **不 pending、offset 原值、可渲染**。**这条修前必 fail（F1 前 pending 焊死）、修后 pass。**
2. **offset_out_of_bounds 锁**：range end_offset > 块 plain_text.length → 断言 pending；块文本改够长 → 断言不 pending（读时重算）。
3. **幂等正控扩到 range metadata**：F1 后，PUT→GET→原样再 PUT → 断言 **range.metadata 无 anchor_* churn**（durable 永不含）。
4. **收紧现有**：dup-id 断言含**两个 note id**；服务端闸测试加 `firstSave.length===N`（rows-not-dropped 显式计数）。
5. **消费者锁（F2）**：client 若有可测面，断言 pending range 不产 badge/不进导出/AI。

**验收**：上述 5 条测试存在并通过；活探（把 F1 的写剥或读重算去掉）→ 红线锁 fail。

## 明确采用的判断（Claude 定）

- **`anchor_status`/`anchor_reason` = 纯读时展示态、绝不 durable、每读从 live 块态重算**（相对不焊的正解）。写剥 + 读重算双向权威。
- **区分两类 metadata**：`anchor_status`（派生展示态·不可存）vs `pre_edit_offsets`/`range_text_cache`（用户原始意图 provenance·可存）——F3 保后者、F1 清前者。
- **红线锁必须"中间存一次"**才暴露焊死——否则测试仍会假绿（这正是 40/40 漏掉它的原因）。
- **不删任何 annotation/range 行**（红线）——pending/null-offset 都是读时态，行永在。
- 存量 DB 若已被旧版烤入 pending：F1 的读重算使其在健康块上自动失效、下次保存被写剥清掉——**无需专门 repair 迁移**（如要更干净可加一次性 UPDATE 清 annotation_ranges.metadata 的 anchor_*，非必须）。

## 不做什么

- 不建自动 re-anchor 引擎（F3 只留依据）。不做跨 block split/merge/reorder 结构 rebase。
