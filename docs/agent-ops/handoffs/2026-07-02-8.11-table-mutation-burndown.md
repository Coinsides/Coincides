# 8.11 收口前 · 第 3 份 burn-down：表格 mutation 完整性（删行列纳入 undo/confirm）

> **前置**：Stage-1（V2.BN.8.11.12）烧 4 HIGH（数据丢失 + AI 污染）；Stage-2（V2.BN.8.11.13）烧 block-backed-shape 生命周期 6 MED + 残尾锁。本单烧**下一个、也是唯一还开着的「数据丢失·产品红线」项**：`CR-8.11.8-01` 删表格行/列不可逆毁数据、无 undo。按 register 自己的排查优先级（§排查建议 priority-2），这是清完数据丢失 HIGH 后最该先填的坑。
> **一件事**：把表格编辑纳入**和画布其它部分同等的 undo/confirm/commit 保障**，消灭"具名销毁却完全不可恢复、而画布他处有 undo"这条红线。
> **过程说明（诚实标注）**：本 spec 的 undo-架构设计与干扰分析由 Claude 主循环亲读代码推演（多 agent 对抗核查因 session limit 未跑）。**验收测试是唯一硬闸**。Claude 会在落地后核 diff。

---

## 核心判断（先读）

画布对 **layout / block create / block trash** 有 undo（`usePlacementHistory` 的 `RuntimeHistoryEntry` 三型 + Ctrl+Z），但对 **table 结构 mutation 零覆盖** → 用户"Ctrl+Z 能救"的心智对表格**静默失灵**。而 `deleteTableRow/Column`（tableObjectService.ts:263-295）是**硬 `.filter()` 掉行列及其 cells**、无 trash/无 restore → **比 demote 更不可恢复**。红线 = 具名销毁命令 + 完全不可恢复 + 画布他处偏偏有 undo。

**修法脊椎**：给 `RuntimeHistoryEntry` 加一个 `structuredMutation` 型（承载 before/after payload），让表格结构 mutation 走和 layout 同一条 undo/redo 管线；再对非空行/列删除加确认 floor（对齐 Stage-2 demote 的 (B) 语义）。

---

## 判断点（Henry 翻牌 ready 前请裁决）

1. **【必裁】删非空行/列的确认 UX。** 三选一（可组合）：
   - **(A) 只加 undo（Ctrl+Z 可撤）**：最小、对齐"画布他处有 undo"的一致性；删了能撤回。
   - **(B) 只加确认对话框**：删非空行/列前 `window.confirm`；空行/列不确认（对齐 Stage-2 demote 空分支）。
   - **(C) 两者都加（推荐 ✅）**：undo 是**必须**（红线本质=撤销心智失灵）；confirm 只在**非空**行/列（有任一 cell 含文本）作软 floor，避免误删又不烦高频删空行。
   - **我的推荐 = (C)**：undo 兜底 + 非空确认。若你嫌确认烦，退 (A) 纯 undo 也满足红线。
2. **【知会】undo 与 cell 编辑的边界**：Ctrl+Z 在 textarea 内被 `isEditableDomTarget` 挡住（historyService.ts:19-22）→ 表格结构 undo 只在**未聚焦 cell**时触发（右键删行列后焦点已离开 cell，正常可用）；cell 内 Ctrl+Z 仍是浏览器文本 undo。此为期望行为、无需改。

## 簇 T — 表格 mutation 完整性

### T1 · 表格结构 mutation 纳入 undo + 非空删除确认（收 CR-8.11.8-01 · 产品红线）

**问题**：
- `RuntimeHistoryEntry`（historyService.ts:4-7）只有 `layout | createdBlock | trashedBlock` 三型，**无 structured/table 型**。
- `deleteTableRow/Column`（tableObjectService.ts:263-295）纯函数 `.filter()` 删行列+cells、返回新 payload；调用点（commandSurfaceService.ts:458-475 / NoteWritingSurfaceLayer 表格右键 handler）直接持久化新 payload，**旧 payload 不入任何 history**。
- 结果：Ctrl+Z 对表格删行列/结构变更完全无效。

**修**：
1. `historyService.ts`：给 `RuntimeHistoryEntry` 加第 4 型
   ```ts
   | { type: 'structuredMutation'; objectId: string; before: <StructuredPayload>; after: <StructuredPayload> }
   ```
   （payload 类型用 table 的 `TableStructuredPayload`，或更泛的 structured payload 以备未来 kanban/chart。）
2. `usePlacementHistory.ts`：
   - 加 `pushStructuredMutationHistory(objectId, before, after)`（走现有 `pushHistoryEntry`）。
   - **`undoRuntimeHistory` 与 `redoRuntimeHistory` 都必须显式处理 `structuredMutation` 分支**：undo → re-persist `before`；redo → re-persist `after`。**⚠ 关键干扰点**：现两函数用 `if(layout)… if(createdBlock)… else 当 trashedBlock` 的隐式兜底（usePlacementHistory.ts:60-93 / 106-143）——**加型后必须在 trashedBlock 兜底之前插入显式 `if(type==='structuredMutation')`，否则表格 undo 会被误当块恢复**。
   - re-persist 需一个新回调 `persistStructuredObject(objectId, payload)`（类比 `persistLayoutSnapshot`），由 controller 从表格保存路径注入；**re-persist 期间 `historyBusyRef` 已置真、不会二次入栈**（沿用现有防环）。
3. 调用点（表格删行列/加行列/其它结构 mutation 持久化处）：mutation 前捕获 `before`=当前 payload、算出 `after`，持久化 `after` 成功后 `pushStructuredMutationHistory(objectId, before, after)`。**建议只对结构性变更入栈**（删/加行列），cell 文本编辑不入（那是文本 autosave、量大且 textarea 内已有浏览器 undo）。
4. **确认 floor（按判断点 1=C）**：删行/列前判断该行/列**是否非空**（任一 cell trim 后有文本）；非空 → `window.confirm`（"删除此行/列？可 Ctrl+Z 撤销。"）；空 → 直接删。`historyService` 的 `deleteTableRow/Column` 是纯函数、确认放在**调用点**（commandSurfaceService / layer handler）。

**验收**（修前 fail / 修后 pass）：
- 删一行有内容的表格 → Ctrl+Z → 断言表格 payload 恢复到删前（行+cells 回来、by-value）。再 Ctrl+Y/Shift+Ctrl+Z → 断言重新删除。
- 单测：`pushStructuredMutationHistory` 后 `undoRuntimeHistory` 调 `persistStructuredObject` 用 `before`；`redoRuntimeHistory` 用 `after`；`structuredMutation` **不**落进 trashedBlock 分支（断言不调 restoreBlock/trashBlock）。
- 删非空行 → 断言弹确认、取消则 payload 不变；删空行 → 无确认直接删。
- 删到 1×1 floor（rows/cols ≤1）仍被 `deleteTableRow/Column` 的 `<=1 return` 守住（回归保持）。

### T2 · Esc-cancel 不再被 blur-save 覆盖（收 CR-8.11.8-02）

**问题**：cell 编辑 Escape → `onCancelCellEdit` 卸载 textarea；同一 textarea 的 `onBlur=commitEditingCell`（TableObjectLayer.tsx:98-107,228-229 / NoteWritingSurfaceLayer.tsx:3340）在卸载时触发 native blur → `commitEditingCell` 只看 stale-closure 的 `editingCell`（卸载前仍真）、**无 cancel-guard** → 把被取消的 draft 当 autosave 存回，盖掉丢弃意图（intent 被静默焊掉）。

**修**：加 `cancelledRef`（或等价一次性标志）：Escape 时置真并令其**权威**；`commitEditingCell` 开头若 `cancelledRef` 为真则**早返回**、不 commit，然后清标志。确保 Escape > blur。

**验收**：修前 fail / 修后 pass：进 cell 编辑、改文本、按 Escape → 断言 cell 文本**未变**（draft 被丢弃），且无 commit 调用；正常 blur（非 Escape）仍 commit。

### T3 · table mutation 客户端单测（收 CR-8.11.8-03）

**问题**：`tableObjectService.ts` 的 normalize/addRow/addColumn/deleteRow/deleteColumn/updateCell **零单测**；index 重编号 + cell 回填只经未测的 normalize；server 测按值断言但从不跑 client add/del/edit → client index 数学回归会静默上线。

**修**：加 `tableObjectService` 按值单测：addRowBelow → rowCount+1 且新 cell 空；deleteColumn → 保留其余列文本且 columnIndex 连续；updateCell → 只改一格；≤1 floor 双侧（deleteRow/Column 在 rows/cols=1 时 no-op）；normalize → jagged/重复(row,col)/索引不连续被修复。**这也是 T1 undo before/after 的回归底座**。

**验收**：新单测存在并通过；故意破坏一处 index 数学（如 deleteColumn 不重编号）→ 对应断言 fail。

### T4 · 结构 mutation / 开菜单前提交在编辑的 cell（收 CR-8.11.8-04 · LOW 连续项）

**问题**：in-flight cell draft 在右键删行列时静默丢：`onTableContextMenu → setEditingTableCell(null)`（NoteWritingSurfaceLayer.tsx:3353 / TableObjectLayer.tsx:213-219）不 commit；后续 add/del 在无 draft 的 payload 上跑 → 正打的字无反馈消失。

**修**：开表格上下文菜单 / 执行结构 mutation 前，先 commit 当前在编辑的 cell（走 T2 修好的 commit，非 cancel 路径）。与 T2 的 cancelledRef 不冲突（这是正常 commit，不是 Escape）。

**验收**：修前 fail / 修后 pass：cell 里打字未 blur → 右键删**另一**行 → 断言正打的 cell 文本被保留（已 commit 进 payload），而非丢失。

## 明确采用的判断（Claude 定，留余地给 Codex 依现状调）

- **T1 undo 型必须在 undo 和 redo 两函数里都显式处理、置于 trashedBlock 隐式兜底之前**（usePlacementHistory.ts 现结构会误吞）。这是本单最容易踩的坑。
- **before payload 在调用点捕获**（mutation 前的当前 payload），不是在 history 里反算。
- **只结构性 mutation 入 undo 栈**（删/加行列），cell 文本编辑不入（避免栈爆 + textarea 已有浏览器 undo）。
- **确认放调用点**、`deleteTableRow/Column` 纯函数不动（保持可测）。
- **1×1 floor 与现有 `<=1 return` 保持**，不因加 undo 而放松。
