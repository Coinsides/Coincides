# 8.11 收口前 · 第 5 份 burn-down：image asset 生命周期 / refcount GC

> **前置**：Stage-1（8.11.12）/ Stage-2（8.11.13）/ Stage-3（表格 mutation）/ Stage-4（annotation 真相，另一份 handoff）。本单烧 **image asset 生命周期的 MED**（CR-8.11.7-01/02 + CR-8.11.9-05；CR-8.11.7-04 作 UX rider·倾向 defer）。
> **一件事**：让 image asset 的生命周期自洽——**删图真正释放它的字节**（不留孤儿 asset 行 + 磁盘 blob），**上传未用不泄漏**，且 **duplicate 共享 asset 时按 refcount 安全 GC**。这是"删即删"成熟度的地基（data-residue 完整性）。
> **过程说明（诚实标注）**：本 spec 基于 Claude 主导的多 agent map→design→critique（逐行核准现状 + 对抗核查）。critique 判**设计根本可靠**、Cluster A 一个 commit 可 ship；已融入其两点校正。**验收测试是唯一硬闸**；Claude 落地后核 diff。

## 核心判断（先读）

**一个权威的 asset 生命周期 choke point**：在 `server/src/services/canvasAssets.ts` 加 `releaseAssetReference(db, userId, assetId, excludeObjectId)`：
- **COUNT** 该 asset_id 的 live `image_object_extensions` 行、**排除正在删的对象**；
- **归零** → 删 `canvas_assets` 行 + best-effort unlink blob（storage_key→路径，吞 ENOENT）；
- **非零** → 什么都不做（共享 asset 存活）。

**唯一调用者** = image KIND_HANDLER 的 `cleanupOnDelete`（现 image handler 在 canvasObjects.ts:1334-1343 **没有**；shape 的在 1320-1322 是模板），由既有通用钩子 `handler?.cleanupOnDelete?.(...)`（canvasObjects.ts:1936，在 deleteCanvasObject 的事务 1911 内、**在 canvas_objects DELETE 1947 之前**）派发。

**为什么 exclude-self 是必需而非防御**（critique 已验证）：`foreign_keys=ON`（init.ts:30）下钩子 1936 在 DELETE 1947 **之前**触发 → 此刻 extension 行（ON DELETE CASCADE, 041:33）**还在** → COUNT 必须排除正在删的对象，否则永远 remaining≥1、永不 GC。

**相对不焊绝对**：refcount 是**读时 COUNT-at-delete**、绝不焊成 counter 列。asset 的"还有没有人用我"是 context-relative（随每次 duplicate/delete/cascade/未来 Agent 路径变），必须从 live extension 行读；counter 列会在任何绕过它的路径（bulk delete、FK cascade、Agent 写）desync → 静默孤儿 blob 或过早删仍被引用的 blob（违"心爱之物不可凭空消失"）。**COUNT 按 user 作用域、不按 note**（duplicate/AI 可把同 asset 放到别的 note，note-scope 会过早删共享 blob）。

## 判断点（Henry 翻牌 ready 前请裁决）

1. **【必裁·CR-8.11.7-02 sweep 范围】** 上传的 blob+asset 行写在 image 对象创建**之前**（canvasAssets.ts:106/111），取消/替换/导航离开留**零引用**孤儿（refcount 永远碰不到，因为它们没 extension 行、且从不 deleteCanvasObject）。**(A) 本单落"共享 unlink primitive"、把实际 sweep 推到 Stage-5 尾或跟进单**（我荐：foundation 期单用户低量，明确记着别静默留）；**(B) 本单连 sweep 一起做**（age-threshold 扫零引用 asset）。我荐 **(A)**：primitive 先就位，sweep 可紧跟。
2. **【必裁·CR-8.11.7-02 机制】** sweep 用 **(A) age-threshold 定期/机会扫**（低风险、复用 unlink primitive）vs **(B) defer-write / 单事务 upload+commit 端点**（更干净但重塑 upload API）。我荐 **(A)** 配 Cluster A 的 unlink primitive。
3. **【可裁·CR-8.11.7-04 上传失败静默】** 我荐 **defer 到统一友好化 pass**（register line 278 的反馈族，🅱）。若要即时 quick-win：只落**客户端预校验 + 通用 toast**（>10MB / 非白名单 mime，镜像 server gate），**loading placeholder 整个 defer**（且若建、必须是 transient runtime 态，绝不持久化成 CanvasObject/asset 行——否则正好制造 CR-8.11.7-02 孤儿）。
4. **【知会·非阻断·critique 校正】bulk-delete 洞是"未来 gap"非"当前泄漏"**：删 note 是**软删**（routes/notes.ts:193-201 UPDATE status='trashed'），**server/src 里没有 hard `DELETE FROM notes`、也没有 account/user 删除路由**（已 grep 验证）→ notes/users 的 ON DELETE CASCADE **今天永不触发**、refcount 完整、无 blob 被 bulk-delete 孤立。**本单的 per-object refcount 对今天存在的每条删除路径都完整。** 只在**未来**有人建"回收站硬清"或"账号删除"时，须让那条路径复用 `releaseAssetReference` 的 unlink primitive 做 per-note/per-user teardown——记为 tracked gap、**不膨胀 Stage-5**。

## 簇（A ship together；B primitive-now-sweep-later；C defer）

### 簇 A · refcount cleanupOnDelete + 共享不变量（收 CR-8.11.7-01 + CR-8.11.9-05）· 一个 commit

**问题**：删 image 对象只 CASCADE 掉 extension 行；`canvas_assets` 行 + 磁盘 blob **永久孤儿**（image handler 无 cleanupOnDelete；asset_id ON DELETE RESTRICT 041:38）。且 **duplicate 复用同一 asset_id**（objectInspectorService.ts:342 spread）→ N 对象→1 asset → GC **必须 refcount**（天真删会 RESTRICT-fail 或孤立幸存副本）。

**修**（一个 commit）：
1. `server/src/services/canvasAssets.ts`：export `releaseAssetReference(db, userId, assetId, excludeObjectId)`：
   ```
   const remaining = db.prepare('SELECT COUNT(*) AS n FROM image_object_extensions WHERE user_id=? AND asset_id=? AND object_id != ?').get(userId, assetId, excludeObjectId).n;
   if (remaining > 0) return;
   // 读 storage_key → DELETE canvas_assets WHERE id=? AND user_id=? → best-effort unlinkSync(join(CANVAS_ASSET_DIR, storage_key))，catch 非 ENOENT 记日志吞掉
   ```
   （`unlinkSync` 从 node:fs 引；existsSync/createReadStream 已在引。）**COUNT 用 user 作用域、不带 note_id**——加**显式不变量注释**："故意 user-scoped、非 note-scoped，asset 跨 note 经 duplicate/AI 共享"，防未来有人加 note_id 过早删。
2. `server/src/services/canvasObjects.ts`：给 image KIND_HANDLER（1334-1343）加 `cleanupOnDelete`（镜像 shape 1320-1322）：读本对象 extension 的 asset_id（`SELECT asset_id FROM image_object_extensions WHERE object_id=? AND user_id=?`）→ `releaseAssetReference(db, userId, assetId, objectId)`。**必须传 excludeObjectId=本 objectId**（钩子在 DELETE 前跑、extension 行还在）。全在 1911 事务内。
3. **duplicate 共享不变量守护**（CR-8.11.9-05）：`objectInspectorService.ts` image 分支（336-350）spread 处（342）加注释"**故意复用 assetId + 共享 blob**（廉价复制=工具/手艺意图，服务端 refcount 管生命周期，**勿深拷成新 asset**）"；`canvasEngineModelContractCheck.ts` 加断言：image duplicate draft 的 `imageObject.assetId===输入 assetId`（同 asset）且 **新 objectId/imageObjectId**——把"共享 by design"锁进契约，防未来有人把 duplicate 改成深拷（翻倍磁盘 + 破坏廉价复制）。

**验收**（critique 校正：blob 断言必须有**真文件正控**）：
- 单引用：save image 对象 → deleteCanvasObject → 断言 `canvas_assets` 行**没了** + extension 行没了。（**FLIP 现有 490-497 的反向断言**——今天它断言 asset 存活。）
- **blob 正控**（否则 seedCanvasImageAsset 只写 DB 行、不写文件、unlink 断言空过）：测试先在 `join(CANVAS_ASSET_DIR, storage_key)` **真写一个文件**（临时 CANVAS_ASSET_DIR 经 env），断言删前 `existsSync===true`、删末引用后 `===false`。
- **duplicate 负控**：image A（asset X）+ duplicate B（复用 X，断言两 extension 行指 X、1 个 asset 行）→ deleteCanvasObject(A) → 断言 **asset X 还在 + blob 还在**（B 持有）→ deleteCanvasObject(B) → 断言 asset X 行没了 + blob unlink。+ 契约断言 image duplicate 复用 assetId、mint 新 objectId。

### 簇 B · 零引用孤儿 sweep（收 CR-8.11.7-02）· primitive 现落、sweep 按判断点

**问题**：`createCanvasImageAssetFromUpload`（canvasAssets.ts:106/111）在任何 image 对象 commit **之前**写 blob+asset 行；取消/替换/导航离开 → **零 extension 行**孤儿 → refcount-at-delete 永远碰不到（从不 deleteCanvasObject）。

**修**：按判断点 1/2。**推荐**：本单落 Cluster A 的共享 unlink primitive 即够；sweep 实现（若本单做）用 age-threshold：
```
DELETE FROM canvas_assets WHERE user_id=? AND kind='image' AND created_at < datetime('now','-N hours')
  AND id NOT IN (SELECT asset_id FROM image_object_extensions WHERE user_id=?)
```
逐个 best-effort unlink 被扫的 storage_key（复用 primitive）。age 阈值护住 upload→commit 在途窗口。若本单不做 sweep，**显式记着这个泄漏、别静默留**。

**验收**（若本单做 sweep）：createCanvasImageAssetFromUpload →（从不建 image 对象）→ age=0 跑 sweep → 断言 asset 行没了 + blob unlink。护栏：age<阈值的零引用 asset **不被扫**（护在途 commit）。

### 簇 C · 上传失败静默死路（CR-8.11.7-04）· 倾向 defer

**问题**：`handleImageFileChange`（NoteWritingSurfaceLayer.tsx **1451-1460**，critique 校正行号）的 `.catch` **只 console.error**（**1457-1459**）→ 选 renamed/非图/超 10MB → server 400 被吞、用户啥都没看到。

## 明确采用的判断（Claude 定，含 critique 校正）

- **refcount = COUNT-at-delete、exclude-self、user-scoped、无 counter 列**（相对不焊）。
- **blob unlink = best-effort、吞 ENOENT、绝不回滚/失败删除事务**（asset 行是权威 provenance、blob 是派生；崩溃中途留孤儿 blob 是良性磁盘泄漏，绝不让它 fail 事务）。
- **duplicate 共享 asset by design**——契约测试锁死、勿深拷。
- **blob 测试必须真写文件**（否则 unlink 断言空过）；**duplicate 负控**必须有。
- **bulk-delete 洞是未来 gap 非当前泄漏**（删 note 软删、无 hard-delete/account-delete 路由）——记着、不膨胀本单。
- 顺序：Cluster A 一个 commit（含校正测试）→ B primitive 现落 sweep 后议 → C defer。

## 不做什么（本单边界）

- **不加 canvas_assets refcount counter 列**（COUNT-at-delete only）。
- **不改 migration 041 的 asset_id ON DELETE RESTRICT**——留作 guard-rail（refcount 只在归零删行、RESTRICT 永不触发、当防御纵深）。
- **不深拷 duplicate 的 asset**——故意共享。
- **不持久化任何 loading placeholder**（若建=transient runtime 态）。
- **不做 note/user 级 bulk asset teardown**（今无 hard-delete 路径、unreachable）——未来建硬清/账号删时再复用 primitive。
- **不做** export 缺席（CR-8.11.7-03）、死的 401 blob fallback（CR-8.11.7-07）、magic-byte sniff（CR-8.11.7-05，与本单白名单协调但另 track）——归后续/友好化。
- 不推进 ContentGroup / Source / Agent / Relation。不整理 dirty workspace。
