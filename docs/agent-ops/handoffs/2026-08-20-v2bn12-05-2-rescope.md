## 设计裁决(Fable,本单的核心不是修 finding,是换方案)

#### 05.2-HIGH-1 — generation receipt 铸造过晚，A→B→A 发生 ABA

`useNoteCanvasDataAdapter.ts:537-551` 确实把 `currentNote = note` 绑定到 callback closure，但 `requestGeneration = routeRequestGenerationRef.current` 在 `:544` 的 callback 调用时才读取。回到同 id 的 A 后，`:543` 的 noteId 相等，`:545-550` 又拿新 generation 与自身比较，故 `:552/:566/:572/:587/:593/:598` 全部通过。

Reviewer sequence：首次 A hydrate并捕获 `saveA` → route B → route A并 hydrate `newerA` → 调首次访问留下的 `saveA(staleA)`。期望零 PUT且 snapshot 保持 `newerA`；实际向 `/annotation-truths/by-note/A` 发出一笔 stale full-array PUT，测试 exit 1。这个 carrier 在 production 可达：`NoteWritingSurfaceLayer.tsx:2146-2185` 的 range edit先 `await onSaveBlock(...)`，随后无论旧 block save返回什么都继续调用闭包里的 `onSaveAnnotationTruths(editResult.next_annotations)`。hold首次 A block PUT，期间 A→B→A并形成新版 A，再释放旧请求，即会调用旧 annotation callback。

建议修法：callback/operation 创建时绑定不可变 `{ noteId, generation }` receipt，让旧 callback永久携带旧 generation；不得在调用体内从 ref现取。range-edit continuation还应检查 matching block save receipt。补真实 handler 的 A→B→A + reload killer，断 stale annotation零 PUT、当前 A snapshot与durable truth均不变。

#### 05.2-HIGH-2 — 全局 tail 吞掉新 note 的有效普通保存

adapter 只在 `useNoteCanvasDataAdapter.ts:357` 初始化一个 `annotationSaveTailRef`，所有 note 的保存都在 `:613-618` 串到该 Promise；route变更既不分桶，也不让新 note 的首笔 publish立即开始。publish直到旧 tail settle后才在 `:565-566` 复核 route。

Reviewer sequence：A save已进入 PUT并 hold → hydrate B → B 在当前 route调用普通 `saveAnnotationTruths(editB)` → 立即离开 B → resolve A并等待两个 save。B调用时是有效的人类意图，却被 A tail阻塞；真正运行时已 stale，于是静默返回。期望 PUT receipts 为 `[A, B]`，实际只有 `[A]`，无 error/toast。真实击键由 `NoteWritingSurfaceLayer.tsx:3715` 以 `void handleBlockTextFlowChange(...)` 进入共用正门，正门在 `useBlockTextFlowEditController.ts:77` await普通 annotation save；该 Promise不会锁住路由。若正文另行保存，就重新形成正文/annotation半提交；即使没有正文 PUT，B annotation也会在 reload丢失。

现有 shared A→B test在释放 A后才 hydrate/保存 B，恰好绕过该状态。修复需把 serialization 至少按 note/route receipt分桶，并让无本 note前序的首笔 publish在enqueue时开始；同 note真正 stale的queued A仍须零 PUT，但不能让无关 A tail把有效 B拖到失效后再静默丢弃。补 `A held → B edit → leave B → release A` killer，断 B恰一 PUT且旧 response不污染当前 snapshot。

#### 05.2-HIGH-3 — draft Slash没有随 durable owner reconciliation迁移

`useDraftBlockController.ts:536` 建立 `draftOwnerReconciliation`，`:402-405` 的 `handleDurableFocusReceipt` 随后清 local draft；这条状态转移没有迁移或关闭 Slash session。`useSlashCommandController.ts:545-557` 的 durable `handleBlockKeyDown` 对 Escape仅在 `slashTarget?.target === 'block'` 时执行 rollback。session仍是 `target:'draft'` 时，Escape直接返回。

隔离 runtime probe按常见快响应顺序执行：draft输入 `draft /hea`并打开 Slash → create/placement立即成功 → 等到 draft→block receipt → 交付 durable focus receipt并聚焦 block → 在 durable textarea按 Escape。期望 event被prevent且session关闭；实际 `prevented=false`，exit 1，创建出的 durable block仍含 `/hea`。现有 R1 integration只覆盖相反顺序“held create → 先 Escape → 后 receipt”，所以没有发现该洞。

建议在 reconciliation 时以 canonical receipt把活跃 draft session迁移为 block owner/range，或在切 owner前按同一普通正门完成 rollback；不得留下旧 draft target。补“快 create/reconcile → Escape”及“reconcile → disabled/annotation/missing”生命周期矩阵，并断 durable TextFlow与annotation inverse rebase一致。
