### 1. Findings

#### MED-1 — v1→v2 migration 在 v2 写失败后仍删除 v1，下一次 reload 丢失 recovery receipt `[技术缺陷][数据安全][恢复路径][状态转移后]`

`draftBlockPersistence.ts:79-85` 的 `writeStorageEntries()` 吞掉 `setItem/removeItem` 异常且不返回写入结果；`loadDraftRecoveryQueue():219-228` 先尝试写 v2，随后不验证成功便把 v1 改写为 `retainedLegacy`。canonical-only 队列的后一步就是删除 v1。`rememberDraftRecoveryReceipt():247-258` 也采用同型“先写新 key、再清旧 key”但不核验前一步的接线。现有 happy-path 正控 `draftBlockPersistence.test.ts:100-139` 只能证明 storage 正常时升级成功；它没有回答写失败后的下一状态。

Reviewer 用 `esbuild` 在内存中加载当前 production 模块（`write:false`），注入一个仅对 v2 `setItem` 抛 `Error('quota')` 的 Map-backed `sessionStorage`。先放入完整 canonical Page v1 receipt，再顺序执行 `loadDraftRecoveryQueue()` → recovery finalizer 返回 `false` → 模拟 reload 再次 `loadDraftRecoveryQueue()`。直接输出为：

```json
{"failedMigrationThenFailedReplay":{"firstReplayable":["canonical-key"],"recovered":[],"v1":null,"v2":null,"afterReloadReplayable":[],"afterReloadBlocked":[]}}
```

第一次 mount 只在内存中暂时还有正文；网络 recovery 失败后，下一次 reload 两个 storage key 都已没有收据，既不 replayable 也不 blocked。这违反 D1“任一步失败保留 receipt、成功才删除”以及本单 Result §R1 的“canonical v1 可安全升级”。该状态在 storage 接近 quota 时尤其现实：迁移暂时需要同时容纳 v1 与 v2，v2 写失败后当前代码反而释放唯一 v1。

建议：让 storage write 返回可验证的成功结果（至少捕获异常并 read back/比对目标 bytes）；只有确认 v2 已持久化后才允许清 v1。`remember` 的 same-key replacement 同样应用该顺序。补常驻 oracle：v2 `setItem` 抛错时 v1 bytes 不变；随后 replay 失败并再次 load 仍能得到原 receipt。

#### MED-2 — owner validator 把无 frame/boundary 的 `canvas_workspace/crossing` raw v1 当成 canonical 并进入写链 `[技术缺陷][owner authority][恢复路径]`

`hasValidCanonicalOwner()`（`draftBlockPersistence.ts:88-106`）在没有 `frame_id` 时只检查 `surface === 'canvas_workspace' && !pageBoundary`，没有检查 `boundary_role`。因此 `crossing`、`frame_id=null`、`pageBoundary=null` 的矛盾 tuple 会经 `upgradeV1Receipt():146-151` 升成 v2；`finalizeDraftRecoveryReceipt():286-295` 又复用同一个宽松 validator，无法在写前拦住。

{"ambiguousCrossingWrite":{"replayable":["ambiguous-crossing"],"blocked":[],"writes":[{"stage":"create","frame_id":null,"boundary":null,"boundary_role":"crossing"},{"stage":"placement","frame_id":null,"boundary":null,"boundary_role":"crossing"},{"stage":"latest","frame_id":null,"boundary":null,"boundary_role":"crossing"}]}}

这不是只停在 parser 的潜在问题：adapter 的 recovery finalizer 在 `useNoteCanvasDataAdapter.ts:950-956` 把该 layout 交给 placement save；`canvasObjectRepository.ts:92-97` 再调用 `buildLayoutPayload()`。没有 boundary 时 classifier 只能把显式 workspace 回退为 `outside/null`，原 `crossing` owner 已不可恢复。它直接反证工单 §R1.c、Result §R1 与 §三个负例所称“无法确定 owner 的 raw v1 均 fail closed”。现有 `draftBlockPersistence.test.ts:69-98` 只覆盖完全没有 surface/coordinate 的窄 ownerless raw，未覆盖三态 tuple 内部自相矛盾。
