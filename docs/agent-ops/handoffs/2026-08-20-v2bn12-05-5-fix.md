#### 05.5-HIGH-1 — reconciliation GET 的 note 绑定错误，A 内容进入可见 B

`reconcileIssuedSave` 在 `useNoteCanvasDataAdapter.ts:1426-1429` 从 **GET 发起时的当前 route** 构造 `reconciliationRouteReceipt`，但 `:1434` 实际读取的是 save 创建时冻结的 `requestedNoteId`。因此旧 A save 在 B 上 settle 时，fence 在 `:1446-1454` 会诚实地判定“B 仍 current”，随后 `:1455-1458` 把 GET 到的 A block 写进 B 的 `blocks`。

Reviewer-only 确定性序列：

```text
A(g0) hydrate server-old → save user-edit held
→ B(g1) hydrate为空
→ 仍停在 B 时旧 A PUT pre-commit reject
→ reconciliation GET /notes/A/blocks 返回 A server-old
→ B 的 blocks 被注入 A block
→ 返回 A(g2)
```

隔离 probe `keeps an old A settlement out of visible B and preserves its edit for return to A` exit 1，1 failed / 26 skipped；唯一对象断言精确收到：

```text
visibleBCrossPolluted: true       (expected false)
userCanRecoverOrWasNotified: false (expected true)
```

这不是“旧 generation 不复活”的允许形态：它把 requested A 与 visible B 混成同一 UI truth。修复必须让 reconciliation receipt 同时绑定 `requestedNoteId + creation generation`；不满足该绑定的 GET 对任一当前 note 都必须是零 UI mutation。

#### 05.5-HIGH-2 — “不复活”以销毁唯一恢复载体实现，旧编辑不可寻回

receipt 创建后只进入 adapter 内存 map（`:1362-1379`）。旧 A save 在 B 上 settle 时：

- `restorePendingEdit` 因 creation route 已过期在 `:1380-1383` 返回 false；
- success/info 的两支条件在 `:1519-1527` 都不成立，reject/error toast 在 `:1561-1562` 也因 A 不可见而不进；
- 返回 A 后 hydration 在 `:582-586` 看到 generation 不同，静默 `delete(blockId)`；
- 全 production 消费面没有 sessionStorage、recovery UI、copy/export 或“稍后恢复”入口。`BlockSaveOutcome.recoveryReceipt` 虽返回给 caller，但 Draft/Slash/rollback/Surface 等普通消费者只按 status 分支，随后丢弃 receipt。

隔离 probe `keeps a rejected old A edit recoverable after A to B to A` exit 1，1 failed / 25 skipped；`durable user edit || local draft || recovery storage` 合取的期望为 true，实际 false（临时 test line 613）。另一个在既有 A→B→A case 尾部追加同一可寻回合取的 probe 也稳定红：expected true / received false。

因此 Result §R1.b 的“旧 generation 不复活内容，但返回 creation-bound receipt，并在该 note 再可见时给提示”只覆盖“先回 A、后 settle”的窄时序；更自然的“仍在 B 时 settle、之后回 A”没有提示且删掉唯一副本。正确语义不是自动复活旧内容，而是把 receipt 转成跨 generation、用户可见且可选择恢复/复制/放弃的载体，并在明确消费或 durable match 前不得静默删除。

#### 05.5-HIGH-3 — stale GET 越过 fence 删除新 carrier

UI 写入 fence 位于 `:1446-1458`；pending map 的读取、匹配和删除位于 `:1460-1475`，完全没有复用 `reconciliationReadIsCurrent()`。次态如下：

```text
save(edit one) → hydration h2
→ PUT settle，reconciliation GET held
→ hydration h3 载入 server newer，同时 recovery draft 仍为 edit one
→ stale GET 返回旧 edit one
→ UI 因 fence 保持 server newer，但 carrier 被无条件删除
→ hydration h4 → draft 从 edit one 变 undefined
```

Reviewer-only probe `keeps recovery after a held reconciliation read is superseded by newer hydration` exit 1，1 failed / 25 skipped；临时 test line 1234 精确为 expected `edit one` / received `undefined`。同时该过期 GET 仍可回报 `durableState: matches_requested`，虽然 h3 已证明其观察过期。

修复必须把 **所有** reconciliation side effects（UI block、carrier clear、outcome classification）纳入同一个 note/route/hydration/operation/outcome fence。stale GET 应为零状态变更，不能只保护 `setBlocks`。
