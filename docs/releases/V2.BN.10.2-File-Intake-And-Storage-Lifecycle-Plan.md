# V2.BN.10.2 Plan - File Intake And Storage Lifecycle

> **状态 (Status)**: completed
> **日期 (Updated)**: 2026-07-11
> **上游范围**: `docs/releases/V2.BN.10-plan.md` v3
> **实现设计**: `docs/agent-ops/analysis/reference-source-storage-design.md` v2
> **前置版本**: V2.BN.10.1 Source Identity And Placement Floor
> **工程回执**: `docs/releases/V2.BN.10.2-File-Intake-And-Storage-Lifecycle-Review.md`
> **定位**: 薄施工单；锁定文件生命周期与失败语义，不预写 parser 或 UI 架构

## 目标

让真实文件安全进入 10.1 已建立的四层 Source 地板，并证明任意失败点都不会永久留下“DB 说存在但文件不存在”或“文件存在但 DB 不知道”的孤儿。

本版本完成以下闭环：

```text
disk temp
  -> validate + streaming SHA-256
  -> DB staging identity floor
  -> same-volume atomic rename
  -> DB ready
  -> authenticated read/list/detail/blob
  -> startup reconciliation sweep
```

它不解析文档、不发布 SourceProjection，也不建设 Source Library 页面。

## 锁定不变量

1. `source_records / source_files / source_materializations / source_project_placements` 仍是唯一 Source 数据脊柱；intake 不建立第二套身份真相。
2. 文件先进入 `<SOURCE_BLOB_DIR>/.tmp`，最终文件只保存在应用控制的 blob root；数据库与 API 永不保存或返回用户原始绝对路径。
3. 服务器计算 SHA-256 是去重最终裁判；client precheck 只是省流量优化，数据库 UNIQUE 仍是并发边界。
4. 上传成功只在 `source_files.storage_state='ready'` 且最终 blob 已存在后返回；`staging` 不冒充“已收”。
5. 同 hash 命中复用既有 Source，并幂等增加当前 Project placement；跨 Project 不出现“已存在但当前 Project 看不到”的死路。
6. 同名不同 hash 建立新 Source，并为 display name 分配稳定 `(1) / (2)` 后缀；原始文件名仍作为事实附件收据保留。
7. rename 失败必须回滚本次 identity floor；rename 成功但 ready flip 未完成时，startup sweep 必须可确定地恢复。
8. 任何请求失败、连接中断或服务重启留下的 temp / staging 状态都必须可清扫；清扫不得误删 fresh in-flight 文件。
9. list / detail / precheck / blob 路径按 `user_id` 隔离，且响应不泄露 `storage_key` 或服务器文件路径。
10. ready 行对应 blob 缺失时返回稳定 `blob_missing` 诊断，不抛无解释 500，也不伪造原件仍可用。

## 文件能力矩阵

10.2 只判断“能否安全收存”，不提前承担 10.3 parser 的内容正确性：

- materializable candidate：PDF、DOCX、TXT、Markdown、PNG、JPEG、WebP；
- stored-only candidate：PPTX、XLSX、CSV；可保存、查看/下载和整体引用，但本版本不承诺内容提取；
- extension、MIME 与最低 magic/text sanity 必须互相一致；OOXML 本版只验证 ZIP 容器签名，解压膨胀、PDF 页数和 parser 语义验证属于 10.3；
- 统一上限 50MB，拒绝空文件、未知类型、签名错配和含 NUL 的伪文本。

## API 边界

本版本允许建立后续 UI 会复用的最小认证接口：

- hash precheck：命中时复用 Source 并补当前 placement；
- multipart upload：只负责 intake，不 fire-and-forget 解析；
- list / detail：返回安全 DTO、存储状态、能力和 placement 摘要；
- authenticated blob：支持 inline / download，不暴露本地路径。

没有 Source Library 页面时，不增加半成品 client store 或临时 UI。

## RED-first 检查

先写失败测试，至少覆盖：

1. 真实 PDF/text/image/OOXML 最小样本通过；扩展名、MIME、magic、空文件、伪文本和 50MB 边界被稳定分类。
2. 正常 intake 后 temp 消失、最终 blob 存在、DB 从 staging 变 ready，响应不含 storage key。
3. 同用户同 hash 并发/重复 intake 只产生一个 Source record/file/run，并可在两个 Project 各有 placement。
4. 同名不同 hash 自动分配 display-name 后缀。
5. rename 注入失败后本次 DB 行与 temp/final blob 均不残留。
6. DB stage 或 placement 注入失败后不留下 temp 或部分 identity floor。
7. rename 后、ready flip 前注入失败会留下可恢复 staging；sweep 将其恢复为 ready。
8. stale staging 且无 blob 被 sweep 删除；fresh staging 不被误删；过期 temp orphan 被清理。
9. ready blob 缺失得到 `blob_missing`；跨用户 list/detail/blob/precheck 均不可见。
10. routes 映射 Multer 体积错误和 typed intake error，不把预期冲突变成 500。

## 预计触点

- Source 独立 upload middleware / storage service / routes；
- `server/src/services/sourceRecords.ts` 的最小读取与 placement 接缝；
- `server/src/index.ts` 的 route mount 与 startup sweep；
- 新增 V2.BN.10.2 contract/integration tests，并加入 `server/package.json` 全量 v2 suite。

具体文件名与函数拆分由实现时决定；不得修改 legacy `middleware/upload.ts` 或把 parser 偷进 intake service。

## 非目标

- PDF/DOCX/TXT/image 内容解析与 SourceArtifact；
- materialization claim/retry、投影 Note/Block 原子发布；
- SourceProjection write policy；
- Source Library / Project Sources UI 与 client WebCrypto 实现；
- Source 硬删除 quarantine、Project 删除迁 Home；
- legacy Documents 迁移、Edition、Agent、embedding、Relation 或 GraphRAG。

## 退出门

- RED 测试全部转绿，故障注入证明 DB/disk 可恢复一致；
- concurrent duplicate、跨 Project placement、同名后缀和用户隔离通过；
- server build、全量 v2 suite 与 `verify:v2-bn8-runtime` 通过；
- `git diff --check` 与 changed-file secret scan 通过；
- 无 UI 的事实在回执中明确，浏览器 smoke 不被伪造为已完成；
- Review 与 current-state 同步，下一前沿指向 V2.BN.10.3。

## 自检问题

收口前必须再问：

> 任意一次 crash 后，单看 DB 和 blob root，系统是否都能确定“恢复、清除或报告缺失”中的唯一动作？

如果答案依赖人工猜测，10.2 不得收口。
