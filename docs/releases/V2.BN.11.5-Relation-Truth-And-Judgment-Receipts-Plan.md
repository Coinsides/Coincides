# V2.BN.11.5 Plan - Relation Truth And Judgment Receipts

> **状态 (Status)**: engineering complete — awaiting independent review
> **日期 (Updated)**: 2026-07-13
> **层 (Layer)**: 执行计划 / Release Plan
> **权威 (Authoritative)**: 否；范围服从 `V2.BN.11-plan.md` 与 Relation / Item 概念设计 v1.1

## 1. 本小版本解决什么

V2.BN.11.5 让 migration 047 中已经存在的 Relation 真相表第一次拥有完整领域命令：两个 active Item 可以建立语义 Relation，Relation 会保存建立判断时的双端 Snapshot 收据，并能被撤销、重建和原子重申。

```text
active Item A + active Item B
  -> server-owned RelationType directionality
  -> current Snapshot A + current Snapshot B
  -> one active semantic judgment
  -> revoke keeps history / reaffirm refreshes receipts atomically
```

本版只建立 Relation 真相与无图读取面。机械新鲜度、Item Inspector UI、diff、assessment 执行器和图形化工作台属于 V2.BN.11.6 以后。

## 2. 必守不变量

1. Relation 端点只允许 Item，不复用 Canvas visual connector、legacy object relation 或 ContentGroup identity。
2. 新建 Relation 的两端必须属于当前用户且仍为 active；missing、retired、cross-user 与 self-loop 均拒绝。
3. RelationType 的 directionality 由 server registry 决定，客户端不能自报方向性。
4. 种子类型固定为：
   - directed：`derives_to / depends_on / supports / contradicts / example_of`；
   - undirected：`equivalent_to / analogous_to / contrasts_with / companion_of`。
5. undirected Relation 按 Item ID 规范序；反向提交不得产生第二条活边。directed Relation 保留提交方向。
6. 同一规范端点对 + relation type 同一时刻只允许一条 active Relation；撤销后可建立一条新 Relation，旧记录继续存在。
7. 判断收据必须引用各自端点 Item 的 Snapshot；Snapshot 内容取 canonical `plain_text`，相同内容复用已有行。
8. `origin_purpose_id` 只是判断发生情景的出处收据：Purpose 删除后降级为 `NULL`，任何 Relation list 都不得把它当 applicability filter。
9. reaffirm 只作用于 active Relation，并在一个事务内完成双端 Snapshot ensure、双指针更新与 `affirmed_at` 更新；任一点失败都保持旧收据与旧时间。
10. `relation_assessments` 本版只提供读取兼容，不执行模型、不伪造人类 assessment、不增加 invalidation / sync flag。
11. Purpose-scope list 的成员域来自 11.4 compiled scope；只有两个端点都在圈内的 Relation 才进入该读取结果，且不因 `origin_purpose_id` 不同而被过滤。

## 3. RED-first 契约矩阵

### 3.1 Seed registry 与规范化

- 九个 seed 类型及固定 directionality 精确断言；
- API 拒绝未知类型和客户端注入的 `directionality`；数据库 `relation_type TEXT` 仍保留未来扩展缝；
- directed 反向提交保持不同方向；undirected 反向提交规范为同一端点序；
- self-loop 在 service 与 DB 两层都被拒绝。

### 3.2 身份、生命周期与单活边

- missing / retired / cross-user endpoint create rejection；
- 同对同型 active duplicate 返回明确冲突；
- revoke 保留旧行，active list 隐藏 revoked；
- revoke 后 recreate 生成新 ID，`all` list 同时解释两条历史；
- wrong-item Snapshot 继续被 migration 047 复合 FK 拒绝。

### 3.3 Purpose 出处与无图读取

- by-Item list 只返回当前用户、且能按 `active | revoked | all` 过滤；
- by-Purpose list 使用 compiled Item scope，要求两个端点均在圈内；
- Relation 即使源自别的 Purpose 或无 origin，只要端点在圈内仍可读；
- origin Purpose 删除后 Relation 与双 Snapshot 继续存在，origin 降级为 `NULL`；
- 删除一个 active Purpose member 后再执行第二轮全量替换，边不会被 hidden recovery 复活（携带 11.4 L1）。

### 3.4 Reaffirm 原子性

- Item 正文未变时 reaffirm 复用 Snapshot；
- Item 正文变化后 reaffirm 切换到当前 Snapshot 并推进 `affirmed_at`；
- `after_from_snapshot / after_to_snapshot / after_relation_update / before_commit` 四个 fault point 分别抛错；
- 每个 fault point 后 Relation 的双 Snapshot、`affirmed_at` 与 `updated_at` 全部保持旧值。

### 3.5 Assessment 兼容与客户端契约

- assessment 读取按时间稳定排序并按 user / Relation 限域；
- schema 不存在 `invalidated / stale / sync_status` 一类存储列；
- client normalizer 保留 directionality、status、双 Snapshot 与 origin receipt；
- client repository 提供 type registry、create/get/list/revoke/reaffirm，不接 UI。

## 4. 实现纵切

### 4.1 Server domain

- 新建 `services/relations.ts`，集中管理 seed registry、方向规范化、ownership、Snapshot receipt、命令事务与读取 hydration；
- 复用 Item 层 canonical Snapshot 能力，不在 Relation service 复制 hash 算法；
- create / revoke / reaffirm 使用明确 AppError，不把 SQLite 约束文本泄漏为产品错误；
- assessment 仅提供内部 list 函数。

### 4.2 API 与 client seam

- 新建 `/api/relations` 路由：types、create、get、list、revoke、reaffirm；
- list query 必须且只能选择 `item_id` 或 `purpose_id` 之一；
- validators 全部 `.strict()`；
- client 增加 Relation DTO、纯 normalizer 与 repository，不建设 Inspector UI。

### 4.3 随行 LOW 清理

- 补 11.4 active Purpose edge 删除的双周期防复活测试；
- 审计 `replaceGroup` fire-and-forget 调用：只在能以小范围错误收口完成时修复，不让它侵入 Relation 主纵切；
- Note 独立删除 receipt 测试与 Relation 无直接因果，继续留档，不借 11.5 扩张。

## 6. 退出条件

- 两个 active Item 能建立、读取、撤销、重建和重申 Relation；
- 无向边反向提交不重复，有向边方向不丢；
- Snapshot receipt 不可串到别的 Item；
- reaffirm 任一步失败都完整回滚；
- Purpose-scope list 使用端点在场性，不使用 origin applicability；
- assessment 表保持历史读取兼容且无失效旗；
- server/client 工程门、API smoke、Review 与第三方复验材料齐全。

## 7. 工程结果（2026-07-13）

V2.BN.11.5 已完成工程实现，当前等待第三方独立复验，不自行签发产品或体验 PASS。

- server 已建立九种 Relation seed registry、方向规范化、create/get/list/revoke/reaffirm 领域命令，以及只读 assessment compatibility；
- create 只接受当前用户的 active Item，Snapshot 收据复用 Item 层 canonical 能力；无向边规范序、单活边、self-loop 与 wrong-item Snapshot 均由 service + DB 约束共同背书；
- Purpose-scope list 使用 11.4 compiled Item scope，要求双端均在圈内；`origin_purpose_id` 只作出处收据，Purpose 删除后按 FK 降级为 `NULL`；
- reaffirm 在单事务中刷新双端 Snapshot 与时间收据，四个 fault point 均验证完整回滚；
- client 已补 Relation DTO、纯 normalizer 与 repository，但没有提前建设 Inspector、freshness 或图形工作台；
- 11.4 随行 LOW 已补：显式删除 active Purpose Item edge 的第二周期防复活、stale payload 单行计数，以及 ContentGroup move/delete 写回失败收口。
