# V2.BN.3 Plan - Freeform NoteBlock Box And Layout Mode

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make NoteBlocks behave like editable content boxes on the formal note page: selectable, movable, resizable, alignable, and able to sit side-by-side without losing NoteBlock content truth.

**Architecture:** V2.BN.3 adds the first layout layer above the natural writing surface from V2.BN.2. NoteBlock content remains canonical content truth; BlockBox / placement state becomes layout truth. The editor may project layout through existing CanvasNode / placement structures if they are sufficient, but must not mix visual position into the NoteBlock body.

**Tech Stack:** React, TypeScript, CSS modules, existing NoteDetail note-block APIs, existing CanvasNode / note block placement data where usable, browser smoke through the local client.

---

## Summary

V2.BN.3 is the first Better Notebook version where Coincides starts to differ from ordinary single-column note editors.

The user should be able to write a text block, shrink it to half-page width, click the empty area beside it, and create another block next to it. This version does not try to finish the whole canvas/export system. It focuses on the practical first layer of freeform page layout:

```text
NoteBlock content
  -> visible BlockBox
  -> resize / move / align
  -> text reflow
  -> layout persists
```

The core rule is simple:

```text
Resize and move change layout truth.
They do not rewrite NoteBlock content truth.
```

## User Workflow

### Workflow 1: Resize A Text Block

1. User opens an existing note.
2. User clicks a paragraph block.
3. The block shows a light selected state.
4. User drags the right resize handle inward.
5. The block width becomes smaller.
6. Text reflows inside the block.
7. The block height grows naturally if the content needs more lines.
8. User reloads the note.
9. The resized layout remains.

Expected data change:

- NoteBlock content does not change.
- Layout placement / BlockBox width changes.

### Workflow 2: Create A Side-By-Side Block

1. User has a text block on the left half of the formal page.
2. User clicks or double-clicks the empty area to the right of that block.
3. A new draft text block appears in that area.
4. User types `/formula`, `/image`, `/quote`, or plain text.
5. The new block is created as a normal NoteBlock with a layout box beside the original block.

Expected visual state:

- The second block does not jump to the next global row.
- The two blocks can align along the top edge.
- The insertion feels spatial, not like a hidden engineering form.

### Workflow 3: Layout Mode

1. User enters layout mode from a top-bar / tool-surface action or shortcut.
2. All editable BlockBoxes show light borders.
3. Selected block shows resize handles.
4. Dragging a block shows snap guides.
5. User exits layout mode.
6. Reading mode hides heavy borders and handles.

Expected rule:

- Layout mode is for moving and resizing.
- Text editing still works through normal click/double-click behavior, but accidental text editing should be reduced while layout mode is active.

### Workflow 4: Old Note Compatibility

1. User opens a note created before V2.BN.3.
2. Blocks appear in a readable default layout.
3. User can select and resize those blocks.
4. Saving layout does not rewrite block content or erase existing metadata.

## Data / State Impact

Touched:

- `NoteBlock` content truth: must remain readable and unchanged by move/resize.
- BlockBox / CanvasNode / note block placement layout truth: primary state touched by this version.
- Page / canvas projection state: may be touched only to support formal-page placement.
- UI draft state: selected block id, layout mode, drag state, resize state, snap guide state.

Not touched unless the audit proves it is strictly required:

- source references and provenance;
- ObjectRelation / RelationType / RelationGroup;
- CanvasEdge / visual connectors;
- TemplateDefinition / CompositionTemplate / DomainBlockSet / PackageManifest;
- Concept-lite;
- GraphRAG adapter;
- OCR/VLM source reconstruction;
- export engine.

### Data Contract Questions To Answer Before Implementation

- Does the current schema already have stable `x`, `y`, `width`, and `height` placement fields usable for note-page BlockBoxes?
- If placement exists only for canvas projection, can it safely serve the formal page without mixing page layout and open-canvas layout?
- If a block has no placement row, what deterministic default box should be generated?
- Should the first version persist layout immediately on drag end / resize end, or use a Save Layout action?
- How does undo interact with layout move/resize in the first version?
- Can multiple visual placements point to the same NoteBlock today? If not, V2.BN.3 must avoid product behavior that implies reusable multi-placement truth.

Important rule:

If the current schema cannot persist the user workflow reliably, this version must include a minimal data fix. Do not defer a required layout truth repair only because `V2.BN.6` exists as a later data-contract consolidation phase.

## Key Product Rules

- NoteBlock is the content unit.
- BlockBox / placement is the layout unit.
- Resize changes the BlockBox, not the NoteBlock body.
- Moving a block changes page layout, not semantic order by itself.
- Visual proximity does not create an ObjectRelation.
- Side-by-side layout does not automatically mean source, relation, or group.
- Reading mode hides engineering chrome.
- Layout mode shows borders, handles, and alignment affordances.
- Snap guide is enabled by default in the first product direction.
- Delete still means delete with undo / trash safety; do not introduce hidden "remove from page" behavior in this version.
- `Advanced insert` remains a fallback tool, but primary insertion should feel spatial and page-native.

## Key Changes

### 1. Current Implementation Audit

Read the current implementation before editing:

- `client/src/pages/Notes/NoteDetail.tsx`
- `client/src/pages/Notes/NoteDetail.module.css`
- current note block API routes;
- current canvas / placement model;
- current patch notes for V2.BN.2.

Record findings in `docs/releases/V2.BN.3-review.md`.

The audit must answer:

- where note block content is rendered;
- where position/size can be stored today;
- whether old note blocks have placement data;
- whether the current page surface is still too tightly coupled to vertical flow;
- which UI behaviors are only fallback and should not become product direction.

### 2. Layout Data Decision

Choose the smallest reliable persistence path:

- reuse existing placement fields if they are already canonical layout truth;
- add a minimal placement field/table only if the current model cannot represent page layout;
- avoid client-only fake layout if reload would lose user work.

Record the decision in:

- `docs/releases/V2.BN.3-engineering-spec.md`;
- `docs/releases/V2.BN.3-review.md`.

### 3. Selectable BlockBox

Implement a visible block selection model:

- unselected reading state is quiet;
- hover state is subtle;
- selected state shows a thin border;
- layout mode shows all eligible block boundaries lightly;
- selected block shows handles.

The first version should prefer restrained black/white UI, no purple-heavy chrome, and no decorative glass effect.

### 4. Resize Handles And Text Reflow

Implement resize affordances:

- right handle changes width;
- corner handles may be included if low risk;
- width has minimum and maximum constraints;
- paragraph text wraps inside the new width;
- height expands to fit content;
- content must not be clipped in normal reading state.

First version can defer:

- text indent ruler;
- full rich text typography panel;
- per-field structured block layout.

### 5. Move / Drag Behavior

Implement block move behavior:

- dragging a selected block moves its BlockBox;
- drag should not accidentally edit text;
- drag end persists layout;
- reload preserves position;
- moving a block should not reorder content truth unless explicitly implemented and documented.

### 6. Snap Guides And Alignment

Implement first alignment aid:

- show horizontal / vertical snap guides when block edges or text baselines are close;
- snap to page margins and nearby block edges;
- keep snap visually light;
- if snap causes bad behavior, expose a temporary disable path in layout mode.

### 7. Spatial Insertion

Implement first spatial insertion behavior:

- clicking empty space inside the formal page can create a draft block at that spatial position;
- clicking to the right of an existing narrowed block should create the new block there;
- the new block should get a reasonable default width based on available horizontal space;
- slash commands continue to work inside the new draft block.

### 8. Tool Surface Fit

Keep global note controls out of the page body:

- title/top actions belong in top chrome;
- `Advanced insert` should be available as a floating or side tool, not as a page-bottom form;
- layout mode / insert actions should remain visible while the page scrolls;
- do not fill the page with permanent control panels.

## Out Of Scope

V2.BN.3 does not implement:

- full page mode vs open canvas mode switch;
- final A4/multi-page export boundary;
- full style editor;
- template field layout editor;
- full structured block field runtime;
- source picker or `/add source`;
- source chain/degraded UX;
- relation mode;
- local graph view;
- AI note generation;
- OCR/VLM source reconstruction;
- GraphRAG adapter;
- iPad handwriting canvas;
- Photoshop-like drawing tools;
- full multi-column automatic flow engine.

## Acceptance Criteria

- User can resize a paragraph block to half-page width.
- Text reflows and remains fully visible after resize.
- User can place another block to the right of the resized block.
- User can manually create left-text/right-text layout.
- User can manually create text/formula or text/image side-by-side layout with placeholder support if image data contract is not ready.
- User can move a block and reload without losing position.
- Layout controls are visible when needed and quiet when reading.
- Old notes still open and remain editable.
- Move/resize does not mutate NoteBlock content.
- Visual adjacency does not create source reference or ObjectRelation.
- Henry must explicitly say the stage passed before the version is considered accepted.

## Graph-Native / Adapter Evidence

- NoteBlock remains the future graph content node candidate.
- BlockBox / placement is projection/layout truth, not a knowledge graph node by default.
- Visual adjacency, side-by-side placement, and page proximity are not ObjectRelation.
- Future GraphRAG should not infer semantic relationship from layout alone.
- If layout patterns later become meaningful, they should become explicit user-confirmed relation or grouping metadata, not accidental graph truth.

## Assumptions

- V2.BN.3 is a human-writing/layout version, not an AI version.
- The first version prioritizes manual layout reliability over automatic layout intelligence.
- Default page writing remains the primary path from V2.BN.2.
- Advanced insert remains available as fallback, but should not dominate the page body.
- If implementation discovers a layout persistence gap, V2.BN.3 may include a minimal data fix.
- Page/canvas/export boundary is deliberately reserved for V2.BN.4.
