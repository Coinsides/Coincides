## 1. 当前判断

V2.BN.10.5 的工程实现与自动化门已经完成。Source identity、Project placement、SourceProjection、receipt 和物理 blob 不再被一条含混的级联删除绑在一起：Project 删除不会威胁 Source；Source 硬删除不会抹掉历史收据；数据库事务也不再假装能回滚已经发生的文件系统副作用。

浏览器真实旅程尚未执行，因此准确结论是：

## 2. 已完成

### 2.1 migration 046 与生命周期契约

- `source_materializations` 允许已经物化的投影后来缺失，同时禁止非 materialized run 携带 projection pointer。
- `note_block_sources` 对 Source record 和 materialization 建立真实 `ON DELETE SET NULL` 外键；删除后 excerpt、locator 与 reference mode 留在收据行。
- 新增内部 `managed_file_cleanup_jobs`，只记录提交后的物理删除/恢复重试，不引入用户可恢复的 Source 软删除。
- 新增 course lifecycle policy registry。契约测试扫描所有带 `course_id` 的表，未登记或过期登记都会失败；当前 56 张表全部覆盖。

### 2.2 Project 删除闭环

- 新增删除影响查询，返回 SourceProjection、用户劳动、其他 placement 与推荐行为。
- 动态默认由服务端决定：纯投影且无其他 placement 时默认删除投影；存在用户劳动或其他 placement 时默认迁往 Home。
- 投影 Block 在其他 Note 中的复用 placement 也属于用户劳动信号；它会触发 move-to-Home，避免 Project 级联误删共享 Block。
- 两个行为都显式可选，但 Project 删除永远不删除 Source record 或事实 blob。
- move-to-Home 迁移 Note、NoteBlock、CanvasObject/Placement/PageFrame/PageStack、AnnotationTruth、ContentGroup/Member/Fragment/Petal、Purpose、GroupFolder scope、image asset 与 operation batch 等已登记卫星数据。
- Project 删除对话先展示影响和服务器推荐值，不让前端自行猜测默认策略。

### 2.3 Source 硬删除闭环

- 唯一用户入口位于全局 Source Library；Project 镜头不提供 Source identity 删除。
- 删除影响查询展示 placement、projection、receipt、projection 用户劳动与 active materialization 阻塞状态。
- 删除前把事实原件移动到同盘 quarantine，再执行数据库事务；事务失败恢复原路径，提交成功后才最终删除 quarantine。
- 最终 unlink 或补偿恢复失败会进入 durable cleanup job，并在服务启动时重试。
- Source record、file、materialization、placements 和 projection 被硬删除；外部 receipt 保留并降级，ContentGroup member 的 Source 状态变为 stale。
- 只删除失去全部 placement 的 SourceProjection 专用 NoteBlock；跨 Note 复用的 block 不被误删。
- active materialization 期间拒绝 Source 删除，避免 parser 与 delete 竞争制造复活或半状态。

### 2.4 物理资产提交边界

- Canvas image asset 的引用释放只在事务内形成清理决策，不再直接 `unlink`。
- Source / Project / CanvasObject 删除均在数据库 commit 后执行物理清理；失败进入统一的 managed cleanup retry。
- 清理任务只能作用于受管理的 Source storage 和 Canvas asset 根目录，拒绝越界路径。

### 2.5 用户界面

- Project 删除对话展示 SourceProjection 数、用户劳动、其他 placement、动态默认与两个明确结果。
- Source 删除对话明确“不可恢复”、projection/placement 消失、历史 receipt 保留降级，以及 active run 阻塞原因。
- 全局 Source Library 已接通真正的硬删除；Project Sources 仍只管理镜头。

## 5. 诚实边界与后续风险

- legacy Documents / SourceAnchor / SourceSnapshot 没有迁移；V10 只停止让旧入口继续产生新数据。
- Source replace、projection rebuild、Edition、Publication 和完整 lineage 不属于本版本。
- active materialization 当前选择阻止删除，不实现取消并等待 parser 收束。
- cleanup job 是内部耐久补偿，没有用户 UI、运维面板或告警；当前通过启动重试与测试证明最终一致性。
- 浏览器尚未证明对话文案、默认选中项、真实长任务阻塞和 move-to-Home 后的用户感受。
- Vite 仍有既有 dynamic import 与主 chunk 体积 warning；这不是本小版本引入的 Source 生命周期失败。

## 6. 工程判断

10.5 的关键价值不是“终于有删除按钮”，而是删除不再拥有越权的语义。Project、Source、projection、receipt 和 blob 各自只改变自己应当负责的生命周期；跨 SQLite 与文件系统的操作也拥有明确的提交线、补偿线和重试线。

这使 Source Floor 在工程上成立，但体验是否真能让用户放心删除，仍应由联合浏览器旅程回答。
