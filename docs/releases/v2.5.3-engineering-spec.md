# v2.5.3 Engineering Spec - Domain Block Set + Package Manifest

## Summary

v2.5.3 introduces runtime data contracts for domain packages. `PackageManifest` describes a local package as safe data. `DomainBlockSet` groups templates and composition templates for a domain so humans and agents can choose a suitable capability bundle without inventing templates ad hoc.

## Data Model

Add migration `027_v2_domain_packages.ts` and mirror it in `server/src/db/schema.sql`.

### `package_manifests`

Minimum fields:

- `id`
- `user_id`
- `package_key`
- `version`
- `manifest_version`
- `package_kind`
- `origin`: `system_seed | user | imported | migration`
- `scope_type`: `global | course`
- `scope_id`
- `package_name`
- `description`
- `author`
- `compatibility`
- `contents`
- `trust`
- `license`
- `import_policy`
- `export_policy`
- `graph_migration_hints`
- `validation_status`: `valid | warning | blocked`
- `status`: `draft | active | deprecated | archived`
- `is_system`
- `metadata`
- timestamps

Unique key:

```text
user_id + package_key + version + scope_type + scope_id
```

### Membership Tables

`domain_block_set_templates` links domain sets to runtime templates.

`domain_block_set_compositions` links domain sets to composition templates.

Both store:

- domain set id;
- target runtime id;
- stable key/version;
- member role;
- `required`;
- `order_index`;
- metadata;
- timestamps.

These membership rows are not graph truth yet, but they are graph-native migration evidence.

## Seed Contract

Seed package:

```text
coincides.core.domain-seeds@0.1.0
```

Seed domains:

```text
learning.math.basic
research.evidence.basic
briefing.general.basic
```

Seeding rules:

- seed runtime `TemplateDefinition` records first;
- seed runtime `CompositionTemplate` records second;
- seed package/domain records third;
- membership links must resolve actual runtime ids;
- re-running seed updates system metadata but does not duplicate rows.

## API Contracts

Add:

```text
GET /api/package-manifests
GET /api/package-manifests/:id
POST /api/package-manifests/seed-system
GET /api/package-manifests/:id/preview
POST /api/package-manifests/preview

GET /api/domain-block-sets
GET /api/domain-block-sets/:id
POST /api/domain-block-sets/seed-system
GET /api/domain-block-sets/:id/compatibility-report
```

Preview response:

```json
{
  "manifest": {},
  "domain_sets": [],
  "template_count": 0,
  "composition_count": 0,
  "warnings": [],
  "blockers": [],
  "validation_status": "valid"
}
```

Validation rules:

- executable code is blocked;
- provider/API keys or secret-like manifest fields are blocked;
- missing package identity fields are blocked;
- required unresolved template/composition refs are blockers;
- optional unresolved refs are warnings;
- preview never persists records.

## Frontend

Add a lightweight Domain Packages section inside `#/templates`.

It must show:

- package list;
- domain set list;
- package preview;
- included template/composition counts;
- validation warnings/blockers.

It must not provide full package editing, import/export, marketplace behavior, or package installation UX.

## Graph-Native Migration Evidence

v2.5.3 review must record:

- `PackageManifest` is a future graph node candidate;
- `DomainBlockSet` is a future graph node candidate;
- domain membership rows are future edge evidence;
- package contents are package metadata until import/export proves a need for deeper normalization;
- package manifests are not executable plugins.
