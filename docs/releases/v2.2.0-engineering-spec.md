# v2.2.0 Engineering Spec - Material Reconciliation Proposal Shell

**Created**: 2026-05-21
**Updated**: 2026-05-21
**Status**: Implemented draft

---

## 1. Implementation Boundary

v2.2.0 implements a review-only Material Reconciliation proposal shell.

It creates `material_reconciliation` proposals from existing v2.1 course material objects:

```text
source_materials
source_fragments
material_segments
material_segment_fragments
```

It does not create persistent evidence sets, canonical blocks, exclusions, conflicts, unmerge records, or source-board objects.

---

## 2. Data Storage

No migration is added in v2.2.0.

The existing `proposals` table stores the proposal:

```text
type = material_reconciliation
status = pending / applied / discarded
data = proposal JSON
```

The existing `operation_batches` table stores a shell review record when the proposal is applied:

```text
source_type = proposal
source_id = proposal.id
label = Review material reconciliation proposal shell
metadata.proposal_type = material_reconciliation
metadata.apply_behavior = review_shell_only
```

No changes are made to:

- `documents`
- `source_materials`
- `source_fragments`
- `material_segments`
- `notes`
- `note_blocks`
- `note_block_sources`

## 3. Proposal Contract

Route:

```text
POST /api/proposals/material-reconciliation
```

Request:

```json
{
  "course_id": "uuid",
  "document_ids": ["uuid"],
  "source_material_ids": ["uuid"],
  "segment_ids": ["uuid"]
}
```

All scope fields except `course_id` are optional. If no optional scope is provided, the whole course material scope is used.

Response:

```json
{
  "id": "proposal-id",
  "type": "material_reconciliation",
  "status": "pending",
  "data": {
    "version": "v2.2.0",
    "proposal_kind": "material_reconciliation",
    "course_id": "course-id",
    "title": "Material reconciliation proposal",
    "description": "Review-only candidate groups for duplicate, overlapping, same-concept, or conflicting source material.",
    "scope": {
      "document_ids": [],
      "source_material_ids": [],
      "segment_ids": []
    },
    "candidate_groups": [],
    "warnings": [
      "v2.2.0 creates review-only reconciliation proposals. Real merge apply is deferred to v2.2.1."
    ],
    "apply_behavior": "review_shell_only"
  }
}
```

Candidate group:

```json
{
  "group_id": "uuid",
  "group_kind": "DUPLICATE",
  "confidence": 0.92,
  "suggested_action": "review",
  "title": "Possible duplicate: Limits",
  "evidence": [
    {
      "source_material_id": "uuid",
      "source_fragment_id": "uuid",
      "material_segment_id": "uuid-or-null",
      "document_id": "uuid",
      "document_chunk_id": "uuid-or-null",
      "title": "Limits",
      "page_start": 1,
      "page_end": 2,
      "excerpt": "short source excerpt",
      "reason": "normalized source text appears identical across multiple materials"
    }
  ],
  "warnings": [
    "Review-only candidate. v2.2.0 does not merge, delete, or hide source material."
  ]
}
```

## 4. Candidate Taxonomy

Allowed group kinds:

```text
DUPLICATE
OVERLAP
SAME_CONCEPT_EVIDENCE
CONFLICT
```

Allowed suggested actions in v2.2.0:

```text
review
keep_separate
defer
future_merge_candidate
mark_conflict
```

Initial deterministic heuristic:

- `DUPLICATE`: normalized source text is identical across multiple source materials.
- `SAME_CONCEPT_EVIDENCE`: fragments share the same heading/title but have different wording.
- `CONFLICT`: fragments share the same heading/title and one side contains simple negation or exception markers.
- `OVERLAP`: fragments in the same document have overlapping page ranges.

The heuristic is intentionally conservative. It may miss candidates; it must not claim final truth.

## 5. Apply / Discard Behavior

`POST /api/proposals/:id/discard`:

- marks proposal as `discarded`;
- does not mutate source/material/note state.

`POST /api/proposals/:id/apply` for `material_reconciliation`:

- validates the proposal shape;
- creates an operation batch with `apply_behavior = review_shell_only`;
- marks the proposal as `applied` through the existing proposal route transaction;
- returns `review_shell_only = true`;
- does not merge, delete, hide, exclude, canonize, or create notes.

Real merge apply is v2.2.1.

## 6. Frontend Surface

Course Detail adds a minimal `Reconcile` action in the Course Material workspace.

The proposal review panel displays:

- proposal title and description;
- safety language that v2.2.0 records review only;
- warnings;
- candidate group kind;
- candidate group title;
- evidence count;
- confidence percent;
- `Mark reviewed` and `Discard` actions.

No visual redesign is included.

## 8. Test Matrix

Automated checks:

- material reconciliation proposal creation;
- duplicate candidate group detection;
- same-concept evidence candidate group detection;
- same-document page overlap candidate group detection;
- conflict candidate group detection;
- creation does not mutate source material status;
- apply shell does not create notes, blocks, canonical objects, or source mutations;
- discard does not mutate source/material/note state;
- existing v2.0/v2.1/v2.1.1 tests remain passing;
- server build;
- client build;
- `git diff --check`;
- changed-file secret scan.

Manual/Henry checks:

- candidate kind language is understandable;
- review-only behavior is obvious;
- evidence excerpts are sufficient for first-pass trust;
- the absence of real merge behavior is acceptable for v2.2.0.
