## 0. Delivery boundary

V2.BN.11.2 establishes the database truth floor for Item and Relation and lands Package B atomically. It does not expose Item services, Item UI, anchor claiming, relation commands, Purpose Item membership, or Package A.

This small version delivers only:

1. migration `047_v2_item_relation_floor` and matching clean-database schema baseline;
2. five new tables: `items`, `item_snapshots`, `item_anchors`, `relations`, and `relation_assessments`;
3. removal of exactly six retired support tables;
4. `content_group_members.item_id` across migration, server, validator, client DTO, client normalizer, and roundtrip tests;
5. course lifecycle registry coverage for both current Project placement columns and historical Project origin receipts;
6. database behavior tests for composite foreign keys, cascades, rebuild atomicity, and lifecycle declarations.

## 1. Locked invariants

### 1.1 Item and snapshot

- Item is durable knowledge identity. Project and Note are nullable origin receipts, both `ON DELETE SET NULL`.
- `items.retired_into_item_id` is nullable and `ON DELETE SET NULL`.
- `item_snapshots` owns `UNIQUE(item_id, content_hash)` and `UNIQUE(item_id, id)`.
- Snapshot content is immutable evidence for Relation endpoints; this version creates the floor but no write service.

### 1.2 Item anchor

- `item_anchors` is a new V11 table and is not `source_anchors`.
- Claimed state requires `item_id` and requires both pool coordinates to be null.
- Pool state requires `item_id` to be null and requires both pool coordinates to be non-null.
- `claimed_at` and `claimed_by` are retained as claim receipts.
- `excerpt` is self-contained evidence. Target coordinates are vocabulary, not foreign keys.
- `source_record_id` degrades with `ON DELETE SET NULL`; deletion of an upstream Source must not delete the anchor receipt.

### 1.3 Relation

- Relation endpoints are Item-only and use composite foreign keys to prove each snapshot belongs to its declared Item.
- `affirmed_at` is `NOT NULL`.
- `origin_purpose_id` is a nullable origin receipt with `ON DELETE SET NULL`; it is never filtering truth.
- Self-loops are rejected.
- Undirected endpoints must be stored in canonical Item ID order.
- A partial unique index allows only one active edge for a canonical endpoint pair and `relation_type`.

### 1.4 ContentGroup Item membership

The rebuilt `content_group_members` table adds nullable `item_id` with `ON DELETE SET NULL` and enforces:

```sql
(kind = 'item' AND item_id IS NOT NULL AND target_id IS NULL)
OR
(kind != 'item' AND item_id IS NULL)
```

An Item member uses `item_id`, never `target_id`. Existing member IDs, order, source receipts, previews, metadata, and timestamps survive the rebuild. A missing Item edge remains `kind='item'`, hydrates with `source_sync_status='missing'`, and exposes orphaned integrity metadata; it is never coerced to `content_range`.

## 2. Migration 047 sequence

Migration 047 relies on the migration runner's per-migration transaction. The sequence is fixed:

1. create `items`, `item_snapshots`, `item_anchors`, `relations`, `relation_assessments`, and their indexes;
2. drop `content_group_petal_fragments`, then `content_group_fragments` and `content_group_petals` so no retired child table references the member table during rebuild;
3. rename `content_group_members` to a temporary legacy table;
4. create the new `content_group_members` shape with `item_id` and the membership check;
5. copy every legacy member field, with `item_id = NULL`, preserving IDs and timestamps;
6. drop the temporary legacy table and recreate member indexes, including an Item lookup index;
7. drop `canvas_edges`, then `object_relations` and `relation_layers` in dependency-safe order;
8. let the migration runner record 047 in the same transaction.

The migration drops exactly these six retired tables:

- `content_group_fragments`
- `content_group_petals`
- `content_group_petal_fragments`
- `object_relations`
- `canvas_edges`
- `relation_layers`

It preserves `learning_canvases`, `canvas_nodes`, the current `canvas_objects(kind='visual_connector')` model, and frozen V10 `source_anchors`.

The clean-database `schema.sql` baseline represents the post-047 shape. Earlier migrations may recreate legacy tables during first initialization; 047 remains responsible for removing them. A second initialization must apply no migration and leave the same shape.

## 3. RED-first evidence

Before implementation, add tests that fail against the 046 floor and prove the missing behavior:

1. schema/table/index assertions for the five new tables and six removed tables;
2. legal same-Item snapshot Relation insertion succeeds;
3. borrowed snapshot Relation insertion fails under `PRAGMA foreign_keys=ON`;
4. empty database initialization and an explicit 046 upgrade fixture converge on the same 047 shape;
5. an injected rebuild-copy failure rolls back the table rename and leaves no partial member table;
6. a complete user family cascades from `DELETE users`, while a cross-user fake reference is rejected at statement end;
7. Item membership roundtrips through validator, server write, database row, server hydrate, DTO, and client normalizer;
8. a missing Item member hydrates as missing/orphaned without kind coercion;
9. lifecycle coverage detects missing entries, stale entries, unregistered course-origin FKs, and declared `ON DELETE` mismatch.

If real SQLite behavior contradicts the composite FK or transactional rebuild assumptions, stop implementation and reopen D-003. Do not weaken database constraints or replace them with silent service conventions.

## 4. Package B implementation

### 4.1 Server

- Add `item_id` to `ContentGroupMemberRow`.
- Admit `kind='item'` in normalization.
- Write `item_id` only for Item members and force their `target_id` to null.
- Force `item_id` to null for non-Item members.
- Include `item_id` in INSERT and conflict update paths.
- Preserve Item kind during hydrate; mark a null Item edge missing/orphaned.
- Replace the permissive member request object with an explicit member schema that admits Item members and validates Item/non-Item coordinate rules.

### 4.2 Client

- Add `item` to `ContentGroupMemberKind`.
- Add nullable `item_id` to `ContentGroupMemberV1`.
- Preserve Item kind and Item ID in normalization.
- Keep `target_id` null for Item members and `item_id` null for non-Item members.
- Represent a missing Item ID as missing/orphaned rather than constructing a content-range source reference.

## 5. Lifecycle registry

Each registry entry declares:

- table;
- Project-reference column;
- policy (`move`, `delete`, `preserve`, or `fk-derived`);
- expected foreign-key `ON DELETE` behavior when the policy is database-derived;
- reason.

Coverage scans every live foreign key that points to `courses`, not only columns named `course_id`. It must therefore discover `items.origin_course_id` and register it as `preserve` with `ON DELETE SET NULL`.

Coverage rejects:

- a live Project reference absent from the registry;
- a registry entry whose table or column no longer exists;
- an origin Project FK omitted because its column is not named `course_id`;
- a declared `ON DELETE` action that differs from the actual schema.

The same change removes retired Petal and legacy Relation entries. The Project-to-Home move path removes calls to the two dropped Petal tables while keeping `content_group_members` movement intact.
