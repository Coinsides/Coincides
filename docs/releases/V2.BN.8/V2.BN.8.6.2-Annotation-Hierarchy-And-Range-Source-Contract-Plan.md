# V2.BN.8.6.2 Annotation Hierarchy And Range Source Contract Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把 `AnnotationTruth` 的父子层级从 UI 约定升级为数据契约，并为后续 source-backed range 文本编辑准备可测试的 offset / rebase 地基。

**Architecture:** V2.BN.8.6.1 通过 UI resolver 临时保证 child label 不再作为顶层 card 展示，但它仍然暴露出一个根问题：child annotation 自己身上没有稳定的 parent truth。V2.BN.8.6.2 要把 `parent_annotation_id` 正式加入 AnnotationTruth 层级，让 Annotation Stack、SelectionDraft、ReadingInterpretation、未来 relation endpoint 都能用同一套层级规则。Range 文本直接编辑不在本版本贸然做 UI 成品；本版本先定义 source-backed range identity、offset rebasing、child preservation 和 undo/redo 期望。

**Tech Stack:** React 18, TypeScript, Vite, Coincides Canvas Engine runtime, TextFlow / TextUnit, AnnotationTruth service, SelectionDraft service, model contract smoke, Henry manual visual pass.

## 1. Why This Version Exists

8.6.1 的补丁已经让 child label 不再平铺成顶层 card，但这个修法仍然是运行时推断：

```text
selected child id
  -> scan every parent.child_annotation_ids
  -> infer root parent
  -> render parent card
```

这个规则能兜住 UI，但不够结实。因为从 child annotation 自己的字段看，它仍然像一个普通 root annotation。后续一旦接入 relation endpoint、ReadingInterpretation、range source editing、undo/redo 或跨 block selection，这个隐性层级会继续制造债务。

V2.BN.8.6.2 要把这一点正式化：

```text
AnnotationTruth.parent_annotation_id === null
  -> root annotation
  -> can render as top-level Annotation Stack card

AnnotationTruth.parent_annotation_id !== null
  -> child annotation
  -> can only render under parent
  -> may be edited, hidden, deleted, and later used as endpoint
  -> but must not become a sibling card by default
```

同时，8.6.1 已经把 range preview 变成 child label 的创建入口。下一步自然会遇到“能不能直接改 range preview 文本”的问题。这个功能不能直接做成普通输入框，因为那会变成 detached copy。正确方向必须是：

```text
edit range preview text
  -> update original TextFlow source
  -> rebase affected annotation ranges
  -> preserve parent/child hierarchy
  -> integrate undo/redo
```

所以 8.6.2 的第二个职责是写清楚并打出第一版 source-backed range editing 地基。实际 range preview 直接编辑 UI 默认留给 8.6.3，除非 8.6.2 的层级契约提前稳定且风险很低。

## 2. Product Decisions

### 2.1 Child Label Is Not A Sibling Label

Child label 的产品定义：

```text
Child label 是 parent label 内部某个语义片段的解释。
它可以有自己的数据 id 和 range。
但它的阅读语境来自 parent。
```

例子：

```text
Parent label:
  label = "definition"
  range = "CSGO is Henry's favourite game."

Child label A:
  label = "concept name"
  range = "CSGO"

Child label B:
  label = "description"
  range = "Henry's favourite game"
```

用户视角里，`concept name` 和 `description` 不应该和 `definition` 平级。它们是在解释 `definition` 这条 annotation 的内部结构。

### 2.2 Parent Ownership Must Live On The Child

8.6.1 之前的结构主要依靠：

```ts
parent.child_annotation_ids = [childId]
```

这个方向不够稳，因为 child 自己不知道 parent 是谁。8.6.2 应该引入：

```ts
parent_annotation_id: string | null
```

推荐 truth 规则：

```text
child.parent_annotation_id 是父子层级 truth。
parent.child_annotation_ids 可以暂时保留为兼容字段或派生缓存。
UI、resolver、contract、future relation endpoint 都应优先读 child.parent_annotation_id。
```

### 2.3 Parent Delete / Hide Cannot Leave Child Ghosts

Parent 和 child 的状态需要先定清楚：

```text
parent hidden
  -> child hidden from top-level visual surfaces
  -> child can still be listed inside parent if inspector explicitly shows hidden state

parent deleted
  -> child should be soft-deleted or orphaned into recovery state
  -> child must not appear as normal root annotation

child deleted
  -> parent remains
  -> parent child list removes or ignores the child
```

8.6.2 的保守选择：

```text
Parent soft delete cascades visual deletion to descendants.
Data can remain recoverable, but no child should render as a visible ghost.
```

### 2.4 Range Preview Is Inspectable, Not A Detached Editor

Annotation Stack 中的 range preview 目前负责展示 marked fragments。后续可以让它编辑，但编辑必须回写原文。

禁止：

```text
edit range preview
  -> only change range_text_cache
```

允许：

```text
edit range preview
  -> update TextFlow unit text
  -> rebase annotation ranges touching same TextUnit
  -> update range_text_cache
  -> preserve child annotation ranges if still valid
```

## 4. Data Contract Delta

### 4.1 AnnotationTruthV1

Current shape:

```ts
export interface AnnotationTruthV1 {
  id: string;
  note_id: string;
  canvas_id: string;
  raw_label: string;
  ranges: AnnotationRangeV1[];
  child_annotation_ids: string[];
  visual_style: {
    color_token: string;
    marker_kind: AnnotationMarkerKind;
  };
  created_by: AnnotationCreatedBy;
  status: AnnotationStatus;
  created_at: string;
  updated_at: string;
  metadata?: Record<string, unknown>;
}
```

Target shape:

```ts
export interface AnnotationTruthV1 {
  id: string;
  note_id: string;
  canvas_id: string;
  raw_label: string;
  ranges: AnnotationRangeV1[];
  parent_annotation_id: string | null;
  child_annotation_ids: string[];
  visual_style: {
    color_token: string;
    marker_kind: AnnotationMarkerKind;
  };
  created_by: AnnotationCreatedBy;
  status: AnnotationStatus;
  created_at: string;
  updated_at: string;
  metadata?: Record<string, unknown>;
}
```

Compatibility rule:

```text
For 8.6.2, keep child_annotation_ids while old code paths are being retired.
New helpers must write both directions consistently.
New readers should prefer parent_annotation_id.
```

Future cleanup:

```text
After all render and relation paths use parent_annotation_id, parent.child_annotation_ids can become derived data or be removed in a later schema cleanup.
```

### 4.2 Annotation Hierarchy Helpers

Add helpers to `client/src/pages/Notes/canvasEngine/annotationEditorService.ts` or split into `annotationHierarchyService.ts` if the file becomes crowded.

Recommended functions:

```ts
export function isRootAnnotation(annotation: AnnotationTruthV1): boolean;

export function getParentAnnotation(input: {
  annotation: AnnotationTruthV1;
  annotations: AnnotationTruthV1[];
}): AnnotationTruthV1 | null;

export function getChildAnnotations(input: {
  parent: AnnotationTruthV1;
  annotations: AnnotationTruthV1[];
  includeHidden?: boolean;
}): AnnotationTruthV1[];

export function resolveAnnotationRootId(input: {
  annotationId: string;
  annotations: AnnotationTruthV1[];
}): string | null;

export function resolveAnnotationInspectorRootIds(input: {
  annotations: AnnotationTruthV1[];
  selectedAnnotationIds: string[];
}): string[];

export function normalizeAnnotationHierarchy(input: {
  annotations: AnnotationTruthV1[];
}): {
  annotations: AnnotationTruthV1[];
  warnings: string[];
};
```

Rules:

- Root means `parent_annotation_id === null`.
- If old data has parent-side child ids but child has no `parent_annotation_id`, normalization fills child parent id.
- If both sides conflict, child parent id wins and warnings record the mismatch.
- Cycles are broken by treating the first repeated node as orphan recovery.
- Deleted annotations are ignored by normal root rendering.

### 4.3 Range Source Editing Foundation

Add a written contract now, even if UI waits.

Required concepts:

```ts
export interface SourceBackedRangeEditIntent {
  annotation_id: string;
  range_id: string;
  replacement_text: string;
}

export interface RangeRebaseResult {
  next_text: string;
  next_ranges: AnnotationRangeV1[];
  invalidated_range_ids: string[];
  warnings: string[];
}
```

Initial helper target:

```ts
export function rebaseTextUnitAnnotationRanges(input: {
  textUnitId: string;
  oldText: string;
  newText: string;
  editedStartOffset: number;
  editedEndOffset: number;
  replacementText: string;
  ranges: AnnotationRangeV1[];
}): RangeRebaseResult;
```

8.6.2 does not need to solve all edit cases perfectly. It needs to define conservative behavior:

- Ranges before edit stay unchanged.
- Ranges after edit shift by delta.
- Ranges fully inside replaced area are invalidated or remapped only if exact containment is clear.
- Ranges crossing the edit boundary are marked invalidated for user review.
- Child ranges follow the same rebase rules as parent ranges.
