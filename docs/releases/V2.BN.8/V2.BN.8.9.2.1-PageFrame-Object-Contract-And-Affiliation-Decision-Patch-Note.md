# V2.BN.8.9.2.1 PageFrame Object Contract And Affiliation Decision Patch Note

Date: 2026-06-26

Status: completed architecture-lock patch before V2.BN.8.9.3.

## Why This Patch Exists

V2.BN.8.9.2 made multiple PageFrames visible and persistent through a transitional note metadata lane. During follow-up review, two architectural questions became important enough to lock before ruler / margin / snap-wall work:

1. Should PageFrame eventually enter the generic `CanvasObject / CanvasPlacement` truth?
2. Should ordinary blocks be owned by a PageFrame?

The decision is:

- PageFrame should become a special `CanvasObject` with generic geometry in `CanvasPlacement` and PageFrame-specific meaning in `PageFrameExtension`.
- Blocks should not be owned by PageFrames.
- The Block/PageFrame relationship should be derived from geometry, not stored as hard ownership.

This keeps Canvas layout readable without turning PageFrame into a second content truth.

## Decisions

### PageFrame Is A Special CanvasObject

PageFrame remains the first highly-special CanvasObject family.

Its final model should split responsibilities this way:

- `CanvasObject`: object identity and broad object kind.
- `CanvasPlacement`: position, size, z-index, and layout geometry.
- `PageFrameExtension`: paper size, content inset, template, export role, primary/secondary role, slots, and other PageFrame-specific behavior.

The current 8.9.2 note metadata persistence under `canvas_engine_page_frames_v1` is still transitional. It is not the final generic CanvasObject database cutover.

### Blocks Are Not Owned By PageFrame

No `block.page_frame_id` ownership model should be introduced.

Instead, a block or other placement can be classified against PageFrames as:

- `inside`: center is inside the PageFrame boundary.
- `crossing`: object intersects the PageFrame boundary but is not cleanly inside.
- `workspace_only`: object is outside all PageFrames.

This relation is used for export/readability/layout decisions, not source ownership.

### `frameId` Is Compatibility Projection, Not Ownership

The current `BlockPlacementModel.frameId` compatibility path can remain for existing runtime projection, but it must not be treated as durable PageFrame ownership.

Long term, PageFrame affiliation should be recomputed from `CanvasPlacement` and PageFrame geometry whenever export / AI-readable layout / crossing policy needs it.

## Code Changes

- Added `pageFrameAffiliationService.ts`.
- Added `PAGE_FRAME_AFFILIATION_MODE = 'geometry_derived_no_ownership'`.
- Added `classifyPlacementAgainstPageFrame`.
- Added `derivePlacementPageFrameAffiliation`.
- Added model-contract coverage that confirms:
  - PageFrame derives into `CanvasObject`.
  - PageFrame derives into `CanvasPlacement`.
  - PageFrame has `PageFrameExtension`.
  - inside/crossing/workspace affiliation never creates ownership.
- Added runtime-boundary coverage that protects the no-ownership affiliation service and rejects hard PageFrame ownership names on runtime types.

## Out Of Scope

- No durable generic `CanvasObject / CanvasPlacement` database migration.
- No `block.page_frame_id`.
- No export preview policy implementation.
- No crossing-object UX.
- No ruler / margin guide / snap wall behavior.
- No PageFrame drag/resize/reorder.
- No ContentGroup projection.
- No Relation runtime.
