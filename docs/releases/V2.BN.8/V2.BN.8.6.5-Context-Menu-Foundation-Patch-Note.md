# V2.BN.8.6.5 Context Menu Foundation Patch Note

Status: patched and browser-harness verified

## What Changed

- Added the first `Command-Surface-Contract.md` for Better Notebook command surfaces.
- Added a pure command taxonomy service for:
  - text selection menu,
  - annotation range preview menu,
  - annotation highlight menu,
  - TextUnit handle menu.
- Added a reusable `ContextMenuLayer` with icons, separators, submenus, disabled states, and outside-click / Escape dismissal.
- Replaced the old right-click selection path with a command-surface menu:
  - user-facing action is now `Label`,
  - `Turn into` is grouped,
  - `Inline` commands are reserved instead of flattened.
- Added a TextUnit handle menu seed:
  - `Turn into` changes TextUnit writing role,
  - `Label this unit` reuses the existing TextUnit annotation path.
- Added an Annotation range preview menu seed:
  - selected range preview text can be copied,
  - selected range preview text can become a `Child label`.
- Added an Annotation highlight menu seed:
  - open label,
  - hide label,
  - copy label range text.
- Reduced the old floating annotation toolbar so regular single-range selection is less intrusive.

## Deliberate Reserves

- Cut / Paste are visible but disabled until custom multi-range mutation is safe.
- Inline formula / inline code / link are visible as reserved commands.
- Remove label from current range is disabled until multi-label and multi-range disambiguation is stable.
- Canvas blank menu, CanvasObject menu, comment / Label Comment, and mini toolbar are not implemented in this patch.

## Manual Test Targets

- Select text, right-click, choose `Label`, and confirm a label is created.
- Select text, right-click, choose `Turn into > Heading / Quote / Bullet / Numbered / To-do / Toggle`, and confirm the TextUnit role changes.
- Right-click a TextUnit gutter, choose `Turn into`, and confirm the row role changes.
- In Annotation Stack, select part of a range preview, right-click, choose `Child label`, and confirm a child label is created under the parent label.
- Right-click a visible label badge / highlighted label area, choose `Open label`, `Hide label`, and `Copy`.

## Known Follow-Up

- Full right-click menu styling will likely need another taste / impeccable pass after Henry manual testing.
- Badge double-click rename remains a follow-up interaction.
- Range-level label removal remains reserved.
- Browser-native edit commands are not replaced yet.

### Retest Matrix

| Annotation badge | Passed | Right-clicking a visible label badge opens the label menu with `Open label`, `Change color`, `Hide label`, `Remove label from this range`, and `Copy`. |

| TextUnit handle / gutter | Partial | A TextUnit handle menu exists, but its hit area is tied to the TextUnit gutter near the unit start. For long wrapped TextUnits, the top of the unit can scroll out of view, making the handle menu feel unavailable from the visible middle of the paragraph. |
| Block shell / layout-selected block | Not implemented | The command surface currently defines no `block_shell` menu. `BlockEditorLayer` only wires right-click for the block annotation badge, not for the block article/body. So selecting a block in layout mode and right-clicking it cannot open a block menu yet. |

### Root Cause Buckets

1. Main text selection uses a fragile live-textarea path.
   `TextBlockProjection.handleTextUnitContextMenu` only opens the selection menu when `textarea.selectionStart !== textarea.selectionEnd`, when an existing draft range contains the caret, or when an annotation contains the caret. In the current Chrome interaction, ordinary selected text on the main writing surface can fail to reach that path as an actionable selection, so the handler returns without creating a menu.

2. Annotation Stack range preview has a separate and healthier route.
   Stack preview text does not prove that the main writing surface is fixed. It has its own context path and can open the range menu even while the main TextBlock textarea route fails.

3. Annotation badge is wired; annotation highlight body is not fully reliable.
   Badges are real buttons with `onContextMenu`. Highlighted text itself is rendered visually, but the textarea can sit on top for editing, so right-clicking the visual highlight may not target the annotation layer.

4. Block context menus are reserved, not broken.
   The current command taxonomy has no block shell menu. The lack of a layout/block right-click menu is therefore an implementation gap rather than a browser inconsistency.

5. TextUnit handle menu exists but has a reachability problem.
   The handle/gutter is currently a small strip at the TextUnit start. For long TextUnits, the user can be reading or editing far below the top of the same unit, with no local handle nearby.

### Follow-Up Patch Scope

1. Stabilize main text selection right-click.
   - On `contextmenu`, prefer an existing SelectionDraft when it contains the clicked text unit/range.
   - If the live textarea still has a native selection, capture it into SelectionDraft before opening the menu.
   - Do not rely only on browser-native selection surviving until the right-click handler.

2. Make annotation highlight right-click deterministic.
   - If right-click lands on text that belongs to an annotation highlight but the target is the textarea, resolve the annotation by caret / offset and open the annotation menu.
   - Keep badge right-click behavior as the stable explicit path.

3. Add a seed block shell command surface, or explicitly defer it in the UI.
   - Suggested seed actions: label block, save block, include/exclude export, hide/show AI visibility, move/trash block.
   - This should be a separate `block_shell` / `block_selection` surface in `Command-Surface-Contract.md`, not mixed into text selection.

4. Improve TextUnit handle reachability.
   - Keep the gutter menu, but consider a visible row/paragraph handle policy for long TextUnits.
   - A later polish pass can decide whether handle should float with the visible line, be repeated per wrapped visual line, or be replaced by a right-click TextUnit body menu.

### Immediate Recommendation

The next code patch should prioritize item 1 first. It is the user-visible blocker: ordinary selected text in the main writing surface cannot reliably open the right-click menu, which makes `Label`, `Turn into`, and `Inline` feel absent. Block shell and TextUnit handle reachability can follow after the main text path is reliable.

### Patch Targets

1. Main text selection menu must be captured before Chrome collapses the textarea selection.
   - Treat live textarea selection, existing SelectionDraft, and native `window.getSelection()` as inputs to one draft resolver.
   - Open the text selection menu from the resolved draft instead of relying on `selectionStart !== selectionEnd` after right-click.

2. TextUnit body should have a fallback menu.
   - If a right-click lands on a TextUnit body with no text selection and no annotation hit, open the TextUnit menu for that unit.
   - This does not replace the gutter; it makes long wrapped units usable when the gutter is off-screen.

3. Block shell needs a first-class command surface.
   - Add `block_shell` as its own command surface rather than forcing block actions into text selection.
   - Seed actions can stay minimal: label block, save block, export visibility, AI visibility, trash.

4. SelectionDraft cleanup needs to be explicit.
   - Clicking away should clear native browser selection and Coincides draft selection together.
   - Otherwise Chrome selection can visually survive while Coincides has no actionable draft.

## Corrective Patch - 2026-06-17

Status: patched and browser-harness verified.

### Fresh Reproduction

Henry reported that Chrome still felt inconsistent:

- selected ordinary text sometimes had no right-click menu;
- layout-selected blocks still did not reliably expose a block menu;
- Annotation Stack range menus worked, which made the missing main-surface menus feel especially suspicious.

Browser harness retest narrowed the real remaining failures to two specific hit-testing gaps:

1. Highlighted label text was visually present, but the editable textarea was still the top hit target. Right-clicking the highlighted body could therefore miss the `LABEL` menu unless the user hit the badge.
2. In Layout mode, right-clicking near the TextUnit gutter / row controls could still open or attempt the TextUnit route instead of the `BLOCK` route.

### Fix

- Main TextBlock context handling now resolves the clicked textarea coordinate back into a TextUnit text offset.
- If that offset falls inside an annotation range, the right-click opens the `LABEL` menu even when the textarea is the actual hit target.
- Layout mode now gives block shell semantics priority over TextUnit/gutter semantics.
- The TextUnit gutter no longer opens the TextUnit menu while Layout mode is active, allowing the event to bubble to the block shell.

### Browser-Harness Verification

| Area | Result | Notes |
| --- | --- | --- |
| Selected ordinary main text | Passed | Right-click opens `SELECTION` with Copy / Cut / Paste / Label / Turn into / Inline / Link. |
| TextUnit body without selected text | Passed | Right-click opens `TEXT UNIT`. |
| Highlighted annotation body, not badge | Passed | Right-clicking text where the textarea is the top hit target now resolves the annotation range and opens `LABEL`. |
| Annotation badge | Passed | Right-click opens `LABEL`. |
| Annotation Stack range preview | Passed | Right-click opens `RANGE`. |

## Henry Manual Retest Discovery - Native Browser Prompt

Status: discovered; patch required.

Henry manual testing found that choosing `Label` from the main writing-surface context menu opens the browser-native `window.prompt()` dialog (`localhost:5173 shows / Label name`) with `definition` prefilled.

This is not acceptable as a product interaction:

- it breaks the Coincides-owned command surface;
- it visually feels like a raw prototype / browser debug prompt;
- it blocks the note surface with a modal outside the app design system;
- it also suggests that other label-name entry paths may still be using the same primitive prompt helper.

Root cause pointer:

- `NoteWritingSurfaceLayer.promptForLabel()` still calls `window.prompt('Label name', fallback)`.
- Current call sites include normal `Label`, `Child label`, and `New annotation set`.

Patch requirement:

- Replace browser-native prompts with a Coincides-owned lightweight label input.
- Prefer an inline command-menu continuation, popover input, or controlled mini panel near the context menu.
- `Label` should feel like part of the right-click command surface, not a browser alert flow.
- The same replacement should cover `Child label` and annotation set creation if they share the same helper.
