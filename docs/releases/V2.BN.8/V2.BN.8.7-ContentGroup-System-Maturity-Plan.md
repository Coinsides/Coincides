# V2.BN.8.7 ContentGroup System Maturity Plan

> Status: active planning target after the 2026-06-22 roadmap correction.
>
> Master execution plan: `docs/releases/V2.BN.8/V2.BN.8.7-ContentGroup-System-Maturity-Master-Plan.md`

## Goal

V2.BN.8.7 moves the current ContentGroup work from "three working surfaces" to a coherent `ContentGroup System 1.0`.

```text
ContentGroup System 1.0:
make ContentGroup stable, understandable, reusable, and ready to be referenced by future Canvas projections.
```

The version exists because the next CanvasObject track will depend on ContentGroup as a reusable object. If ContentGroup remains unclear, Canvas will inherit the confusion.

## Scope Lock

### In Scope

- Rail / Gallery / Single Editor role cleanup.
- OpenDesign visual parity follow-through where it directly improves the three ContentGroup surfaces.
- Member and source boundary hardening.
- First explicit `ContentGroupMember != ContentRange` product contract in runtime code and docs.
- GroupFolder / Gallery resource-manager maturity.
- Reference / Duplicate / Fork / Materialize / Open original language and first service boundaries.
- Empty, stale, archived, deleted, rejected, draft, accepted, and orphaned states where they affect normal ContentGroup use.
- Browser and model-contract checks for the matured flows.
- Documentation sync for Roadmap, V2.BN.8 README / Plan, ContentGroup / GroupFolder contract, Review, Experience Review, CHANGELOG, and Open Issues.

### Out Of Scope

- CanvasObject / media / drawing seed.
- Cross-note CanvasObject reuse.
- Full multi-entity database migration out of note metadata in one pass. The staged exceptions are explicit small versions: `V2.BN.8.7.1` cuts the `ContentGroup` root entity, `V2.BN.8.7.2` cuts `GroupFolder` / folder placement, and later 8.7.x versions cut `ContentGroupMember` and `ContentGroupPetal`.
- Full GraphRAG / graph database storage.
- Relation runtime / relation line overlay.
- AI autonomous ContentGroup generation beyond documented proposal hooks.
- Full source reconstruction or full bidirectional source editing.

## Product Rule

ContentGroup must be able to answer these questions before Canvas depends on it:

```text
What am I?
Where am I organized?
What are my members?
Where did I come from?
Am I synced with the source?
What happens when I am referenced, duplicated, forked, or materialized?
```

## Work Blocks

### 1. Three-Surface Role Cleanup

Rail, Gallery, and Single Editor must stop competing as three partial control centers.

```text
Rail:
  collect, quick inspect, quick enter from current note.

Gallery:
  organize, search, browse folders, manage cross-note/project group scope.

Single Editor:
  refine members, petals, identity, summary, role, topic, and source relationship.
```

Acceptance target: a user can tell whether they are collecting, organizing, or refining.

### 2. Member / Source Boundary

The version should make the current product doctrine explicit:

```text
ContentGroupMember is group-local content truth.
ContentRange / SourceAnchor is source location truth.
They are linked, but they do not auto-sync.
```

Runtime and docs should start expressing:

- member current content;
- source reference;
- source snapshot;
- sync status;
- refresh from source;
- apply member back to source.

This does not require the full member/source database migration yet, but it should stop treating `preview_text` as if it were enough to model member content. `V2.BN.8.7.1` handles the root `ContentGroup` entity cutover first; member/source table work remains separate.

### 3. GroupFolder / Gallery Resource Manager

GroupFolder should feel like a resource manager for ContentGroups, not a local note metadata category.

Implementation plan: `docs/releases/V2.BN.8/V2.BN.8.7.2-GroupFolder-Entity-And-Placement-Cutover-Plan.md`.

Minimum maturity:

- create folder;
- move group;
- inspect current folder membership;
- distinguish active / archived / deleted states;
- keep room for future multi-placement or saved graph scope;
- avoid implying that moving a group moves source text.

### 4. Reuse Semantics

ContentGroup needs a stable reuse language before CanvasObject reuse begins.

```text
Reference:
  link to the original group without changing its body.

Duplicate:
  create a copy in the current context.

Fork:
  create a local editable branch while preserving lineage.

Materialize:
  write members into a note, first version usually one member = one block.

Open original:
  navigate to the source object or source note.
```

The UI may expose only part of this in 8.7, but the service and docs should avoid using contradictory names.

### 5. Stability And State Pass

ContentGroup System 1.0 should handle normal edge states without collapsing into ambiguity:

- empty group;
- group with stale source;
- orphaned member;
- deleted source note;
- archived folder;
- rejected / accepted identity;
- edited member after accepted identity;
- petal with no fragments;
- materialize target unavailable.

This pass should prefer clear messaging and safe no-op behavior over aggressive automation.

## Deferred Canvas Track

The previous V2.BN.8.7 CanvasObject / media / drawing plan is deferred.

```text
V2.BN.8.8+:
  CanvasObject / media / drawing seed.

V2.BN.8.9+:
  Canvas reliability / scale / export reserve.
```

When the CanvasObject track resumes, CanvasObject should treat ContentGroup as an underlying reusable object and should create a canvas projection / placement instead of copying ContentGroup body data into the canvas object.

## Close Criteria

V2.BN.8.7 can close when:

- Rail / Gallery / Single Editor each have a clear role.
- ContentGroup members can be explained without confusing them with original source ranges.
- GroupFolder / Gallery can organize groups without implying source text movement.
- Reference / Duplicate / Fork / Materialize / Open original have stable product meanings.
- Existing ContentGroup checks pass.
- Browser pass confirms the three surfaces are understandable enough for Henry manual review.
- V2.BN.8 docs no longer present CanvasObject seed as the active 8.7 target.
