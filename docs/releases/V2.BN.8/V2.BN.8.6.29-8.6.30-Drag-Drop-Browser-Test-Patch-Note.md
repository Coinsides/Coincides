# V2.BN.8.6.29-8.6.30 Drag Drop Browser Test Patch Note

## Context

This note records the first Browser Harness smoke test for the drag/drop work added in:

- `V2.BN.8.6.29-Global-Drop-to-Block-Foundation`
- `V2.BN.8.6.30-TextFlow-Drag-Reorder-Insert-Safety-Gate`

The test used a fresh test account from `.env`, a newly created smoke project, and a newly created note with a long TextFlow paragraph block.

## Passed

- The smoke note loaded with multiple TextUnit rows.
- A text selection could become a Draft Range visually.
- The text-selection context menu opened correctly.
- `Label` created a visible annotation badge and highlight.
- `Create group from label` created a ContentGroup in the right Groups Rail.
- Group Gallery opened from the current note folder.
- Single ContentGroup Editor opened from the group card.
- `New petal` created a Petal.
- A member source range could be assigned into the Petal.
- Removing a Petal fragment did not delete the top-level member or source label.
- Re-assigning the fragment and refreshing the editor preserved the Petal fragment.

## Failed

### 1. Draft Range drop to blank area does not create a new TextBlock

Observed behavior:

- Draft Range handle appears above the selected text.
- Dragging the handle into blank note/page space does not create a new block.
- The original block remains unchanged.
- Follow-up inspection also showed the handle could fail before `dragstart` because its mouse handlers called `preventDefault()`.

Expected behavior:

- Dropping a Draft Range into blank note/page space should create a new TextBlock using copied text.
- Source text must remain untouched.

### 2. Label badge drop to blank area does not create a new TextBlock

Observed behavior:

- Label badge drag starts successfully.
- Dragging the badge into blank note/page space does not create a new block.
- TextUnit count remains unchanged.

Expected behavior:

- Dropping a label badge into blank note/page space should create a new TextBlock from the label's range text.
- Source label and source text must remain untouched.

### 3. Drag into existing TextFlow is likely blocked by the same root cause

Observed evidence:

- The real browser drag event sequence shows `dragstart`, `dragenter`, and `dragover`.
- No `drop` event is emitted on the blank target.
- `dataTransfer.types` includes `application/x-coincides-content-item` and `text/plain`.

Likely impact:

- Existing TextBlock/TextFlow insertion may also fail because the TextUnit `dragover` handler uses the same payload-reading gate.

### 4. Default label name leaks semantic meaning

Observed behavior:

- The normal Label entry initialized its label name as `definition`.
- The multi-range selection toolbar also reset its label draft to `definition`.
- If a user or future Agent accepted the default, the system would store a semantic role that was never explicitly chosen.

Expected behavior:

- Generic Label actions must not imply a knowledge role.
- Explicit commands such as `/definition` may still create a `definition` label because the user intentionally chose that role.
- Generic Label creation should use a neutral per-note label name, such as `Label 1`, `Label 2`, or require explicit user input.

Impact:

- This is a product bug, not just a UI quirk. If an Agent creates labels through the same path later, silent `definition` defaults would pollute ContentGroup titles, label badges, and downstream interpretation.

## Root Cause

The current `dragover` handlers call `dataTransfer.getData()` through `readContentGroupDragPayload()` before calling `event.preventDefault()`.

In real browser drag/drop, `dataTransfer.types` is available during `dragover`, but custom payload content is often not readable until `drop`. Because `dragover` cannot read the payload yet, the handler does not call `preventDefault()`. The browser then refuses to dispatch the final `drop` event.

Affected code paths:

- Blank surface drop foundation in `NoteWritingSurfaceLayer`
- TextFlow insertion drop foundation in `TextBlockProjection`
- Groups Rail drop foundation in `ContentGroupPanel`

The Draft Range handle also had a separate drag-start blocker:

- `TextBlockProjection` prevented the default mouse down/up behavior on the draggable Draft Range handle.
- That made the handle visibly present but unreliable as a native drag source.

## Patch Direction

Change drag/drop gating into two stages:

1. During `dragover`, only check whether `event.dataTransfer.types` contains `application/x-coincides-content-item` or `text/plain`.
2. Call `event.preventDefault()` and set `dropEffect = 'copy'` when the drag type is supported.
3. During `drop`, read the full payload with `readContentGroupDragPayload()`.
4. If payload parsing fails at `drop`, do nothing safely.

This should unblock both:

- Draft Range / Label -> blank area -> new TextBlock
- Draft Range / Label -> existing TextFlow -> copied text insertion

Change generic Label naming:

1. Replace generic `definition` defaults with a neutral per-note name like `Label 1`.
2. Keep explicit `/definition` behavior unchanged.
3. Keep the service-level empty-label fallback semantic-neutral.

## Patch Applied

- Added a drag-type gate so `dragover` checks `dataTransfer.types` instead of reading the custom payload body too early.
- Updated blank page drops, TextFlow insertion drops, and Groups Rail drops to use the drag-type gate.
- Removed `preventDefault()` from the Draft Range handle mouse down/up handlers so native `dragstart` can fire.
- Changed generic label toolbar and text-selection prompt defaults from `definition` to neutral `Label N` names.
- Changed the low-level empty-label fallback from `Untitled annotation` to `Untitled label`.

## Patch Verification

- `npm run build:client` passed after the drag/drop and default-label changes.
- Right-click generic Label prompt now initializes as `Label 1`, not `definition`.
- Multi-range toolbar label input now initializes as `Label 1`, not `definition`.
- Saving that multi-range label produced one label with two ranges.
- Label badge drop to blank page space created a new TextBlock.
- Label badge drop into an existing TextFlow inserted copied text without removing the source label.
- Draft Range handle now fires `dragstart`.
- Draft Range handle drop to blank page space created a new TextBlock.
- Draft Range handle drop into an existing TextFlow inserted copied text.

## Multi Range Label Browser Test

This follow-up test used a clean note with four TextUnits. The tested path was:

1. Select a partial range in the first TextUnit.
2. Hold `Ctrl` and select a second partial range in the third TextUnit.
3. Create one label from the two draft ranges.
4. Create a ContentGroup from that label.
5. Open the Single ContentGroup Editor.
6. Create a Petal and assign both source ranges into it.
7. Refresh the page and verify persistence.

### Passed

- `Ctrl` additive selection produced two draft ranges in the same selection session.
- The label toolbar showed `2 ranges`.
- Creating the label persisted one annotation with `ranges.length === 2`.
- The two persisted ranges kept separate `text_unit_id`, offsets, and cached preview text.
- `Create group from label` created one ContentGroup member from the label.
- The ContentGroup member preserved both underlying source ranges in `metadata.source_ranges`.
- The Single ContentGroup Editor displayed the member as one annotation source with two separate `TEXT RANGE` entries.
- Creating a Petal and assigning both entries produced two ContentGroup fragments.
- The Petal persisted both fragment ids after page refresh.

### Superseded Automation Caveat

An earlier browser automation pass changed the label input value through DOM scripting once, but React state still submitted the old default `definition` label. That evidence is now superseded by this patch because generic Label defaults no longer use `definition`.

Current verification:

- right-click generic Label prompt initializes as `Label 1`;
- multi-range toolbar Label input initializes as `Label 1`;
- saving the multi-range label persisted one `Label 1` annotation with two ranges.

### Result

The multi-range label core path is healthy:

- one label can contain multiple text ranges;
- that label can become one ContentGroup member;
- the member can be split into multiple Petal fragments;
- refresh persistence keeps the ranges, fragments, and Petal assignment.
