# V2.BN.8 8.6.12 之后 ContentGroup Editor 阶段路线

status: planning reference
created: 2026-06-19 America/Toronto
scope: ContentGroup Editor、GroupFolder、Groups Rail、Group Gallery、Single ContentGroup Editor、Item intake、全局拖拽能力

> 这份文档记录 8.6.12 之后 ContentGroup Editor 的阶段路线。它暂时不是小版本切分文档，而是后续切小版本之前的总纲。真正的小版本编号、实现顺序和验收标准，会在这份路线被确认之后再拆。

## 0. 核心参考与负面提示

主要参考：

- `docs/brainstorm/产品完善/会议记录/2026-06-18-1510-ContentGroup-Editor-Three-Surface-Interaction-Meeting-Notes.md`
- 2026-06-19 主线程里关于 `Item`、`Draft Range`、`Label`、`GroupFolder`、`Gallery`、`Rail`、`Petal`、全局拖拽行为的补充讨论。

明确的负面提示：

- 不要把 Group Gallery 做成气泡窗。
- 不要把 Group Gallery 做成浮在 Page / Canvas 上的局部面板。
- 不要把 Groups Rail 做成万能编辑器。
- 不要把所有操作按钮都浮在表面。
- 不要为了保留测试数据而设计 legacy adapter。
- 如果数据结构重构需要清空现有测试账号数据，可以清空。当前没有投产用户，所有账号均是测试账号。

三层界面的总规则：

```text
Groups Rail = collect
Group Gallery = organize
Single ContentGroup Editor = refine
```

更直白地说：

```text
Rail 管现场收集。
Gallery 管全局整理。
Editor 管单包精加工。
```

## 1. 最终界面角色

### 1.1 Groups Rail：当前 scope 的轻量整理盒

Groups Rail 是跟随当前 navigation scope 的迷你资源管理器。

它的入口来自全局 `Groups / Content` 按钮。这个按钮不应该只存在于 Note 页面，而应该跟随当前用户所在位置变化。

规则：

```text
在 Projects / 全局区域打开
  -> 显示 project-level 或 workspace-level group scope

在某个 Project 内打开
  -> 显示当前 project root GroupFolder

在某个 Note 内打开
  -> 显示当前 note root GroupFolder
```

一句话：

```text
在哪里打开 Groups，就看到哪里对应的 root group folder。
```

Groups Rail 负责：

- 快速查看当前 scope 下的 folders / groups。
- 新建 ContentGroup。
- 接收当前 item。
- 设置或显示 active group。
- 展开轻量预览。
- 跳转到完整 Group Gallery。
- 跳转到 Single ContentGroup Editor。

Groups Rail 不负责：

- 全局 folder 管理。
- 大规模筛选。
- 批量管理全部 ContentGroups。
- 复杂字段编辑。
- Petal 精细管理。
- 替代 Group Gallery。

Groups Rail 的视觉目标：

```text
窄、轻、安静、跟随当前页面位置。
```

### 1.2 Group Gallery：全屏资源管理区

Group Gallery 是全屏资源管理器。

它必须和 Page / Canvas 平行：

```text
Page
Canvas
Group Gallery
```

Group Gallery 不是右侧栏扩展，不是气泡窗，也不是局部浮层。

左侧导航栏需要新增一个一级入口：

```text
Group Gallery
```

这个入口和 `Home`、`Projects`、`Source Library`、`Template Studio`、`Settings` 平级。

Group Gallery 负责：

- 浏览 GroupFolder tree。
- 查看当前 folder 下的子 folder。
- 查看当前 folder 下的 ContentGroups。
- 支持 Project root folder 和 Note root folder 视图。
- 支持 workspace-level folders。
- 支持 Folder / Topic / Role 三种视图。
- 支持批量整理。
- 从某个 ContentGroup 进入 Single ContentGroup Editor。
- 必要时跳回原 Project 或 Note。

默认展示规则：

```text
子 folder 优先显示。
ContentGroup 后显示。
ContentGroup 默认按 updated_at 倒序排列。
```

Gallery 顶部视图切换：

```text
Folder | Topic | Role
```

关键规则：

```text
Folder 回答：它在哪里？
Topic / Role 回答：它是什么？
```

Topic / Role 不能替代 folder 系统。它们只是当前 folder 范围内的重排和聚合。

### 1.3 Single ContentGroup Editor：单个内容包精加工台

Single ContentGroup Editor 只服务于一个 ContentGroup。

它负责：

- 查看 ContentGroup 的 display name、identity、topic、role、summary。
- 查看 members。
- 查看每个 member 的 source reference。
- 把 member 里的局部内容分配给 Petal。
- 新建、重命名、删除 Petal。
- 从 member 跳回原文位置。
- 为后续 relation 版本保留清晰、可追溯的内容结构。

它不负责：

- 浏览全局 folder tree。
- 批量整理多个 ContentGroup。
- 替代 Group Gallery。
- 替代 Groups Rail。

一句话：

```text
Single Editor 是工作台，不是资源管理器。
```

## 2. 核心对象定义

### 2.1 Draft Range

Draft Range 是临时选区。

它可以是：

- 连续文字选区。
- Ctrl 多段选区。
- 用户还没有保存成 Label 的临时 range package。

Draft Range 不是知识对象。它是交互过程中的临时对象，也是可能进入 ContentGroup 的 item 来源。

### 2.2 Label

Label 是持久化的、有名字的 range package。

它和 Draft Range 的底层逻辑非常接近：

```text
Label = named persistent set of Draft Range-like source ranges
```

两者区别主要在生命周期和视觉呈现：

- Draft Range 是临时的。
- Label 是持久化的。
- Label 有 display name。
- Label 可以在正文里显示高光。
- Label 可以被反复作为 item 使用。

Label 不是 ContentGroup。它只是用户在正文里做标记和复用选区的方式。

当 Label 被加入 ContentGroup 后，它应该被视为一个 range package。在完整 Editor 里，它可以被拆开：

```text
Label item
  range A -> Petal: concept name
  range B -> Petal: description
  range C -> 保留为 source package 的一部分
```

### 2.3 Item

Item 是动作层概念。

凡是可以被选中、拖拽、右键加入 ContentGroup 的东西，都可以叫 item。

第一阶段 item 包括：

- Draft Range item。
- Label item。
- Block item。

未来扩展 item 包括：

- Table region item。
- Image region item。
- Canvas object item。
- ContentGroup reference item。

暂时不把 TextUnit 单独作为第一阶段 item。用户如果想要整个自然段，就选中整个自然段即可。

### 2.4 ContentGroupMember

ContentGroupMember 是 item 进入 ContentGroup 后形成的稳定引用。

它不应该复制原文真相，而应该保存 source reference。

可能的 member source：

```text
Text range
Multi-range package
Label
Block
Future table region
Future image region
Future canvas object
Future ContentGroup reference
```

### 2.5 ContentGroup

ContentGroup 是内容包。

它的产品目的：

```text
把散落、混杂、松散的知识碎片，整理成更紧凑的知识集合。
```

ContentGroup 不会把原文从 note 中搬走。它建立的是引用、映射和整理关系。

例子：

```text
某个 Note 包含 Chapter 1 到 Chapter 3。

Chapter 1 下面有一个 ContentGroup:
  Definition of Power Series

它的 members 可能包括：
  - 包含 concept name 的 range
  - 包含 definition description 的 range
  - 一个包含相关例子的 Label
  - 一个公式 block
```

### 2.6 Petal

Petal 是 ContentGroup 内部的局部角色。

它回答的问题是：

```text
这个碎片在当前 ContentGroup 里扮演什么角色？
```

例子：

- concept name
- description
- condition
- statement
- example
- example result
- proof step
- remark

Petal 不是 child label。

Petal 不需要第一阶段做排序。第一阶段的重点是分配，而不是排序。

未来可以允许用户拖动 Petal 来改变视觉位置，但当前地基不应该依赖 Petal 排序。

### 2.7 GroupFolder

GroupFolder 是 ContentGroup 的组织目录。

它回答的问题是：

```text
这个 ContentGroup 放在哪里？
用户现在处于哪个浏览边界？
这个 group 的 folder path 给它什么上下文？
```

GroupFolder 不是 ContentGroup。

Project 和 Note 是文档世界的 scope。它们可以拥有系统 root GroupFolder，但它们不是 GroupFolder 本身。

每个 Project 和 Note 都应该有一个系统 root GroupFolder：

```text
Project: AMATH 231
  system root GroupFolder: AMATH 231 groups

Note: Chapter 1-3 note
  system root GroupFolder: Chapter 1-3 note groups
```

GroupFolder path 替代显式 ContentGroup depth：

```text
Depth 从 folder path 派生。
Depth 不是 ContentGroup 的用户显式主字段。
```

## 3. 阶段路线

### 阶段 1：对象与数据契约定型

目标：

先稳定概念和数据边界，再扩展界面。

需要定型：

- Draft Range。
- Label 作为持久化 range package。
- Item 作为动作 payload。
- ContentGroupMember 作为 source reference。
- ContentGroup 作为内容包。
- Petal 作为局部角色。
- GroupFolder 作为组织目录。

关键决定：

- Label 和 Draft Range 进入 ContentGroup 时，处理方式基本一致。
- Label 继续承担正文高光和可复用 range package 的作用。
- AnnotationSet 不应继续作为长期核心模型。
- TextUnitGroup 需要重新评估，它更像 ContentGroup / item grouping 的历史前身，不应继续作为用户侧核心结构。
- Child label 退场，因为 Petal 接管 ContentGroup 内部局部角色划分。

数据重构原则：

```text
当前没有投产用户。
所有现有账号均为测试账号。
如果干净的数据结构需要删除现有账号数据，可以删除。
不要为了测试数据设计 legacy adapter。
```

### 阶段 2：GroupFolder 地基

目标：

建立组织目录系统，避免 ContentGroup 同时承担 folder、depth、scope、relation boundary 等职责。

需要支持：

- Workspace-level folders。
- Project system root folders。
- Note system root folders。
- 用户创建的普通 folders。
- 移动 folder。
- 必要时复制 folder。
- 后续 AI 生成 folder 时的 origin / status。

暂时不要：

- Pin folder。
- Link folder。
- Shortcut folder。
- 多种 folder 类型。

一种 folder 类型足够：

```text
GroupFolder
  origin: system | user | ai
  status: temporary | saved | archived
  parent_folder_id
  scope hints
```

Folder 行为：

- Folder location 决定组织路径。
- Folder path 派生 depth。
- Folder boundary 后续可以限制 relation view。
- Folder 不拥有 relation truth。

### 阶段 3：入口体系

目标：

让 ContentGroup 在 workspace、project、note 中都有自然入口。

入口 1：左侧导航栏

```text
Group Gallery
```

这个入口打开全屏 Group Gallery。

入口 2：全局 scope-aware Groups / Content 按钮

这个按钮打开 Groups Rail，并跟随当前 navigation scope。

规则：

```text
从 project overview 打开 -> project-level 或 workspace-level scope
从 Project 内打开 -> 当前 project root GroupFolder
从 Note 内打开 -> 当前 note root GroupFolder
```

入口 3：Rail 跳转 Gallery

Groups Rail 必须能从当前 folder / scope 打开完整 Gallery。

入口 4：Rail 跳转 Single Editor

每个 group row 可以打开对应的 Single ContentGroup Editor。

### 阶段 4：Item intake

目标：

确定用户如何把碎片扔进 ContentGroup。

第一阶段支持三类 item：

- Draft Range。
- Label。
- Block。

基本路径：

```text
用户选中文字
  -> 形成 Draft Range
  -> 可以直接加入 ContentGroup
  -> 也可以保存为 Label
  -> Label 之后也可以加入 ContentGroup
```

加入方式：

- 拖拽。
- 右键菜单。
- 少量浮在表面的按钮。

规则：

```text
Label 是可复用的 Draft Range 包。
Label 被加入 ContentGroup 时，不应该被当成不可拆的原子。
完整 Editor 里可以拆解 Label 的内部 ranges。
```

### 阶段 5：全局拖拽地基

目标：

把拖拽视为全局编辑基础能力，而不是 ContentGroup 专属功能。

拖拽要服务于：

- 整理知识。
- 移动或复制文本。
- 生成新 block。
- 重新排列 block 或文本片段。
- 把 item 加入 ContentGroup。
- 把 member 细分到 Petal。

第一阶段可拖拽 payload：

- Draft Range。
- Label。
- Block。

ContentGroup 相关 drop target：

- Drop 到 active group。
- Drop 到 Groups Rail 中的某个 group row。
- Drop 到 Gallery 中的某张 ContentGroup card。
- Drop 到 Single Editor 的 members 区域。
- Drop 到某个 Petal assignment 区域。

非 ContentGroup 的 drop target：

1. Draft Range / Label 拖到 Page 空白区域。

预期行为：

```text
在鼠标落点创建一个新的 block。
新 block 包含被拖拽的文本内容。
原始来源仍应可追溯。
```

第一版应该优先使用非破坏式复制 / projection，除非用户明确执行 move。

2. Draft Range / Label 拖到已有 TextBlock 内部。

预期行为：

```text
插入到鼠标对应的 caret 位置。
如果 source 和 target 是同一个 TextBlock，则可能演变成文本重排操作。
```

同 block 内拖动需要格外谨慎，因为这会改变原文。

3. Draft Range / Label 拖到两个段落之间。

预期行为：

```text
在两个段落之间插入为新的段落或新的 text segment。
```

4. Draft Range / Label 拖到 PageFrame 空白区域。

预期行为：

```text
在鼠标位置创建新的 TextBlock。
```

5. Draft Range / Label 拖到 Canvas scratch 区域。

预期行为：

```text
在 canvas 坐标位置创建新的自由 block。
```

6. Block 拖到 Page 或 Canvas。

预期行为：

```text
根据操作模式 move 或 copy block。
第一版中，已有 block 布局操作可以偏向 move；
ContentGroup intake 则应偏向 reference / copy。
```

拖拽引擎需要：

- 统一 drag payload model。
- source reference 保留。
- drop target resolver。
- drop preview indicator。
- copy / move 行为区分。
- destructive move 的 undo。
- invalid drop target 的安全 fallback。

关键区别：

```text
Drop into ContentGroup = 创建引用 / member。
Drop into document 或 canvas = 创建或改变可见内容。
```

前者不应该改变原文。后者可能改变原文，所以必须有更强的保护。

### 阶段 6：Groups Rail 实现方向

目标：

把 Rail 做成 scope-aware 的迷你资源管理器和 intake surface。

Rail 默认结构：

- 极简顶部。
- 新建 group 图标。
- 关闭图标。
- 搜索 / 筛选后续再做。
- active group 轻提示。
- 当前 scope 下的 folder / group 列表。

Rail 列表项显示：

- display name。
- identity icon。
- expand arrow。
- 可选的轻量 topic color signal。

Rail 默认不显示：

- 大标题。
- 大输入框。
- summary editor。
- topic editor。
- role editor。
- members 明细。
- petals editor。

Rail 上下文操作：

- 从当前 item 创建 group。
- 把当前 item 加入 active group。
- 把当前 item 加入某个具体 group row。
- 打开 editor。
- 打开完整 Gallery。

### 阶段 7：Group Gallery 实现方向

目标：

把 Gallery 做成完整资源管理器工作区。

Gallery 必须全屏。

主要布局：

```text
Top bar:
  breadcrumb
  Folder | Topic | Role view switch
  search / filter / sort 后续再做

Left area:
  folder tree 或局部 folder list

Main area:
  child folders first
  ContentGroup cards second
```

Folder view：

- 显示 folder hierarchy。
- 子 folder 优先。
- ContentGroup 后显示。
- ContentGroup 默认按最近编辑时间倒序。

Topic view：

- 仍然尊重当前 folder boundary。
- folder 仍然优先显示。
- ContentGroup 按 topic 聚合。

Role view：

- 仍然尊重当前 folder boundary。
- folder 仍然优先显示。
- ContentGroup 按 role 聚合。

ContentGroup card 显示：

- display name。
- summary 或 member preview。
- identity icon。
- topic signal。
- role tab 或结构化 marker。
- 必要时显示 member count / petal count。

### 阶段 8：Single ContentGroup Editor 实现方向

目标：

让单个 ContentGroup 可以作为精加工的知识包被编辑。

必要区域：

- Header：display name、identity、source folder path。
- Metadata：topic、role、summary。
- Members：source references、preview、source jump。
- Petals：当前 group 内的局部角色。
- Assignment workspace：把 member fragments 分配给 Petals。

Petal 规则：

- Petal 只属于一个 ContentGroup。
- Petal 不是 child label。
- Petal 可以拥有 member fragments 的引用。
- Petal 第一阶段不需要排序。
- Petal 视觉排序可以后续优化。

Member 拆解：

- Label member 可以展开成内部 ranges。
- Multi-range Draft Range member 可以拆给不同 Petals。
- Block member 后续如果支持，可以暴露内部 range。

### 阶段 9：Command Surface 与按钮瘦身

目标：

避免 UI 继续变成按钮施工现场。

操作分三类：

1. 浮在表面的按钮。

只放高频、明确、不依赖上下文的操作：

- New group。
- Close。
- Back。
- Open Gallery。
- Open Editor。
- Save。

2. 右键菜单。

放对象上下文操作：

- Label。
- Create group。
- Add to group。
- Turn into。
- Inline。
- Link。
- Open editor。
- Move。
- Archive。
- Delete。

3. 拖拽。

放空间整理行为：

- Draft Range 拖进 group。
- Label 拖进 group。
- Block 拖进 group。
- ContentGroup 拖进 folder。
- Content fragment 拖进 Petal。
- Text range 拖到 page / canvas / block position。

判断规则：

```text
如果用户已经指向某个对象，右键菜单可以出现。
如果用户正在整理碎片，拖拽优先。
如果操作是全局、恒定、高频，才浮在表面。
```

### 阶段 10：同步、持久化与完整性

目标：

让系统刷新后稳定，源内容变化后不乱。

必须处理：

- GroupFolder 持久化。
- Project / Note root folder 自动创建。
- ContentGroup 持久化。
- Member source references。
- Petal assignments。
- Label references。
- source range 被删除或改动。
- stale / missing source preview。
- destructive drag / drop 的 undo。

source sync 规则：

```text
ContentGroup preview 不应该成为第二份真相。
source reference 仍然是真相。
preview 可以缓存，但必须可刷新，或者能标记 stale。
```

### 阶段 11：视觉设计阶段

目标：

让三个界面变得可理解、安静、有层级，而不是圆角气泡窗互相套。

这一阶段使用 taste 方向。

推荐视觉语言：

- 资源管理器。
- 属性编辑器。
- 知识整理工作台。
- 边角克制。
- 层级清楚。
- 少嵌套气泡。

避免：

- 气泡窗套气泡窗。
- 圆角输入框密集堆叠。
- Rail 中出现大表单。
- Gallery 变成浮层。
- 明显字段重复写标题。
- 显而易见的图标还配大量文字说明。

三层界面视觉分工：

- Rail：紧凑、安静、跟随当前 scope。
- Gallery：全屏、folder-first、cards / list 管理。
- Editor：聚焦、可追溯、支持精加工。

### 阶段 12：验收阶段

目标：

通过真实用户路径检验系统，而不是只测单个按钮。

手动验收路径：

1. 从 Note 出发：

- 选中文字。
- 形成 Draft Range。
- 保存为 Label。
- 把 Label 拖入 ContentGroup。
- 打开 Single Editor。
- 把 Label 内部 ranges 分配给 Petals。
- 跳回原文。

2. 从 Project 出发：

- 打开 scope-aware Groups Rail。
- 确认显示 project root folder 内容。
- 创建 project-level ContentGroup。
- 从当前 scope 打开 Gallery。

3. 从左侧导航出发：

- 打开 Group Gallery。
- 浏览 workspace folders。
- 浏览 project / note root folders。
- 切换 Folder / Topic / Role 视图。
- 打开 Single Editor。

4. 拖拽行为：

- Draft Range 拖进 ContentGroup。
- Label 拖进 ContentGroup。
- Block 拖进 ContentGroup。
- Draft Range 拖到 Page 空白区域创建 block。
- Draft Range 拖到 Canvas scratch 区域创建 block。
- 同一 TextBlock 内拖动只在安全且可 undo 时启用。

5. 持久化：

- 刷新页面。
- 确认 folders、groups、members、petals 仍然存在。
- 确认 source references 仍可追溯。

### 阶段 13：文档整理阶段

目标：

在实现稳定后，把主文档和正式 contract 统一到新模型。

## 4. ContentGroup Editor 第一版成熟评审标准
