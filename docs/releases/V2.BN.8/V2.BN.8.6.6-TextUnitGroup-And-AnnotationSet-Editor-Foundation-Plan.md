# V2.BN.8.6.6 TextUnitGroup And AnnotationSet Editor Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在进入 V2.BN.8.7 CanvasObject / media / drawing seed 之前，把 V2.BN.8.6 已经做出的 AnnotationTruth 地基补成“可组织”的版本：TextUnitGroup 成为清晰、可操作的写作层 range helper；AnnotationSet 成为可创建、可编辑、可排序、可投影的 annotation collection / composite endpoint seed。完成后，用户可以把自然写作中的行组起来，把多个 label 组织成集合，并让 AI reading projection / future relation 可以读取这套组织结果。

**Architecture:** 8.6.6 插在 8.6.5 Context Menu Foundation 和 8.7 CanvasObject Seed 之间。它不改变根分工：Block 是空间 / 渲染根，TextFlow 是写作根，AnnotationTruth 是语义根，AnnotationSet 是多个 AnnotationTruth 的组织根。TextUnitGroup 不重新升格为 semantic truth，不再写入 `knowledge_role`，只负责稳定 TextUnit 范围；AnnotationSet 承担“多个 annotation 作为一个组”的语义组织和 future CompositeEndpoint reserve。

**Tech Stack:** React 18, TypeScript, Vite, Coincides NoteCanvas runtime, TextFlow / TextUnit / TextUnitGroup, AnnotationTruth / AnnotationSet services, Command Surface contract, Annotation Inspector / Organizer panel, ReadingInterpretation projection, model contract smoke, Henry manual visual pass.

## 1. Version Position

### 1.1 Why 8.6.6 Exists

V2.BN.8.6 已经让用户可以：

- 选择文本；
- 创建 label；
- 创建 child label；
- 给 label 改颜色；
- 编辑 source-backed range preview；
- 通过右键菜单调用部分 text / label 操作；
- 让 AnnotationTruth 成为可保存的 semantic root。

但 8.6 到 8.6.5 仍然缺一层组织能力：

```text
single AnnotationTruth
  -> 可以存在
  -> 可以显示
  -> 可以编辑

many AnnotationTruths
  -> 还不能被舒服地组织
  -> 还不能作为一个用户可见的 group
  -> 还不能稳定投影给 AI / relation
```

同时，TextUnitGroup 已经存在于 contract 和 runtime 类型中，但目前它更像 placeholder / projection seed。它需要明确变成一个真正可用的写作层 range helper。

8.6.6 的职责就是补上这层：

```text
TextUnitGroup
  writing-layer grouping of rows
  stable helper for selection / annotation / extract / split / projection

AnnotationSet
  semantic / organizational grouping of annotations
  future relation composite endpoint reserve
```

### 1.2 Relationship To 8.7

8.7 会引入 CanvasObject / image / drawing / media annotation seed。

如果 8.7 直接开始让图片、画笔对象、region 进入 annotation range，而当前 AnnotationSet 仍然不可编辑，那么后续 relation / AI projection 会继续只能面对散落的 annotation。

因此 8.6.6 是 8.7 的前置稳固版本：

```text
8.6.6
  organize text annotations and text-unit groups

8.7
  introduce canvas objects that can also be annotated

later relation
  can use AnnotationTruth or AnnotationSet as endpoint
```

8.6.6 不做 CanvasObject，但它要让 8.7 新增的 CanvasObject annotation 未来能自然加入 AnnotationSet。

### 1.3 Relationship To A9 Structure Studio

8.6.6 不是完整 Annotation Studio。

A9 仍然负责：

- 完整 annotation proposal review；
- project-local annotation pattern；
- advanced style system；
- annotation workflow customization；
- AI reading/debug projection studio；
- relation proposal / interpretation workflow。

8.6.6 只做当前 note 内的基础组织能力：

- TextUnitGroup basic editor；
- AnnotationSet basic editor；
- projection and command surface integration；
- minimal visual affordance；
- smoke tests and contract update。

## 2. Product Definition

### 2.1 TextUnitGroup Product Meaning

用户不需要知道“TextUnitGroup”这个词。

用户视角：

```text
我把几行内容临时绑在一起。
它们仍然是原来的文字。
它们没有变成一个新知识点。
它们只是被我当作一组行来处理。
```

工程视角：

```text
TextUnitGroup
  groups TextUnit ids
  belongs inside one TextFlow
  helps selection / annotation / split / merge / extract / projection
  does not own semantic meaning
```

它适合解决：

- 用户选中几行，并希望后续能一起操作；
- 一个 annotation 跨多行，需要稳定 range helper；
- 未来 split / extract / promote 时保留行组；
- AI reading projection 需要知道“这些行被用户组织过”；
- future relation 需要知道某个 semantic annotation 的 raw source spans 来自哪些 text rows。

它不适合解决：

- “这几行是什么意思”；
- “这几行是不是 definition”；
- “这几行是不是 prerequisite group”；
- “这几行能不能作为 relation endpoint”。

这些属于 AnnotationTruth / AnnotationSet。

### 2.2 AnnotationSet Product Meaning

用户视角：

```text
我把几个 label 放进一个集合。
这个集合可以叫做 Power Series prerequisites。
集合里面可以有 definition、theorem、example。
它们不需要挨在一起。
它们可以共同成为一个学习组、步骤链、前置条件包。
```

工程视角：

```text
AnnotationSet
  references AnnotationTruth ids
  owns set label / ordering / kind
  can be projected for AI reading
  can later behave as CompositeEndpoint in relation runtime
```

AnnotationSet 适合解决：

- A + B -> C 这种 future relation 需求；
- 多个 annotation 共同构成一个 topic / step chain / prerequisite pack；
- 用户想整理本 note 里某一类被标记出来的知识点；
- AI 需要把多个分散 label 当作一个 reading unit。

它不适合解决：

- 文字本身如何换行；
- 单个 annotation 的 child label；
- rich text 渲染；
- canvas object drawing；
- full relation editor。

### 2.3 TextUnitGroup Versus AnnotationSet

这两个东西容易混，所以 8.6.6 必须把边界写进产品和代码：

| Object | Layer | Owns Meaning | Typical User Wording | Future Relation Use |
| --- | --- | --- | --- | --- |
| TextUnitGroup | TextFlow writing layer | No | group these rows | anchor helper only |
| AnnotationTruth | Semantic label layer | Yes | label this as X | endpoint |
| AnnotationSet | Semantic organization layer | Yes, as a collection | group these labels | composite endpoint |

Example:

```text
Rows 1-3 are grouped visually.
  -> TextUnitGroup

Phrase in Row 1 is labeled "definition".
  -> AnnotationTruth

"definition" + "theorem" + "example" are grouped as "Power Series prerequisites".
  -> AnnotationSet
```

### 2.4 User Experience Target

8.6.6 should feel like this:

1. User writes in a TextBlock naturally.
2. User can select several rows from the TextUnit gutter and group them.
3. A quiet left-side bracket / rail indicates these rows are grouped.
4. User can ungroup or rename the group from a row/group context menu.
5. User can click labels and open an organizer that shows available labels and sets.
6. User can create an AnnotationSet from selected labels.
7. User can add/remove labels from a set.
8. User can reorder set members.
9. User can choose set kind: collection / sequence / all-of.
10. Reading projection prints sets in a way future AI can understand.

8.6.6 should not feel like a heavy database admin UI.

## 5. Data Model Changes

### 5.1 TextUnitGroup Contract Change

Current `TextUnitGroup.knowledge_role` is legacy debt.

8.6.6 rule:

```text
New TextUnitGroup writes must set knowledge_role to null.
No UI may expose knowledge_role.
No service may infer semantics from knowledge_role.
```

Implementation choice:

- Keep the field in TypeScript for compatibility in 8.6.6.
- Add normalization so missing or stale values do not break.
- Write docs saying the field is deprecated and must not be used by new code.
- Future cleanup can remove it when all plans and code paths are stable.

Preferred runtime type after 8.6.6:

```ts
export interface TextUnitGroup {
  id: string;
  label: string | null;
  knowledge_role: string | null; // deprecated compatibility field; new writes use null
  children: Array<TextUnitRef | TextUnitGroupRef>;
  order_index: number;
  metadata: {
    group_kind?: 'manual_rows' | 'annotation_helper' | 'projection_helper';
    collapsed?: boolean;
    color_token?: string;
    [key: string]: unknown;
  };
  status: TextFlowObjectStatus;
}
```

Do not introduce global knowledge roles here.

### 5.2 AnnotationSet Contract Change

Add explicit organization semantics to `AnnotationSetV1`.

New type:

```ts
export type AnnotationSetKind =
  | 'collection'
  | 'sequence'
  | 'all_of';
```

Proposed type extension:

```ts
export interface AnnotationSetV1 {
  id: string;
  note_id: string;
  canvas_id: string;
  label: string;
  description?: string | null;
  set_kind?: AnnotationSetKind;
  annotation_ids: string[];
  status: AnnotationStatus;
  visual_style?: {
    color_token?: string;
    marker_kind?: 'quiet' | 'badge';
  };
  created_at: string;
  updated_at: string;
  metadata?: Record<string, unknown>;
}
```

Compatibility rules:

```text
missing set_kind
  -> collection

missing description
  -> null

missing visual_style
  -> quiet default

annotation_ids order
  -> canonical member order for V2.BN.8.6.6
```

### 5.3 Set Kind Semantics

`collection`:

```text
These annotations belong together.
Order is not important.
```

Example:

```text
Important demand concepts
  - price
  - income
  - information
```

`sequence`:

```text
These annotations are a user-ordered chain.
Order matters for reading.
```

Example:

```text
Assignment 1 solution steps
  1. define variable
  2. apply theorem
  3. simplify result
```

`all_of`:

```text
These annotations together act as a prerequisite pack.
Future relation may use this as A+B -> C.
```

Example:

```text
Power Series prerequisites
  all of:
    - sequence definition
    - convergence theorem
  imply:
    - can understand power series example
```

8.6.6 only stores and projects this meaning. It does not implement relation runtime.

## 6. UX Design

### 6.1 TextUnitGroup UI

TextUnitGroup should be quiet.

Do not add big badges between lines.

Preferred visual:

```text
left edge of TextBlock
  subtle vertical bracket / rail
  optional tiny group label on hover
```

Reason:

- TextUnitGroup is writing-layer scaffolding, not semantic highlight.
- It should not compete with annotation highlights.
- It should not make the page feel like a database panel.

### 6.2 TextUnit Row Selection

Entry points:

1. Click TextUnit handle to select one row.
2. Shift-click TextUnit handle to select a contiguous row range.
3. Ctrl-click TextUnit handle to toggle non-contiguous rows.
4. Right-click TextUnit handle opens row context menu.

Minimum 8.6.6 behavior:

```text
single selected row
  -> context menu includes Group row disabled unless at least 2 rows selected

multiple selected rows in the same TextBlock
  -> context menu includes Group selected rows

selected rows across multiple blocks
  -> Group selected rows disabled
  -> future instruction says use AnnotationSet / future assembly workflow
```

If row multi-select is too much for first patch, fallback acceptable for 8.6.6:

```text
Shift-click contiguous TextUnit handles only.
```

But the final 8.6.6 manual test should prove at least two rows can be grouped.

### 6.3 TextUnitGroup Commands

Commands:

- `Group selected rows`
- `Rename group`
- `Ungroup`
- `Delete group`
- `Focus group`

Command rules:

```text
Group selected rows
  available when >= 2 active TextUnits in the same TextFlow are selected

Rename group
  available when pointer/context is inside a group rail

Ungroup
  removes group object only
  does not delete TextUnits
  does not delete annotations

Delete group
  soft deletes group
  same user effect as ungroup in 8.6.6
  kept separate for future history / audit

Focus group
  scrolls / highlights grouped rows
  no semantic mutation
```

### 6.4 Annotation Organizer UI

Annotation Stack and Annotation Organizer should be separate concepts.

Annotation Stack:

```text
current selected annotation
edit label / color / ranges / child labels
```

Annotation Organizer:

```text
note-level list of annotations and sets
create / edit AnnotationSet
add / remove / reorder members
```

Preferred entry:

- button in Annotation Stack header: `Organizer`;
- command menu action: `Open label organizer`;
- context menu action on highlight: `Add to set`;
- context menu action on selected labels: `Create set from selected labels`.

### 6.5 Annotation Organizer Panel Layout

Panel sections:

```text
Annotation Organizer

Selected labels
  [selection summary]
  [Create set]

Sets
  [Set card collapsed]
  [Set card expanded]

Loose labels
  annotations that are not in any active set
```

Set card expanded content:

```text
set label input
set kind segmented control:
  Collection | Sequence | All-of

description textarea

members:
  1. Annotation label
     preview text
     up / down / remove

actions:
  Add selected labels
  Delete set
```

Visual rule:

- Do not use card-inside-card-heavy nested bubbles.
- One set can be a compact bordered panel.
- Member rows should be dense list rows.
- Details can collapse.

### 6.6 Set Member Selection

8.6.6 can use current selected annotation ids.

Sources of selected annotations:

- clicked annotation badge/highlight;
- Annotation Stack active item;
- future multi-selection state.

If only one annotation is selected:

```text
Create set
  creates set with one member
```

If multiple annotation ids are selected:

```text
Create set
  creates set with all selected members in current selection order
```

If no annotation is selected:

```text
Create set
  disabled
```

### 6.7 Add To Existing Set

From highlight context menu:

```text
Add to set
  submenu:
    Create new set...
    Existing Set A
    Existing Set B
```

If submenu is too expensive in current menu service:

```text
Add to set
  opens Annotation Organizer
  preselects the current annotation
```

The fallback is acceptable for 8.6.6 if documented in patch note.

### 6.8 AnnotationSet Badge Display

8.6.6 does not need visible set badges in the main text.

Reason:

- Text already has annotation highlights and badges.
- Adding set badges risks noise.
- Set membership is an organizational layer, not necessarily a reading overlay.

Allowed minimal indicator:

```text
Annotation Stack / Organizer shows which sets contain selected annotation.
```

Main text set overlay is deferred.

### Task 2: TextUnitGroup Service

Create:

```text
client/src/pages/Notes/canvasEngine/textUnitGroupService.ts
```

Service functions:

```ts
createTextUnitGroup(input: {
  flow: TextBlockContentV1;
  label?: string | null;
  textUnitIds: string[];
  colorToken?: string;
}): TextBlockContentV1

renameTextUnitGroup(input: {
  flow: TextBlockContentV1;
  groupId: string;
  label: string | null;
}): TextBlockContentV1

ungroupTextUnitGroup(input: {
  flow: TextBlockContentV1;
  groupId: string;
}): TextBlockContentV1

softDeleteTextUnitGroup(input: {
  flow: TextBlockContentV1;
  groupId: string;
}): TextBlockContentV1

setTextUnitGroupCollapsed(input: {
  flow: TextBlockContentV1;
  groupId: string;
  collapsed: boolean;
}): TextBlockContentV1

resolveTextUnitGroupUnits(input: {
  flow: TextBlockContentV1;
  groupId: string;
}): TextUnit[]
```

Rules:

- `createTextUnitGroup()` only accepts active TextUnits that exist in the same flow.
- Duplicate unit ids are deduped.
- Children are stored in TextUnit order, not click order.
- New groups write:

```ts
knowledge_role: null
metadata: {
  group_kind: 'manual_rows',
  color_token: input.colorToken || 'blue',
  collapsed: false,
}
```

- `ungroupTextUnitGroup()` removes the group object from active list or marks deleted.
- It must not delete TextUnits.
- It must not delete annotations.
- If recursive group references are present, avoid orphan crashes by filtering missing references in resolver.

Acceptance:

- Service can create a group from two rows.
- Service can rename group.
- Service can ungroup without mutating units.
- Service can resolve group text from children.
- Service ignores invalid ids conservatively.

## 9. Design Risks

### 9.1 TextUnitGroup Could Become A Second Semantic Layer

Risk:

```text
Developer starts putting meaning into TextUnitGroup because it is convenient.
```

Prevention:

- Keep `knowledge_role` deprecated.
- Do not show semantic role UI on TextUnitGroup.
- Use AnnotationTruth / AnnotationSet for meaning.
- Contract tests assert new groups write `knowledge_role: null`.

### 9.2 Annotation Organizer Could Become Too Heavy

Risk:

```text
Organizer becomes a nested dashboard and interrupts writing.
```

Prevention:

- Keep organizer as optional side panel.
- Default writing surface remains text-first.
- No set badges in main text for 8.6.6.
- Use compact list rows instead of nested cards.

### 9.3 AnnotationSet And Child Annotation Confusion

Risk:

```text
Child annotation explains part of one annotation.
AnnotationSet groups multiple annotations.
UI mixes the two.
```

Prevention:

Product rule:

```text
Child label
  inside a parent label
  explains subrange

Set
  across labels
  organizes independent labels
```

UI rule:

- Child label stays in Annotation Stack.
- Set membership stays in Annotation Organizer.

### 9.4 Relation Scope Creep

Risk:

```text
Because AnnotationSet resembles CompositeEndpoint, implementation starts building relation runtime.
```

Prevention:

- Store set kind and order only.
- Projection can mention future relation reserve.
- No relation line, relation editor, graph edge, or relation inspector in 8.6.6.

### 9.5 Row Selection Interferes With Text Editing

Risk:

```text
Clicking a row handle steals focus or breaks caret behavior.
```

Prevention:

- Row selection is only from gutter/handle.
- Text body click remains caret/editing.
- Escape clears row selection.
- Do not intercept normal text click/drag.

## 13. Self-Review And Execution Handoff

### 13.1 Spec Coverage Check

This plan covers the current 8.6.6 decision set:

- TextUnitGroup is kept as a writing-layer helper, not semantic truth.
- `knowledge_role` is treated as legacy compatibility and new writes must use `null`.
- AnnotationSet becomes the first user-visible way to group multiple AnnotationTruth objects.
- AnnotationSet is allowed to become a future CompositeEndpoint, but 8.6.6 does not implement relation runtime.
- Annotation Organizer is separated from Annotation Stack so child labels and annotation sets do not collapse into one UI idea.
- Reading projection becomes useful for grouped annotations instead of only listing raw ids.
- 8.7 CanvasObject work gets a stable handoff: future CanvasObject annotations can join AnnotationSet without reopening the annotation foundation.

Known out-of-scope work is explicitly deferred:

- full relation editor;
- graph view;
- cross-note / project-level AnnotationSet;
- full A9 Annotation Studio;
- rich text / InlineStructure full editor;
- block split / merge / promote / demote;
- CanvasObject / drawing / image tools;
- visible set badges in main text.

### 13.2 Implementation Guardrails

The implementing worker should not simplify this version into only a UI panel. The important thing is the truth split:

```text
TextUnitGroup
  writing-layer row/range helper

AnnotationTruth
  one confirmed semantic mark

AnnotationSet
  several confirmed semantic marks handled together
```

The worker should also not make AnnotationSet look like child labels:

```text
Child label
  inside one parent annotation
  explains a subrange of that parent

AnnotationSet
  across annotations
  organizes independent labels as a collection, sequence, or all-of pack
```

If the implementation hits a choice between a clever automatic semantic guess and a boring explicit user-controlled action, choose the explicit action. 8.6.6 should be stable before it is smart.

### 13.3 No-Placeholder Check

The plan intentionally avoids undefined product placeholders. Any future item is routed as one of:

- out of scope;
- deferred but reserved;
- future A9 Structure Studio;
- future relation phase;
- future V2.BN.8.7 CanvasObject work.

The code tasks identify concrete files, service functions, UI surfaces, commands, test checks, and manual acceptance steps. If an implementation worker finds a referenced file has already moved, they should update the plan while preserving the same responsibility boundary, not quietly invent a parallel subsystem.

### 13.4 Execution Choice

When Henry says to start implementation, there are two reasonable execution styles:

1. **Task-by-task execution**: follow Tasks 0-16 in order, pausing after service/model work and again after UI wiring.
2. **Two-stage execution**: first implement model/services/tests/projection, then implement UI/commands/docs/patch note.

