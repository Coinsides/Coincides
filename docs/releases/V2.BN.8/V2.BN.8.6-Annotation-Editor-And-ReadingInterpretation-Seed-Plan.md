# V2.BN.8.6 Annotation Editor And ReadingInterpretation Seed Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把 V2.BN.8.5 的 AnnotationTruth seed 补成第一版可用的 annotation editor：用户可以给同一段内容添加多个 label，处理重叠标注，标注整块 block，创建多范围 annotation，并让 annotation 能被投影成未来 AI / Relation 可读的解释材料。

**Architecture:** V2.BN.8.6 延续 annotation-first 方向：TextFlow 负责自然写作，AnnotationTruth 负责用户确认过的语义标记，ReadingInterpretation 负责 AI 的临时解释和 proposal。它不引入全局 canonical role / slot schema，不把 definition/example/theorem 重新做回 block family，也不提前做完整 Structure Studio。实现上优先补 annotation render service、annotation editor service、multi-range draft state、inspector stack view、block-level range creation 和 AI-readable projection seed。

**Tech Stack:** React 18, TypeScript, Vite, Canvas Engine runtime, TextFlow editor, AnnotationTruth service, Note metadata persistence, `client/scripts/canvasEngineModelContractCheck.ts`, Browser Harness / Henry manual visual pass.

---

## 0. Scope Lock

V2.BN.8.6 是 annotation editor completion seed，不是完整 AI reading system，也不是 relation runtime。

它要解决的问题来自 V2.BN.8 Open Issue 顶部的 `V2.BN.8.6 Annotation Completion Handoff`，以及 V2.BN.8.5 手测后暴露出的真实使用问题：

```text
同一段文字可以有多个 label。
多个 annotation 可以重叠。
annotation 不应该互相吞掉视觉显示。
用户需要标注整个 block。
用户需要跨 TextUnit / 多范围标注。
Inspector 不能只展示一个孤立 annotation。
annotation 要能进入 AI-readable projection。
ReadingInterpretation / AnnotationProposal 要有最小模型闭环。
```

### In Scope

- Multiple labels on the same selected text range.
- Overlapping annotation ranges with deterministic visual rendering.
- Multiple annotation badges / stack indicators on the same word, phrase, TextUnit, or TextBlock.
- Block-level annotation UI.
- Multi-TextUnit / multi-range annotation creation with explicit range boundaries.
- More complete partial span visual rendering, building on the V2.BN.8.5 projection layer.
- Annotation Inspector upgrade: list all annotations touching a selected range, show ranges, children, visual style, and actions.
- Right-click / TextUnit gutter / block toolbar annotation entry points.
- Child annotation seed UI enough to create a child label from an existing annotation range.
- AnnotationSet service seed enough to group existing annotations for future composite endpoints.
- ReadingInterpretation / AnnotationProposal seed upgrade: local proposal data, accept / reject, project accepted proposal into AnnotationTruth.
- AI-readable annotation projection helper.
- Documentation sync: Annotation Contract, TextFlow Contract, Notebook Object Inventory, V2.BN.8 README / Plan / CHANGELOG / Review.

### Out Of Scope

- Full AI agent, automatic note understanding, or Mr.Zero workflow.
- Relation runtime or graph database work.
- SourceReference attach / source snapshot region annotation.
- Media annotation / image region annotation. That belongs to V2.BN.8.7.
- CanvasObject drawing tool or shape tool. That belongs to V2.BN.8.7.
- Full rich text editor.
- Full Structure Studio / Annotation Studio productization. That belongs to V2.BN.9.
- Global canonical role taxonomy.
- Fixed role slot schema.
- Perfect range rebasing after arbitrary edits. V2.BN.8.6 only needs a conservative first pass.

## 1. Product Decisions

### 1.1 AnnotationTruth Remains The Semantic Root

V2.BN.8.6 must not walk back the annotation-first decision.

```text
Block
  answers: where and how is this object presented?

TextFlow
  answers: how was this naturally written?

AnnotationTruth
  answers: what meaning did the user or accepted AI proposal mark?
```

This means:

- `definition`, `example`, `claim`, `step`, `topic`, `game`, `疑问`, `我觉得很难` are all possible `raw_label` values.
- The app does not decide that only one of them is the correct global role.
- The app stores the user-confirmed mark and makes it visible, editable, searchable, and projectable.

### 1.2 Multiple Labels Are Normal

The same text can participate in several annotations.

Example:

```text
Text:
  CSGO is Henry's favourite game.

Annotation A:
  raw_label = "definition"
  range = full sentence

Annotation B:
  raw_label = "game"
  range = "CSGO"

Annotation C:
  raw_label = "Really?"
  range = "Henry's favourite game"
```

V2.BN.8.6 should treat this as normal, not as a conflict.

### 1.3 Overlap Is Not Error

Overlapping annotation ranges should not force the newest annotation to replace older visual state.

The first version can use a deterministic display rule:

```text
one range:
  highlight

two or more ranges:
  highlight + subtle underline stack or stripe

selected annotation:
  stronger highlight / outline

badge:
  show primary label + "+N" stack indicator when several labels touch this row/range
```

The exact visual polish can be improved later, but the data model and render model must allow overlap.

### 1.4 Child Annotation Replaces Fixed Slot Schema

If a larger annotation needs internal pieces such as `concept name`, `description`, `condition`, `equation`, the system should use child annotations instead of a fixed schema.

Example:

```text
AnnotationTruth raw_label="Power Series definition"
  ranges:
    sentence or paragraph range
  children:
    AnnotationTruth raw_label="concept name"
      range: "power series"
    AnnotationTruth raw_label="description"
      range: "a series of the form ..."
```

V2.BN.8.6 does not need a heavy child annotation editor. It needs enough UI and service functions to create, list, and delete child annotation links.

### 1.5 AnnotationSet Is The Future Composite Endpoint Shape

When several annotations together imply another annotation, the user-facing object should be `AnnotationSet`, not a new relation-only object.

Example:

```text
AnnotationSet raw_label="Power Series prerequisites"
  member A: sequence definition
  member B: convergence theorem
  member C: example problem

Future relation:
  from AnnotationSet(A, B, C)
  to AnnotationTruth(D)
```

V2.BN.8.6 should add model/service seed and debug projection, but not a full set editor.

### 1.6 ReadingInterpretation Is Proposal, Not Truth

ReadingInterpretation is AI's reading layer:

```text
AI reads note/source
  -> ReadingInterpretation
  -> AnnotationProposal(s)
  -> user accepts / rejects
  -> accepted proposal creates AnnotationTruth / AnnotationSet seed
```

The first version can be manual/debug generated. It does not need an actual AI call.

## 9. Risks

### Risk 1: Textarea Highlight Projection Can Drift

V2.BN.8.5 uses a non-interactive highlight layer behind textarea.

Risk:

```text
font, wrapping, scroll, or narrow block width can make highlight drift.
```

Mitigation:

- keep identical typography classes between textarea and highlight layer;
- avoid multiline magic inside one TextUnit for this version;
- record drift cases for V2.BN.8.x polish.

### Risk 2: Overlap Rendering Can Become Noisy

Too many labels can make writing unreadable.

Mitigation:

- use one primary visual highlight;
- encode additional labels through badge count / subtle underline;
- let inspector reveal full stack.

### Risk 3: Multi-Range Draft Can Feel Heavy

If the UI asks too much from the user, annotation becomes work.

Mitigation:

- keep normal one-range `Mark` flow fast;
- make `Add range` optional;
- never require multi-range draft for ordinary use.

### Risk 4: Child Annotation Can Recreate Slot Hell

If child annotations become mandatory fields, the old fixed slot schema returns under another name.

Mitigation:

- child annotation is optional;
- no role requires mandatory children;
- no global schema is introduced.

### Risk 5: ReadingInterpretation May Look Like AI Is Implemented

The model seed may be mistaken for real AI reading.

Mitigation:

- label it as seed / debug / proposal layer;
- do not add UI copy promising automatic intelligence;
- do not call external AI in V2.BN.8.6.
