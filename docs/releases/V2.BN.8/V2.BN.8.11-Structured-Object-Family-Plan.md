# V2.BN.8.11 Structured Object Family — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 先把 CanvasObject 管线做成 **kind-通用**，再让基础对象家族（图形 / 连接线 / sticky / 图片 / 表格）骑上去。**地基的正确性 > 任何单个对象**——所以本版以"通用化管线"开局，对象简单到难依次跟上。

## 0. 重写历史

- 2026-06-25/27：原计划从 ContentGroup projection 开局 → 改为普通对象生命周期开局（ContentGroup projection 顺延到 8.12）。
- **2026-06-28（本次重写，地基优先）**：核查发现持久化（`server/src/services/canvasObjects.ts`）**只硬编码两种 kind**（`page_frame` @334、`paragraph_block_projection` @458，读路径同样按这两 kind 分支）；shape/connector 只活在 seed service、无 UI；image/table/object-style/asset 尚不存在。即——**cutover 建的是"两个特例"，不是"通用底座"**。故本版**改为地基优先**：先把管线通用化（成熟闸门之第一道"通用性"），再建对象。

## 1. 第一原则：地基正确 > 任何单个对象

**地基一旦偏，将来新加一个 canvas object 很可能要重写 runtime 的一部分——这不可接受。** 所以：
- **先把管线（持久化 / runtime / AI-tree / 渲染）从"页面或块"的硬编码分支，改成"认 kind"的一条通用路径。**
- 用最简单的纯对象 **shape 当强制函数**：建它会逼出管线里每一处"假设是页面或块"的地方。shape 跑顺 = 管线证明通用。
- 之后每个对象 ≈ 一个 thin kind + 一个 tool + 一段渲染；不再触碰 runtime 主干。

> 即使某个对象本版不发布也无所谓；**唯独管线必须真正 kind-agnostic**。这是本版唯一不可让步的东西。

## 2. 两层，必须分清

> **🔑 通用 ≠ 抹平所有特殊性**（Henry 2026-06-28）。正确形态是 **通用 CanvasObject/Placement 核心 + kind-specific extension**，不是把所有 kind 塞成一个巨型 JSON 黑盒。PageFrame 仍是特殊 object（有 `page_frame_extensions`），block projection 有 mount。
>
> **关键实证（5-面扫描）**：这个「核心+扩展」形状在**数据层（migration 035）其实已经存在**——`canvas_objects`(id/kind/backing/object_class/status) + `canvas_placements`(几何) 是 kind 无关核心；已有**两种扩展风味**：①「自有 typed 边车」= `page_frame_extensions`（object_id FK CASCADE，PageFrame 专属列）；②「投影/绑定 mount」= `content_mounts`（object_id FK + target_kind + target_id，block 镜像外部真相用）。**所以地基没偏；要做的不在 schema，而在它上面的派发层。** 而唯一真的 JSON 黑盒恰恰在 **validator**（`z.record(z.unknown())`，见 8.11.1.2 ③）。

### 2a. 共享基建（建一次，每个对象都骑它）
- **kind-通用的派发，不是 kind-抹平**：核心（canvas_objects + canvas_placements）已通用；要把它上面**四个派发层**（route / validator / repository+engineModel / runtime+AI-tree）从"页面或块"硬编码，改成「通用核心 + 按 kind 注册的 typed extension」。新 kind = 注册一个 (validator, extension-writer, builder) 三元组，**不碰核心**。
- **建/选/移/删一个画布对象的交互面**：command/tool 入口（`commandSurfaceService` 框架在，"建对象"未接线）。
- **object-style / 视觉预设能力**：把 block-type 与 object-style 解耦（"同一个 block truth，可有不同 canvas presentation"）。
- **block-backed canvas object 路径**（durable 版）：CanvasObject 挂 paragraph block（`fillShapeWithParagraphBlock` 现为 seed，未进持久化）。
- **AI-tree 的 kind-通用表达**：每种 object 可被 AI 读；尤其表格的结构化 payload 必须流进 AI-tree。

### 2b. 各对象自己的坑（不是加个 kind 就完事）
- **图片** → asset 存储 + asset-backed 对象（文件存哪、CanvasObject 怎么引用——真新基建，`backing='asset'` 现仅预留）。
- **连接线** → `visual_connector` 持久化 + 端点模型（连哪两个对象、吸附点；`RelationEndpointReserve` 现休眠）。
- **表格** → 后端无关的 table 数据模型（v1 自建 + 未来从 Excel/Word/PDF表/图片表导入，**填同一个模型**）。

## 3. 不可让步的边界

- 不做 ContentGroup tile projection / reuse verbs / Petal projection（全顺延 8.12）。
- 不做 Relation runtime；**普通 visual connector 永远不是 Relation**（无 relation type / 无 endpoint role / 无语义；AI 最多读成"这俩在布局上被视觉连接了"）。
- 不做 GraphRAG / Agent write、完整 infinite canvas、完整 PDF/export engine、完整 top bar/ribbon、完整 context-menu 系统（只做对象级最小入口）。
- **🪤 接缝：别现在焊死**（昨日两条铁律套到本版地基上）：
  - 给新 kind 加表 / 改持久化时，**别把单项目（`course_id`）焊成不可逆**——身份保持"项目无关-capable"。
  - 连接线端点绑 CanvasObject 没问题（空间的）；但**别让这套端点被 relation 直接复用**——relation 端点要绑 ContentGroup 身份。

## 4. 对象家族（Henry 2026-06-28 设计）

1. **基础图形 (shapes)**：纯 `CanvasObject`（矩形/圆/箭头块/多边形），先只承担视觉布局。用户往里写字 → 升级成 **block-backed canvas object**，底下挂 paragraph block。
2. **视觉线 / connector**：独立的视觉连接对象，**不是 relation**。可有起点/终点/方向/线型/箭头样式/吸附到哪个 object；**不要 relation type、不要 endpoint role、不要语义**。跟 ContentGroup/Petal Relation 完全不是一张表、不是一套语义。
3. **Sticky note**：**不是新内容类型**，是 paragraph block 的一种**视觉 preset**。它证明：**同一个 block truth，可有不同 canvas presentation**。
4. **图片**：asset-backed canvas object。先做展示/移动/缩放/caption-alt-text。不做复杂编辑/裁剪/标注，不把图片塞进 textflow。
5. **表格**：天然结构化，比图形/图片复杂一点。v1 做轻量 table block/object：行列、单元格文本、基础增删行列。**先别追 Excel、别公式、别复杂合并单元格。** 价值是 AI 能读到"第几行第几列是什么"。**埋坑要埋对**：v1 数据形状要让未来从 Excel/Word/PDF表/图片表导入能填进**同一个模型**（契约优先、来源可换，类比 SourceArtifact），最大限度保真、降低重建成本。
