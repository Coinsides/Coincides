# V2.BN.8.6.7 ContentGroup Rebuild And Legacy Retreat Plan

```text
status: planned
date: 2026-06-18
position: after V2.BN.8.6.6 and before V2.BN.8.7 CanvasObject work
purpose: align code with the TextFlow-first / ContentGroup-aware model turn
```

## 1. Why This Subversion Exists

V2.BN.8.6.6 made TextUnitGroup and AnnotationSet usable as seeds.

Manual testing and product reasoning then changed the root model:

```text
TextFlow is the content root.
ContentRange is the location root.
AnnotationTruth is the label / marker layer.
ContentGroup is the serious content package.
GroupFolder is the organization/path layer for ContentGroups.
Petal is the local part inside a ContentGroup.
Accepted identity is a ContentGroup state, not a separate object.
Relation will connect ContentGroup / accepted ContentGroup identity / CompositeEndpoint.
```

This means the documents are now ahead of the code.

V2.BN.8.6.7 is the cleanup and rebuild version that pulls the code direction back into alignment before V2.BN.8.7 CanvasObject / media work begins.

It is not a visual polish release. It is not a relation runtime release. It is a model alignment release.

## 2. Four Work Blocks

### Block A - New Build

Build the first real ContentGroup foundation.

Target concepts:

```text
ContentGroup
  id
  project_id
  note_id?
  primary_folder_id?
  placements[]
  title
  topic?
  local_role?
  summary?
  status
  created_by
  created_at
  updated_at
  members[]
  petals[]
  interpretation?
  view_state?
```

Folder placement rules:

```text
GroupFolder.path
  derives browsing depth / scope / relation-view boundary

ContentGroup
  does not own primary depth
```

`ContentGroup.members[]` must store traceable member references, not copied text.

Draft member shape:

```text
ContentGroupMember
  id
  group_id
  kind: content_range | annotation | block | future_object
  target_id
  role_hint?
  order_index
  metadata?
```

Build the first Petal foundation.

```text
Petal
  id
  content_group_id
  label
  order_index
  members[]
```

`Petal.members[]` uses the same traceable member-reference model as `ContentGroup.members[]`.

First version can stay small:

- create ContentGroup from current selection / ContentRange / AnnotationTruth;
- add selected range or annotation to an existing ContentGroup;
- create Petal inside a ContentGroup;
- add selected range or annotation to a Petal;
- list groups for the current note;
- persist and project groups for debugging.

### Block B - Refactor / Reuse

Refactor useful existing seed work into the new model.

Candidate reuse:

- AnnotationSet label / description editing can inform ContentGroup title / identity editing.
- AnnotationSet ordered members can inform ContentGroup member ordering.
- AnnotationSet color token can inform optional group display style, but it should not define semantic identity.
- TextUnitGroup range grouping can inform ContentGroup creation from selected rows if the UX is not harmful.
- SelectionDraft and ContentRange should become the preferred creation path for ContentGroup members.

Refactor rules:

- Do not preserve compatibility just because a seed exists.
- There is no production user dataset to migrate.
- If a seed blocks the cleaner model, delete or hide it.
- If a seed provides useful mechanics, rename and reshape it into ContentGroup / Petal.

### Block C - Delete / Retreat

Prepare old objects and flows for deletion or removal from normal UX.

Targets:

```text
TextUnitGroup
  no longer a long-term independent object
  either rewrite into ContentGroup workflow or remove from normal UX

AnnotationSet
  no longer a product destination
  useful mechanics may migrate into ContentGroup / GroupFolder / ContentGroup Gallery

ChildLabel
  superseded by Petal
  do not expand as the internal-structure model
```

Concrete tasks:

- hide or stop expanding TextUnitGroup row rail UI if it harms natural writing;
- stop planning new AnnotationSet capabilities as product features;
- remove ChildLabel from new command language;
- keep legacy child annotation data readable only while needed for current test data;
- mark any remaining old flows as legacy in code comments or projection output.

### Block D - Downgrade / Reposition

Reposition existing objects without deleting their useful parts.

```text
AnnotationTruth
  downgrade to label / marker / visible highlight
  can feed ContentGroup, but is not itself the default content package

InlineStructure
  downgrade to special render / interaction anchor
  formula, inline code, link, source marker
  not semantic truth by itself

TextUnit
  writing unit only
  paragraph / heading / list item / todo item / toggle item
  not default relation endpoint

Block / NoteBlock
  spatial render object
  placement / size / shell / special object behavior
  not knowledge identity by default
```

The implementation should make these boundaries harder to accidentally violate.

## 3. Desired User Shape

The user should not feel like they are operating schema.

Near-term visible workflow:

```text
select text / range
  -> Label as lightweight mark
  -> Save as ContentGroup when it is a serious package
  -> Open ContentGroup when they need deeper organization
  -> Create Petals inside the group if needed
```

The UI language should prefer:

```text
Label
Content package
Part
Open package
Add to package
```

Internal names can remain:

```text
AnnotationTruth
ContentGroup
Petal
ContentRange
```

## 4. Visible Interaction And UX Contract

V2.BN.8.6.7 needs a real visible surface, not only a data seed.

The first product shape is a quiet ContentGroup rail on the right side of the note surface.

### 4.1 Right-Side ContentGroup Entry

Add a dedicated right-edge button for ContentGroups.

Rules:

- it opens the ContentGroup rail;
- it is independent from Annotation Stack;
- it should not look like a debug inspector;
- it should stay visually quiet while the user is writing;
- it should be reachable without stealing the page writing focus unless the user explicitly opens it.

The right rail is a sidebar, not a modal and not a floating bubble.

### 4.2 ContentGroup Rail

The rail defaults to a collapsed list of all current-note ContentGroups.

First open behavior:

- do not auto-expand any ContentGroup;
- show group titles only;
- show a clear `New group` action;
- show an empty-state line only if no groups exist;
- do not show raw schema fields by default.

Each ContentGroup row behaves like a toggle row:

```text
Group title
  collapsed by default
  expands to member previews
```

Expanded rows show previews, not full detail.

The preview rules:

- text/range members show a short readable excerpt;
- annotation/label members show the label badge/name first, not the full annotation internals;
- block members show the block type/title/excerpt, not the full block editor;
- previews can be removed from the group;
- clicking a preview opens the full ContentGroup workspace/detail view.

### 4.3 New Group And Add Content Workflow

The rail owns a lightweight collection workflow.

`New group` creates a temporary group draft with a drop zone.

The user can drag selected content into the draft:

- a selected text range;
- a committed SelectionDraft;
- an existing label / AnnotationTruth badge;
- a block or future canvas object, when those sources are ready.

Dragging several times creates several members.

For existing ContentGroups, provide an `Add content` mode:

- the group opens a drop zone;
- the user drags more selected content into it;
- each drop becomes one traceable member reference;
- members can be removed before or after save.

Important rule:

The rail does not copy text as truth. It creates member references. Any displayed text is preview/cache only.

### 4.4 Full ContentGroup Workspace

The rail is not enough for deep editing.

Clicking a group title or member preview should allow the user to enter a full ContentGroup workspace/detail surface.

This surface is for serious organization:

- list and batch-manage ContentGroups;
- open one ContentGroup in detail;
- edit group title/topic/interpretation metadata;
- inspect all members;
- delete or reorder members;
- create Petals;
- rename Petals;
- delete Petals;
- add members to Petals;
- remove members from Petals;
- edit Petal-backed content through source-backed ranges where supported.

This may be implemented as a right-side expanded workspace, a dedicated internal panel, or a note-level mode, but it must not become nested bubble UI.

The first version can be modest, but the architecture should leave room for a larger ContentGroup editing workspace.

### 4.5 Petal Editing And Bidirectional Sync

Petal is the local part inside a ContentGroup.

Petal editing rules:

- Petals own member references, not detached copied text;
- editing a Petal member must update the original TextFlow source when the member is source-backed and editable;
- editing the original TextFlow source must refresh the Petal/member preview;
- if a member cannot be edited safely, the UI should make it read-only rather than pretending to sync;
- label/annotation members may be shown by badge/name in compact views;
- detailed member views may show source excerpt, source block, and trace target.

This is the same principle as source-backed annotation range editing:

```text
source is truth
preview is cache
ContentGroup/Petal members are traceable references
```

### 4.6 Visual Design Constraints

Use product UI restraint.

The ContentGroup experience should feel like a quiet organizer attached to the notebook, not an engineering database.

Required visual direction:

- no nested card-in-card-in-card structure;
- no bubble window nested inside another bubble window;
- prefer rows, sections, disclosure headers, tabs, and quiet dividers;
- keep raw metadata collapsed by default;
- make drag targets visible only when collecting content;
- keep the writing surface wider than the controls whenever possible;
- use consistent icon buttons and tooltips;
- make destructive actions secondary and explicit;
- keep motion short and state-driven only.

Information hierarchy:

```text
Right rail
  quick collection
  collapsed group list
  compact member preview

Full workspace/detail
  serious editing
  member management
  Petal management
  source-backed sync
```

The first UI pass should use the `impeccable` product-register guidance: familiar, restrained, and task-oriented. `taste` can be used as a secondary critique, but the interface should not become a decorative showcase.

## 5. Non-Goals

V2.BN.8.6.7 does not implement:

- relation runtime;
- Accepted identity review UI as a full product;
- GroupFolder / ContentGroup Gallery full query/filter experience;
- Source Reconstruction production pipeline;
- CanvasObject / drawing / image work;
- full Structure Studio;
- migration adapters for old test data;
- full rich text editor rewrite;
- cross-project ContentGroup UI beyond preserving project ownership and future GroupFolder placement hooks.

The first version also does not need:

- complete drag-and-drop from every possible source;
- complete cross-block range editing;
- complete ContentGroup workspace polish;
- AI proposal/review workflow for ContentGroups;
- final visual design for every state.

However, it must not block those later directions.

## 6. Implementation Order

Suggested order:

1. Add or reshape runtime types for ContentGroup, ContentGroupMember, Petal, and Petal member references.
2. Add service helpers for creating groups from ContentRange / AnnotationTruth / Block.
3. Add projection/debug output so the model can be inspected without a polished UI.
4. Add the right-side ContentGroup rail entry.
5. Add the collapsed current-note group list.
6. Add `New group` draft and compact drop-zone workflow.
7. Add `Add content` mode for existing groups.
8. Add compact member previews with remove actions.
9. Add a minimal full ContentGroup workspace/detail surface.
10. Add Petal creation, rename, delete, and member assignment inside the detail surface.
11. Route one or two existing command surfaces into ContentGroup creation.
12. Hide or mark TextUnitGroup / AnnotationSet / ChildLabel surfaces as legacy.
13. Update model contract smoke checks.
14. Use browser harness/browser use to self-test the core flows.
15. Iterate obvious bugs and awkward states before Henry manual test.
16. Write patch note and stop before Henry manual test.

## 7. Acceptance Boundary

V2.BN.8.6.7 can be accepted when:

- ContentGroup exists as a first-class runtime / persistence seed.
- ContentGroup members are traceable references, not copied text.
- Petal exists as a local part inside ContentGroup.
- Petal also uses member references.
- AnnotationTruth still works as label/highlight, but no longer pretends to be the content-package truth.
- TextUnitGroup is either hidden from normal UX or clearly routed as a legacy / rewrite candidate.
- AnnotationSet is not expanded as the main future object.
- ChildLabel is not used as the future internal-structure model.
- A right-side ContentGroup entry opens a ContentGroup rail.
- The rail lists current-note groups collapsed by default.
- The rail supports a first collection path from selection/range/annotation into a ContentGroup.
- Existing groups can accept additional content.
- Group member previews can be inspected and removed.
- A minimal ContentGroup detail/workspace surface exists.
- Petals can be created, renamed, deleted, and assigned members.
- Compact views show label/annotation members by badge/name first.
- Full views can inspect the underlying referenced content.
- Editable source-backed member changes sync through source truth rather than detached copies.
- The ContentGroup UI avoids nested bubble/card clutter.
- Browser self-test covers create group, add member, expand preview, open detail, create Petal, refresh persistence, and basic removal.
- Contract smoke or equivalent non-browser checks pass.
- Henry can manually test the basic group creation / group viewing path before V2.BN.8.7 begins.
