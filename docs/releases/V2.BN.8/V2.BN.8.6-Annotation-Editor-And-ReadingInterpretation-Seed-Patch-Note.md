# V2.BN.8.6 Annotation Editor And ReadingInterpretation Seed Patch Note

status: engineering implementation complete; non-browser verification passed; Henry manual visual pass explicitly deferred to Henry
date: 2026-06-16

## Summary

This patch turns the V2.BN.8.5 AnnotationTruth seed into a first usable annotation editor seed. The implementation keeps Coincides on the annotation-first path:

```text
TextFlow writes naturally.
AnnotationTruth stores confirmed semantic marks.
ReadingInterpretation and AnnotationProposal stay proposal/debug layers.
```

The patch does not introduce a global canonical role taxonomy, fixed role slot schema, full AI agent, relation runtime, media annotation, or drawing tools.

## What Changed

- Added overlap-aware annotation rendering through `annotationRenderService`.
- Added multi-label / same-range annotation helpers, child annotation helpers, and AnnotationSet service helpers through `annotationEditorService` and `annotationTruthService`.
- Added ReadingInterpretation / AnnotationProposal seed helpers through `readingInterpretationService`.
- Added precise partial-span rendering so local text selections can show highlight without forcing the whole TextUnit to light up.
- Added annotation stack behavior for multiple annotations touching the same TextUnit or range.
- Added block-level annotation entry from the block control surface.
- Added context-menu annotation entry for selected text.
- Added multi-range annotation draft controls in the selection toolbar.
- Upgraded the Annotation Inspector so it can show multiple selected annotations, create same-range labels, create child labels, hide/show, rename, and soft-delete.
- Added note metadata persistence seeds for:
  - `canvas_engine_annotations_v1`
  - `canvas_engine_annotation_sets_v1`
  - `canvas_engine_reading_interpretations_v1`
  - `canvas_engine_annotation_proposals_v1`
- Expanded the model contract smoke to cover overlap segmentation, same-range labels, block ranges, multi-range annotations, child links, AnnotationSet, ReadingInterpretation, proposal acceptance, and AI-readable projection.

## User-Facing Result

The intended first-version user experience is:

```text
select text -> mark it with a label
select the same text again -> add another label
select overlapping text -> keep both annotations visible
select a block -> label the whole block
add several selected ranges -> commit them as one annotation
open inspector -> see the annotation stack and edit/hide/delete labels
```

This remains a seed. It is not the final annotation studio, not automatic AI reading, and not relation runtime.

## Hotfix - Annotation Stack Editing And Additive Range Selection

date: 2026-06-16
status: implemented; needs Henry manual retest

Henry manual testing found that Annotation Stack editing could visually break the note surface. The hotfix makes the stack panel behave as an isolated editor surface instead of letting its pointer, click, double-click, and keyboard events leak into the canvas / block interaction layers.

This hotfix also adds a first additive range-selection interaction:

```text
Ctrl / Command + mouse selection -> add selected text range to the annotation draft
```

The draft range list now deduplicates equivalent ranges, so selecting the same span twice does not create duplicate ranges in the committed annotation. This is the first Coincides-native path toward Word-like discontiguous selection; it is not yet a full native multi-caret text selection system.

## Hotfix Follow-Up - Inspector Input Crash And Visible Draft Ranges

date: 2026-06-16
status: implemented; needs Henry manual retest

Henry manual retest showed that child-label editing could still break the page. Browser reproduction found the concrete root cause: Annotation Inspector input handlers were reading `event.currentTarget.value` inside React functional state updaters, after the event target had already become `null`. Rename, same-range label, and child-label inputs now capture the input value before calling the state updater.

The additive range-selection path also now has a first visible feedback loop:

- Ctrl / Command + mouse-selected draft ranges render as temporary inline highlights before commit.
- Clicking blank page space clears the draft ranges and browser selection.
- Starting a normal non-additive text selection clears the previous multi-range draft.
- Releasing modifier keys such as Ctrl / Command no longer reprocesses the same text selection as a normal selection, so the just-added draft range is not immediately cleared.
- Ctrl / Command selection now keeps a short additive selection session through the textarea `select` event path. This prevents the regular selection handler from clearing the draft range immediately after `mouseup`.

This still is not the final custom selection engine. It is a safer seed that makes the current Ctrl / Command path visible enough to retest without leaving invisible mistaken ranges behind.
