# V2.BN.8.6.1 Selection Draft Engine Patch Note

Date: 2026-06-16

## Scope

This patch promotes text selection from scattered browser-selection side effects into the first Coincides-owned `SelectionDraft` engine seed.

It also folds the unfinished child-label entry from V2.BN.8.6 into the new selection foundation.

## Changed

- Added `selectionDraftService.ts`.
  - Defines `SelectionDraftV1` and `SelectionDraftRangeV1`.
  - Supports replace selection, additive selection, range dedupe, draft-to-annotation conversion, and parent-annotation containment checks.
- Added `useSelectionDraftController.ts`.
  - Owns runtime selection draft state.
  - Exposes replace, append, clear, visible draft ranges, latest range, and parent containment helpers.
- Updated `NoteWritingSurfaceLayer.tsx`.
  - Normal text selection now creates a visible draft instead of relying on browser highlight only.
  - Ctrl / Command selection appends to the same draft.
  - Draft highlight is rendered through the same annotation render path before commit.
  - Blank surface click, outside click, Esc, and toolbar close clear the draft.
  - Annotation commit now consumes `SelectionDraft`.
  - Child label can be created from a subrange selected inside the active parent annotation.
- Updated `SelectionToolbarLayer.tsx`.
  - The toolbar is now marked as a selection-draft surface.
  - It can show child-label action when the current draft is inside an active parent annotation.
  - Commit count now reflects the actual draft range count.
- Updated `AnnotationContextMenuLayer.tsx`.
  - Context menu is marked as a selection-draft surface.
  - The old add-range action is reduced to a disabled draft-status indicator until the mature custom range-selection UI is complete.

## Manual Retest Follow-up - Draft Interaction Gap

Henry's manual retest found that the current implementation still does not fully own the selection experience.

The intended interaction is:

- A normal drag selection creates a `SelectionDraft`.
- Clicking back inside the highlighted draft region should enter the actionable draft state, showing the selected ranges as Coincides-owned highlights rather than relying on browser-native blue selection.
- Clicking unselected text, blank page/canvas space, or other unrelated UI should clear the draft.
- Ctrl / Command + drag selection should append a new range to the existing draft.
- A normal drag selection without Ctrl / Command should replace the draft.
- If the user first creates a normal selection and only later decides to hold Ctrl / Command for another range, the first range should remain and the next range should be appended.

Observed broken behavior:

- Ctrl / Command + selecting a second range can visually and structurally drop the first range.
- The browser-native blue highlight is still acting like the visible truth during multi-range selection.
- Clicking selected text and clicking unselected text are not yet separated enough; the system currently treats most outside mouse down events as draft-cancel events.

Likely root cause:

- `SelectionDraft` data helpers already support append, but `TextBlockProjection` still emits selection changes through native textarea events.
- `onSelect`, `onMouseUp`, and `onKeyUp` can fire in different orders. The additive mouseup path can append a range, then a later non-additive selection event can replace the draft with only the latest range.
- `NoteWritingSurfaceLayer` has a global mousedown clear rule that clears the draft for any click outside toolbar/context-menu/input surfaces. It does not yet distinguish "click inside an existing draft highlight" from "click unrelated text".
- The UI still depends on browser-native selection for part of the user-visible state. A mature version should convert browser selection into `SelectionDraft`, clear browser selection, then render every selected range through Coincides-owned draft highlight segments.

Next patch direction:

- Introduce explicit draft interaction phases such as `capturing`, `draft`, and `active`.
- Treat browser selection as a short-lived capture signal only.
- On mouseup, capture the selected range into `SelectionDraft`, then clear native browser selection.
- Render all draft ranges from `SelectionDraft`, including previous additive ranges.
- Add draft hit-testing so clicks inside a draft range keep or activate the draft, while clicks outside clear it.
- Suppress non-additive `onSelect` / `onKeyUp` replacement when the current gesture is additive.
- Keep child-label creation on top of the same draft model; child labels should inherit the improved draft hit-testing and additive range behavior.

## Follow-up Patch - Draft Ownership Tightening

Implemented after the manual retest gap above.

### Changed

- Added `SelectionDraft.phase` with an `active` state.
- Added `activateSelectionDraft()`.
- Added `selectionDraftContainsCapturedSelection()` for draft hit-testing.
- Updated `useSelectionDraftController()` to expose `activateDraft()`.
- Updated `TextBlockProjection` selection handling:
  - Ctrl / Command drag selection no longer lets textarea `onSelect` replace the existing draft.
  - Mouseup is the final selection capture point for pointer selections.
  - After capture, textarea-native blue selection is cleared so Coincides draft highlight becomes the visible source of truth.
  - Collapsed mouseup is treated as draft hit-testing rather than annotation creation.
- Updated `NoteWritingSurfaceLayer` selection handling:
  - Clicking inside an existing draft range activates the draft.
  - Clicking unrelated text clears the draft.
  - Global outside-click cleanup no longer clears draft before text-unit hit-testing can run.
- Added a `SelectionDraft engine` model-contract smoke group.
  - Verifies additive selection preserves previous ranges.
  - Verifies draft activation.
  - Verifies hit-testing accepts ranges inside the draft and rejects unrelated text.
  - Verifies annotation commit still receives every drafted range.

### Retest Focus

- Select range A; the browser-blue selection should collapse into Coincides draft highlight.
- Ctrl / Command select range B; range A should stay highlighted and range B should be added.
- Click inside range A or B; the draft should remain actionable.
- Click unrelated text; the draft should clear.
- Annotating after Ctrl / Command multi-range selection should include all selected ranges.

## Follow-up Patch - Annotation Stack Responsibility Cleanup

Implemented after Henry's Annotation Stack responsibility review.

### Scope

This patch narrows Annotation Stack back to its proper role: managing existing annotations and creating child labels only from a concrete sub-selection inside a parent annotation range.

### Changed

- Remove `Add same-range label` from Annotation Stack.
  - Same-range labels should come from selecting the source text again, not from a duplicate action in the stack.
- Remove the blank `Add child label` input from Annotation Stack.
  - Child labels must come from a real subrange selected inside a parent annotation range preview.
- Keep annotation range previews visible.
  - Multi-range annotations should continue showing each selected fragment as a separate row.
- Added a parent-range child-label draft path.
  - Selecting text inside an Annotation Stack range preview exposes a lightweight child-label action.
  - Committing that action creates a child annotation linked to the parent and scoped to the selected subrange.
- Show child annotations in the parent stack card after creation.
- Collapse technical metadata by default.
  - Created by, status, range count, and children count remain available but do not dominate the normal surface.
- Demote or remove the `Draft N` toolbar button because it is internal state.
- Added `createChildAnnotationRangeFromParentRange()` to translate range-preview local offsets back to source TextFlow offsets.
- Added `placeSelectionToolbar()` so the selection toolbar stays near the selection without appearing uncontrolled at the top of the screen.

### Explicitly Deferred

- Source-backed range text editing is deferred to V2.BN.8.6.2 or V2.BN.8.6.3.
  - Editing range preview text must update the original TextFlow source, recalculate offsets, preserve child annotations, and integrate with undo / redo.
  - This cleanup patch only makes range previews selectable as child-label sources; it does not make them editable source mirrors.

### Retest Focus

- Annotation Stack no longer shows `Add same-range label`.
- Annotation Stack no longer shows a blank `Add child label` input.
- Metadata is collapsed by default.
- Range previews still show every fragment in a multi-range annotation.
- Selecting text inside a range preview exposes a child-label action.
- Creating a child label from the range preview links it to the parent and displays it in the children area.
- Selection toolbar no longer exposes `Draft N` as a primary action.

## Follow-up Patch - Child Label Hierarchy Fix

Implemented after Henry's manual retest showed child labels were rendered as sibling label cards.

### Scope

Child labels are data entities, but they are not top-level Annotation Stack cards. They exist to explain semantic parts inside a parent label.

### Changed

- Added Annotation Stack root resolution.
  - Selecting a child annotation now resolves back to its root parent for top-level inspector rendering.
  - Selecting both parent and child no longer renders two sibling cards.
- Creating a child annotation now keeps the parent annotation selected.
  - The child remains visible and editable through the parent's `Children` area.
  - The child does not become an independent top-level stack card after creation.

### Retest Focus

- Create a parent annotation, then create a child label from a range preview.
- Annotation Stack should keep one parent card.
- The child label should appear only under the parent's `Children` section.
- Clicking or selecting the child annotation should still open the parent stack context, not a separate sibling card.
