# V2.BN.8.6.25 Unified Item And Content Range Drag Foundation Patch Note

## Implemented Drag Sources

- Draft Range now writes the new `draft_range` payload.
- Legacy `draft_ranges` remains readable only for compatibility.
- Draft Range uses a small icon handle above the selected text instead of a passive text badge.
- Label badge drag payload now carries `annotation_id`, label name, ranges, preview text, and source note id when available.
- Block toolbar label action can be dragged as a block item without reusing the block-move handle.

## Implemented Drop Targets

- Groups Rail new-group drop target creates a group from the dragged item.
- Groups Rail group row drop target adds the dragged item to that specific group.
- Group Gallery card drop target adds the dragged item to that card's group and persists the note metadata.
- Single ContentGroup Editor members area accepts dragged items and appends members without auto-assigning Petals.

## Source Protection Rules

- Drop into ContentGroup creates member references only.
- Original text, Label, and block remain in place.
- Block item drag does not move the block layout.
- Member preview is cache; source reference / content range is truth.
- If a payload cannot be parsed or contains empty ranges, the drop is ignored.

## Manual Test Checklist

- Select text to create a Draft Range, drag the small handle above the selection into a Groups Rail row, and confirm the member count increases.
- Ctrl-select two ranges, drag the draft affordance into a new group drop area, and confirm both ranges appear as members.
- Create a Label, drag its badge into a Gallery card, then open Single Editor and confirm the member is present.
- Open a block toolbar, drag the label/tag control into a Groups Rail row, and confirm a block member appears while the original block stays put.
- Drag a Draft Range or Label into Single Editor members area and confirm it appends to members without creating a Petal.
- Refresh the note after ContentGroup drops and confirm persisted members remain.

## Deferred Drag Scenarios

- Directly dragging from the highlight paint layer is deferred because that layer overlays editable text. Enabling pointer events there would risk reintroducing the old "click text but cannot edit" class of bugs. This should wait for a dedicated internal selection/drag layer.
- Drop Draft Range / Label onto PageFrame or Canvas to create visible TextBlocks is still guarded. The safe copy/projection resolver is documented, but visible block creation should be implemented when the page/canvas drop boundary is explicit enough.
- TextBlock-internal drag reorder/copy is deferred because it can mutate source writing and needs caret insertion, undo, and move-vs-copy rules.
- Petal fragment assignment from a Label or Draft Range remains deferred to the Petal assignment version.
