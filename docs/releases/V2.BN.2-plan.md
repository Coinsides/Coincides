# V2.BN.2 Plan - Natural Page Writing

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the first ordinary note-writing action feel natural: open a note, click the page, see a caret, type, and persist a default text NoteBlock without using an engineering Add Block form.

**Architecture:** V2.BN.2 should add a lightweight page-writing layer on top of the existing `NoteDetail` and note block APIs. The canonical truth remains `NoteBlock`; draft caret/editor state is local UI state until the user enters text. Slash commands create or convert blocks through existing runtime template metadata where possible.

**Tech Stack:** React, TypeScript, CSS modules, existing `/api/notes/:id/blocks` and `/api/note-blocks/:id` routes, runtime `TemplateDefinition` options.

---

## Summary

V2.BN.2 is the first real writing-experience version in the Better Notebook track.

It does **not** try to solve freeform block boxes, A4 export, source chain, relation graph, OCR import, or AI note generation. It fixes the first-second problem:

```text
blank note
  -> click page
  -> caret appears
  -> user types
  -> system creates a default text NoteBlock
```

The current note editor already supports creating and editing NoteBlocks, but it exposes that through a template selector, textarea, and Add Block button. V2.BN.2 should keep those data paths but hide the engineering feeling behind a natural page-writing surface.

## User Workflow

### Blank Note

User opens a note with no blocks.

Expected result:

- the page shows a quiet writing area, not a dashboard empty state;
- the user clicks the formal page area;
- a caret appears at the first writing position;
- typing creates a draft text block in the UI;
- persistence happens only once there is meaningful content.

### Existing Note

User opens a note with existing blocks.

Expected result:

- blocks read like note content, not stacked engineering cards;
- clicking a block lets the user edit its content;
- the existing source badges and source jump behavior remain available;
- the old Add Block form may remain temporarily as an advanced fallback, but it should not be the primary writing path.

### Slash Create

User types `/` in an empty draft block.

Expected result:

- a small grouped command menu opens;
- first-version commands include at least `Text`, `Heading`, `Formula`, `Image`, `Code`, `Quote`, `Definition`;
- selecting a command creates the corresponding block type/template metadata when saved.

### Slash Convert

User types normal paragraph text and then uses `/definition` or `/formula`.

Expected result:

- the UI treats this as conversion, not insertion;
- first version uses deterministic parsing plus user confirmation;
- conversion updates block metadata/template and preserves original text unless the user confirms a field extraction.

## Data / State Impact

Touched:

- NoteDetail page UI state;
- draft block local state;
- runtime template option selection;
- NoteBlock create/update payloads;
- possibly small client helpers for slash command parsing and conversion preview.

Not touched unless strictly required:

- database schema;
- source references;
- ObjectRelation;
- CanvasEdge;
- CanvasNode freeform placement;
- SourceRegion/OCR/VLM pipeline;
- GraphRAG adapter.

## Key Product Rules

- A blank page click should feel like writing, not object creation.
- Empty draft caret state should not create durable database rows.
- Default text block should use runtime template metadata when available.
- New block creation must preserve the v2.5.0 compatibility rule: old blocks remain readable and new blocks prefer runtime template metadata.
- `Enter` creates a normal newline inside the current block in V2.BN.2.
- `Ctrl+Enter` creates a new block after the current block in V2.BN.2.
- `Shift+Enter` may be treated the same as newline for the first version unless implementation cost is low.
- Slash command must distinguish create and convert.
- Paragraph/text remains the free writing block.
- Definition/formula/theorem/proof/example/exercise are structured block candidates, but V2.BN.2 only needs a seed conversion path.
- Delete should mean real delete/restore-through-undo in product language; if undo cannot be safely implemented in V2.BN.2, keep existing trash behavior but do not introduce a hidden "remove from page" concept.

## Out Of Scope

V2.BN.2 does not implement:

- freeform block resize;
- multi-column layout;
- layout mode;
- A4/multi-page export boundary;
- block field layout editor;
- complete structured field schema runtime;
- source picker or `/add source`;
- source chain/degraded UX;
- relation mode;
- local graph view;
- AI note generation;
- OCR/VLM source reconstruction.

## Acceptance Criteria

- User can write in a blank note without pressing Add Block.
- Empty click state does not create durable database rows.
- New default text block writes runtime template metadata.
- Existing NoteBlocks remain readable/editable.
- Slash command opens a first-version grouped menu.
- Slash command distinguishes create vs convert.
- Paragraph -> structured block conversion preserves user text.
- Existing source jump behavior still works.
- Existing canvas workspace still opens.
- No source, relation, template, package, or canvas truth is silently mutated.

## Graph-Native / Adapter Evidence

V2.BN.2 should record whether natural writing introduces any new evidence for future graph-native migration.

Expected evidence:

- `NoteBlock` remains the canonical content unit.
- Draft caret state is UI state and should not become graph truth.
- Slash command selected template strengthens `NoteBlock -> TemplateDefinition` future `USES_TEMPLATE` edge evidence.
- Convert-to-structured-block suggests future graph node labels may come from structured fields, but V2.BN.2 should not implement graph migration.

## Assumptions

- V2.BN.2 may use the existing linear Note page before freeform layout exists.
- V2.BN.3 will handle true resize / layout mode / side-by-side placement.
- V2.BN.5 or V2.BN.6 will mature structured field layout and schema contracts.
- Runtime template metadata from v2.5.0 remains the right path for new blocks.
- No new database migration is required unless implementation proves existing note block placement cannot support natural insertion safely.
