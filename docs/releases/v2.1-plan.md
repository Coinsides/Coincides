## 1. Goal

v2.1 turns existing parsed course documents into reviewable note proposals that apply into the v2.0 NoteBlock system.

The release seeds Course Material Library behavior without attempting full material reconciliation or a source snapshot viewer. Its core job is to bridge:

```text
Course documents / chunks
  -> course material sources
  -> source fragments
  -> material segments
  -> material map proposal
  -> organized note proposal
  -> reviewed NoteBlocks
```

v2.1 must preserve the product rule that AI organizes and proposes, while the user reviews and applies.

---

## 2. Product Position

v2.0 created a durable NoteBlock foundation. v2.1 makes that foundation useful with real uploaded material.

The user-facing promise is:

```text
I found these source ranges.
I organized these candidate blocks.
This proposal needs your review before applying.
```

Coincides should not claim complete understanding of a course, diagnose learner weakness, or silently overwrite user notes.

---

## 3. Version Boundary

v2.1 includes:

- Course-level material library seed over existing uploaded `documents` and `document_chunks`.
- First real implementation plan for `SourceMaterial`, `SourceFragment`, and `MaterialSegment`.
- Material map proposal from parsed course documents.
- Scope-based organized note proposal.
- Proposal-first review/apply flow into existing v2.0 `notes`, `note_blocks`, `note_block_placements`, and `note_block_sources`.
- Source references from proposed/generated NoteBlocks back to documents, chunks, and page ranges where available.
- Basic UI for selecting course material scope and reviewing generated note proposals.
- Version-scoped plan, engineering spec, quality review, experience review, and changelog.

v2.1 must not include:

- full Source Snapshot Viewer;
- bbox or region selection;
- full OCR pipeline;
- full Material Reconciliation;
- duplicate-source merging;
- source authority ranking;
- old Card/Deck migration;
- custom NoteBlock type system;
- drag-and-drop NoteBlock UX polish unless required for proposal review;
- adaptive summaries;
- cross-course concepts;
- Package Studio.

Deferred UX debt from v2.0 remains tracked in `docs/releases/v2.0-experience-review.md`. v2.1 may fix only the UX issues that block material map or note proposal review.

## 4. Implementation Scope

### 4.1 Course Material Library Seed

Use existing uploaded documents as the first course material source layer.

Committed direction:

- Existing `documents` remain valid and are not replaced.
- Existing `document_chunks` remain valid and become the first source for proposal-ready fragments.
- v2.1 adds only the metadata/state needed to show whether a course document is parsed, fragmentable, segmentable, proposed, used in a note, failed, or needs review.
- Original upload and parsing behavior must remain intact.

### 4.2 SourceFragment / MaterialSegment

Promote parsed document chunks into proposal-ready learning material.

Initial segmentation should use simple deterministic heuristics:

- document-level segment;
- chunk group segment;
- page-range segment when page metadata exists;
- heading-derived segment when chunk headings exist.

v2.1 should store confidence and source metadata where useful, but it must not attempt deep material reconciliation.

### 4.3 Material Map Proposal

Add a proposal type for material maps.

A material map proposal should preview:

- detected source documents;
- candidate fragments;
- candidate segments;
- proposed order;
- confidence;
- warnings or missing metadata.

Applying a material map proposal marks selected material structure as accepted for note generation. Discarding it leaves source documents and notes unchanged.

### 4.4 Organized Note Proposal

Add a proposal type for organized notes.

The user selects course and material scope. Coincides proposes:

- note title;
- candidate NoteBlocks;
- block types;
- source references;
- confidence and warnings.

Applying the proposal creates a v2 note and NoteBlocks through the v2.0 foundation. No large AI structural note change may apply without user review.

### 4.5 Basic UI Surface

Add the smallest UI surface that proves the v2.1 workflow:

- course-level material sources are visible;
- parsed/failed/pending source state is understandable;
- user can select a material scope;
- user can create a material map proposal;
- user can create an organized note proposal from selected/accepted material;
- user can review, apply, or discard proposal output;
- applied output can be opened in the Note editor.

## 6. API / Contracts

v2.1 must define a small explicit backend surface in the engineering spec.

Required route groups:

- Course material library:
  - list course material sources;
  - list source fragments for a course or document;
  - list material segments for a course or document;
  - update segment status or order where needed for proposal review.
- Proposal creation:
  - create material map proposal from course/document scope;
  - create organized note proposal from accepted or selected material scope.
- Proposal apply:
  - apply material map proposal;
  - apply organized note proposal into v2.0 notes and blocks.

Existing routes that must remain usable:

- `/api/documents`
- `/api/proposals`
- `/api/notes`
- `/api/note-blocks`
- `/api/projections`
- old Card/Deck routes

Payloads must be proposal-first and source-aware. Exact route names and request/response schemas belong in the engineering spec.

---

## 7. Agent Tool Contract

v2.1 does not allow the agent to directly create large note structures.

Allowed v2.1 agent behavior:

- inspect course documents and chunks;
- propose material maps;
- propose organized notes;
- include source references;
- include confidence and warnings;
- explain proposal limits in factual language.

Required language style:

- "I found these source ranges."
- "I organized these candidate blocks."
- "This proposal needs your review before applying."

Disallowed behavior:

- silently applying generated notes;
- claiming complete understanding of a course;
- diagnosing learner weakness by default;
- overwriting user notes without Proposal -> Review -> Apply.

---

## 8. Migration

v2.1 migration must be additive.

Migration rules:

- Do not rewrite existing `documents` or `document_chunks`.
- Do not delete existing v2.0 notes or NoteBlocks.
- Do not migrate old Card/Deck data.
- Preserve existing proposal history.
- Add only the smallest schema needed for SourceMaterial, SourceFragment, MaterialSegment, and proposal apply metadata.
- Verify empty database and existing v2.0 database paths.
