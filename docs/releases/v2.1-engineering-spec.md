# v2.1 Engineering Spec - AI Note Proposal + Course Material Library Seed

**Created**: 2026-05-19
**Updated**: 2026-05-19
**Branch**: `feat/v2.0-noteblock`
**Status**: Spec created / pending implementation

This spec is the implementation contract for v2.1. It promotes the roadmap's AI Note Proposal + Course Material Library Seed into concrete schema, API, proposal, UI, and verification requirements.

---

## 1. Implementation Boundary

v2.1 builds the first proposal-driven bridge:

```text
documents / document_chunks
  -> source_materials
  -> source_fragments
  -> material_segments
  -> material_map proposal
  -> organized_note proposal
  -> v2.0 notes / note_blocks / note_block_sources
```

v2.1 must not implement full Source Snapshot Viewer, full material reconciliation, duplicate-source merging, source authority ranking, old Card/Deck migration, custom NoteBlock types, drag-and-drop NoteBlock editing, cross-course concepts, or Package Studio.

Existing upload/parsing, Card/Deck, v2.0 Notes, NoteBlocks, Projections, and Proposals routes must remain usable.

### 2.1 `source_materials`

One row represents a course-level material source backed by an existing document.

```sql
CREATE TABLE IF NOT EXISTS source_materials (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  course_id TEXT NOT NULL REFERENCES courses(id) ON DELETE CASCADE,
  document_id TEXT NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
  source_type TEXT NOT NULL DEFAULT 'document',
  title TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'active',
  parse_status TEXT NOT NULL DEFAULT 'pending',
  fragment_status TEXT NOT NULL DEFAULT 'not_started',
  segment_status TEXT NOT NULL DEFAULT 'not_started',
  proposal_status TEXT NOT NULL DEFAULT 'not_proposed',
  used_in_note_count INTEGER NOT NULL DEFAULT 0,
  confidence REAL,
  warnings_json TEXT NOT NULL DEFAULT '[]',
  metadata TEXT NOT NULL DEFAULT '{}',
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  UNIQUE(user_id, document_id)
);
CREATE INDEX IF NOT EXISTS idx_source_materials_user_course_status ON source_materials(user_id, course_id, status);
CREATE INDEX IF NOT EXISTS idx_source_materials_document ON source_materials(document_id);
```

Allowed values:

- `status`: `active`, `archived`, `needs_review`, `failed`
- `parse_status`: copied from `documents.parse_status`
- `fragment_status`: `not_started`, `ready`, `failed`, `needs_review`
- `segment_status`: `not_started`, `proposed`, `accepted`, `failed`, `needs_review`
- `proposal_status`: `not_proposed`, `map_proposed`, `map_accepted`, `note_proposed`, `note_applied`

### 2.2 `source_fragments`

One row represents proposal-ready source text derived from a document chunk or whole document.

```sql
CREATE TABLE IF NOT EXISTS source_fragments (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  course_id TEXT NOT NULL REFERENCES courses(id) ON DELETE CASCADE,
  source_material_id TEXT NOT NULL REFERENCES source_materials(id) ON DELETE CASCADE,
  document_id TEXT NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
  document_chunk_id TEXT REFERENCES document_chunks(id) ON DELETE SET NULL,
  fragment_type TEXT NOT NULL DEFAULT 'chunk',
  title TEXT,
  content TEXT NOT NULL,
  page_start INTEGER,
  page_end INTEGER,
  order_index INTEGER NOT NULL DEFAULT 0,
  confidence REAL,
  warnings_json TEXT NOT NULL DEFAULT '[]',
  metadata TEXT NOT NULL DEFAULT '{}',
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_source_fragments_material_order ON source_fragments(source_material_id, order_index);
CREATE INDEX IF NOT EXISTS idx_source_fragments_course ON source_fragments(user_id, course_id);
CREATE INDEX IF NOT EXISTS idx_source_fragments_chunk ON source_fragments(document_chunk_id);
```

Allowed `fragment_type`: `document`, `chunk`, `page_range`, `heading`.

### 2.3 `material_segments`

One row represents a proposed or accepted learning segment such as a whole document, chunk group, heading section, or page range.

```sql
CREATE TABLE IF NOT EXISTS material_segments (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  course_id TEXT NOT NULL REFERENCES courses(id) ON DELETE CASCADE,
  source_material_id TEXT REFERENCES source_materials(id) ON DELETE CASCADE,
  segment_type TEXT NOT NULL DEFAULT 'chunk_group',
  title TEXT NOT NULL,
  summary TEXT,
  status TEXT NOT NULL DEFAULT 'proposed',
  order_index INTEGER NOT NULL DEFAULT 0,
  page_start INTEGER,
  page_end INTEGER,
  confidence REAL,
  warnings_json TEXT NOT NULL DEFAULT '[]',
  metadata TEXT NOT NULL DEFAULT '{}',
  accepted_at DATETIME,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_material_segments_course_status_order ON material_segments(user_id, course_id, status, order_index);
CREATE INDEX IF NOT EXISTS idx_material_segments_source_material ON material_segments(source_material_id);
```

Allowed `segment_type`: `document`, `chunk_group`, `page_range`, `heading`.

Allowed `status`: `proposed`, `accepted`, `needs_review`, `discarded`.

### 2.4 `material_segment_fragments`

Join table connecting segments to fragments.

```sql
CREATE TABLE IF NOT EXISTS material_segment_fragments (
  segment_id TEXT NOT NULL REFERENCES material_segments(id) ON DELETE CASCADE,
  fragment_id TEXT NOT NULL REFERENCES source_fragments(id) ON DELETE CASCADE,
  order_index INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (segment_id, fragment_id)
);
CREATE INDEX IF NOT EXISTS idx_material_segment_fragments_fragment ON material_segment_fragments(fragment_id);
```

## 3. Material Derivation Rules

v2.1 derives material structure from existing parsed documents. It does not change document upload/parsing behavior.

### 3.1 Source material sync

Whenever course materials are listed or a material-map proposal is created:

- ensure each owned `documents` row for the course has one `source_materials` row;
- copy current `documents.parse_status` into `source_materials.parse_status`;
- set `title` from `documents.filename`;
- set `fragment_status = 'ready'` only when fragments exist or can be derived;
- keep failed/pending/parsing documents visible with warnings.

### 3.2 Fragment derivation

For a completed document:

- if `document_chunks` exist, create one `source_fragments` row per chunk;
- if no chunks exist but `documents.extracted_text` exists, create one document-level fragment;
- set `order_index` from `document_chunks.chunk_index` or `0`;
- copy `heading`, `page_start`, and `page_end` when available;
- set `confidence = 0.8` for chunk/page fragments and `0.6` for whole-document fragments;
- do not duplicate fragments for the same `document_chunk_id`.

### 3.3 Segment derivation

Initial deterministic segments:

- one `document` segment per source material;
- `heading` segments when chunk headings exist;
- `page_range` segments when page ranges exist;
- fallback `chunk_group` segments grouping consecutive fragments in batches of up to 5.

Segments begin as `proposed`. Applying a material-map proposal marks selected segments as `accepted`.

## 5. Proposal Contracts

Reuse the existing `proposals` table.

New proposal types:

- `material_map`
- `organized_note`

Proposal status remains:

- `pending`
- `applied`
- `discarded`

### 5.1 Create material map proposal

`POST /api/proposals/material-map`

Body:

```json
{
  "course_id": "course-id",
  "document_ids": ["document-id"],
  "source_material_ids": ["source-material-id"]
}
```

At least one scope field is required. If both are omitted, use all course documents.

Stored proposal data:

```json
{
  "version": "v2.1",
  "proposal_kind": "material_map",
  "course_id": "course-id",
  "title": "Material map proposal",
  "description": "Detected material structure from course sources.",
  "source_material_ids": ["source-material-id"],
  "segments": [
    {
      "temp_id": "seg-1",
      "source_material_id": "source-material-id",
      "segment_type": "heading",
      "title": "Limits",
      "summary": "Candidate segment from source heading.",
      "order_index": 0,
      "page_start": 1,
      "page_end": 3,
      "fragment_ids": ["fragment-id"],
      "confidence": 0.8,
      "warnings": []
    }
  ],
  "warnings": []
}
```

### 5.2 Apply material map proposal

`POST /api/proposals/:id/apply`

For `material_map`:

- verify proposal is pending and owned;
- create/update selected `material_segments`;
- create `material_segment_fragments`;
- set applied segments to `accepted`;
- update related `source_materials.segment_status = 'accepted'`;
- update related `source_materials.proposal_status = 'map_accepted'`;
- create an `operation_batches` row with `source_type = 'proposal'`;
- do not create notes or note blocks.

### 5.3 Create organized note proposal

`POST /api/proposals/organized-note`

Body:

```json
{
  "course_id": "course-id",
  "source_material_ids": ["source-material-id"],
  "segment_ids": ["segment-id"],
  "document_ids": ["document-id"],
  "note_title": "Week 1 Organized Notes"
}
```

Scope preference:

1. `segment_ids`
2. `source_material_ids`
3. `document_ids`
4. all accepted material segments for the course

If no accepted segments exist, the route may derive deterministic proposed segments and include a warning.

Stored proposal data:

```json
{
  "version": "v2.1",
  "proposal_kind": "organized_note",
  "course_id": "course-id",
  "title": "Week 1 Organized Notes",
  "description": "Candidate note generated from selected source material.",
  "generation_mode": "ai",
  "source_material_ids": ["source-material-id"],
  "segment_ids": ["segment-id"],
  "blocks": [
    {
      "temp_id": "block-1",
      "block_type": "heading",
      "title": "Limits",
      "content_json": { "body": "Limits" },
      "plain_text": "Limits",
      "order_index": 0,
      "source_references": [
        {
          "document_id": "document-id",
          "document_chunk_id": "chunk-id",
          "source_page_start": 1,
          "source_page_end": 2,
          "source_excerpt": "excerpt",
          "reference_type": "chunk",
          "confidence": 0.8,
          "metadata": { "source_fragment_id": "fragment-id", "material_segment_id": "segment-id" }
        }
      ],
      "confidence": 0.8,
      "warnings": []
    }
  ],
  "warnings": []
}
```

### 5.4 Organized note generation

Generation uses AI first:

- read Anthropic config through existing user Settings/env pattern;
- provide only scoped source excerpts/chunks;
- ask for factual organized notes, not learner diagnosis;
- require JSON output with title, blocks, source references, confidence, and warnings;
- validate/sanitize result before storing.

Fallback mode:

- if AI is unavailable, missing key, malformed, or fails, create deterministic blocks from segment titles and fragment excerpts;
- set `generation_mode = 'deterministic_fallback'`;
- add a warning explaining that AI generation was not used.

Allowed generated block types for v2.1:

- `heading`
- `paragraph`
- `definition`
- `theorem`
- `proof`
- `formula`
- `example`
- `exercise`
- `answer`
- `sidenote`

Do not introduce custom block types in v2.1.

### 5.5 Apply organized note proposal

For `organized_note`:

- verify proposal is pending and owned;
- create `operation_batches` row with `source_type = 'proposal'`, `source_id = proposal.id`, `status = 'applied'`;
- create one `notes` row with `source_kind = 'proposal'`;
- create `note_blocks` rows with `source_kind = 'proposal'`;
- create `note_block_placements` ordered by proposal block order;
- create `note_block_sources` for every source reference;
- update related `source_materials.proposal_status = 'note_applied'`;
- increment `source_materials.used_in_note_count`;
- mark proposal `applied`;
- return `{ message, note_id, blocks_count }`.

Discarding an organized note proposal must not create or mutate notes, blocks, sources, material segments, or source materials.

## 6. Frontend Contract

Add the v2.1 UI inside Course detail, not as a separate top-level app section.

Expected user flow:

```text
Course Detail
  -> Course Material / Proposal area
  -> view material sources
  -> create material map proposal
  -> review/apply/discard material map
  -> create organized note proposal
  -> review/apply/discard organized note
  -> open applied note editor
```

Frontend additions:

- store/service methods for course materials and v2.1 proposal creation;
- Course Detail material area showing document parse/material statuses;
- proposal preview for `material_map` and `organized_note`;
- apply result navigation to `/notes/:noteId` when an organized note proposal is applied.

UX constraints:

- keep UI compact and work-surface oriented;
- use source-aware wording: "I found these source ranges" and "This proposal needs review before applying";
- show warnings visibly;
- do not claim complete course understanding;
- do not add drag/drop NoteBlock editing unless proposal review is blocked without it.

## 7. Step Plan

### Step 1: Course Material Library seed

Implement migration 016, schema.sql updates, material derivation helpers, `courseMaterials` routes, shared/client types, and tests for additive schema plus material source listing.

Completion criteria:

- empty DB and existing v2.0 DB paths create new tables;
- course documents appear as source materials;
- completed documents can expose fragments;
- pending/failed documents stay visible with status/warnings.

### Step 2: SourceFragment / MaterialSegment foundation

Implement deterministic fragment and segment derivation.

Completion criteria:

- chunks become fragments;
- unchunked parsed documents become document fragments;
- document/heading/page-range/chunk-group segments are proposed;
- segment update route works.

### Step 3: Material Map Proposal

Implement `POST /api/proposals/material-map` and apply behavior for `material_map`.

Completion criteria:

- proposal previews sources, segments, confidence, and warnings;
- apply accepts selected segments without creating notes;
- discard does not mutate material or notes.

### Step 4: Organized Note Proposal

Implement AI-first/fallback organized note proposal creation and apply behavior.

Completion criteria:

- proposal contains note title, candidate blocks, source references, confidence, and warnings;
- fallback works without an AI key;
- apply creates note, blocks, placements, sources, and operation batch.

### Step 5: Review/apply UI and smoke

Implement Course Detail material/proposal UI.

Completion criteria:

- Henry can go from course materials to applied note;
- applied note opens in existing Note editor;
- warnings and source references are visible enough for v2.1 foundation.
