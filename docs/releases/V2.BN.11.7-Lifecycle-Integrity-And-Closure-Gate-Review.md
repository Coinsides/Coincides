## 1. 本轮解决了什么

V2.BN.11.7 没有增加新的 Relation 能力。它关闭的是 V11 真相层最容易在真实删除、全量保存和遗产残留中破裂的接缝：

1. surviving Purpose 在普通保存中保持原身份，Relation 的 `origin_purpose_id` 不再被意外清空；
2. 真正删除 Purpose 时，组织边删除、Item 与 Relation 存活，origin receipt 诚实降级为 `NULL`；
3. 删除 Note、Project 或 ContentGroup 不会把独立 Item / Snapshot / Anchor / Relation 一起误删；
4. retired Item 仍可解释既有 active Relation，但不能 reaffirm，仍允许 revoke；
5. 已经卸载且底层表已由 migration 047 删除的旧 Relation routes 与 service branches 被物理移除；
6. V11 父计划的 26 项工程 Closure Gate 建立了逐项证据。

## 2. Purpose identity-preserving replacement

原实现会先删除 Note 下全部 Purpose，再用相同 ID 重建。由于 `relations.origin_purpose_id` 使用 `ON DELETE SET NULL`，这会让一次看似普通的保存永久洗掉 Relation 的 Purpose 出处收据。

本轮将 `replaceNotePurposes` 改为事务内 reconcile：

- 预先规范化并去重 payload Purpose ID；
- 拒绝复用属于另一用户或另一 Note 的 Purpose ID；
- 暂时释放 Note default 唯一约束；
- 同 ID、同用户、同 Note 的 Purpose 原地 `UPDATE`；
- 新 Purpose `INSERT`；
- surviving Purpose 的成员边执行 full replacement，并恢复 filtered hidden edge；
- payload 真正 omitted 的旧 Purpose 最后删除；
- 空 payload 仍创建 Note default Purpose。

新增 RED-first 证明：

- surviving Purpose replacement 保留 Relation origin receipt；
- omitted Purpose 删除组织边、保留端点 Item 与 Relation，并使 receipt 降级；
- 跨 Note / 跨用户 Purpose ID claim 被拒绝；
- 既有 hidden-edge 与 stale payload 行为继续通过。

## 3. 生命周期集成闭环

新增 `v2RelationLifecycleClosure.test.ts`，通过真实 service 与 SQLite FK 行为覆盖四条纵切：

| 场景 | 结果 |
|---|---|
| 独立删除 Note | Item、Snapshot、Anchor、Relation 存活；`origin_note_id -> NULL`；Anchor target/excerpt receipt 保留 |
| 删除 Project | Item、Relation 存活；Project / Note / Purpose origin receipt 降级；另一 Project 的 ContentGroup / Purpose Item edge 继续可读 |
| 删除 ContentGroup root | 只删除该 group 的 member edges；Item 与 Relation 存活 |
| retire Relation endpoint Item | active Relation 仍可读、可 revoke；reaffirm 被拒绝 |

这组测试不引入 soft-delete 垃圾桶，也不把组织容器重新变成知识真相 owner。
