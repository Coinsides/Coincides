# V2.BN.10.1 Source Identity And Placement Floor 工程回执

> **状态 (Status)**: engineering complete

## 1. 收口判断

V2.BN.10.1 已完成工程收口，可以进入 V2.BN.10.2 File Intake And Storage Lifecycle。

本版本只建立 Source 的身份与生命周期地板。它证明了 Source identity、事实文件、物化 run 和 Project 可见位置可以彼此独立存在；没有提前开放上传 UI，也没有伪装成已经具备解析、投影或完整删除补偿能力。

## 2. 已完成

- 新增 migration 045，建立 `source_records`、`source_files`、`source_materializations`、`source_project_placements` 四层数据脊柱。
- 数据库保证同用户 content hash 唯一、Source/Project placement 唯一、v1 每 Source 一个 materialization run、每用户每种 system course 唯一。
- materialization 状态与 `projection_note_id` 建立双向约束：只有 `materialized` 可携带投影指针，`materialized` 也必须携带该指针。
- Origin 与 Placement 分离；删除 Project 只删除对应 placement，并通过 `origin_course_name_snapshot` 保留出身收据。
- 新增最小 Source identity 服务：建立四层地板、按 hash 查询、幂等补 placement。
- 新增 Home system course 服务；Home 幂等创建、不可删除、不可改名，普通 Project 行为不受影响。
- `notes.note_class`、`courses.system_kind` 与 `note_block_sources` 的 Source receipt 接缝已加入；普通公共 validator 不接受系统身份注入。
- 历史 canvas backing note 被迁移为 `system`，learning canvas 与 composition template 两条前向创建路径也显式写入 `note_class='system'`。
- 修复 ContentGroup member 的 `source_sync_status='stale'` 在读写往返后被洗回 `fresh` 的缺口。

## 5. 工程判断

四层职责没有重新合并到单表或 metadata：

```text
source_records             = 用户心智中的稳定 Source identity
source_files               = 不可变事实附件
source_materializations    = durable parser/materialization run
source_project_placements  = Project 可见镜头
```

当前最重要的后续边界是：10.2 必须把真实文件生命周期接到这四层地板上，并把 hash 冲突从数据库异常转成幂等命中流程；不能另建第二套上传真相。
