# V2.BN.5 Plan - Block Visual Language And Control Layer

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make NoteBlocks read like notebook/report content instead of backend cards, while keeping the first preset block set narrow enough to protect the Better Notebook writing flow.

**Architecture:** V2.BN.5 builds on V2.BN.2 natural writing, V2.BN.3 BlockBox layout, and V2.BN.4 page/canvas/export boundaries. NoteBlock remains content truth. Placement / BlockBox remains layout truth. TemplateDefinition remains template truth. This version improves visual language and control surfaces without turning normal note editing into a schema editor.

**Tech Stack:** React, TypeScript, CSS modules, existing NoteDetail note-block APIs, existing runtime template metadata where available, existing placement/layout persistence path, browser smoke through the local client.

---

## Summary

V2.BN.5 is the first Better Notebook version focused on the look and handling of individual blocks.

The product goal is simple:

```text
Reading mode should show content.
Selected mode should show controls.
Inspector/debug mode should show structure and backend details.
```

This version deliberately narrows the default block set. `definition` and `formula` are the first structured knowledge blocks. Theorem, proof, example, exercise, answer, table, and image/diagram variants are not removed from the runtime world, but they should not be pushed as first-class default structured presets in this version. Most of them belong to later Template Studio Productization or future media/table contracts. Callout is stricter: it is not needed as a Better Notebook default block and should only remain readable for legacy compatibility if old runtime data contains it.

## User Workflow

### Workflow 1: Read A Note Without Seeing Engineering Chrome

1. User opens a note.
2. User sees text, headings, formulas, code, quotes, source quotes, and sticky/scratch notes as content.
3. Backend labels, template ids, debug ids, export labels, and AI visibility labels do not clutter the default reading surface.
4. User can enable preview/debug/inspector modes when they need metadata.

Expected result:

- A note feels like a notebook/report page.
- Metadata exists, but it is not always shouting at the user.

### Workflow 2: Select A Block And See The Right Controls

1. User clicks a block.
2. The block shows a light selected boundary.
3. Resize/move controls appear only when relevant.
4. The floating toolbar exposes high-frequency actions.
5. Less common actions move to more/context/inspector surfaces.
6. Clicking empty page space exits selected state.

Expected result:

- Reading is calm.
- Editing affordances are discoverable.
- Selection does not permanently pollute the page.

### Workflow 3: Insert Or Convert A Narrow Default Block Set

1. User types `/` or uses the Insert control.
2. The default menu shows a narrow first-version set.
3. User can create text, heading, definition, formula, code, source quote, or sticky/scratch note.
4. Theorem/proof/example/exercise are not promoted as first-version default presets.
5. Advanced/runtime templates stay accessible only through fallback or Template Studio paths.

Expected result:

- Users are not overwhelmed by the whole template registry.
- First-version defaults are understandable and useful.

### Workflow 4: Use Formula As A Visual LaTeX Object

1. User creates a formula block.
2. Reading mode shows rendered formula, not raw input.
3. Editing mode exposes raw LaTeX input and rendered preview.
4. Invalid LaTeX keeps user input and shows a warning instead of data loss.
5. Resize and alignment affect presentation without corrupting formula truth.
6. Field values have a first-version rule, especially where `latex_input`, optional `formula_name`, optional `explanation`, and future `variables` should live or be represented.

Expected result:

- Formula behaves like a precise notebook object.
- The raw source remains recoverable.
- Future AI/search/export can read the formula from structured fields instead of guessing from one mixed text blob.

### Workflow 5: Use Definition As The First Structured Knowledge Block

1. User creates or converts to a definition block.
2. Definition shows at least a concept/name field and a description/body field.
3. Reading mode presents it like content, not a form panel.
4. Selected/editing mode lets the user edit field values.
5. Field schema editing remains a Template Studio responsibility.
6. Field values have a first-version rule, especially where `concept_name` and `description` should live or be represented.

Expected result:

- Structured knowledge becomes readable to humans and future graph/AI flows.
- Normal note editing does not become schema editing.

## Surrounding Contract Decisions For This Version

V2.BN.5 must not try to mature every surrounding contract at once.

```text
Field Values:
  Must be clarified before implementation.
  This version needs a first-version rule for Definition and Formula.

Field Layout:
  Only fixed visual seeds and state boundaries in this version.
  Heavy field layout editing belongs to V2.BN.7 Template Studio Productization after V2.BN.6 data contract work.

Category Membership:
  Rules only in this version.
  Allowed entrances: Default, Math, User Defined.
  Full management belongs to V2.BN.7.
```

## First-Version Default Block Policy

### Default User-Facing Blocks

```text
Basic:
  Text / Paragraph
  Heading

Structured:
  Definition
  Formula

Technical:
  Code

Source:
  Source Quote

Workspace:
  Sticky / Scratch Note
```

### Deferred Or Template-Only Blocks

```text
Theorem
Proof
Example
Exercise
Answer
Table
Image / Diagram
```

These may remain in compatibility/runtime data, but V2.BN.5 should not make them the main default writing choices.

`Concept` is not a user-facing default block. It belongs to metadata/search/AI/local-graph layers.

`Callout` is not needed as a Better Notebook default block. If older runtime data contains callout/warning templates, keep them readable for compatibility, but do not promote them in the default insert path.

## Data / State Impact

Touched:

- NoteBlock content truth: should remain stable.
- NoteBlock field values: first-version Definition / Formula rules must be defined, even if stored in existing `content_json` or metadata-compatible shape.
- BlockBox / CanvasNode / placement layout truth: may be used for visual size, position, selected state support, and layout mode.
- TemplateDefinition metadata: read/use only where existing metadata is sufficient.
- UI state: reading, hover, selected, editing, layout, preview/debug/inspector.
- Export and AI visibility: visual display only; no new export/AI engine.

Not touched unless implementation audit proves it is strictly required:

- database migrations;
- full structured field schema storage redesign;
- Template Studio productization;
- Style Studio / Appearance Studio;
- relation runtime;
- source library;
- OCR/VLM reconstruction;
- GraphRAG adapter;
- package import/export.

### Data Contract Questions To Answer Before Implementation

- What is the first-version Field Values rule for Definition and Formula?
- Can current NoteBlock `content_json` represent `definition` and `formula` field values well enough for V2.BN.5?
- Should metadata carry compatibility hints, while `content_json` remains the content truth?
- Do we need a temporary compatibility mapper for old block content to display as definition/formula?
- Where should raw LaTeX live for formula blocks in this version?
- Can field layout be stored in existing placement/display overrides, or should it remain UI-only until V2.BN.6?
- Which block visual choices are durable user choices versus transient UI state?
- How do old theorem/proof/example/exercise blocks continue to render if they are no longer default presets?
- How do Default / Math / User Defined categories affect only menu grouping without changing template identity?

Important rule:

If a visible user workflow needs a small data repair to avoid fragile client-only state, do it in this version. Do not leave required state as invisible cache only because V2.BN.6 is later.

## Key Product Rules

- Default block set is not the full template registry.
- Field Values are the core structured block truth for this version.
- `formula` is the first pure LaTeX structured block.
- `definition` is the first structured knowledge block.
- `heading` helps structure a page but is not a knowledge object by itself.
- Theorem/proof/example/exercise are template variants for later productization, not first-version defaults.
- Advanced insert is a fallback/runtime precision tool, not the primary writing path.
- Reading mode hides engineering metadata.
- Selected mode reveals object controls.
- Inspector/debug mode reveals structure.
- Field values can be edited in normal notes.
- Field schema belongs to Template Studio.
- Field layout in this version is a fixed visual seed, not a mature layout editor.
- Category membership is a discovery/menu rule in this version, not a taxonomy or domain system.
- Style freedom is deferred to Style Studio / Appearance Studio.

## Key Changes

### 1. Current Block Rendering Audit

Read the current implementation before editing:

- `client/src/pages/Notes/NoteDetail.tsx`
- `client/src/pages/Notes/NoteDetail.module.css`
- `client/src/pages/Notes/noteSlashCommands.ts`
- `client/src/pages/Notes/noteBlockConversion.ts`
- current note block API routes and validators;
- current runtime template seed/list behavior.

Record findings in:

- `docs/releases/V2.BN.5-review.md`
- `docs/releases/V2.BN.5-engineering-spec.md`

The audit must answer:

- which block types the UI currently exposes;
- which runtime templates exist but should not be default presets;
- where block type labels are rendered;
- where formula/definition content is stored today;
- which controls are in toolbar, more menu, inspector, or fallback insert.

### 2. Default Block Set And Insert Menu

Refine slash/insert to treat the first-version default set as the main path:

```text
Text
Heading
Definition
Formula
Code
Source Quote
Sticky / Scratch Note
```

Advanced/runtime template insert can remain available, but it should be visually secondary and clearly named as a fallback/precision path.

Template category entrances for this stage should stay narrow:

```text
Default
Math
User Defined
```

Do not pre-create Physics, Chemistry, Biology, History, Engineering, or Research categories in this version.

### 3. Reading / Selected / Editing / Debug States

Implement or refine state boundaries:

```text
Reading:
  content only, minimal chrome.

Hover:
  very light affordance only.

Selected:
  boundary, toolbar, handles, context controls.

Editing:
  content-specific editor.

Layout:
  box/handle/snap controls.

Debug / Preview:
  template/source/export/AI/debug metadata.
```

### 4. Formula Visual Language

Formula block should:

- read as rendered formula;
- edit as raw LaTeX plus preview;
- preserve raw input;
- show parse warning instead of losing content;
- avoid rich-text formatting inside raw input;
- allow basic alignment / size through block presentation.

If full formula rendering is too large for this version, the engineering spec must define the minimum safe fallback and the next version path.

### 5. Definition Visual Language

Definition block should:

- have a clear readable presentation;
- expose concept/name and description/body as separate field values where possible;
- avoid looking like a backend JSON/form card;
- keep schema editing out of normal notes;
- be ready for future local graph label extraction from `concept_name`.

If current data does not support full field values, the version may implement a visual seed while recording the exact data gap for V2.BN.6.

### 6. Block Indicators And Metadata

Move noisy metadata out of the default page:

- export role labels;
- AI visibility labels;
- template/debug labels;
- source/relation indicators that are too loud.

Preferred surfaces:

- badge;
- hover tooltip;
- selected toolbar;
- inspector;
- preview/debug panel.

### 7. Controls And Context Menu

Refine controls so high-frequency actions are easy and low-frequency actions do not crowd the block:

- selected toolbar for common block actions;
- context menu for less common operations;
- inspector for structure/source/template/debug details;
- no duplicate "advanced insert" entry in unrelated more menus.

## Out Of Scope

V2.BN.5 does not implement:

- full Template Studio Productization;
- full Style Studio or Appearance Studio;
- user-defined CSS;
- arrow/connector style editor;
- full table editor;
- full image/media data contract;
- OCR image-to-LaTeX;
- AI template selection engine;
- full source library;
- relation definition runtime;
- local graph view;
- GraphRAG adapter;
- full PDF export.

## Acceptance Criteria

- Reading mode shows block content without permanent engineering labels.
- Selected block controls are visible and do not permanently occupy document flow.
- Empty page / normal writing still works from V2.BN.2.
- Block resize/text reflow from V2.BN.3 still works.
- Page/canvas/export labels from V2.BN.4 are still available through preview/inspector, not always-on clutter.
- Slash/insert default choices are narrow and understandable.
- `definition` and `formula` are the first structured block targets.
- Theorem/proof/example/exercise are not first-version default presets.
- Existing old blocks using theorem/proof/example/exercise templates still render in a compatibility-safe way.
- Formula raw input is not lost.
- Definition content remains editable.
- No source, relation, template, or export truth is silently rewritten.

- Default block list should stay intentionally small.
