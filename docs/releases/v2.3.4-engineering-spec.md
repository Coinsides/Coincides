# v2.3.4 Engineering Spec - Source Annotation / Media Snapshot Planning Patch

**Created**: 2026-05-22
**Updated**: 2026-05-22
**Status**: Planning-only spec complete

---

## 1. Implementation Boundary

v2.3.4 is a docs-only planning patch.

It does not create:

- database migrations;
- backend routes;
- frontend surfaces;
- new dependencies;
- provider calls;
- PDF/Web/Media ingestion code.

Its job is to name the future contracts clearly enough that later Source Annotation, PDF/Web snapshot, media snapshot, Source Board, and Canvas work can be planned without mixing scopes.

---

## 2. Source Annotation Future Contract

Future concept names:

```text
SourceAnnotation
AnnotationTarget
AnnotationLayer
AnnotationKind
```

Recommended first implementation direction:

- annotations should attach to stable source objects, not raw viewer coordinates alone;
- initial targets should prefer `SourceAnchor`, `SourceScope`, `SourceSnapshotPage`, and `SourceBoardNode`;
- bbox, region, and text-offset targets should be additive future target kinds;
- annotations should be reversible or archivable, not destructive source edits;
- AI-generated annotations must remain proposal-first before applying user-visible structure.

Potential target kinds:

```text
source_snapshot
source_snapshot_page
source_anchor
source_scope
source_board_node
future_text_range
future_bbox_region
future_media_timestamp_range
```

Potential annotation kinds:

```text
highlight
comment
question
correction
importance
relationship_hint
source_warning
future_media_marker
```

---

## 3. Media Snapshot Future Contract

Future concept names:

```text
MediaSnapshot
MediaSnapshotFrame
MediaAnchor
MediaTranscriptSegment
```

Recommended first implementation direction:

- start transcript-first for audio/video rather than frame-first;
- treat timestamps as source ranges similar to page ranges;
- use keyframes later for visual trust and navigation;
- do not require media snapshot work before v2.4 Canvas;
- keep media anchors compatible with SourceBoard and proposal inputs.

Potential media source units:

```text
transcript_segment
timestamp_range
keyframe
chapter_marker
speaker_turn
slide_frame
```

## 4. PDF / Web / Media Tool Candidates

No candidate is adopted in this version.

Future evaluation candidates:

| Area | Candidate | Intended Job | Adoption Timing |
|---|---|---|---|
| PDF | `PDF.js` | render pages and page text in-browser | after text-first source viewer needs visual PDF fidelity |
| PDF | `EmbedPDF` | embedded PDF viewer/reference candidate | compare before PDF.js adoption |
| Web | `Mozilla Readability` | extract readable article text | when Web Snapshot enters active scope |
| Web | `DOMPurify` | sanitize extracted HTML | required before showing stored web HTML |
| Web | `Playwright` | controlled webpage capture | only after External Tool Gate approval |
| Web | `SingleFile` | full webpage archive reference/candidate | evaluate as archive strategy, not default assumption |
| Media | transcript-first provider/tool | convert video/audio into text ranges | later media-source version |
| Media | keyframe extraction | visual checkpoints for video | after transcript anchors exist |

External Tool Gate questions for later:

- Does this tool solve a real source-trust problem that the existing text snapshot cannot?
- Can it work locally on Windows?
- Does it keep Coincides source evidence and proposal model independent?
- What data remains if the tool is removed?
- Does it increase secret, network, binary, or maintenance risk?

---

## 5. Relationship To v2.4

v2.3.4 does not begin Canvas.

It prepares v2.4 by making the future source layers compatible with Canvas:

```text
SourceAnnotation / MediaAnchor
  -> SourceBoardNode
  -> future CanvasNode
```

Canvas should reference source-grounded objects rather than copying source text or media content as a second truth.
