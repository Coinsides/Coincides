> **For agentic workers:** V2.BN.7 是复盘、审查、调研、当前 branch 收口和 Canvas Engine 开工门禁阶段。不要把它扩展成完整 Canvas Engine、Template Studio、Source Library、Relation Runtime 或 GraphRAG adapter。

## Summary

V2.BN.7 的目标已经从“继续讨论 editor runtime”调整为更明确的三件事：

```text
1. 解剖当前 runtime
   把 V2.BN.1 到 V2.BN.6 做出的 self-owned editor prototype 盘清楚。

2. 给当前 branch 收口

   复用已有 canvas / AFFiNE / BlockSuite 调研，找出第八阶段还缺哪些新调研和工程前置问题。
```

当前判断：

- 当前 `NoteDetail.tsx` 里的模拟 page/canvas runtime 已经基本走到尽头。
- 它证明了 Coincides 可以自研一套符合自身产品逻辑的编辑体验。

- 因此 V2.BN.7 不应继续把旧 runtime 打磨成无限画布引擎。
- V2.BN.7 应把旧 runtime 当作 prototype evidence 来解剖，把经验沉淀成合同，把代码实现中不应继承的技术债标出来。

一句话：

```text
V2.BN.7 不是继续修旧 runtime。
V2.BN.7 是旧 runtime 的结案审计，也是 Canvas Engine clean branch 的开工门禁。
```

## Current Assessment

### 当前 runtime 已经证明的东西

V2.BN.1 到 V2.BN.6 已经证明：

- Coincides 可以做 note-first workspace；
- 页面可以从工程卡片变成接近笔记软件的写作表面；
- `NoteBlock` 作为内容单位、`BlockBox / Placement` 作为布局单位的方向成立；
- block resize、文本重排、layout mode、slash command、preview overlay、block control bar、structured field seed 都有真实交互价值；
- Page 是 canvas 上的正式 frame，workspace 是 PageFrame 外的 canvas area，这个产品模型成立；
- source / link / relation / template / editor state 的边界已经能讲清楚；
- self-owned runtime 不是空想。

### 当前 runtime 已经走到尽头的地方

当前 `NoteDetail.tsx` runtime 不应继续被当成未来 Canvas Engine 的长期地基：

- 它是在 note 页面里模拟 canvas，而不是真正 canvas-native runtime；
- page/canvas mode 仍然像视图切换，不是统一 NoteCanvas 下的自然缩放与移动；
- block measurement / auto-height 曾多次出 bug；
- overlay、preview、toolbar、control bar 的图层关系曾反复冲突；
- elastic avoidance 说明布局交互有潜力，但也说明模拟 collision engine 很脆；
- slash menu 和 popover 定位依赖当前 DOM flow，未来 pan/zoom 后需要重做；
- undo/redo、operation batch、selection、focus、rebuild state 还不是统一 runtime contract；
- large document、hundreds/thousands blocks、formula-heavy、media-heavy、relation-heavy 还没有真正验证；
- connector endpoint、relation path、port、route、animation、view budget 还没有进入 runtime。

### 当前 branch 的新定位

当前 branch 应被收口为：

```text
experiment branch
  -> 证明产品体验方向
  -> 保留当前有限页面 / 大画布 fallback
  -> 作为 UX reference
  -> 作为失败时可回退路线
  -> 不再承担未来 Canvas Engine 的长期兼容债
```

未来 Canvas Engine 应默认新开 clean branch：

```text
canvas-engine clean branch
  -> 可以重写 NoteDetail runtime
  -> 可以 clean reset 实验性 layout 数据
  -> 以 V2.BN.6/V2.BN.7 contract 为参考
  -> 不承诺兼容当前 better_notebook_layout 的所有细节
```

### R7-1 Current Runtime Autopsy

定义：

在 V2.BN.7 中，`runtime` 指的是用户打开一篇 note 之后，支撑“写作、选择、移动、resize、预览、布局、字段编辑、source/relation/export/AI 状态展示”的那套正在运行的编辑系统。

它不是单个文件，也不是单纯 UI，也不是持久数据本身。

更准确地说，runtime 是夹在“用户正在操作的界面”和“Coincides Core 持久 truth layer”之间的运行层。它负责把数据库里的 note、NoteBlock、layout、source、template、relation 等 truth 读出来，临时组织成用户可以操作的对象；也负责把用户的点击、输入、拖动、resize、选择、预览、模式切换等动作，重新写回正确的 truth layer。

它包括：

- 数据被读入 editor 后如何变成可操作对象；
- 用户点击、输入、拖动、resize 时状态如何变化；
- block 如何测量高度、计算位置、避免重叠；
- slash menu、popover、preview、toolbar、control bar 如何定位和显示；
- page mode / canvas mode 如何决定哪些对象可见；
- editor state、operation state、persistent truth 之间如何分工；
- runtime 如何把用户操作转回 Coincides Core 的 content truth、layout truth、source truth、relation truth 或 template truth。

它不包括：

- NoteBlock 的 canonical content truth 本身；
- layout / placement 的 canonical truth 本身；
- source provenance、ObjectRelation、TemplateDefinition 的最终数据主权；
- GraphRAG、OCR/VLM、AFFiNE/BlockSuite 等外部 adapter 的索引或投影结果；
- 单纯的视觉皮肤、主题色或静态页面样式。

一句话：

```text
runtime = 用户正在操作笔记时，连接产品体验、临时交互状态、交互计算和持久 truth layer 的运行层。
```

因此，V2.BN.7 不是问“现在这段代码能不能继续修”，而是问：

```text
这套 runtime 原型证明了哪些产品规则？
踩出了哪些未来不能再踩的坑？
哪些能力必须在 Canvas Engine 里正式重建？
```

目标：

- 审计当前 runtime 已有能力；
- 标注 stable / useful prototype / fragile prototype / dead end / unknown；
- 把每个能力拆成：
  - 产品价值；
  - 当前实现方式；
  - 是否应继承到 Canvas Engine；
  - 是否只保留为经验；
  - 是否应彻底丢弃。

R7-1 的正式报告必须产出三张表。

注意：本 plan 只定义三张表的任务结构，不在这里提前填完整答案。真正的逐项审计会在 R7-1 执行时完成。三张表的目的，是把当前 `NoteDetail.tsx` prototype 中已经跑出来的经验拆成三类，避免未来 Canvas Engine 开工时把“值得继承的产品规则”和“不该继承的实现债”混在一起。

三张表的安排如下：

```text
Table A: Keep As Product Rule
  -> 保留为未来产品体验规则。

Table B: Keep As Warning
  -> 保留为未来工程避坑清单。

Table C: Rebuild As Engine Feature
  -> 保留为未来 Canvas Engine 的能力清单。
```

三张表之间不能互相替代：

- Table A 讲“未来用户体验必须继续成立什么”；
- Table B 讲“当前实现里哪些东西已经证明不能照搬”；
- Table C 讲“哪些能力不能再靠补丁模拟，必须在 engine 层正式实现”。

R7-1 完成后，Table A / B / C 会分别流入：

```text
Table A -> Canvas Engine Requirement Draft 的验收标准
Table B -> Canvas Engine Research Gap Report 的风险清单
Table C -> Canvas Engine Foundation / V2.BN.8.x 的工程任务池
```

### Table A: Keep As Product Rule

整理当前 runtime 证明成立、未来 Canvas Engine 必须继承的产品规则。

示例：

```text
block resize 后文字必须自动重排
slash command 是 block type 入口
preview overlay 默认不干扰写作
source badge / relation badge / block type badge 不应常驻污染正文
```

字段：

```text
体验规则
来自哪个当前功能/补丁
为什么要保留
未来 Canvas Engine 的验收方式
相关 contract / roadmap 引用
```

输出要求：

- 每一条都必须是用户体验层面的规则，而不是当前代码写法；
- 每一条都要说明它为什么对 Better Notebook 成熟体验重要；
- 每一条都要能转化成未来 V2.BN.8 / V2.BN.8.x 的验收项。

### Table B: Keep As Warning

整理当前 runtime 踩过的坑，未来 Canvas Engine 不能照搬的实现方式。

示例：

```text
DOM flow + 手动高度修补导致 block overlap
popover 绑定页面流导致 slash menu 漂移
preview panel 和 selected block toolbar 图层冲突
elastic avoidance 在模拟 layout 中容易产生误触发
```

字段：

```text
问题/坑
触发场景
根本原因
未来不要怎么做
未来需要的 engine 机制
```

输出要求：

- 每一条都要从当前 prototype 的真实问题出发；
- 不能只写“有 bug”，必须写清楚为什么在旧 runtime 里容易发生；
- 每一条都要对应一个未来 engine 层应该提供的机制，避免只留下抱怨。

### Table C: Rebuild As Engine Feature

整理当前 runtime 只是模拟过、未来必须在 Canvas Engine 中正式实现的能力。

示例：

```text
measurement / auto-height service
canvas-native placement model
pan / zoom / viewport persistence
selection and hit-testing under transform
popover positioning under transformed canvas
relation connector endpoint / path reserve
large document virtualization
```

字段：

```text
未来 engine 能力
当前 prototype 对应物
为什么当前实现不够
最低可接受版本
风险等级
是否阻塞 Canvas Engine Foundation
```

输出要求：

- 每一条都必须是 engine 层能力，不是单个 UI 按钮；
- 要区分 `V2.BN.8` 必须有、`V2.BN.8.x` 继续打磨、以及可以推迟到 Source/Relation/Template 阶段的能力；
- 对 high-risk 项必须说明 fallback：如果自研 Canvas Engine 做不稳，当前 branch 或有限大画布方案如何作为后备道路。

覆盖：

- block resize / reflow；
- layout mode；
- page mode；
- canvas workspace seed；
