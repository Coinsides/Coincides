V2.BN.11 不是给旧 Relation 表换一个名字，而是把 Coincides 的知识身份与关系真相建立在新的 `Item` 之上。开始 V2.BN.11.1 代码施工前，必须同时满足以下事实：

1. V2.BN.9 Purpose Foundation 已完成，`purpose_members` 的 role / fitness / order 已住在成员边上；
2. V2.BN.10 Source Floor 工程门已完成，`source_records`、Source receipt 与 Project-as-lens 边界可供 Item Anchor 使用；

4. `items / item_snapshots / item_anchors / relations / relation_assessments` 的职责以概念设计 v1.1 为准；
5. Item 是 Relation 的唯一 durable endpoint；ContentGroup 是 Item 的组织方式，Purpose 是情景与成员边，Canvas 只负责显化；
6. `relation_assessments`、机械新鲜度和至少一个人工认领 / 铸卡入口都属于 V11 地板，不得整体后移；
7. 当前仓库的 `PRODUCT.md`、Better Notebook Roadmap、Current State 与若干 active contracts 仍保留“ContentGroup / Petal 是 Relation endpoint”的旧教义。该同步由 Claude 随版负责，不计入 Codex 交付，但在 V11.1 开工前必须完成，不能让 active authority 与新代码相互矛盾；**✅ 2026-07-13 已完成（7 张面,见 handoff `2026-07-13-v2bn11-doctrine-sync-report.md`）**；
8. V11 不依赖当前 1.x Agent，不调用 embedding / GraphRAG，也不假设已有成熟 RelationProposal 机器。

### 0.1 migration 047 前置验证

047 是仓库内第一次使用“端点 Item + 端点 Snapshot”复合外键。迁移必须先有失败测试，再实现迁移，并用真实 SQLite 行为证明：

- `(from_item_id, from_snapshot_id)` 只能引用同一 Item 的 Snapshot；
- `(to_item_id, to_snapshot_id)` 同理；
- 合法的同卡快照可插入；
- 借用另一张卡的 Snapshot 必须被数据库拒绝；
- `PRAGMA foreign_keys = ON` 的生产初始化路径与测试路径行为一致；
- migration 可在空库和 046 已应用的升级库各运行一次；
- migration 失败时不留下半重建的 `content_group_members`。

如果 SQLite 的复合 FK、整表重建或迁移事务行为与预期不一致，立即重开 `D-003`，不通过删约束或改成静默服务层约定绕过。

## 1. 版本目标

V2.BN.11 建立 Coincides 的 **Item Identity And Relation Truth Floor**：

```text
Source / TextFlow
  -> 收集为原料 Anchor
  -> 人工认领 / 铸成 Item
  -> ContentGroup 捆绑 Item
  -> Purpose 赋予情景、角色与顺序
  -> Relation 对 Item 做带判断收据的连接
  -> Inspector 读取关系与安静的新鲜度
```

版本完成后，用户至少可以：

- 从现有内容收集一条原料，并把它铸成可独立编辑、跨 Note / Project 存活的 Item；
- 把 Item 作为 ContentGroup 成员或 Purpose 直接成员使用；
- 在两张 Item 之间建立 directed / undirected Relation；
- 查看一张 Item 的关系列表、对端、类型、方向、备注与机械新鲜度；
- 对 Relation 做 revoke 与 reaffirm，且判断收据不会被静默改写；
- 删除 Project 后继续找到生于该 Project 的 Item 与 Relation，origin 只降级为历史收据；
- 不再产生新的 Petal 数据，也不会从旧学习画布端点复活旧 Relation 表。

V11 的完成态是“知识身份与关系真相可被人可靠使用”，不是图谱产品、AI 自动推理或 Relation Studio。

## 2. 锁定的产品与工程判断

### 2.1 四层楼不能再混写

```text
原料池
  可重建候选；尚未成为知识作品；由 pool scope 定位。

Item
  稳定知识身份；拥有可编辑本体、type/topic 与 N 条 Anchor 收据。

ContentGroup
  Item 与其他允许成员的捆绑 / 组织方式；不再冒充最细知识身份。

Purpose
  “为什么做、在什么情景下做”的薄节点；role/order/fitness 住 membership edge。
```

同一 Item 可以被多个 ContentGroup 捆绑，也可以在某个 Purpose 中直接出现。若同一 Purpose 既直接包含 Item，又通过 ContentGroup 包含它，compiled read model 按 `item_id` 去重；持久层不合并、不改写两条来源边。

### 2.2 Item 是身份，不是缓存

- `items.body_json` 是 Item 的结构化内容真相；
- `items.plain_text` 是同一次写事务产生的可检索 / 可 hash 文本镜像，不允许独立编辑成第二真相；
- `item_type` 与 `topic` 是 Item 固有标量，v1 使用自由文本和种子建议，不建类型定义实体；
- Item 不提供 hard delete；正常退出只有 `active -> retired`；
- 合并 / 取代通过新 Item + `retired_into_item_id` 表达；
- 拆分通过新建多个 Item、转移 / 新建 Anchor、退役旧 Item 表达，不把多后继硬塞进单列；
- Project / Note 只是 origin receipt，删除后 `SET NULL`，不能级联删除 Item。

### 2.3 Anchor 是使用收据，不是 canonical fragment

`item_anchors` 一表两态：

```text
pool state
  item_id = NULL
  pool_scope_kind / pool_scope_id 均非 NULL

claimed state
  item_id 非 NULL
  pool_scope_kind / pool_scope_id 均为 NULL
  claimed_at / claimed_by 均记录认领跃迁
```

- 同一 Source range 支撑两张 Item 时保存两行 Anchor；
- 第一张 Item 可通过 UPDATE 认领池中 Anchor，第二张 Item 新建自己的收据行；
- `excerpt` 必须自足；靶对象、Source 或 Note 消失后，活跳转可降级，收据文本不可被 sweep 掉；
- `source_record_id` 在锚定时 copy-on-anchor，之后不随上游同步；
- v1 `target_kind` 至少支持 `block / content_range / canvas_object / table_region / image_region`，统一使用共享词表，不再引入 `note_block` 方言；
- pool v1 从 ContentGroup 区起步，`pool_scope_kind='content_group'`。

### 2.4 Snapshot 是 Relation 的判断收据

- Snapshot 内容取 Item 当时的 `plain_text`；
- hash 对 `plain_text` 计算，格式抖动不制造假漂移；
- `UNIQUE(item_id, content_hash)` 允许相同内容重用既有 Snapshot；
- Snapshot 不是 Item 的另一个可编辑版本；
- 只要仍被 Relation 引用，就不能被 GC；
- composite FK 保证 Relation 的 Snapshot 真正属于对应端点 Item。

### 2.5 Relation 只连接 Item

V11 的种子关系：

```text
directed
  derives_to
  depends_on
  supports
  contradicts
  example_of

undirected
  equivalent_to
  analogous_to
  contrasts_with
  companion_of
```

规则：

- directed Relation 保留 from / to 方向；
- undirected Relation 在服务层按 Item ID 规范化存序；
- 禁止 self-loop；
- 同一规范化端点对、同一 relation_type 同时只允许一条 active Relation；
- 异议不并排堆多条 active 边，使用 revoke + recreate + note 留痕；
- `origin_purpose_id` 只记录判断发生时的情景出处，不参与 Relation 的适用性过滤；
- Relation 不 hard delete，使用 `active / revoked`；
- 新建与 reaffirm 只接受同一用户拥有的 active Item；跨用户完整性继续使用仓库现有服务层 scoping + 测试，不额外发明全库 user_id 复合 FK 习语；
- 视觉 `visual_connector` 与 Relation 始终是两套真相，不互相代替。

### 2.6 新鲜度读时派生，不建同步状态列

V11 不给 Relation 增加 `fresh / stale` 存储列，也不建立人工 sweep：

```text
from_changed = hash(current from_item.plain_text) != from_snapshot.content_hash
to_changed   = hash(current to_item.plain_text)   != to_snapshot.content_hash

freshness =
  fresh
  from_changed
  to_changed
  both_changed
```

`endpoint.updated_at > max(relation.affirmed_at, latest_assessment.created_at)` 可作为待检查排序信号，但最终机械判断以内容 hash 为准。新鲜度是安静状态，不是全局任务、红点或催促。

### 2.7 重申是一个事务

Relation reaffirm 必须在一个数据库事务内完成：

1. 读取并验证两端 active Item；
2. 对两端当前 `plain_text` 计算 hash；
3. `INSERT OR IGNORE` / select 复用两端 Snapshot；
4. 同时更新 `from_snapshot_id`、`to_snapshot_id` 与 `affirmed_at`；
5. 提交后返回新的机械新鲜度。

任何一步失败都回滚，不能只更新一端。历史 assessment 不加 `invalidated` 标记；新的 `affirmed_at` 会自然覆盖旧 assessment 在派生工单中的时间权重，但历史署名记录仍保留。

### 2.8 Project 是镜头，不是知识 owner

V11 后删除 Project：

- `items.origin_course_id -> NULL`，Item 本体、Anchor、Snapshot 继续存在；
- `relations.origin_purpose_id` 只在 Purpose 被删时 `SET NULL`，Relation 继续存在；
- Item 的 `origin_note_id` 在 Note 删除后 `SET NULL`；
- ContentGroup / Purpose 自身继续遵守各自既有生命周期；
- UI 必须把 Origin 降级解释为“原 Project 已删除”，不能表现成知识消失。

### 2.9 Petal 与旧 Relation 世界必须停止产出

Package C 将 `ContentGroupFragment / ContentGroupPetal / Petal assignment` 作为同一旧内部精修路径退役：先移除 client 类型、CRUD 和 Single Editor 入口，再移除 server hydrate / replace / prune，最后由 047 删除无消费者的三张 Petal 支持表。

legacy v2.4.4 Relation 清场只删除已确认的三张死表：

```text
object_relations
canvas_edges
relation_layers
```

同时下架旧 Courses Learning Canvas 的页面、路由、服务和播种器，否则 READ 会重新播种 relation_layers 或直接崩页。`learning_canvases / canvas_nodes` 等更广遗产不在本 Plan 中顺手落表，除非另有实证与拍板。现役 BN `canvas_objects(kind='visual_connector')` 不受影响。

## 3. 数据脊柱与不变量

### 3.1 `items`

最低字段：

```text
id / user_id
body_json / plain_text
item_type / topic
status = active | retired
retired_into_item_id nullable, SET NULL
origin_course_id nullable, SET NULL
origin_note_id nullable, SET NULL
created_by / metadata / created_at / updated_at
```

硬约束：

- `plain_text` 与 `body_json` 同事务写入；
- `retired_into_item_id` 只允许出现在 retired Item；successor 必须是同用户 active Item、不能指向自己，且服务层必须沿 successor 链检查并拒绝环；
- active Relation 不阻止 Item 退役，但 Inspector 必须显示端点已退役；
- 不开放通用 `DELETE /items/:id`；账号级 cascade 不是产品删除动作。

### 3.2 `item_snapshots`

最低字段：

```text
id / item_id / user_id
content / content_hash / created_at
UNIQUE(item_id, content_hash)
UNIQUE(item_id, id)
```

Snapshot 不开放独立编辑 API。

> **2026-07-13 · V2.BN.11.3 口径更替**：自 V2.BN.11.3 起，Item create / update / cast 写路径按 canonical `plain_text` 生成或复用 Snapshot，使用 `UNIQUE(item_id, content_hash)` 与 `INSERT OR IGNORE` 去重。原“只能由 Relation create / reaffirm 命令建立”的口径由本注取代；V2.BN.11.5 的 Relation create / reaffirm 继续复用端点 Item 的 Snapshot，不获得独立篡改 Snapshot 的能力。

### 3.3 `item_anchors`

最低字段：

```text
id / user_id / item_id
pool_scope_kind / pool_scope_id
target_kind / target_id / range_json
excerpt / reference_mode / source_record_id
collected_for
claimed_at / claimed_by
metadata / created_by / created_at / updated_at
```

硬约束：

- 两态 CHECK 必须由数据库背书；
- claimed Anchor 的 `claimed_at / claimed_by` 由认领命令写入，不能从 `updated_at` 猜；
- pool Anchor 可以安全硬删；claimed Anchor 随 Item 身份保存，不提供普通清场动作；
- target 不做级联 FK；事实对象被删后 excerpt 仍可解释；
- Source 删除只允许活链接降级，不得级联删除 Anchor。

### 3.4 `relations`

最低字段：

```text
id / user_id
from_item_id / to_item_id
relation_type / directionality
from_snapshot_id / to_snapshot_id
note / created_by / origin_purpose_id
status = active | revoked
affirmed_at / created_at / updated_at
```

硬约束：

- 两端 Item FK 使用 NO ACTION / RESTRICT 语义；
- 两个复合 FK保证 Snapshot 属于端点 Item；
- 禁止 self-loop；
- undirected 规范序由 CHECK + service normalization 双重保证；
- partial unique 保证同对同型只有一条 active Relation；
- `origin_purpose_id` 删除时 SET NULL，且任何 list/query 都不得把它当 applicability filter。

### 3.5 `relation_assessments`

最低字段：

```text
id / relation_id / user_id
verdict = still_holds | questionable
model_key / created_at
```

V11 只落表、约束、读取兼容和测试，不接本地小模型，不让人类判断伪装成 AI assessment，也不增加失效旗。

### 3.6 `content_group_members` Package B

新增：

```text
item_id REFERENCES items(id) ON DELETE SET NULL
```

整表重建时加入：

```sql
CHECK (
  (kind = 'item' AND item_id IS NOT NULL AND target_id IS NULL)
  OR
  (kind != 'item' AND item_id IS NULL)
)
```

并保持：

- 既有 member ID、顺序、source receipt 与 metadata 不丢；
- `kind='item'` 时 Item 本体是真相，member 的 preview 只是显示缓存；
- Item 被退役时 member 可继续作为历史组织边显示，但默认选择器不再推荐；
- Item FK `SET NULL` 只防非产品级异常删除，hydrate 必须把坏边明确标为 missing，不能静默强转成 content_range；
- server dbValues / INSERT / upsert / hydrate 与 client DTO / normalizer 同一小版本完成。

### 3.7 `purpose_members` Package A

`member_kind` 扩为：

```text
content_group | item
```

并保持：

- server normalizer 不再遇到 Item 就 throw；
- insert 按 kind 查询对应实体且验证 user ownership；
- visible read 过滤 retired Item，镜像现有 deleted ContentGroup 过滤；
- hidden-edge recovery 同时保护两种 kind；
- client normalizer 不再把未知 kind 静默洗回 content_group；
- Purpose 内由 ContentGroup 带入的 Item 只在 read model 派生，不写入 `purpose_members`；
- 用户手动从场外拉入的 Item 才保存直接 Item membership。

### 3.8 生命周期注册表

V11 必须更新并验证 V10 建立的 lifecycle registry：

```text
items                  preserve   origin_course_id ON DELETE SET NULL
item_snapshots         user-scoped, no course_id
item_anchors           user-scoped, no course_id
relations              user-scoped, no course_id
relation_assessments   user-scoped, no course_id
```

现有 registry 只按 `course_id` 列名扫描。V11.2 必须把注册键至少扩成 `table + project-reference column + policy`，或通过 `PRAGMA foreign_key_list` 等等价方式覆盖所有指向 `courses` 的 FK，使 `items.origin_course_id` 能登记为 `preserve / SET NULL`，同时不把 origin receipt 错当成 move/delete 目标。

同时移除已落表的 `canvas_edges / object_relations / relation_layers` 与已删除 Petal 支持表的过期注册项。schema coverage test 必须同时抓 missing、stale entry、未登记 origin FK 与声明的 `ON DELETE` 行为不一致。

## 4. 生命周期协议

### 4.1 收集原料

```text
用户在 ContentGroup 区选择可引用内容
  -> 生成 pool-state item_anchor
  -> 冻结 excerpt / target / range / source_record receipt
  -> 不创建 Item
  -> 不改变 Source、TextFlow、ContentGroup member 或 AnnotationTruth
```

相同内容允许被多次收集；v1 不做全局自动去重，也不做 AI 批量收料。

### 4.2 快铸与融铸

最小人工入口至少提供一条真实路径：

```text
池中选择一条或多条 Anchor
  -> 输入 / 确认 Item 本体、type、topic
  -> 单事务创建 Item
  -> 将所选 Anchor 从 pool state UPDATE 为 claimed state
  -> 返回 Item 与 Anchor receipt
```

直接从一个选择范围快铸时，可在同一命令中先建立 Anchor 再立即认领。认领事务失败时 Item 与 Anchor 状态一起回滚。创建 Item 不暗中把它加入所有 Purpose 或 ContentGroup；组织动作由显式 UI 完成。

### 4.3 编辑、退役、合并与拆分

- 编辑 Item 只改 Item 本体与 `updated_at`，不自动改 Snapshot、Anchor excerpt、Relation note 或 Source；
- retire 保留 Item、Anchor、Snapshot 与 Relation；
- 指定 successor 时验证同用户、目标 active、不是自身，并拒绝任何会形成 successor cycle 的写入；
- merge 是“建新 Item -> 为来源建立 / 转移使用收据 -> 退役旧 Item 并指向新 Item”；
- split 是“建多个新 Item -> 各自取得 Anchor 收据 -> 退役旧 Item”，不要求 V11 提供血统面板；
- v1 UI 只需提供普通编辑、retire 与可选 successor，不必把 merge/split 做成完整工作台。

### 4.4 ContentGroup 与 Purpose 组织

- 把 Item 加入 ContentGroup 只新增 `kind='item'` 的组织边；
- 删除该 member 不删除 Item；
- 把 Item 直接加入 Purpose 只新增情景边；
- 删除 Purpose member 不删除 Item 或 ContentGroup；
- compiled Purpose read model 汇总 direct Item 与其 ContentGroup 内 Item，去重后返回来源说明；
- 派生结果不反写数据库。

### 4.5 建立 Relation

```text
选择 active Item A 与 active Item B
  -> 选择种子 relation_type
  -> service 推导 directionality
  -> undirected 时规范化端点顺序
  -> 对两端当前 plain_text upsert Snapshot
  -> 写 Relation + origin Purpose receipt + note
  -> affirmed_at = created_at
```

如果同对同型 active Relation 已存在，返回可解释冲突并指向既有 Relation；不得偷偷覆盖 note 或 Snapshot。

### 4.6 Reaffirm 与 Revoke

- reaffirm 使用 §2.7 单事务协议；
- revoke 只把 Relation 状态改为 `revoked` 并更新时间；
- revoked Relation 默认不出现在 Inspector 主列表，但可由未来历史入口查看；
- revoke 后允许同对同型重新创建 active Relation；
- Relation 不提供普通 hard delete。

### 4.7 上游对象消失

- Source / Note / Block / CanvasObject 消失：Anchor excerpt 继续存在，活跳转降级；
- origin Project 消失：Item / Relation 保留，origin receipt 置空；
- ContentGroup / Purpose 组织边消失：Item / Relation 不受影响；
- Item 退役：Relation 保留并显示 retired endpoint，不静默改指 successor；
- 用户账号删除：沿既有 user-owned cascade 彻底清理，不属于产品内 retire 语义。

## 5. 用户工作流

### 5.1 从 ContentGroup 原料区铸卡

1. 用户在 ContentGroup surface 选择已有成员或可引用范围；
2. 选择“收集为原料”，系统建立 pool Anchor；
3. 用户在原料区选一条或多条材料，选择“铸成 Item”；
4. 最小编辑面允许确认正文、type 与 topic；
5. 成功后原料从池中消失，Item 保留对应 Anchor receipt；
6. 用户可显式把 Item 加入当前 ContentGroup。

交互形态标记为待实测，但“至少一条可用入口”不能缺席。

### 5.2 直接快铸

1. 用户选择一个已经有稳定 excerpt / range 的内容；
2. 选择“快速铸卡”；
3. 系统同事务创建 Item 与 claimed Anchor；
4. UI 打开 Item 最小检查面；
5. 用户可继续编辑或关闭。

### 5.3 Purpose 内使用 Item

1. 当前 Purpose 可通过 ContentGroup 派生看到其中的 Item；
2. 用户也可手动搜索并把场外 Item 拉入当前 Purpose；
3. 直接 membership 保存 role / fitness / order；
4. 同一 Item 多路进入时 Inspector 只显示一个节点身份，但保留来源边信息。

### 5.4 建立与维护 Relation

1. 用户从 Item Inspector 选择“建立关系”；
2. 搜索对端 Item，选择种子类型并填写可选 note；
3. 创建成功后出现在当前 Item 的关系列表；
4. 若任一 Item 后续改变，列表安静显示机械新鲜度；
5. 用户查看后可 reaffirm 或 revoke；
6. 系统不弹全局催促，不自动替用户改 Relation。

### 5.5 删除 Project

1. 用户删除生出若干 Item 的 Project；
2. Project 自有视图与原有删除协议照常执行；
3. Item 与 Relation 继续存在；
4. Item Inspector 的 Origin 显示为已删除 / 不可跳转；
5. 其他 ContentGroup、Purpose 与关系入口仍能找到这些知识身份。

## 11. Definition Of Done

V2.BN.11 完成意味着：

- `Item` 已成为跨 Note / Project 稳定的知识身份；
- Anchor 把知识作品与来源痕迹连接起来，但不冒充 canonical fragment；
- ContentGroup 回归组织，Purpose 保持情景薄层；
- Relation 成为 Item 之间带 Snapshot 判断收据的独立真相；
- 内容漂移可以被机械识别，却不会制造全局噪音；
- 用户可以亲手铸卡、建边、查看、重申与撤销；
- 删除 Project 不再删除知识；
- Petal 与旧 Learning Canvas Relation 世界停止继续生产数据；
- V11 没有偷做图谱 UI、Agent 推理或 GraphRAG；
- 所有机器工程门通过，并留下独立第三者可复核的 handoff。

做到这里，Coincides 的知识底座第一次拥有完整的“内容 -> 身份 -> 组织 -> 情景 -> 判断”链条。后续磨合期可以审判它是否真正好用，而不需要再靠旧 Petal、旧 Relation 表或 Agent 假设支撑基本语义。
