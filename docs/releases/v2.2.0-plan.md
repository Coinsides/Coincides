## 1. Goal

v2.2.0 promotes Material Reconciliation from roadmap direction into the first active implementation boundary.

The goal is to create a conservative, review-first proposal shell that can look at existing course materials and produce candidate reconciliation groups:

```text
source_materials / source_fragments / material_segments
  -> material_reconciliation proposal
  -> candidate groups + evidence summary + confidence + warnings
  -> Henry/user review
```

v2.2.0 must make reconciliation visible and reviewable. It must not silently merge, delete, hide, or canonize source material.

---

## 2. Version Boundary

v2.2.0 includes:

- first `material_reconciliation` proposal type;
- candidate group taxonomy:
  - `DUPLICATE`
  - `OVERLAP`
  - `SAME_CONCEPT_EVIDENCE`
  - `CONFLICT`
- deterministic candidate grouping heuristic over existing v2.1 material objects;
- evidence summary for each candidate group;
- confidence and warning fields;
- suggested action field;
- proposal-first review flow;
- discard flow that leaves source/material/note state unchanged;
- apply hook that does not perform real merge yet;
- minimal Course Detail review entry or reuse of the existing proposal review area;
- docs, quality review, experience review, and changelog scaffolding.

v2.2.0 excludes:

- conservative merge apply;
- persistent `EvidenceSet`;
- persistent `ExcludedMaterialScope`;
- persistent `ConflictReviewItem`;
- unmerge / split / recovery;
- full Source Snapshot Viewer;
- Source Board;
- Canvas;
- cross-course reconciliation;
- source authority ranking;
- automatic deletion, hiding, or merging of materials;
- visual redesign beyond what is necessary to review the proposal shell;
- external tools or new dependencies.

## 3. Product Contract

Material Reconciliation is not simple deduplication.

v2.2.0 must distinguish four candidate meanings:

```text
DUPLICATE
  Two fragments appear to be substantially the same source content.

OVERLAP
  Two fragments share meaningful content, but neither fully replaces the other.

SAME_CONCEPT_EVIDENCE
  Multiple sources appear to support the same learning object, but their wording or context differs.

CONFLICT
  Sources appear to disagree or provide incompatible definitions, formulas, conditions, examples, or conclusions.
```

The user-facing language should stay factual:

- "These sources may overlap."
- "These fragments may support the same concept."
- "This candidate group needs review before any merge."
- "No source material was changed by creating this proposal."

Avoid language that claims final truth, such as:

- "These are definitely duplicates."
- "This is the canonical version."
- "The weaker source was removed."

## 4. API / Contracts

The engineering spec will lock final payload names and exact schemas. v2.2.0 should begin with these route-level contracts:

```text
POST /api/proposals/material-reconciliation
GET /api/proposals
GET /api/proposals/:id
POST /api/proposals/:id/apply
POST /api/proposals/:id/discard
```

`POST /api/proposals/material-reconciliation` should accept a course-rooted scope:

```json
{
  "course_id": "course-id",
  "source_material_ids": ["optional-source-material-id"],
  "segment_ids": ["optional-material-segment-id"],
  "document_ids": ["optional-document-id"]
}
```

The created proposal should use:

```text
type = material_reconciliation
status = pending
```

The proposal data should include:

```json
{
  "version": "v2.2.0",
  "proposal_kind": "material_reconciliation",
  "course_id": "course-id",
  "scope": {},
  "candidate_groups": [],
  "warnings": [],
  "apply_behavior": "review_shell_only"
}
```

`POST /api/proposals/:id/apply` for `material_reconciliation` in v2.2.0 must not merge sources or create canonical blocks. It may only mark the proposal as reviewed/applied shell and create an operation batch record if the engineering spec decides that is useful for audit continuity.

`POST /api/proposals/:id/discard` must leave `documents`, `source_materials`, `source_fragments`, `material_segments`, `notes`, `note_blocks`, and `note_block_sources` unchanged.

## 5. Data Model

v2.2.0 conceptual entities:

- `MaterialReconciliationProposal`
- `ReconciliationCandidateGroup`
- `ReconciliationEvidenceSummary`
- `ReconciliationWarning`
- `SuggestedReconciliationAction`

Future placeholders that should be named but not implemented in v2.2.0:

- `EvidenceSet`
- `MergedSourceEvidence`
- `ExcludedMaterialScope`
- `ConflictReviewItem`
- split / unmerge / recovery metadata

Candidate group draft shape:

```json
{
  "group_id": "generated-id",
  "group_kind": "DUPLICATE",
  "confidence": 0.72,
  "suggested_action": "review",
  "title": "Candidate duplicate: Lecture 1 overview",
  "evidence": [
    {
      "source_material_id": "source-material-id",
      "source_fragment_id": "source-fragment-id",
      "material_segment_id": "material-segment-id",
      "document_id": "document-id",
      "document_chunk_id": "document-chunk-id",
      "page_start": 1,
      "page_end": 2,
      "excerpt": "short source excerpt",
      "reason": "similar heading and overlapping text"
    }
  ],
  "warnings": []
}
```

Real table names, indexes, migration number, and whether to persist candidate groups outside the existing `proposals` table belong in `docs/releases/v2.2.0-engineering-spec.md`.

Default assumption: reuse the existing `proposals` table for the first proposal shell unless the engineering spec finds a concrete need for additive tables.

## 6. Agent Tool Contract

The agent may:

- inspect course materials, source fragments, and material segments;
- create a material reconciliation proposal;
- explain candidate group kinds and warnings;
- recommend review actions.

The agent must not:

- silently merge fragments;
- delete or hide materials;
- create final canonical truth;
- claim a source is definitely wrong;
- rewrite notes based on reconciliation without a later approved proposal/apply step.

Allowed wording:

```text
I found candidate overlaps that need your review.
I grouped these fragments because their headings or excerpts appear similar.
This proposal does not change your materials until a later merge flow is approved.
```

---

## 7. Migration

v2.2.0 should prefer a minimal migration posture.

Default plan:

- reuse `proposals` for `material_reconciliation` proposal JSON;
- do not add persistent `EvidenceSet` tables yet;
- do not mutate existing `source_materials`, `source_fragments`, `material_segments`, `notes`, or `note_blocks` during proposal creation;
- allow the engineering spec to add a small audit or status field only if needed for proposal tracking.

If a migration is introduced, it must be additive, reversible by leaving old data valid, and verified on both empty DB and existing v2.1.1 DB.

## 8. Implementation Steps

### Step 1: Reconciliation Taxonomy

Define the four candidate group kinds and suggested actions in shared/server-safe code.

Minimum suggested actions:

```text
review
keep_separate
defer
future_merge_candidate
mark_conflict
```

Completion condition:

- taxonomy is available to proposal generation and tests;
- unknown group kinds are rejected or safely normalized.

### Step 2: Proposal Shell Data Contract

Add the `material_reconciliation` proposal creation contract.

Completion condition:

- a pending proposal can be created for a course scope;
- malformed scopes fail safely;
- empty scopes return a clear error.

### Step 3: Candidate Grouping Heuristic

Implement deterministic first-pass grouping over existing materials.

Initial heuristic may use:

- identical or near-identical headings;
- overlapping page ranges;
- similar normalized excerpts;
- same document chunk metadata;
- same material segment title;
- warning when confidence is low.

Completion condition:

- the heuristic produces candidate groups with evidence summaries;
- it avoids claiming final truth;
- low-confidence groups remain review-only.

### Step 4: Proposal Review UI

Add a minimal review surface.

Acceptable v2.2.0 UI:

- a button or entry point to create reconciliation proposal from Course Detail;
- proposal review panel showing group kind, confidence, evidence excerpts, warnings, and suggested action;
- apply and discard buttons with clear non-merge language.

Completion condition:

- Henry can understand what the proposal is suggesting;
- the UI makes clear that no merge has happened yet.

### Step 5: Non-Mutating Safety

Verify discard and v2.2.0 apply behavior.

Completion condition:

- discard leaves material and note state unchanged;
- apply does not merge, delete, hide, or create canonical blocks;
- operation batch behavior is documented if used.

## 10. Acceptance Criteria

v2.2.0 is complete when:

- a user can create a `material_reconciliation` proposal for a course material scope;
- the proposal shows candidate groups with kind, confidence, evidence summary, warnings, and suggested action;
- candidate group kinds distinguish duplicate, overlap, same-concept evidence, and conflict;
- creating a proposal does not mutate source/material/note state except for storing the pending proposal;
- discarding the proposal leaves source/material/note state unchanged;
- applying the v2.2.0 shell does not perform real merge or deletion;
- existing v2.1 material map and organized note proposal flows still work;
- existing v2.1.1 template-aware NoteBlock behavior still works;
- quality review is `PASS` or `PASS_WITH_FOLLOWUP`;
- experience review records any deferred UX debt;
- Henry makes the release/hold decision.
