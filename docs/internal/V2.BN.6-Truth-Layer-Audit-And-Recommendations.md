## 0. 写作原则

这份报告回答三个问题：

1. 现在代码里已经有什么事实？
2. 这些事实分别属于哪一层 truth？
3. 以一个成熟软件公司 / 产品工程团队的视角看，它们哪里还不成熟，哪里需要 Henry 拍板？

为了避免把想法和事实混在一起，本文使用以下标记：

```text
[事实]        当前代码或现有文档中已经存在的东西。
[推断]        从代码结构和产品目标推出来的判断。
[问题]        当前设计容易出错、不成熟、边界不清或未来会拖累工程的地方。
[建议]        我建议 V2.BN.6 或后续版本采用的处理方式。
[需拍板]      需要 Henry 明确确认的产品 / 数据主权 / 版本边界决定。
```

## 2. 总体结论

### 2.1 一句话结论

[推断] Coincides 现在不是“没有数据地基”，而是已经有了相当多 v2.x 地基：`NoteBlock`、`Placement`、`SourceSnapshot`、`SourceAnchor`、`SourceScope`、`SourceBoard`、`LearningCanvas`、`CanvasNode`、`CanvasEdge`、`ObjectRelation`、`TemplateDefinition`、`CompositionTemplate`、`DomainBlockSet`、`PackageManifest` 等都已经存在。真正的问题是：这些东西还没有被正式整理成 Better Notebook 的 truth-layer contract。

### 2.2 当前最大风险

[问题] 当前风险不是单点 bug，而是“多个对象正在承担相似职责”：

- `note_block_placements.display_overrides_json` 在承担页面内 block 布局。
- `canvas_nodes.x/y/width/height` 在承担学习画布布局。
- `source_board_nodes.layout_x/layout_y/layout_width/layout_height` 在承担 source board 布局。
- 前端 `NoteDetail.tsx` 又在用 `better_notebook_layout` 约定保存 x/y/width/height、export role、AI visibility、surface。

[推断] 如果 V2.BN.6 不把 content truth、layout truth、source truth、relation truth、template truth、editor state、adapter index 分清楚，后续 Template Studio、Source Library、Relation、GraphRAG、OCR/VLM import 和 Canvas Engine 都会互相污染。

### 2.3 当前最有价值的基础

[事实] 当前最有价值的基础有四个：

1. `note_blocks` 和 `note_block_placements` 已经把“内容”和“投放位置”拆开了。
2. `template_definitions` 已经支持 `system_type`、`learning_role`、`field_schema`、`default_content`、`render_hints` 和 agent summary。
3. `source_snapshots`、`source_anchors`、`source_scopes` 已经给 source provenance 做了初版地基。
4. `canvas_edges` 和 `object_relations` 已经隐约分开了 visual connector 和 semantic relation。

[建议] V2.BN.6 应该围绕这四个基础写 contract，而不是急着做新功能。

## 4. 内容 Truth：Note 与 NoteBlock

### 4.1 当前事实

[事实] `notes` 表保存 note 的身份信息，包括 `id`、`user_id`、`course_id`、`title`、`description`、`status`、`source_kind`、`page_format`、`metadata`、`operation_batch_id`、时间戳和 `trashed_at`。

[事实] `note_blocks` 表保存 block 的身份和内容，包括：

```text
id
user_id
course_id
block_type
title
content_json
plain_text
status
source_kind
metadata
operation_batch_id
created_at / updated_at / trashed_at
```

[事实] 后端创建 block 时，`server/src/routes/notes.ts` 会把 `content_json`、`plain_text`、`metadata` 写入 `note_blocks`，并同时创建 `note_block_placements`。

[事实] 更新 block 时，`server/src/routes/noteBlocks.ts` 允许更新 `block_type`、`title`、`content_json`、`plain_text`、`metadata` 和 `status`。

[事实] 前端 `NoteDetail.tsx` 已经把 Definition 和 Formula 当成 structured block seed：

- Definition 使用 `concept_name` 和 `description`。
- Formula 使用 `latex_input`、`formula_name`、`explanation`。
- 前端保存时会把这些字段写入 `content_json.field_values`，并兼容 `structured_fields`。

### 4.2 当前问题

[问题] `block_type` 仍然是 legacy enum：`heading`、`paragraph`、`definition`、`theorem`、`proof`、`formula`、`example`、`exercise`、`answer`、`sidenote`。它能兼容旧数据，但不足以表达未来的 `template variant`，例如 `definition.math`、`definition.chemistry`、`formula.engineering`。

[问题] `content_json` 是 opaque JSON，validator 只验证它是 object，不验证 `field_values` 是否符合 `TemplateDefinition.field_schema`。

[问题] `plain_text` 现在由前端生成并提交。长期看它应该是 derived text，可以从 `content_json.field_values`、`content_json.body`、template schema 重建，不应该成为用户内容的唯一 truth。

[问题] `metadata` 现在承载 template key、template id、legacy inference、UI hints、迁移 hints 等多种含义。它是必要的兼容层，但不能让它成为字段内容 truth。

[问题] 现在删除 block 是把 `status` 改为 `trashed`。这符合“删除但可恢复”的方向，但和用户前面说的“普通 block 删除需要 Ctrl+Z 可恢复，trash 入口另算”之间还需要正式生命周期定义。

### 4.3 建议

[建议] V2.BN.6 正式确认：

```text
NoteBlock content truth =
  id
  primitive family / legacy block_type
  template reference
  content_json.field_values
  content_json.body fallback
  title
  status
```

[建议] `plain_text` 明确为 derived search/export/preview text。后续应该有 rebuild 函数或 service，可以从 canonical content 重建它。

[建议] `metadata` 明确为兼容和辅助信息，不允许成为唯一内容 truth。凡是用户真正填写的结构化内容，必须进入 `content_json.field_values`。

[建议] V2.BN.6 不做大 migration，但 contract 应要求未来所有 structured block 都以 `content_json.field_values` 为第一容器。

### 4.4 需 Henry 拍板

[需拍板] 是否正式确认：

```text
content_json.field_values = structured block 的内容 truth
plain_text = 可重建派生文本
metadata = 兼容 / hints / migration / template reference，不存唯一内容 truth
```

我建议确认。这是后续 AI、GraphRAG、local graph、export、Template Studio 能稳定读 block 的核心。

[事实] `server/src/services/templateDefinitions.ts` 已经提供 runtime template definition 的校验与合并能力，包括 field schema key、label、kind、required、字段数量上限等。

### 5.2 当前问题

[问题] FieldSchema 已经有表和 service seed，但 `NoteBlock.content_json.field_values` 还没有被后端按 schema 校验。

[问题] 当前静态模板、shared types、server runtime template definitions 之间有重复定义的倾向。重复定义不一定错，但未来如果不同步，会导致“前端以为有字段，后端以为没有字段”或“AI adapter 读错字段”。

[问题] Product 决策已经收窄默认 block set，但静态 registry 里仍然保留 theorem/proof/example/exercise/answer/callout/concept 等模板。这些可以兼容存在，但不应该全部暴露到第一版写作入口。

[问题] FieldLayout 现在还没有真正的数据结构。当前 Definition / Formula 的显示样式主要是前端固定样板，不是用户可编辑 layout schema。

### 5.3 建议

[建议] V2.BN.6 用合同明确三层：

```text
FieldSchema
  由 TemplateDefinition 拥有，定义有哪些字段。

FieldValue
  由 NoteBlock.content_json.field_values 拥有，保存某个 block 的真实字段值。

FieldLayout / RenderTemplate
  控制字段如何显示，第一版先用固定模板，成熟编辑留给 V2.BN.8 或更后。
```

[建议] V2.BN.6 不重做 template runtime，但要明确 runtime 的位置：它是 Template Studio 和 structured block 的底层能力，不是普通写作时暴露给用户的全部菜单。

[建议] V2.BN.8 做 Template Studio Productization 时，再处理用户自建模板、复制系统模板、field schema 安全编辑、field layout 安全编辑。

### 5.4 需 Henry 拍板

[需拍板] 默认第一版用户可见 block 是否继续收窄为：

```text
Text / Paragraph
Heading
Definition
Formula
Code
Source Quote
Sticky / Scratch
```

我建议继续收窄。Theorem、Proof、Example、Exercise 等应作为 Template Studio 后的用户/领域模板，而不是第一版默认菜单。

[需拍板] `concept.basic` 是否明确不作为用户默认 block，只作为兼容 / search / AI / local graph seed？

我建议确认。Concept 是检索和图谱层，不应该和 Definition 的写作入口混在一起。

## 6. 布局 Truth：Placement、BlockBox、Page、Canvas

### 6.1 当前事实

[事实] `note_block_placements` 表已经把 NoteBlock 内容和 note 中的投放位置拆开。字段包括：

```text
note_id
block_id
parent_placement_id
order_index
display_mode
display_overrides_json
```

[事实] `note_block_placements` 当前有 `UNIQUE(note_id, block_id)`，也就是说同一个 block 不能在同一篇 note 里出现多个 placement。

[事实] 前端 `NoteDetail.tsx` 在 `display_overrides_json.better_notebook_layout` 中保存：

```text
x
y
width
height
rotation future
rotation_origin / pivot future
surface: formal_page | canvas_workspace
export_role
ai_visibility
version
```

[事实] 当前 layout seed 已经能表达平移和尺寸，但还没有正式表达 block 的旋转角度。根据 Better Notebook 的自由排版目标，`rotation` 应该被视为 layout truth 的未来字段，而不是内容 truth。

[事实] 前端现在已经有 `surfaceMode = page | canvas`，并用 `isCanvasWorkspaceBlock` 在 page mode 里过滤掉 page frame 外的 canvas workspace block。

[事实] 前端当前有：

- page/canvas 切换。
- formal page boundary seed。
- scratch workspace label seed。
- snap alignment。
- elastic avoidance。
- layout undo/redo history。
- preview overlay toggles。
- block type / AI visibility / export status overlay。

[事实] 另外，`learning_canvases`、`canvas_nodes`、`canvas_frames`、`canvas_viewport_states` 已经存在，说明 v2.x 已经做过更通用的 canvas substrate。

### 6.2 当前问题

[问题] 现在存在三套布局表达：

```text
note_block_placements.display_overrides_json
canvas_nodes.x/y/width/height
source_board_nodes.layout_x/layout_y/layout_width/layout_height
```

这些不是马上要删掉，但必须有清晰边界。

[问题] `NoteDetail.tsx` 的 page/canvas 能力目前更像“在 note 页面里模拟 canvas”，而不是正式的无限画布引擎。它已经足够支持近期 Better Notebook 操作体验，但还不能承担长期 Canvas Engine 的全部责任。

[问题] `display_overrides_json` 是 opaque JSON。它能快速迭代，但如果 contract 不写清楚，后续很容易把 export role、AI visibility、surface、x/y/width/height、selection state、preview state 全塞进去。

[问题] 当前 `surface` 存在于 `better_notebook_layout` 中，但不是数据库强类型字段。短期可接受，长期需要 V2.BN.9 Canvas Engine 统一。

[问题] `UNIQUE(note_id, block_id)` 阻止了同一个 NoteBlock 在同一 note 中多次投放。若未来需要 reusable block / transclusion / multi-placement，这个约束会成为阻碍。

[问题] 当前布局 contract 只显式讨论 `x / y / width / height`，还没有把 `rotation` 纳入正式预留。对于无限画布、手写/图形对象、图片、便签、推理草稿、自由排版来说，只考虑矩形位置和尺寸不够。

[问题] Relation 的视觉端点需要在布局层预留位置。虽然 relation 成熟实现属于 V2.BN.11+，但 canvas/layout contract 需要提前承认：可视连接线不只是 source/target 两个对象，它还需要端点、port、路径、控制点、动画提示等一小套视觉数据。否则后续 relation 版本会反过来冲击 layout 数据结构。

### 6.3 Page 与 Canvas 的产品定义

[推断] 根据 Henry 的产品定义，应该统一口径为：

```text
Canvas 是 Note 的底层承载面。
Page 是 Canvas 里的固定 formal export frame。
Scratch / Workspace 是 Page frame 外的 canvas area，不是第三种独立 surface。
Page size 指 PageFrame 的尺寸，不是整张 canvas 的尺寸。
```

[推断] Page-first note 和 Canvas-first note 是两种 note preset：

```text
Page-first note:
  从一个 formal PageFrame 开始，适合导出、打印、分享、线性阅读。

Canvas-first note:
  从开放画布开始，适合展示、区域化学习、推理、空间化理解。
```

[推断] 第一版不做直接 preset switching。将来如果用户想把 canvas-first note 转成 page-first note，应该走：

```text
duplicate note
-> copy NoteBlocks / SourceReferences / ObjectRelations
-> create target canvas/page preset
-> AI-assisted repagination proposal
-> user review and apply
```

这不是一个普通 toggle，而是 layout migration proposal。

### 6.4 建议

[建议] V2.BN.6 创建 `Canvas-Page-Surface-Contract.md`，明确：

- `NoteCanvas / DocumentSurface`
- `PageFrame / FormalPage`
- `CanvasWorkspace`
- `PageBoundary / ExportFrame`
- `PageSize / PagePreset`
- `CanvasFirstNote`
- `PageFirstNote`
- `OverlayMode`
- `ExportPreview`

[建议] V2.BN.6 只定义 contract，不把当前 `NoteDetail.tsx` 升级成完整无限画布引擎。

[建议] V2.BN.9 作为 Canvas Engine Foundation，处理：

- formal page frame 和 open canvas 的统一模型。
- page frame 外对象的长期持久化。
- viewport、zoom、pan。
- frames / regions。
- canvas-first note。
- placement 与 canvas node 的关系。
- block rotation、rotation origin / pivot、未来可能的 scale 边界。
- relation visual endpoints / ports / control points 的布局预留。

[建议] V2.BN.6 在 layout contract 中先预留以下未来字段，但不要求本版本实现：

```text

  rotation
  rotation_origin / pivot
  scale future

CanvasConnector / CanvasEdge future:
  source_port
  target_port
```

1. Contract 缺失：代码里已经有很多对象，但产品语义没有锁死。
2. JSON 过载：`content_json`、`metadata`、`display_overrides_json` 都很灵活，但没有合同会变成长期风险。
3. 多套布局模型并存：placement、canvas node、source board node 都有 layout。
4. Proposal/adapter/truth 边界还没有被强制：未来 AI/OCR/GraphRAG 进来时会非常危险。

### 15.3 当前最值得投入的方向

[建议] V2.BN.6 不应该急着再打一轮 UI patch。应该先把“图纸”补上：

1. 先写 truth-layer inventory，也就是本文。
2. 再写六个 contract 文档。
3. 再同步 PRD / Architecture / Data Model / Roadmap / Reality Check。
4. 最后只做必要的小兼容修复，不扩大功能。

### 15.4 对后续版本的建议

[建议] V2.BN.7 作为 Editor Runtime Spike Gate 是合理的，因为前几版已经做了不少 editor 肌肉，但还没系统复盘。V2.BN.7 应该回答：

- 自研 editor runtime 继续走是否现实？
- 当前 block measurement / layout history / slash menu / structured field editing 是否能作为长期底座？
- 哪些行为应该从 `NoteDetail.tsx` 抽离成 editor runtime service？
- 与 AFFiNE / BlockSuite 横向对比后，我们自研的代价和收益是什么？

[建议] V2.BN.8 做 Template Studio Productization 是合理的。因为没有用户自建 block/template 的能力，Better Notebook 只能算 better paper，不算成熟 notebook。

[建议] V2.BN.9 再做 Canvas Engine Foundation 是合理的。因为 canvas-first note、page frame、open workspace、viewport、frames、pan/zoom 是一整套引擎，不应在 V2.BN.6 或 V2.BN.7 顺手硬做。

[建议] V2.BN.10 做 Source Library / Provenance Foundation 合理。Source chain 已经成为核心产品能力，但它依赖 V2.BN.6 的 source contract。

[建议] V2.BN.11+ 再做 relation maturity 合理。Relation 是 Coincides 的关键差异点，但它必须建立在 content/layout/source/link 边界清楚之后。

## 18. 最终建议

[建议] 现在不要急着进入 V2.BN.7，也不要把 V2.BN.6 做成无限 UI patch 版本。V2.BN.6 最有价值的事情是把当前项目从“已经做出很多东西”升级为“知道这些东西分别属于什么 truth layer”。

[建议] 如果以软件公司标准看，V2.BN.6 应该被视为一次 architecture design review，而不是功能开发。它的产物不是按钮，而是后续工程不会乱的合同。

[建议] 当前最关键的三条红线是：

```text
1. Coincides Core owns truth.
2. Editor/canvas owns projection and interaction.
3. Adapter/AI/GraphRAG/OCR owns candidate/proposal/index, not truth.
```

只要这三条守住，后续 Better Notebook、Template Studio、Source Library、Relation、GraphRAG、OCR/VLM import 都可以逐步长出来，而不会互相覆盖、互相污染。
