# 编辑器组复核回应:成因与修法方案(builder 2026-11-07,只读,未改码)

依据:Main_Designer 转述的 Tester 独立复核要点。复核报告原文我还没看到,读到后可能修订。
所有行号指当前工作树 `client/src/pages/Notes/canvasEngine/hooks/useHeadingStructureController.ts`(编辑器组冻结版本)。
以下成因都是读码得出,**没有复现**;复现以 Tester 在真浏览器里的结果为准。

## 1. 窗口内回车,第二个结构首次落地前失败,窗口里打的字全没(新增,🅰)

**成因(读码确认)**:窗口内按了回车,`placeTyped` 发现需要第二个结构(约 353–356 行),于是把打的字整体塞进第二个结构的请求 `structure.nextTextFlow`,然后调 `onHeadingStructure`。第二个 `commitStructure` 一开始就关掉旧缓冲(`previousBuffer?.typing.close()`),再开新缓冲,新缓冲的初始文本取自请求里那个单元。
- 从这一刻起,字**只存在于这个请求对象里**:旧缓冲关了,新缓冲的 `initialText` 已经包含这些字,所以 `changed()` 是 false。
- 第二个结构在 `applyEdit` 落地之前失败(`whenWritesIdle` 卡住、建块 500、看门狗),`exitQueue` 调 `placeTyped`;因为 `!typing.changed()`,它直接关缓冲,什么都不写,也不进 `localStorage`。
- 修前这些字是在第一个窗口结束后才回放的,不会经过第二个结构,所以这是本单新增。

**修法**:字在真正落进笔记之前,必须始终算「未落地」。
- 转交时不再把字只交给请求。新缓冲记下一份「携带」:`carry = { blockId, unitId: 标题单元, initialText: 笔记里该单元当前的实际文字, text: 窗口里打的全部内容(含回车后的正文) }`,并立即 `rememberUnplacedWords` 写入 `localStorage`。
- 第二个结构的 `applyEdit` 成功返回(`edited` 为真)时,才清掉 `carry` 并 `forget`。
- 任何在此之前的退出(失败、看门狗、切笔记),都按 `carry` 走现有的留住路径:屏幕上显示、带提示、存进 `localStorage`、回到笔记时再写。
- 回归测试:注入「建块 500」「`whenWritesIdle` 永不返回」两种失败,窗口内打「标题字 + 回车 + 正文」,断言字要么在笔记里,要么在留住的缓冲和 `localStorage` 里。修前构建应为绿(字在),当前构建应为红。

## 2. 窗口内回车后马上点标签离开,标题字和正文一起丢(既有,修前同样丢)

**成因(读码确认)**:同一个转交点(356 行)在关旧缓冲后无条件调 `settled()`,把 `whenTypingSettled` 的等待者全部放行,即使这时 `buffer.current` 已经是新缓冲、第二个结构刚开始。离开路由于是继续,`noteId` 一变,第二个结构被放弃。`leaveBuffer` 只在新缓冲 `changed()` 时留字,而按第 1 条它是 false,所以全丢。

**修法**:
- `settled()` 改为只在真正结束时放行:`buffer.current === null` 或缓冲已转为留住,并且 `busyRef.current === false`。转交那一刻不放行。
- `whenTypingSettled` 也要等结构跑完,不只看缓冲。
- 第 1 条的 `carry` 也覆盖这里:即使离开时第二个结构没完成,`leaveBuffer` 也会按 `carry` 留字。
- 回归测试:窗口内回车后立即调用离开流程(`flushPendingSaves`),断言离开要等到字落进笔记;再测一次离开时第二个结构失败,断言字被留住。

## 3. 留字放错块;回显框盖到前面的块上(同一个根因)

**成因(读码确认)**:单元编号按块计,`tu-1`、`tu-2` 在每个块里都有。有两处只按单元编号找:
- `placeTyped`(285 行):焦点块里找不到单元时,在所有块里找「含有这个单元编号」的第一个块。拆块后标题单元换了块,这一步很容易找到前面某个块的同号单元,把字写进去。
- 回显框的 `findEditor(unitId)`(`structureTypingBuffer.ts`):在整页所有编辑器里找 `data-text-unit-id === unitId`,不看块。拆块后它会跟随前面块里同号单元的编辑器,于是盖到前面的块上。

**修法**:单元的身份是「块 + 单元」,永远不能只凭单元编号找。
- 缓冲不再自己按单元编号找位置,改由控制器提供 `locate()`:返回当前持有这个单元的那个块里的那个编辑器。结构每走一步(提取、移动)后,控制器按 `lastFocus` 更新它跟随的块。
- `placeTyped` 找不到焦点块时不再全页搜同号单元。块还在就用块;块不在就走留住,不猜。拆块后的单元去向已经由结构自己的 `lastFocus` 和焦点请求给出,用这个。
- `localStorage` 里的记录本来就带 `blockId`;回到笔记时块不存在就留住并提示,不往别的块写。
- 回归测试:页内放两个块,都有 `tu-1`,在第二个块的 `tu-1` 上触发结构,断言回显框跟随第二个块、字写进第二个块。修前这条走的是旧回放,应为绿;当前构建应为红。

## 4. 失败后在行首打的字被挪到行尾

**成因(读码确认)**:`placeOnLiveText`(59 行)在笔记里的实际文字和缓冲的初始文字不同时,把新增的字统一接到末尾(`live + inserted`)。

**修法**:三方合并,而不是一律追加。
- 先算新增的字在初始文字里的位置 `start`(共同前缀长度)。
- 如果笔记里的实际文字在 `start` 之前与初始文字相同,就插在 `start`。
- 否则在实际文字里找初始文字中 `start` 前后的锚点(前缀后缀各取一段)再定位。
- 都对不上才追加到末尾,并且这种情况走留住提示,不默默挪位置。
- 回归测试:初始 `Sec`,在行首打 `X`(得 `XSec`),笔记里实际是 `# Sec`,期望 `# XSec` 或留住提示,不能是 `# SecX`。

## 5. 草稿转成的标题,撤销后光标少两格

**成因(读码确认)**:`onHeadingStructure`(397 行)用 `request.focus.caret` 算撤销用的 `beforeSelection`。但 `focus.caret` 是去掉 `# ` 之后的偏移,撤销恢复的是带 `# ` 的原文,所以差了前缀的长度(2)。

**这不只影响草稿**:持久编辑器里打 `# ` 也走同一个 `applyHeadingInputAtLine`,应该同样差两格。修前是否存在要核;我推断持久编辑器那条修前就有。

**修法**:请求里带上「转换前的光标」。`applyHeadingInputAtLine` 本来就拿到了原始 `caret`,把它作为 `beforeCaret` 放进请求;`onHeadingStructure` 用 `request.beforeCaret ?? request.focus.caret`。`headingRequestForDraftText` 也传真实的 `offset`。
- 回归测试:`Intro\n# Title` 光标在末尾转标题,撤销后光标应在 `# Title` 的末尾(偏移 7),而不是 5。持久编辑器路径各补一条。

## 修订 1(builder 2026-11-07,读完复核原文 `tester-evidence/independent-review-2026-11-07.md` 后)

原方案按 Main_Designer 的转述写,读原文后有下列补充。条目编号用复核原文的 id。

### 原方案已覆盖,需要更正的
- **buffer-0 / buffer-1 / commit-0(第 1、2 条)**:丢的不只正文,**窗口里回车之前打的标题字也一起丢**,因为它们同样只存在于第二个结构的请求里。`carry` 必须覆盖窗口里的全部内容,不只回车之后的部分。复核还给了不需要卡住的触发:第一个结构的 reorder 失败、或拆完后某次放置写失败,`whenWritesIdle` 会立刻 reject。注入矩阵要加这两种。
- **buffer-2(第 3 条)**:第二票更正了根因。`lastFocus` 在两条复现路径上都是 null,真正的原因是全页按单元编号搜。我原方案的修法(找不到块就留住,不猜)正对这个,不靠 `lastFocus`。
- **buffer-4(第 4 条)**:复核确认在常见情形(光标在行尾,如新行打 `# head`)上,修后反而比修前对(`#head` 对 `head#`)。三方合并要保住这一点。回归测试两种情形都要有。
- **leads-3(第 5 条)**:与原方案一致。

### 原方案漏掉的,本单新增(pre=no)
- **buffer-3:新开一个标题会抹掉屏幕上留住的字**。`commitStructure` 开头无条件 `previousBuffer?.typing.close()`,不留住、不转移;新窗口结束时 `finish` 又按同一个笔记键 `forgetUnplacedWords`,把旧字的唯一存档也删了。最常见的触发是:拆块失败、字被留住后,在同一个块里再打一个键就会发起新结构。
  - **修法**:前一个缓冲有未落地的字(`changed()` 或已留住)时,先把它转为独立的留住条目,再开新缓冲,不关闭。存档从「每笔记一条」改为「每笔记一个列表,按条目编号」;`finish` 只删自己那一条。
  - **测试**:留住的字在屏上时开新标题,新标题成功后旧字仍在屏上和存档里,撤销或重试后写进笔记。
- **handoff-1:草稿交接留下的旧回执,会挡住这个块以后所有的自动聚焦**(第二票复现了真实路径:草稿首块里非首行打 `/` 选「Text」后,光标不回来,按键打到 body)。成因是我在 A-18 加的守卫(`BlockEditorLayer.tsx:414`):回执里的单元不在,就不聚焦任何单元。本意是「单元还没渲染时等它」,但单元**已经不存在**时也一直等。
  - **修法**:只在回执单元确实还会出现时等,即它仍在这个块当前的 flow 里、只是还没渲染。不在 flow 里就退回旧行为,聚焦第一个单元。
  - **测试**:回执单元不在 flow 里时聚焦第一个单元;回执单元在 flow 里但未渲染时等待。
  - `BlockEditorLayer.tsx` 在编辑器组清单内。

### 既有,但在本单宣称修好的路上
- **commit-1:A-21 的写回仍可能发生**。复核用 React 18.3.1 核实:同步优先级的渲染不带默认优先级的更新,所以一次改了宿主状态的点击会在转移结果提交前触发 `useLayoutEffect`,提前放行等待者。条件比修前窄(修前一帧就够),但没关死。

  - 改动很小,只在 `useHeadingStructureController.ts` 的 `rendered()` 和放行函数里。
  - **测试**:宿主 blocks 和 drafts 用 React 状态(不是可变对象,我原来的测试正因为这点漏了它),第一次转移后插一次同步提交,断言第二次提取读到的是新 flow。修前构建应为红,这里的修前指 A-21 之前的版本。

### 条件 e:字守恒测试(机械闸)
**目的**:交接处丢字这一类问题,不再靠逐条补矩阵来堵。

**形式**:vitest,跑在 `useHeadingStructureController` 的测试宿主上。宿主的 blocks 和 drafts 改用 React 状态(commit-1 证明可变对象会掩盖时序问题),持久层用假实现,可以按指令失败或挂起。

**事件**(固定种子的伪随机组合,每个种子一条序列):
- `type`:每次打一个**唯一记号**(如 `a0`、`a1`…),便于计数。
- `enter`
- `heading`:在当前单元或别的单元触发 `# `。
- 失败,对下一次写入生效:建块 500、转移 500、reorder 失败、放置失败、`whenWritesIdle` 卡住到看门狗。
- `leaveInApp`(走 `flushPendingSaves` 再换 `noteId`)、`leaveUnguarded`(直接换 `noteId`)、`return`(回到原笔记)。
- `undo`、`redo`
- `settle`:等所有窗口和重试结束。

**断言**(每条序列结束并 `settle` 后):每个打过的记号恰好出现在下面三处之一,不少也不重复:
1. 笔记里,任一块的任一单元;
2. 屏上留住的缓冲;
3. `localStorage` 的留字列表。

撤销会合法地删掉字,所以处理为:
- 撤销只在两种情况下出现在序列里:失败后释放扣押,或后面紧跟 `redo`。
- 「`undo` 后紧跟 `redo`」的组合,断言前后记号集合相同,即撤销可逆。
- 释放扣押的撤销,按它实际撤掉的那个历史条目记账:被撤的记号从「应在」集合中移出,并断言它们确实不在三处之一出现。这样撤销不会变成丢字的掩护。

**规模**:200 个种子 × 每条 12–20 个事件,`maxForks=3`。单次运行控制在 60 秒内;超出就减种子数,不减断言。失败时打印种子和事件序列,方便复现。

**阳性对照**:同一个测试文件拷到 scratch 副本,跑在冻结版本上(`scratchpad/editor-frozen-20261107/`,SHA256 已记)。必须对已知的三种丢字各红至少一次:第 1 条(转交后失败)、第 2 条(转交后离开)、buffer-3(新标题抹掉留住的字)。做不到就不算闸,回报。
